# Whose subscription builds it: a bead's originator, per-person groups, and a yardmaster that talks on each person's login

Design yardr-2k0x, proposed 2026-10-14. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory beads are worked in; a bead is one durable piece of work; a route sends a stage's beads to a group, and a group is who works them. A harness is the agent program herdr starts (claude, codex); a login is that program's own authentication, kept in a folder in the OS user's home. The operator is the person who runs the yard; a user is a person of the yard, with a name and an inbox; a crew member is an always-on agent tied to no bead, and the yardmaster is the one that coordinates. An interactor is a person who talks to the yard directly; a bystander gives input through a flow from outside (a Linear issue, a GitHub comment) and never talks to the yard. The originator of a bead is the person the bead is for, whose subscription pays for building it. See docs/glossary.md for all of yardr's words.

## 1. The question

mckean, 14 Oct 2026: a shared yard should not run everyone's work on the operator's Claude or Codex subscription. "Would there be a way to somehow bring your own subscription into a shared yard?" — "the creator/originator of a bead is the one that dictates the subscription that is used" — with login without a terminal, where the harness gives a URL, the person signs in, and pastes a code. And, the same afternoon: in such a yard, one yardmaster on one subscription, or split by subscription with one personality — and should everyone have their own yardmaster in a way, sharing notes? The question is what the smallest version is that carries this: the person a bead is for decides whose login builds it, each person logs in once without needing a terminal, and the yardmaster talks with each person on their own login while keeping one line.

## 2. What exists today

### 2.1. A group's panes can carry another login, by environment

A herdr group may name an env file (`--set env_file=~/.yardr/groups/<group>.env`) whose `KEY=VALUE` lines join each agent pane's environment (docs/groups.md, "Outbound credentials"; the file reader is shared with the crew's, docs/crew.md, "Outbound credentials"). The store never holds the values. A command that prints such lines (`env_command`) is a crew member's setting only (`ConfigKeys`, internal/store/configkeys.go): groups have no such key, and carrying a login from a command's output is out of scope (§4). The harness CLIs honour a folder override in the environment: the table of where a running agent's model is read says Claude Code's session files live under `CLAUDE_CONFIG_DIR` when it is set, and Codex's under `CODEX_HOME` (docs/groups.md, "Models"). So a group whose env file sets `CLAUDE_CONFIG_DIR` to another folder runs its agents on whatever login that folder holds. Nothing in yardr puts a login there: the folder is made by logging in.

### 2.2. A harness login led without a terminal, for the machine's own login only

`yardr harness login <kind> --json` runs the harness's own login command on pipes and leads it for a program: needs on stdout as JSON lines (`choose`, `open_url`, `input`, `confirm`), answers on stdin, secrets passed to the harness and kept nowhere (internal/cli/harnesslogin.go; the recipe — argv, methods, the page and input patterns — is `login_recipe` in harnesses/<kind>.yaml, read 14 Oct). Only claude has a recipe today (harnesses/claude.yaml, verified from `claude auth login`, Claude Code 2.1.288); codex, kimi and the rest are logged in in a terminal, on their own screens. Footplate's first run already leads this flow (its src/setup.rs; design yardr-x4t5 §2.3 confirms the harness-login path). The led login and its proving call inherit the yardr process's environment: `leadLogin` and `tryHarnessCall` set no env of their own (internal/cli/harnesslogin.go), so an ambient `CLAUDE_CONFIG_DIR` or `CODEX_HOME` redirects both into another folder today. What is absent is a group-specific environment: no flag joins a group's env, so the login lands in the default folder unless the whole process's environment says otherwise.

### 2.3. Routes match labels, and beads record who created them

A route takes the open, unblocked beads of its stage that match its filters: `--type`, `--depot`, `--label` (repeatable, the bead must have every one), `--bead-priority` (docs/groups.md, "Which beads a route takes"; internal/cli/ops.go `routeCmd`; internal/store/routing.go `Route`, `SortRoutes`, `MatchRoute`). A filter the route does not give matches any bead (`Route`: "Nil fields match any"). Priority wins first, then specificity (each label, the type, the depot, the bead priority count as one). A route may name further groups with `--else` and gate each on its provider's usage windows (`--group 'builders@Weekly<80'`), in which case the bead waits with one `quota_wait` event when no condition holds (docs/groups.md, "A route with further groups and quota conditions"). A bead no route matches waits with one `unrouted` event of the class attention (internal/dispatch/dispatch.go `reportOnce`; internal/store/crew.go `AttentionKinds`). `yardr bead show` says routing in one line under the bead's owner.

Every bead records its creating actor (`CreatedBy`, internal/store/beads.go): whoever the command acted as. A bead filed while working another records `--discovered-from` as an edge, and inherits nothing of the origin today ("Nothing of the origin is inherited", internal/store/beads.go `NewBead`). Bead metadata (`--meta key=value`) is a free merged map any writer can change (`BeadPatch.Metadata`).

A group itself names no user: `Group` is a name, a runner, a config map, a limit, members and subscriptions (internal/store/routing.go), and its config keys are the fixed `ConfigKeys` table groups and crew members share (internal/store/configkeys.go) — `env_file` among them, a user owner not. A user likewise names no group or login folder: `User` holds cursors, subscriptions, notify settings and source identities (internal/store/users.go). Nothing stored says "this group's env is this person's login"; the proposal adds that as a group setting (§3.2).

### 2.4. Limits describe the operator's login only

`yardr limits` asks each provider's declared source command and prints its windows; its own help says the answer "is for the login the provider reads on this machine, which is the operator's", and that a group or crew member whose env gives its harness another account "is not described by it" (internal/cli/limits.go). Route quota conditions and the harness-error path read the same ambient answer for the group's provider. A group or crew member may say which provider its agent burns (`provider` setting, docs/groups.md, "Changing a group").

### 2.5. Hook-born beads are the yard's own, made as `hook:<name>`

A hook's `makes` lines make a bead of a type in a stage for a thread no open bead tracks (internal/store/hooks.go `Make`); the dispatcher creates it with actor `hook:<hook name>` (internal/dispatch/makes.go). Its originator, in this design's words, is nobody yet.

### 2.6. Users, identities, and what a linked name is good for

A user is a name and an inbox; the operator is a user, and only the operator adds users (docs/users.md). `yardr user identity <name> --source <source> --id <id>` records who a user is in Linear or GitHub, set only by the user or the operator — but today it has one use, assigning a thread (`yardr thread open --assign`), and "no delivery of a source is matched to a user by it".

### 2.7. One crew member, one session, one inbox, one journal

The daemon keeps each crew member running in its own session (docs/crew.md). Its inbox is one cursor over the event log: its own mail plus the kinds its `--on` hears, acknowledged through one seq (`Store.Inbox`, `AckInbox`, `Cursor` in internal/store/crew.go). A fresh session primes from the journal bead, the handoff, the inbox, memories, timers and open asks (`Store.CrewPrime`). Concurrent writes to one bead are refused by revision: a stale `Expect` fails (`UpdateBead`).

### 2.8. The terms, as read for the service design

Design yardr-8wxe §2.10 (Anthropic's page, read 12 Oct 2026): each end user authenticates with their own subscription through Anthropic's own flow; no collecting or intermediating credentials; Pro and Max assume ordinary individual use. Anthropic's Consumer Terms (https://www.anthropic.com/legal/consumer-terms), read 14 Oct 2026, add two sentences this design must reckon with: §2, "You may not share your Account login information ... or make your Account available to anyone else"; and §3(7), no access "through automated or non-human means, whether through a bot, script, or otherwise" except via an API key or where explicitly permitted — whether a yard's agent sessions on the person's own login fall under either is open question 5. OpenAI's Europe Terms (https://openai.com/en-GB/policies/eu-terms-of-use/), read in a browser during the third critique on 14 Oct (the page refuses programmatic reads, then and for this draft too): its Registration section says the same of sharing credentials or making an account available to anyone else — whether a yard's agent sessions on the person's own login fall under it is the same open question 5. Kimi's and the rest are unread. One reading on one day, as 8wxe says of its own. And the trust boundary that design records: every agent, the daemon and the server run as the one OS user, so an env file's 0600 is "a line, not a wall" (yardr-8wxe §§2.4, 3.6; docs/integrations.md). Whoever runs the machine can read every login folder on it.

### 2.9. Reviewers burn a subscription; the refinery burns none

The starter pack's build and review stages run agents (groups `builders`, `reviewers`); the landing stage runs a script (group `assembly`, `run: scripts/merge-local`; packs/starter/pack.yaml). The yardr depot's own line is the same shape: `approved` goes to `yardr-refinery`, an exec group running merge-local (docs/line.md, docs/flows.md). A review session burns its harness's subscription like a build session; an exec group's script burns no model subscription of its own.

## 3. The proposal

One sentence first: every bead names the person it is for; routes send that person's beads to groups whose panes carry that person's login; each person makes that login once, led by a program; and the yardmaster talks with each person in a session on their login while one line session keeps the yard. Four existing mechanisms carry it — the group's env, the led login, route filters, the crew session — and what is new is the field on the bead and the setting on the group that tie them together.

### 3.1. The originator: a field on the bead, not a label and not meta

The originator is a stored field on the bead holding a user's name. It is not a label, because it decides whose subscription pays and labels are anyone's to change; it is not meta, because meta is a free merged map any writer can rewrite (`BeadPatch.Metadata`), while this field needs access control and an event. Beads from before the field get the operator as originator when the store migrates, so every route without the new filter keeps matching exactly what it matched. The name is stored as written, like a group member's or a mail party's: renaming the operator later does not re-point originators. An empty originator reads as the operator's, so a bead from any path the change misses still routes as today.

How it is set at create (`yardr bead create --for <user>` names it outright):

- A person creating a bead is its originator: when the call comes from no agent's pane and the actor is a user's name, that user.
- `--for <user>` names another user outright, and the user must exist. It is refused from the pane of a bead's agent: the store knows the pane by its own records (`paneSession`, whatever actor the command names), as `checkMembers` and `maySpeakAs` already refuse — an agent must not spend another person's subscription by naming them. It is accepted everywhere else: a crew member filing for its person is its intended user, and a person at a shell can already name any actor, since yardr authenticates no one (docs/users.md, "Who is acting"), so refusing them would be theater. A line against mistakes, not a wall.
- A crew member's actor without `--for` leaves the bead the operator's: a yardmaster-created bead with no requester is the yard's own work and runs on the operator's subscription, as every bead does today. A crew session that wants its person's subscription says `--for`.
- A bead filed while working another (`--discovered-from`) inherits the origin's originator: a follow-up is the same person's work. An explicit `--for` wins over inheritance outside an agent's pane; from an agent's pane `--for` is refused and inheritance is the only way another person's name arrives.
- A bead created from a bead agent's pane without `--discovered-from` takes that pane's bead's originator: what is filed from inside someone's work is the same person's work. The pane's session names its bead.
- A hook-born bead follows the hook rule below. A bead arriving over the peer link is the operator's: nothing of the other yard's person crosses (§4).
- An actor that is neither a user's nor a crew member's name — a login name nobody, a session name, anything else — leaves the bead the operator's, as every bead is today.
- The rule behind the defaults: a default never spends another person's subscription. Only an explicit `--for`, or arriving through a bead already theirs (`--discovered-from`, or the pane's bead), puts another person's name on a bead.
- A `question` bead (never routed) takes its originator by the same rules; it matters only to the record.

The hook rule: a hook-born bead's originator is the operator — the outside commenter is a bystander, giving input through a flow, and the operator took the work on. Where the delivery's author matches a linked identity (`yardr user identity`, §2.6) of a yard user — the event's actor id in its source (`readRuleEvent`, internal/dispatch/rules.go) against `Identity.is` — the originator is that user instead, when that user both has their own login and has a personal route in the made bead's stage. "Has their own login" is declared, not probed: a herdr group whose config sets `login_for` to that user (§3.2). The route check is a `MatchRoute` probe for a bead of theirs in that stage, and it counts only when the matched route's first group — the one that says who works the stage (`Worker`, §2.3) — declares `login_for` for the same user. Otherwise the bead is the operator's, and the `hook_rule` event records the linked author it fell back from and which check failed: `no_personal_group` (no herdr group declares `login_for` for them) or `no_personal_route` (one does, but no personal route takes the stage — the matched route is a subsidy route, or there is none). A subsidy route never proves a login: `--originator mckean2 --group builders` sends mckean2's beads to the operator's groups on purpose (§3.2) and leaves hook beads the operator's. A missing or mispointed env file does not move the bead either: the declaration wins, the bead is the interactor's, and the group waits with the existing `runtime_down` until the file is fixed (docs/groups.md, "Outbound credentials") — a transient file state must not silently rebill interactor work to the operator. An interactor's work bills the interactor even when it arrives through a hook, and a bystander's never stalls for want of a route.

After create, only the operator changes the originator (`yardr bead update <id> --originator <user>`, refused to anyone else by the store's `operatorOnly` check, the one `user add` uses), and the change logs an event with the bead, from, to and by. That check reads the actor name, which anyone who can run yardr may claim (docs/users.md, "Who is acting"), so operator-only here is a guardrail against mistakes, not an access boundary. The `created` event carries the originator too (`createdData`), so the record says whose subscription a bead was born to. `yardr bead show` prints the originator beside the owner, and `--json` carries it.

### 3.2. Routing: a route may match `--originator`, beside labels

`yardr route add` gains `--originator <user>`: the route takes only that originator's beads — and `--originator any`: the route takes every originator's. A route without the flag takes only the operator's beads: the one exception to "a filter not given matches any bead" (§2.3). Scoping is by non-match, not by rank: a general route never takes another person's beads, however high its priority or specificity, so the catch-all in the example below cannot swallow mckean2's work when their own route is absent, and no competing general route can outrank it for those beads. Cross-originator use is opted into per route, visibly in the table: `--originator mckean2 --group builders` spends the operator's subscription for mckean2 on purpose, and `--originator any` spends it for everyone.

Whose login a group carries is declared on the group: `login_for=<user>` in its config, a new key in the `ConfigKeys` table (§2.3) for herdr groups only. It names a user that must exist, refused at write naming why, in the style of the peer group's checks (`checkPeerGroup`, internal/store/peersend.go). A group with `login_for=mckean2` runs its panes on mckean2's personal login, carried by its `env_file`; a group without it runs on the operator's, whether its env is ambient or a file of outbound credentials. The operator needs none: absence means the operator's (naming the operator is allowed and means the same). `yardr group show` prints it as any setting, and `yardr doctor` warns when a `login_for` group names no `env_file`, since then nothing carries the login it declares. Existing groups get no `login_for`: all of today's groups are the operator's, and routing reads unchanged. A person's own groups carry their login by env (§2.1), so the operator's table for one depot reads:

```sh
yardr user add mckean2
yardr group add mckean2-builders --runner herdr --set kind=claude \
  --set login_for=mckean2 \
  --set env_file=~/.yardr/groups/mckean2.env   # CLAUDE_CONFIG_DIR=~/.yardr/logins/mckean2
yardr route add --stage new --depot web --originator mckean2 --group mckean2-builders
yardr route add --stage new --depot web --group builders   # the operator's, as today
```

The operator's own beads match the second route; mckean2's match the first alone.

A route taking some originator's beads is personal or subsidy by its first group. For originator X the route is personal when its first group declares `login_for=X` — further groups after it may be anything, since a personal route with `--else builders` fails over to the operator's groups on quota visibly. Any other route taking X's beads is a subsidy route: `--originator mckean2 --group builders` spends the operator's subscription for mckean2 on purpose. The check reads the groups at dispatch time; nothing is stored on the route. One misconfiguration is warned, not refused, in the style of the quota warnings (docs/groups.md, "Two conditions that cannot work are said"): a route that takes operator beads — an omitted `--originator`, or `any` — whose first group declares `login_for` for someone else burns that person's login for the operator's work, and `route add` says so on stderr.

Of the routes that match a bead, the highest `--priority` wins, then the most specific (§2.3): a named originator counts as one filter, and `any` counts as none, so an exact originator route beats an `any` route of the same priority. A named originator makes the route "by bead" (`ByBead`), which packs leave alone; `any` and omission leave the route the pack's to own. `any` is a keyword, not a user: `yardr user add any` is refused as a crew member's name is, and `--for` and bead update never take it — an originator is a person. `route add --originator` names a user that must exist, so a typo strands nothing silently. `yardr route list` prints the originator as it prints labels, and `--json` carries it.

One rule keeps the line moving through stages that burn no subscription: a route whose first group is a script, people, or another yard takes every originator's beads. `AddRoute` defaults such a route to `any` — it already reads the group's runner to check quota conditions — unless `--originator` is given; packs generate `any` for stages whose group is a script or people (`run:`, `people:`, with no pack file syntax change, since the stage already names the group's kind); and the migration sets `any` on existing routes to groups whose runner is not `herdr`. The assembly, the refinery, the decide bench and the peer road take every originator's beads, since none burns a local subscription. Agent stages (`herdr`) carry no originator: the operator's builders take the operator's beads, and each person's route is added by hand. Nothing that routed before stops: every pre-field bead is the operator's, and every existing agent route matches the operator's beads exactly as it matched everything.

Views that ask for a bead made with no label and no priority (`yardr flow show`, the web flows) ask for one with no originator too, which reads as the operator's (§3.1): they name the group such a bead goes to, as today.

The fallback, which this draft picks, is to wait. A bead whose originator has no route — no own group, no login — waits as an unrouted bead does today, with the one `unrouted` event of the class attention, extended to name the originator and say no route takes their beads ("no route for stage new type task originator mckean2"). Waiting is explicit where spending the operator's subscription would be a surprise, and the operator can still subsidise: a route with `--originator mckean2 --group builders` — or an `--else builders` after the own group — sends that person's beads to the operator's groups on purpose, visibly in the route table. Nothing waits silently: `unrouted` already reaches whoever hears attention.

### 3.3. Group login: the led login, run with the group's env

`yardr harness login <kind> --group <group>` loads the group's `env_file` (the same file reader the runner uses) and leads the login with it joined: the login lands in that person's folder, and the proving call at the end runs under the same env. The JSON steps are unchanged, so footplate leads a group login as it leads the first run today; the web view leads it later (§6, B9). Only kinds with a recipe are led — claude today (§2.2); a kind without one is logged in in a terminal with the env set, which the command says. The operator makes the person, the group and the empty folder; the person answers the steps on their own device; the token is the harness's own business throughout: the person signs in through the provider's own flow, and whether the yard's agents may then use that login is open question 5. The folder the login lands in is the one the group's env names, and `login_for` (§3.2) is what says whose login that folder holds: the operator sets both together.

```sh
mkdir -p ~/.yardr/logins/mckean2   # mode 0700; the operator's hands only
printf 'CLAUDE_CONFIG_DIR=%s\n' ~/.yardr/logins/mckean2 > ~/.yardr/groups/mckean2.env
chmod 600 ~/.yardr/groups/mckean2.env
yardr harness login claude --group mckean2-builders --json   # led by footplate on mckean2's device
```

### 3.4. Limits and quota read the login that will burn, not the machine's

`yardr limits --group <group>` runs the provider's source command with that group's env and prints the windows of that login; without the flag the command answers as today, for the operator's machine login. The dispatcher's quota checks and the harness-error reads do the same for the group whose session they judge: a route condition such as `mckean2-builders@Weekly<80` then gates on mckean2's windows with no new syntax, and `session_harness_error` says what that person's subscription carries. The provider name stays the harness's (`provider=claude` burns claude's report); whose login it is comes from the env, not the name.

Reports say whose work. `yardr route report` gains the originator: each row names it, and `--originator <user>` reads one person's beads. The live sessions — `yardr session list` and the web view's sessions, the yard's departure board — show each session's bead originator beside its group, so a glance says whose login is burning.

### 3.5. The trust note, said plainly

The operator can read every login folder on the machine, and so in principle can any agent, since all run as the one OS user (§2.8). `login_for` is a declaration and the folder is what burns: nothing enforces that a group's env file points at the declared user's login, so a valid file naming another existing login runs on that account; the check is the operator's eye on `yardr group show`, which prints the account the folder's login names beside `login_for` where the harness writes one (Claude's folder does). Like every actor check in yardr, operator-only originator changes are a guardrail on the actor name, not an access boundary (docs/users.md, "Who is acting"). Bringing a subscription into a shared yard trusts the operator the way logging into the machine's own account trusts them today: the mechanism separates whose quota burns, not who can read what. This is stated where the login is led and in docs/groups.md, not footnoted.

### 3.6. The yardmaster, three shapes

mckean's afternoon question was whether a shared yard has one yardmaster on one subscription, or one per person sharing notes. Three shapes, and what each costs:

- **(A) One yardmaster; conversations split per login.** One identity — name, memories, journal, handoff, all in the store already. The line-keeping session runs on the operator's login; a conversation with person X runs in a yardmaster session on X's login, which talks, files and shapes beads for X (originator X) but does not run the line: no dispatch, no landings, no triage of faults. With no own login, X's conversation falls back to the line session. Costs: the session-per-user mechanism and the sliced inbox (§3.7). Keeps the single source of truth and one personality.
- **(B) A yardmaster per person inside one yard.** Several coordinators on one line: each person's yardmaster keeps their own conversations and all of them steer the same beads, landings and triage. Costs: rules for who triages and lands, and for how concurrent coordinators divide faults and the line; every meeting of two yardmasters on one bead is a conflict to design. Gains nothing over (A) that the slice does not already give.
- **(C) A yard per person, linked as peers.** Exists in large part: mail, asks and beads already cross between yards (docs/peers.md); memories do not. Costs: each person runs a yard, and the single source of truth is lost — two stores, two lines, two journals that merely exchange mail. This is shape 2 territory of design yardr-8wxe, with its seam.

The trial (§3.8) is written against (A), the yardmaster's pick; open question 1 takes the direction.

### 3.7. Shape (A), in the mechanism: sessions per user, a sliced inbox, a shared journal

**How a crew member gets a session per person.** A crew member's config gains per-user env beside its own (`env_file` stays the line session's): `yardr crew set yardmaster env_for_mckean2=~/.yardr/groups/mckean2.env`, held to the same rule as `env_file` (regular file, mode 0600 or stricter, read at each start; docs/crew.md, "Outbound credentials"). The daemon starts one conversation session per user so listed, on that env — a crew session per originator, like a group's. The mechanism is general to crew members; the yardmaster is its first user. Only the operator sets these keys, as for every crew definition. This is the crew-side association, separate from the group-side `login_for` (§3.2): groups answer whose login builds, crew answers whose login talks. The hook rule (§3.1) reads the group side only — a conversation session is no proof a bead would build on that login.

**The two sessions do not steer the same bead twice.** They cannot corrupt one: every write carries the revision its writer read, and a stale one is refused (`Expect`, §2.7), so the second session to move a bead gets the refusal and reads again. The role divides the rest: the line session dispatches, lands and triages; a conversation session talks, files and shapes for its person with `--for`, and never takes line outcomes. Where both sessions legitimately note one bead, notes append and both stand.

**Whose journal entries are whose.** One journal bead, shared: each entry is tagged with the session that wrote it (the line session or the person's conversation), so the reader knows who learned what. The handoff — what the next session must know — is per session: the line session hands off to its next line session, each conversation to its own next one, since what a conversation must remember about its person is not what the line must remember about the yard.

**The inbox is one log; each session reads a slice.** Today both sessions would get every notification, since a crew member has one inbox and one cursor (§2.7). The store keeps one inbox and gives each session its own cursor over it: delivery routes by correspondent, and acking in one slice never hides what another has not seen:

- mail from person X goes to X's conversation session (nudge, inbox view and ack scoped to it);
- events, and mail from people with no conversation session, go to the line session;
- an ask's answer goes to the session that asked, whichever it was.

Each slice acks through its own cursor, so reading the line's inbox marks nothing in a conversation read. The crew member's existing cursor becomes the line session's slice, and a per-user slice starts at the cursor's position when the slice is made, so an upgrade with unread items neither replays nor hides any (B6). `yardr crew show` and prime show the session its slice; the full log stays readable as today for debugging.

### 3.8. The trial

mckean has no second person, so he is two: he adds himself as a second user (mckean2), logs a group mckean2-builders in with the same account in a second folder first — decided (§5); a second account is the trial's stretch — and a bead for mckean2 builds there with the second login, seen in its session: the pane env carries the second `CLAUDE_CONFIG_DIR`, the departure board shows the bead's originator beside the group, and `yardr limits --group mckean2-builders` reads the second login's windows. The trial has two halves: the build half (routing, login, limits, reports) and the conversation half (a yardmaster session for mckean2 on the second login, mail routed to its slice, a bead it files carrying originator mckean2). Both halves run together in the one trial bead (§6, T) — decided (§5). What the trial writes down: that each half ran on the login it names, each place the wrong login could have burned instead, and whether one yardmaster with two sessions felt like one person to talk to.

## 4. Left out

- **A hosted service and billing.** The bead leaves these out: who pays whom for machine time is not this design's. What a login burns shows through `yardr limits --group` (§3.4); money never enters the yard.
- **Other providers' terms beyond naming them.** The terms case is Anthropic's pages as read on 12 and 14 Oct and OpenAI's Europe Terms as read in a browser during critique (§2.8). Kimi's and the rest are unread, and each stands as the same question; nothing here depends on their answers except which logins a cautious operator offers — and open question 5 says what to confirm before offering any.
- **The volume edge, as a limit.** Advertised Pro and Max limits assume ordinary individual use (§2.8); a yard with a yardmaster and several builders on one person's login may not be that. Provenance vouches for the shape — the origin is a person who took the work on, a bystander only gave input — and mckean accepts the edge. It is stated, not solved.
- **The originator crossing the peer link.** A bead worked by a linked yard (runner `peer`, docs/peers.md) is that yard's bead to bill: the working yard's rules name its originator, and nothing of this yard's person crosses. Per-person billing across yards is a later design.
- **Login recipes for kinds that have none.** Codex, kimi and the rest keep their terminal login; a group login for them is made in a terminal with the group's env set. A recipe is read from what one harness version prints and goes stale with it (§2.2); each is its own bead when wanted.
- **A group's `env_command`.** Groups read only `env_file` (§2.1); a command that prints the environment is a crew member's setting. Carrying a personal login from a command's output would need a new group key and its failure story, for no login this design needs — the file holds one folder override.
- **A sandbox or a wall between logins.** The trust note (§3.5) is the whole of it: separating reads would mean separate OS users or machines, which is design yardr-8wxe's shape 1, not a shared yard.
- **API keys as a person's login.** A key is a line in an env file, and how a person hands one over without a shell is design yardr-0qs5's question (yardr-8wxe §3.4). This design carries subscription logins, made in the harness's own flow.

## 5. Open questions

1. **Which yardmaster shape: (A), (B) or (C). (Asked.)** (A) One yardmaster, conversations split per login: one identity and one line, at the cost of the session-per-user mechanism and the sliced inbox (§3.7). (B) A yardmaster per person inside one yard: each person gets their own coordinator, at the cost of dividing triage, landings and faults between concurrent coordinators on one line. (C) A yard per person linked as peers: mostly exists, at the cost of a yard each and no single source of truth. I would take (A), and the trial is written against it; (C) stays the answer for a person who will not share a machine at all.
2. **Whose subscription reviews a bead. (Decided: the originator's.)** Review stages route by `--originator` like build stages, so each person gets reviewer groups beside builder groups (`mckean2-reviewers`): one rule everywhere, shown in the route table. The losing option, one shared `reviewers` group on the operator's login, would have spared the per-person reviewer groups but made the operator subsidise every person's quality gate. The refinery needs no answer: it is exec and burns no model subscription (§2.9).
3. **What the trial logs in with. (Decided: the same account in a second folder first, a second account as the stretch.)** The mechanics — routing, env separation, per-login limits reads — are proven free, since every check the trial makes is about which folder burned, not which bill; if the mechanics fail, no account is spent learning it. The losing option, a second account first, would have proven apart billing directly at the cost of the account.
4. **Whether the conversation half lands with the build half. (Decided: together.)** Routing, login, limits, reports, crew sessions and the sliced inbox land first, then the trial runs both halves in one trial — the split inbox is the part whose shape is costly to get wrong, and trying it late re-tries the trial. The losing option, the build half first, would have been smaller steps at the cost of two trials with every conversation meanwhile on the operator's login.
5. **Whether the yard's agent sessions may use a person's consumer subscription. (Asked.)** (a) Proceed on the reading: the person signs in through the provider's own flow (§3.3), the login sits in their own folder, and the agents act for them alone — at the cost of depending on that reading of "make your Account available to anyone else" and "automated or non-human means" (§2.8), which the provider could read the other way, stranding every per-person login. (b) Confirm with the provider first, as design yardr-8wxe's open question 3 does for the hosted case, at the cost of waiting, and of a question that may go unanswered. The trial's same-account mechanics half is automated use of a consumer account too, and runs meanwhile on mckean's own logins alone, which risks only his. I would take (b) before offering a second person a login. The shared machine stays stated either way (§3.5): the operator can read every login folder, which is part of what "available to anyone else" could mean.
