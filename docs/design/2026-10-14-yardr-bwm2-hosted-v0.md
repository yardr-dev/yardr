# Hosted v0: a person signs up at the edge and gets a yard container on the Mac

Design yardr-bwm2, proposed 2026-10-14. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory that beads are worked in; a bead is one durable piece of work; the crew are the yard's always-on agents, and the yardmaster is the one that coordinates; a harness is the agent program herdr starts (claude, codex); the operator is the person who runs the yard; a user is a person of the yard, a name and an inbox; a device is one program of a user that calls the yard from outside it; the edge is whatever stands in front of the yard. footplate is the native window over a yard, in its own repository and depot. See docs/glossary.md for all of yardr's words. This design is the first step of design yardr-8wxe (docs/design/2026-10-12-yardr-8wxe-yard-as-a-service.md) made concrete, not a second opinion: its shape 1, on this Mac, for a trial. "The service" below means the thing a person signs up to, "the customer" the person who gets a yard, and "the Mac" mckean's machine, which hosts the trial.

## 1. The question

mckean, 14 Oct 2026 (mails 30987, 31028, 31072): "the plan is to make yardr hostable, so users can sign up and they get their yard." His shape: a single Kratos where people sign up; behind it a yard per user, a Docker container for now, VMs (EC2, k8s) later; the user connects to the web view or footplate and onboards themselves; Kratos maps users to yards, Oathkeeper handles access, Hydra for footplate's token. Build on the Mac, in this yard, as the testbed; for the trial "just make it work technically". A later mail (31115) asked whether the whole Ory suite is the pick; mckean then agreed (mail 31158) that Oathkeeper is out of v0 and Kratos plus our own router is the edge. D3 in section 3 records that narrower answer as decided, superseding the bead's third decided point. A later mail the same day (31683) adds a droplet per user instead of a container for anyone beyond the Mac trial; D1 records that as decided.

## 2. What exists today

### 2.1. The service design this builds on

Design yardr-8wxe proposes shape 1, a yard per customer hosted whole, with the wall between customers being the machine (its 3.2), the service's pieces listed in its 3.3 (sign-up and the edge, provisioning, the GitHub App with broker and router, git, a way to the login pane, being told, upgrades and backups, metering, stopping idle machines), the yardr changes in its 3.4 (a server script, the view acting as one named user, a person handing the yard a secret), the customer's path in its 3.5, and risks in its 3.6. Its open question 2 weighed a virtual machine each against a microVM each against a container each, and the draft would not take the container; mckean's decision for this trial takes it (D1 below). Its open question 5 weighed where the service's code lives and would take a repository of its own; this design does that (section 3.2). Its 3.7 is the trial this design's trial replaces: one outside person, one machine, one week, reached over ssh — here the person never sees a terminal.

### 2.2. A yard from one script, and what it still assumes

`contrib/server-yard/server-yard --harness <kind> --operator <name>` (8wxe B1, landed) sets a yard up on a fresh Linux machine: herdr's server as a systemd user unit, linger so the services run with nobody logged in, `yardr init --harness <kind> --operator <name> --start`, the daemon and the web view as login services, ending with `yardr doctor` (its README). A second run changes nothing. It assumes a systemd user session, which a Docker container does not have; section 3.4 says what runs in the container instead. `yardr up` and `yardr down` (internal/cli/updown.go) bring the yard up — herdr's server, the yard's server, the daemon — and stop it again, safe to repeat, with `--json` for a program.

### 2.3. The web view acts as one named user

`yardr web serve --as <user>` (design 8wxe's B2 and B3, beads yardr-y6ty and yardr-bvt3, both merged) shows the yard in a browser and, for that user, sends mail to a crew member, shows the conversation, answers asks and moves a bead that waits for a person (docs/web.md, "Acting as a user"). Without `--as` every route is GET only. The user resolves in three layers — `--as`, else `YARDR_WEB_AS`, else the yard's `web_as` setting (internal/store/settings.go, `WebAsSetting`), else read-only. The view listens on loopback, or with `--unsafe` on any address, answering only to the names `--host` gives (421 otherwise; internal/cli/web.go). `yardr web install` is loopback only, so a view that faces the private network is started, not installed, exactly as 8wxe 3.3 item 1 has it: `yardr web serve --unsafe --addr <private address>:8791 --host <the customer's name for it>`.

### 2.4. The yard's half of gateway identity is filed, not built

Design yardr-scpj (docs/design/2026-10-14-yardr-scpj-web-jwt-identity.md), approved 14 Oct: with `web_jwt_issuer` set, the view verifies a gateway's JWT per request against a JWKS URL and maps its email claim to a yard user through `web_jwt_users`. Its beads yardr-rrce (verify per request) and yardr-0hrq (the verified user acts) are unlanded today (rrce in review, 0hrq in new), unparked from behind PWA plus web push with mckean's go. As built, rrce's issuer check takes only absolute http or https URLs, and its JWKS check allows plain http only on loopback; this design's contract respects the first and proposes one hosted revision to the second (3.2, Y1). This design's router mints the JWT those beads verify; they land before the trial (open question 2, decided for JWT mode: rrce and 0hrq are already in new, unparked with mckean's go).

### 2.5. A device enrols by code, and footplate pairs and sets up

`yardr user device pair <user> <device> --url <address>` (internal/cli/devicepair.go; docs/users.md, "Enrolled by a code") opens a ten-minute pairing: an eight-character code, good once, which the device calls with at `POST <address>/user/pair` and is answered with its token. The yard then serves the 21 calls of docs/api.md ("Over the network") under `/user/` to that device as that user. Opening a pairing is the operator's; the yardmaster cannot do it from its pane; and with no listener the command refuses, since no device could call with the code (devicepair.go, "this yard has no listener"). The listener is the yard's hook listener, not the web view: a separate TCP server serving `/hooks/`, `/peers/` and `/user/` (internal/server/server.go, `serveHooks`; internal/rpc/user.go), on the `hook_addr` setting or `YARDR_HOOK_ADDR`, and on nothing at all when neither is set. `:8790` is every interface (docs/configuration.md, `hook_addr`). footplate's first screen (its README, "No yard") offers three ways, the pair-with-an-address road among them, keeping the token in a 0600 file; and its "Set up a yard here" road (design yardr-3az6, built) runs the first run with no terminal, leading `yardr harness login <kind> --json` for a kind with a recipe.

### 2.6. A harness login led without a terminal

`yardr harness login <kind> --json` plays the kind's login recipe under a terminal of yardr's own and prints what it needs as JSON lines — `choose` (the method menu), `open_url` (the browser sign-in), `input` (the code to paste back), `confirm` — taking answers on stdin and ending with `done` (internal/cli/harnesslogin.go). Only claude has a recipe today (`login_recipe` in harnesses/claude.yaml, read from `claude auth login`, Claude Code 2.1.288; no other file under harnesses/ defines one). Led locally, the pasted code travels on stdin and is never stored. Led through conversation it would persist, because the web talk page sends through `Mail` (docs/web.md, "Talk") and mail is the durable event log the conversation reads back (docs/api.md, `Conversation`); so the trial's relay answers `input` through secret asks instead (Y5, section 3.5). Design yardr-2k0x (originators, per-person logins, landed with its beads filed) adds `--group` to this command in its B3 and leads a group login from the web view in its B9, after its trial — neither is built, and this design does not wait for them.

### 2.7. A secret handed over, and what the edge changes

A secret ask is answered unseen: its answer records only the names that were given, and the value is in no note (internal/store/asks.go, "its answer is the names that were given ... and the value is in no note"). `GiveSecret` writes the value to a file (internal/store/secretask.go); from a device it is taken only from a device of the yard's operator and only when the request reached the listener from the yard's own machine — a loopback peer, and no `X-Forwarded-Proto` saying plain (internal/rpc/user.go, the client's rule "https, or loopback"; docs/api.md, "For the operator alone"). footplate already answers secret asks this way, in a masked field it keeps nothing of (its src/window.rs, "Nothing typed of a secret is kept"); the web view shows the ask but answers it only by naming the terminal command (internal/web/templates/bead.html). Behind a router on another container the loopback condition does not hold, so the trial carries two small yardr changes: the yard takes `GiveSecret` from its router (Y3), and the web view answers secret asks itself (Y4). `ApproveAsk`, which runs the operator's commands, stays loopback-only; running them from the edge is a named follow-up (section 4). No secret in the trial is typed in conversation: conversation is mail, and mail persists (3.5).

### 2.8. The repository reaches the yard through the pack

GitHub is `packs/github`, a pack of kind source: a webhook pointing at the yard's hook listener, a secret file, `yardr hook add`, a credential (a token, or a GitHub App installation token minted by `contrib/github-mint/github-mint` as the source's `mint_command`), the identity, the grants, the daemon's reads (8wxe 2.7). A token credential lives in an env file of the crew member that reads the source, `~/.yardr/crew/<name>.env` as `GITHUB_TOKEN`, with the mode narrowed (packs/github/SETUP.md, "The crew member's credential"). The git transport uses whatever git on the machine is configured with; yardr sets up no git credential. The trial uses a token of mckean's own; the App, broker and router of 8wxe 3.3 item 3 come later (section 4).

### 2.9. The Mac as the testbed

OrbStack runs Docker containers on the Mac today (a supabase set answers `docker ps` now; footplate's Linux shot containers are built the same way), and a dokku VM beside them. The yard's public pieces reach the internet through a Cloudflare tunnel (signalbox.yardr.dev) and tailscale serve. Kratos, Oathkeeper and Hydra are as design yardr-xpf8 read them on 12 Oct 2026 (its 2.7): Kratos holds identities, gives a native app a session token for `Authorization: Bearer` through its API flows, and answers `GET /sessions/whoami`; Oathkeeper authorizes each request as a reverse proxy, needing no database; Hydra is an OAuth2 server that needs a login and consent application. This design uses Kratos alone (D3). Kratos is API-only: the sign-up and login pages are someone's to run. Ory's is a reference implementation, not a bundled UI: `ory/kratos-selfservice-ui-node` (Node/Express, all flows: login, registration, settings, recovery, verification), run as its own container and told where Kratos's public API is (`KRATOS_PUBLIC_URL` server-side, `KRATOS_BROWSER_URL` where the browser reaches it, per its README). A registration can call the service back: Kratos runs `after` webhooks on its flows, so sign-up can reach the provisioner server-side; provisioning itself waits for the verified address (3.2).

### 2.10. A hand-made droplet as the evidence

Today a yard was set up by hand on a DigitalOcean droplet (46.101.199.186): 95 seconds of `server-yard`, first bead merged in 2 minutes. That droplet is the evidence the provisioner's second backend (3.2) automates: the same steps, run by cloud-init instead of a person.

## 3. The proposal

The existing mechanisms carry almost all of it: the server-yard steps, the view in JWT mode, device pairing by code, secret asks answered unseen, the led harness login, footplate's pair-by-address road, and Kratos as Ory ships it. What is new is the service repository with its image, provisioner and router, footplate's hosted mode, and three small yardr changes (Y3–Y5). Three points are decided by mckean (D1–D3), written in as decided; five the bead leaves to this design (3.2–3.7).

**D1. The wall is a container per user for the Mac trial, a droplet per user for anyone else.** Decided by mckean (the container trial in his mails 30987, 31028 and 31072; the droplet beyond it in mail 31683). The Mac trial runs each yard in its own Docker container on its own Docker network, as designed throughout: a container shares a kernel with other users' code, fine for a trial with people he knows, named as the limit, with the per-user network keeping one tenant's code from another tenant's listeners (3.2, H2's isolation check). Anyone after the trial gets their own DigitalOcean droplet — its own kernel, which takes care of the kernel concern — made by the provisioner's second backend (3.2, H6). Losing: one shared machine for all trial users — no wall at all; k8s now — a platform to run before anyone has signed up.

**D2. Hosted users bring their own harness credential, subscription login or API key; misuse is on them; the service keeps no harness credential.** The harness's own login screen, or an API key the user hands the yard. Under it stands 8wxe's condition (§2.10, §3.6, open question 3): a service that runs Claude Code for its customers agrees to Anthropic's Commercial Terms whichever way the end user authenticates, the CLI unmodified, each end user on their own subscription or key, and no collecting, storing or intermediating of Claude.ai credentials or session tokens. Design yardr-2k0x's decided question 5 proceeds on the reading that a yard's agent sessions on the person's own login, signed in through the provider's own flow, are that person's use — same-account trial included, no provider asked — and this hosted trial proceeds on that same reading, kept as a known limit. The relay of 3.5 carries the person's own login input through the hosted service in memory to the waiting login process (Y5): stored nowhere, but passing through the service on the way, which the no-intermediary reading above does not plainly allow — mckean accepts exactly this relay as a stated trial limit (open question 4, decided yes on ask 4703, 14 Oct), and the trial runs. The one credential the trial retains anywhere is the GitHub token of 3.7, kept in the customer yard for the pack and revocable by the user, which is not a harness credential. Losing: the service collecting a subscription token into a paste field — forbidden as read for Claude (8wxe 2.10), and the harness's own screen exists. This is not a legal conclusion.

**D3. Identity: Kratos alone holds accounts, and our own router fronts the yards.** Decided by mckean (mail 31158), superseding the bead's point 3. The router is the edge: it reads the user-to-yard map, checks the Kratos session on each request, and mints the JWT the yard verifies per request — beads yardr-rrce and yardr-0hrq are the yard's half. The browser uses Kratos's browser flows; footplate, a first-party client, uses Kratos's API flows and sends its session token, no OAuth2. No Hydra, no Oathkeeper: the router does its one rule with one fewer process. Losing, a line each: Hydra plus Oathkeeper as 8wxe sketched — two more processes, a login and consent application to write for Hydra, and Oathkeeper moves slowly; Zitadel — accounts and OAuth2 in one binary, but a new product to learn and run for a trial; Keycloak or Authentik — full identity providers, heavier to run than Kratos for one rule; Clerk or Auth0 — no process to run, but a per-user bill and an outside service in the path of every login.

### 3.1. The pieces in one picture

```text
one origin for all users: https://<the trial's one tunnel name> (no per-user subdomain)

browser ── /login, /registration, ... ──▶ UI (Ory's reference pages) ──▶ Kratos (accounts, one for all)
browser ── /kratos/* ──▶ Kratos public (browser flows; the session cookie is first-party here)
browser ── /ready ──▶ router (provisioning state, pairing code; the session's own row only)
browser ── / ──▶ router (checks the Kratos session, mints the yard JWT) ──┬─▶ A's container :8791, web view in JWT mode
                                                                          └─▶ B's container :8791, web view in JWT mode
footplate ── Kratos API login at /kratos ── session token beside the yard entry
footplate ── router (checks the session token, passes all headers on) ──▶ A's container :8790, /user/* with the device token
GitHub ── webhook ─▶ router ── /hooks/<user>/* ──▶ that user's yard :8790 (per-yard secret verified there; the App comes later)
Kratos ── registration after-webhook ─▶ provisioner ──▶ image, volume, container, server-yard steps inside, map row the router reads
provisioner, droplet backend ──▶ droplet on DigitalOcean's VPC (cloud-init: the Dockerfile steps, server-yard, JWT settings)
router ── over the VPC ──▶ droplet's yard (its VPC address only; nothing public on the droplet)

one user's container, one OS user, on its own Docker network `yard-<user>`, ports unpublished:
  herdr server · yardr server (hook listener :8790: /hooks/, /user/) · yardr daemon · web view :8791 in JWT mode · claude, logged in by the user
  /home/yard (a named volume: store, packs, depots/<repo>) · nothing of another user · no route to another user's network
the router is attached to every user's network, and only the router joins more than one
one user's droplet: the same yard, listening on its VPC address only, reached by the router over the VPC;
  webhooks arrive through the router's /hooks/<user>/* as on docker
```

### 3.2. The user-to-yard map and provisioning: `yardr-hosted`

The service's code lives in a repository of its own, `yardr-hosted`, added as a depot of this yard (8wxe Q5, decided here for the trial). It holds the router beside the provisioner: one small Go service that is the edge (D3) and the provisioning hook. The provisioner has two backends behind one interface — `provision <user>` makes a yard reachable at an address: `docker` (the Mac trial as designed below, H2) and `droplet` (DigitalOcean, H6: create from a base image, cloud-init running the same steps the Dockerfile runs — the installs, user `yard` with linger, `server-yard`, the JWT settings; the token for the DigitalOcean API is the provisioner's secret, read from a file). The map of user to yard is a small SQLite store on the Mac that both read: user name, Kratos identity id and verified email, backend (`docker` or `droplet`), the target the router dials (the container's Docker DNS name, or the droplet's VPC address), the volume or droplet name, a state (`pending`, `ready`, or `failed` with the error), and when the yard was made. A flat file would do for two users and fail at twenty; a database server would be a third process for one table. SQLite is the middle: one file, backed up by H5's command, read by the provisioner at sign-up and by the router on each request. On the `docker` backend each user gets their own Docker bridge network, `yard-<user>`, made by the provisioner, with the yard container attached only to it — containers on different user-defined bridge networks cannot reach each other — and the router, attached to every user's network, dials the container by its Docker DNS name on that network: `http://<container>:8791` for the web view, `http://<container>:8790` for the hook listener. A recreated container under the same name needs no map change (H5 keeps the name and verifies the routes after). Losing: one shared network for all yards — any tenant's code could reach any other tenant's listeners by name, which the per-user layout refuses by construction. On the `droplet` backend the yard listens on its VPC address only and nothing is public on the droplet; the router joins DigitalOcean's VPC and dials the row's VPC address. How the Mac-hosted router reaches the VPC is the droplet bead's to choose and document (H6; the expected shape is a WireGuard link from the Mac to the VPC).

All users share one origin: the router answers one fixed tunnel name for everybody, and tells users apart by session, never by hostname. The Kratos session cookie is first-party on that origin, so the router can check it on every request; no wildcard DNS, no per-user TLS name, no cookie scoping. Losing: a subdomain per user — wildcard tunnel ingress and cookie-domain scoping, for names that distinguish nothing the session does not.

What a sign-up triggers, in order:

1. The account is made in Kratos, on Ory's reference pages (open question 1, decided). Kratos's registration `after` webhook calls the provisioner server-side with the identity, which the provisioner records as a `pending` row; provisioning itself runs only after the address is verified — `/ready` triggers it once the identity reads verified, the one webhook staying the registration one — and only for invited addresses (H0's list; open question 3, decided for the invite list). An unverified identity, even with an invited address, provisions nothing, and a non-invited identity may exist in Kratos and keeps a yardless `pending` row. For a verified invited address the provisioner makes the yard: on `docker` it builds or pulls the image (3.3), makes a named volume for the user's home and the user's own bridge network `yard-<user>`, starts the container on that network with no published ports, and runs the server-yard steps inside it with `--harness claude --operator <user>` (3.4); on `droplet` it makes the droplet of H6. The router joins the network too — at runtime the provisioner attaches it at sign-up — but that step lands in H3 with the router itself, so H2 builds and tests the yard on its network with stand-in peers and no router container (section 6). The web view listens on the container's `:8791` with `--host <the one origin name>`, in JWT mode with the five `web_jwt_*` settings of the contract below (open question 2, decided for JWT mode); the hook listener is the yard's `hook_addr` set to `:8790`, every interface, reachable only on the user's own network (2.5); on a droplet both listeners bind the droplet's VPC address only (H6). The yard also takes `GiveSecret` from the router (Y3's setting, written by the provisioner) and keeps dated store copies for backup (the daemon's settings, read by H5's command).
2. The provisioner opens the device pairing for footplate (`yardr user device pair <user> footplate --url <the one origin>`, run in the yard — inside the container on `docker`, over H6's channel on a droplet — which refuses without the listener of step 1) and writes the code to the hosted store, where the "your yard is ready" page reads it. The code holds ten minutes; if it lapses, the service operator re-opens it during the trial (self-service re-pairing is a named follow-up, section 4).
3. The provisioner moves the map row to `ready` when the yard answers — or to `failed` with the error when a step fails, in which case `/ready` shows the error with a retry, and the provisioner, idempotent per user, resumes the same user rather than doubling. The edge learns a new yard's address by reading the map, not by a reload: the router looks the user up from the Kratos session on each request and proxies to that row's target. There is no rules file to regenerate and nothing to reload. Losing: a rules file the provisioner regenerates — one more artifact whose diff must be reviewed per change, for a rule ("this session's user reaches their own row") a lookup expresses directly. The sign-up flow lands the browser on the router's `/ready` page (the UI's post-registration return address), which requires a valid Kratos session and reads that identity's own map row: before verification it says to verify the address, once `ready` it shows the yard's address and the pairing code, on `failed` the error with its retry.

Email changes are disabled in v0: the Kratos settings flow offers no email change — the reference UI's settings page is limited by Kratos configuration, or the router refuses the settings route — so the email the yard maps never changes under a live user (H3). The verified update path is a later bead (section 4).

The router's rule, in full, has two halves. The session half: a request with no Kratos session, or one whose session Kratos no longer knows, is refused at the router and reaches no yard on any session route; a session whose identity maps to no row is refused as no yard of theirs exists; otherwise the request is proxied to that row's target, and only there. For the web view the router mints the yard's JWT per request — `iss` `http://router:8080/`, `aud` `yardr-web`, the session's email as the `email` claim, a minute's life, carried in `X-Edge-JWT` (H4) — and the yard verifies it (rrce) and maps it to its user (0hrq); the router publishes its keys at `http://router:8080/jwks.json`, reachable from each yard over its own network, which is what each yard's `web_jwt_jwks` names — on a droplet the same URL, with `router` resolving to the router's VPC address through a hosts entry the provisioner writes, so both backends share one contract. The issuer is URL-shaped because Y1's setting check takes only absolute http or https URLs — the issuer is compared with the token's claim, never fetched. The plain-http key URL is allowed by Y1's hosted revision for the router's exact network name `router` and nothing else (Y1, H4): on a user's Docker network the only other container is the router, and on a droplet the hosts entry points at the router's VPC address, so the fetch has no third party on its path; a fetch or redirect to any other host, dotless or not, is refused. HTTPS stays the rule everywhere else. For `/user/*` the router passes all headers on, and the yard reads the device token as today. Session answers are kept a minute, so a logout is honoured within a minute; a minute is also the JWT's life, so a stolen one dies with it. The webhook half carries no session by design, in both backends: `/hooks/<user>/*` is proxied to that user's target with the user prefix stripped, and the yard verifies the delivery against that yard's own hook secret as today (internal/server/server.go, `/hooks/` by signature or token); an unknown user answers 404 at the router and reaches no yard. The router also serves its own account paths — `/kratos/*` to Kratos's public API, the UI's account routes to the UI container (H3), `/ready` itself — of which `/kratos/*` and the UI routes take no yard session, while `/ready` requires a valid Kratos session and reads that identity's own map row before it shows anything.

The customer is their yard's operator user, as in 8wxe 3.3 item 2: the commands that are "the operator's" are run by the provisioner, at provisioning, or by the customer in conversation with their yardmaster where a command exists for it.

### 3.3. The image: one Dockerfile, a volume for home

`image/Dockerfile`, on Debian: yardr, herdr, git and claude — the only harness with a login recipe (2.6), so the only one the trial leads — each pinned by version, with a `versions.txt` the provisioner prints into the trial note. Other harness kinds stay out of the image until one has a recipe and a login flow the relay can lead (section 4). The yard's home is a named volume mounted at the yard user's home, so deleting the container deletes nothing of the user's. Backup has two halves, in one command (H5): each yard keeps dated, consistent copies of its store by itself — the daemon's `backup_every`/`backup_keep` settings, through the running server in one read transaction (docs/configuration.md, "Copies of the store") — and the host nightly tars each volume to the Mac's disk, kept seven days; the tar may hold a torn live `yard.db`, which is never restored — restore puts a dated copy in place as the store, the documented copy-restore. The hosted map is backed up with the same command (SQLite `.backup` to a dated file, kept seven days). Restore is a volume made from a tarball with the newest dated copy as its store, a fresh container of the same name over it, and the map from its backup. Copies on the same Mac cover a lost container or volume, not loss of the host; that limit is said plainly to the trial users. Upgrade is rebuild and recreate: a new image is built, each container is stopped and started again from it under the same name over the same volume, and the server and daemon take the new binary up themselves while the web view starts fresh with the container. Losing: baking the home into the image — a build per user and no upgrade path; losing for backup: restoring the live `yard.db` from the tar — a torn store instead of a copy made in one read transaction. The `droplet` backend builds no image: cloud-init on a Debian base image runs the same steps the Dockerfile runs — the installs pinned as `versions.txt`, user `yard` with linger, `server-yard --harness claude --operator <user>`, the JWT settings — so Dockerfile and cloud-init change together (H6). A droplet's home is its disk; the dated store copies cover it, while volume tarballs are the `docker` backend's only. Idle cost is the droplet's price; snapshot-and-destroy on idle is a later bead (section 4).

### 3.4. No systemd in the container: the entrypoint runs the yard

`server-yard` writes systemd user units and turns linger on, and a container has neither. So the container's entrypoint does the same steps without them: `yardr init --harness claude --operator <name>` if the volume holds no yard yet, then `yardr up` (herdr's server, the yard's server with its hook listener on the `hook_addr` the provisioner wrote, the daemon), then `yardr web serve --unsafe --addr :8791 --host <the one origin name>` in the foreground, in JWT mode from the settings the provisioner wrote. Unpublished ports keep both listeners on the user's own network only; from another user's network they do not answer (H2's isolation check). Docker's restart policy brings the container back after a reboot, which is linger's job done by the host. The entrypoint is idempotent like the script: a second start over a volume that holds a yard starts it, and makes nothing twice. No yardr change: every command it runs exists. On a droplet there is systemd, so there is no entrypoint: cloud-init runs `server-yard` itself with linger on, and the yard comes back after a reboot the way a server yard does (2.2).

### 3.5. The harness login with no terminal: the yardmaster relays the led login

Two options, as the bead frames them: a terminal in the browser on `herdr agent attach <yard>-yardmaster` behind the router, or the yard waiting for the login to appear while the person answers the harness's own flow elsewhere. This design takes the second: the yardmaster runs `yardr harness login claude --json` in its pane and relays each need through the conversation, in the web talk page or footplate — `choose` as buttons, `open_url` as a link, `confirm` as a yes — passing the answers back on the command's stdin. The `input` need is not relayed through conversation: conversation is mail and mail persists (2.6), and a login code or API key persisted there would be the collecting D2 forbids. Instead the yardmaster asks a login-input secret ask (Y5): a secret ask whose value `GiveSecret` hands to the waiting login process in memory, recording only that it was given, never the value — the secret-ask guarantee of 2.7 with a login process as the destination instead of a file. The value still passes through the hosted service — the browser or footplate, the router, the yard's server memory — on its way to the login's stdin: stored nowhere, but carried, which mckean accepts as a stated trial limit (open question 4, decided yes) rather than the design claiming no intermediary handling. The relay is the login path in both backends; ssh into the droplet with the user's key is the technical fallback, not the design's path. The person signs in through the harness's own flow (D2); an API-key user answers the key at the same ask, where the harness's flow asks for it. Both surfaces answer it with their secret-ask fields: footplate's exists (2.7), the web's is Y4. Losing: the browser terminal — a new pane-driving surface behind the edge, typing into panes yardr otherwise never types into, a larger build and a larger review for a trial. What the relay costs is an agent in the loop of a login: slow, and the trial writes down each place it stuck, which orders the later leading beads (2k0x B9 for the view, a footplate remote-login bead after it).

### 3.6. footplate's hosted mode: the Kratos session beside the yard entry, pairing as today

The person signs in from footplate with Kratos's API flow at the origin's `/kratos` path, the native-app road Kratos documents (email and password fields in footplate itself, no system browser), and footplate keeps the session token beside that yard's entry, in a 0600 file next to the device token, never in the settings file. On each call footplate sends both: the device token in `Authorization: Bearer`, exactly as today, and the session token in a second header, `X-Edge-Token`, which the router checks with Kratos's `/sessions/whoami` before proxying, passing all headers on. The yard reads `Authorization` and changes nothing. Pairing stays pairing by code as today (2.5): the session does not replace the device pairing. Losing: the session replacing the device pairing — the yard would have to verify the router's JWT on `/user/*`, the scpj shape built for a second surface, before anyone has tried the first. The relay's login inputs need no new footplate bead: they arrive as secret asks, which footplate already answers in a masked field it keeps nothing of (2.7).

What footplate shows on the first screen for a hosted yard: a fourth way, "Open a hosted yard", beside the three of 2.5. It asks for the router address — the one origin — then shows the hosted yard's row in three states: "Sign in" (the Kratos account's email and password, in the window), "Pair this device" (the name and the code from the ready page), and, paired, the yard's conversations with the signed-in account named under the yard's name. A refused session token and a refused device token are told apart on screen: the first offers sign-in again, the second offers pairing again, and neither is retried silently. The signal is the response's shape: the router refuses a missing or unknown session with 401 carrying `X-Edge-Refusal: session` and a JSON body naming the edge; the yard refuses a bad device token with its own 401 — plain `Unauthorized` with `WWW-Authenticate: Bearer` (internal/rpc/user.go, the refusal path) — which the router passes through byte for byte, adding nothing. Footplate offers sign-in again on the first shape and pairing again on the second; H3 and F1 assert both shapes, so the two depots' builders implement the same protocol.

### 3.8. Care

The risks are 8wxe 3.6's, narrowed to the two trials: another user's agent reads this user's code — on `docker` the container is the wall, a kernel shared between users who run arbitrary code, named as the limit (D1); on a droplet each user has their own kernel, which takes care of the kernel concern; the router mistakes one user for another — the yard verifies the minted JWT per request, so a router fault mints for the wrong user rather than silently serving them, and the router's rule is one lookup to review; a stolen footplate token pair reads the yard as the user — removal at the yard (`device rm`) and the session revoked in Kratos ends it; the service operator reads the user's code — nothing technical stands against it, and it is said to the trial users plainly; a login code or key persists where it should not — the relay answers inputs only through secret asks whose values reach just the waiting login process (Y5), the in-memory carrying itself is the stated limit mckean accepted, and the trial searches the mail history to prove it (3.7); the machine is lost — the repository is on GitHub, the store's dated copies and the volume tarballs are on the same Mac and go with it, a login is made again.

## 4. Left out

- **Billing and metering.** The trial's users pay nothing and cost machine weight only; what a user costs is read from Docker's own accounting outside the yard, and a droplet's price from DigitalOcean's. Money enters through the provisioner's records in `yardr-hosted`, never the yard.
- **Stopping idle yards.** A yard survives a stop, but a stopped container receives no webhook and fires no timer, so the router would have to wake it (8wxe 3.3 item 9). A later lever on cost, in the provisioner; on droplets the shape is snapshot-and-destroy on idle, its own later bead.
- **EC2, k8s.** The scaling after droplets (D1); the provisioner learns each as one more backend behind `provision <user>`.
- **The GitHub App with broker and router.** The trial uses a token of the user's own (3.7) and direct webhooks at `/hooks/<user>/*`, verified per yard (3.2); the App, the token broker and the single-address webhook router are 8wxe 3.3 item 3, unchanged, in `yardr-hosted` when strangers arrive.
- **A brand and a landing page.** The trial's pages are the sign-up, the ready page and the yard itself; marketing is not a bead here.
- **A multi-tenant store.** Excluded by the premise: every customer gets an isolated yard of their own, and yardr is not made multi-tenant (8wxe 1).
- **A sandbox inside yardr.** The container or droplet is the wall; the harness's own permission modes are what a group chooses from. Same exclusion as 8wxe's.
- **The service keeping a harness credential.** D2: the harness's own flow, never a paste field of the service's — and the relay of 3.5 carries the person's own input in memory without storing it on mckean's explicit accept (open question 4, decided yes). The trial's GitHub token is the one retained credential: kept in the customer yard for the pack at `~/.yardr/crew/<member>.env`, disclosed at the ask, revocable by the user (3.7).
- **A public 443 per droplet with its own certificate.** Yards and webhooks stay behind the router over the VPC (3.2); a droplet answering the public internet itself is not in v0.
- **Changing email on a live account.** Disabled in v0 (3.2); the verified update path — re-provisioning the yard's `web_jwt_users` mapping after a verified change — is its own later bead.
- **Harness kinds without a login recipe in the image.** Only claude has one (2.6); a kind joins the image with its recipe and the relay flow for it, each its own bead when wanted.
- **Approving the operator's commands over the edge.** `GiveSecret` travels the edge in the trial (Y3); `ApproveAsk`, which runs the operator's commands, stays loopback-only (2.7), and whether it ever travels is its own design after the trial.
- **Self-service re-pairing.** During the trial the service operator re-opens a lapsed pairing (3.2); a user doing it themselves — a button on the ready page, or a narrow capability the yardmaster may use — waits for the trial's note on how often it was needed.
- **Oathkeeper.** Decided out of v0 by mckean (mail 31158): the later first gate in front of everything, where any valid Kratos account passes and the router still maps user to yard and mints the JWT. Webhook deliveries, which carry no session by design (3.2), pass it by path, not by account.
- **Hydra.** Separately deferred in D3: footplate is a first-party client needing no OAuth2. Hydra comes back only for third-party applications reading a yard, as xpf8 3.5 sketched for someone else's application.

## 5. Open questions

All four are decided; each keeps its options and costs as the record, with the decision and who took it.

1. **What are the sign-up and login pages?** Kratos is API-only and needs a UI (2.9). (a) Ory's reference UI, `ory/kratos-selfservice-ui-node`, run as a container in H3's compose and pinned by image digest: all flows, the least code, the least control over what the person sees, and H3 verifies its routes answer through the router's single origin. (b) A small page of the service's in `yardr-hosted`, calling Kratos's API flows: the trial's own words, at the cost of owning registration, login, recovery and every edge of each. I would take (a) for the trial: the trial learns about yards, not about forms. Decided by the yardmaster for (a): Ory's reference UI, pinned by digest.
2. **Does the trial run in JWT mode, or on router-checked sessions with `--as`?** (a) JWT mode: beads yardr-rrce and yardr-0hrq land before the image and the trial, unparked from behind PWA plus web push for hosted — the trial tests the shape strangers get, at the cost of moving two beads ahead of mckean's parked order, with his go. (b) The router checks Kratos sessions and proxies to `--as` views for the trial, and the yard starts verifying the minted JWT when rrce and 0hrq land after — the trial runs sooner and touches no parked order, at the cost of testing a weaker shape than strangers get and re-trying identity later. I would take (a): the minted JWT is the router's whole point in D3, and a trial that never verifies it proves the proxying but not the trust. Decided by the yardmaster for (a): JWT mode; rrce and 0hrq are already in new.
3. **Who may sign up for the trial?** (a) Anyone with the address: the truest test, and strangers' code on a shared kernel (D1) from day one. (b) An invite list the provisioner checks — one list of emails or codes, no other machinery: people mckean knows, matching the wall's stated limit, at the cost of one more thing the operator tends by hand. I would take (b): the trial's wall is named for people he knows, and the sign-up should say the same. Decided by the yardmaster for (b): the invite list.
4. **Does the trial accept the relay carrying the harness login input in memory?** The relay of 3.5 carries the person's own one-time code or API key through the hosted service — browser or footplate, router, yard server memory — to the waiting login's stdin, stored nowhere (Y5). (a) Yes, as a stated trial limit: the person types their own input into their own yard's login prompt; the service carries it in memory and keeps nothing. The cost is the reading: the provider terms forbid intermediating session tokens, and if this input counts as one the trial reads them wrongly. (b) No: hosted v0 ships no harness login, the trial yard's harness stays unlogged, and the trial as briefed — landing one bead — cannot run. I would take (a): without the relay there is no trial, and the relay stores nothing. Decided by mckean for (a) on ask 4703 (14 Oct): yes, as a stated trial limit; the trial runs. This is not a legal conclusion.
