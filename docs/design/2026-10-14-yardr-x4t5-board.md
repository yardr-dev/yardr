# A board in the yard: HTML pages agents and people share, shown in footplate and the web view

Design yardr-x4t5, proposed 2026-10-14. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory beads are worked in; a bead is one durable piece of work. A crew member is an always-on agent of the yard, tied to no bead; the yardmaster is the one that coordinates. The operator is the person who runs the yard; a user is a person of the yard. Footplate is the yard's native app: a window onto the yard for talking with the crew. The web view is `yardr web serve`: the yard in a browser. A blob is a file the yard keeps in its home under the SHA-256 of its bytes. A note is evidence attached to a bead (`yardr bead note`); mail is a message to a crew member or a user (`yardr mail`). A peer is another yard this one is linked with. See docs/glossary.md for all of yardr's words.

## 1. The question

mckean, 14 Oct 2026, from his friend Flavio: "the most important feature is having a design board, basically a canvas board with html markup so ideas and visualizations can be shared, like artifacts, in footplate." Today a crew member or builder can only share words and PNGs, attached to a note or to mail; an explanation, a mockup, a chart or a diagram has to leave the yard altogether — on 14 Oct the yardmaster used claude.ai artifacts for the footplate head mockup and its write-up. The question is what the smallest version is that carries the need before any canvas — an HTML page kept as a blob, attached like an image, and opened from footplate and the web view — and what a board then adds: several pages laid out on one surface.

## 2. What exists today

### 2.1. Blobs are images only, content-addressed, attached to notes and mail

The yard keeps a file in its home, in `blobs/` under the SHA-256 of its bytes, once however often it is attached, and never changes it (`Store.PutBlob` in internal/store/blobs.go). What the bytes are is what counts, never the file's name: `blobType` reads the type with `http.DetectContentType`, and anything but `BlobTypes` — today `image/png` and `image/jpeg` — is refused, as is anything over the yard's cap (`blob_max_bytes`, 8 MiB unless set: `BlobMaxSetting`, `DefaultBlobMax`). One note carries at most 8 files and one mail at most 8 (`MaxNoteFiles`, `MaxMailFiles`). A blob nothing names is pruned past an hour's grace (`BlobGrace`, `pruneBlobs`).

A note carries files only when written with `yardr bead note --file` (internal/cli/bead_note.go): the note still needs words saying what the picture shows, and where the note is read the files stand under the words on a line of their own starting with the mark no writer's words can carry (`NoteFilesMark`, `NoteFilesLine`: "◆ 1 image: \<path\>"). Mail carries files with `yardr mail --file` (docs/users.md, "An image in mail"; `putFiles` in internal/cli/crew.go puts each file, in order, before the mail is sent): with a file the text may be left out, and the letter reads the picture by opening the blob file, as any file. In `--json` both have `files`, a list of `{hash, type, bytes}`.

### 2.2. The web view serves a note's images only, inside a strict policy

`GET /blobs/<hash>` (`handleBlob` in internal/web/beads.go) serves only blobs a note on some bead names (`Store.NoteBlob` in internal/store/blobs.go): any other hash, a mail's image included, answers as a missing blob, "since the view has no login" (docs/web.md, "One bead"; held by `TestBlobRoute` in internal/web/blobs_test.go). The bead's page draws each note's images below its words, with the words as alt text, and a line saying so for one the yard no longer holds, never a broken icon (internal/web/templates/bead.html; the `Missing` map in internal/web/beads.go). Note that the talk page renders mail files the same way (internal/web/templates/talk.html) but those bytes 404 under the rule above; that quirk is filed as yardr-k5j6 and whatever mail-attached pages do inherits the rule until it is decided.

The view is server-rendered `html/template`: one stylesheet, htmx vendored under `internal/web/assets/` and embedded in the binary — no CDN, no build step — and a test fails on any URL naming another host (docs/web.md, "No other host"). Every response carries `Content-Security-Policy: default-src 'self'` with no inline script or style and `form-action 'none'` (or `'self'` on a view that acts), plus `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` (`policy` and `ServeHTTP` in internal/web/server.go; the blob route gets these headers too, since they are set before the mux serves). The view listens on loopback only (default `127.0.0.1:8791`) unless started with `--unsafe`, answers only to loopback names and names given with `--host`, and answers 421 to anything else, so a page on another site cannot read the yard through a visitor's browser by DNS rebinding (`knownHost` in internal/web/server.go; docs/web.md, "Loopback only" and "Behind a proxy"). With `--as <user>` the talk page and asks take writes, each checked against the request's `Origin` (docs/web.md, "Acting as a user"); without it every route is GET and HEAD only.

### 2.3. Footplate draws natively and fetches images over the socket

Footplate is Rust on gpui (`=0.2.2` in footplate's Cargo.toml): it draws everything itself and has no web engine — `wry`, `webview`, `tao` and `webkit` appear in neither its Cargo.toml nor its Cargo.lock package names (read 14 Oct). An image of a mail or of a note is drawn with gpui's `img` from `Image::from_bytes`, at a fixed height, with a faint line where there is none ("an image footplate cannot draw", "image \<hash8\>: the yard no longer has it"): `picture` in footplate's src/window.rs, called for mail entries and for bead notes shown on cards. The bytes come from the yard over the existing calls: `blob` in footplate's src/api.rs does `GET /blobs/<hash>` over the unix socket on a local yard and `GET /user/blobs/<hash>` with the device's token on a paired yard (`Way::Socket` and `Way::Listener`, `send`), served by `a.blob` in internal/rpc/server.go and the `/user/` mux in internal/rpc/user.go, which answer any blob the yard holds. Sending goes the same way: `put_blob` (`PutBlob` with base64 bytes) and `mail` with file hashes, and pasted images attach to the draft. Footplate already opens URLs with gpui's `cx.open_url`: a clicked link (`links` in footplate's src/select.rs accepts `http://` and `https://`, opened at src/select.rs:903) and the first-run flow (src/window/firstrun.rs:77). The `https`-only `is_page` guard (src/setup.rs:980) belongs to the harness-login `Need::Page` path alone, not to link clicks — so a loopback `http://` view URL follows the precedent clicked links already set, on macOS and Linux alike.

### 2.4. Peer links carry files as inert bytes, by hash, under the `file` kind

`yardr mail <name>@<peer> --file yard.png` sends each file as one message of kind `file` before its mail, when the link carries `file` as well as `mail` in that direction (docs/peers.md, "An image with the mail"). The receiving yard checks the bytes against the hash they came under, reads the type from the bytes as for a blob put there, and holds them to its own `peer_file_max_bytes` (`takeFile` in internal/store/peerfiles.go); one it holds already is not written again. What it did not take stands on the mail as `not taken:` with why — the link, the cap, or "it did not arrive" (`mailFiles`). A file is one message, never cut in parts, at most 32 MiB (`MaxPeerFile`). Each yard tells the other what its build understands with every request (`understands` in `yardr peer show`); a yard from before a kind passes its messages by, and mail with a file to a peer that never said it understands `file` is refused before anything is queued. The receive path refuses bytes of no known type the same way it refuses bytes of the wrong hash (`RefusedNotFile`), so a type a new build sends and an old build does not know lands as "it did not arrive", never as bytes served under a claimed type.

## 3. The proposal

The smallest version is a page: one self-contained HTML file as a blob, attached to a note or to mail exactly as an image is today, and opened from the web view and from footplate. No new store, no new server, no new attach command. What follows is that version under the decisions in section 5; where a fork lives, the section names it and points at the question.

### 3.1. One mechanism carries it: blobs

`BlobTypes` gains the HTML type, and everything else inherits it. `http.DetectContentType` answers `text/html; charset=utf-8` for HTML bytes (run 14 Oct against the toolchain's `net/http`), so the type is read from the bytes as image types are, and what is not HTML is refused as images are — including SVG files, which the sniffer answers as `text/plain; charset=utf-8` (run 14 Oct; see section 4). Inherited unchanged: the `blob_max_bytes` cap, content addressing (a second put writes nothing, `keepBlob`), the 8-files bounds, the prune past `BlobGrace`, the peer receive checks in `takeFile`, and footplate's `put_blob`/`blob`, which already move bytes of any held type. What is new: the type string in `BlobTypes`; the "N images" wording where a letter's or note's files are shown (`FilesLine` in internal/store/blobs.go), which must say pages apart from images; the `--file` help in `yardr bead note` and `yardr mail`, which today says PNG or JPEG; and the two viewers below.

### 3.2. An agent makes one by attaching a file, as images are today

The agent writes `page.html` in its worktree and attaches it:

```sh
yardr bead note yardr-9c2k "Footplate head mockup, third pass: the head row with the decision count." --file page.html
```

The page is one file: styles and SVG inline, images as `data:` URLs or none at all. Nothing fetches anything external — the sandbox the page opens in has no network (sections 3.3, 3.5) — and relative links to other blobs resolve to nothing, since the serving routes answer only hashes named from a page of their own. The size limit is the blob cap, 8 MiB unless the yard sets `blob_max_bytes`, as for images. A note with a page still needs its words, saying what the page shows. There is no update in place: the content address is the version, so a changed page is a new blob on a new note, and the note order is the version order. Both attach, but only note pages open in this version: mail pages are kept and shown, and open once mail viewing is decided (sections 3.3, 3.4; yardr-k5j6). How a person makes one is question 5; the first version is agent-authored.

### 3.3. The web view lists a note's pages and serves their bytes, static

The bead's page lists each page under the note's words where images stand today: not an `<img>` but a link, `page <hash8>`, opening the bytes in the reader's browser. The bytes come from the existing `GET /blobs/<hash>` under the existing `NoteBlob` rule — note pages are visible, mail pages answer as missing blobs like mail images (section 2.2, yardr-k5j6) — so opening is note-only in this version. Served as `text/html`, the page must open inert: `handleBlob` replaces, for the HTML type, the page policy `ServeHTTP` set before the mux served (internal/web/server.go:257) with a page policy of its own. The `sandbox` directive alone is not that policy: it kills scripts, forms and plugins, but it does not block network loads or frames, so the policy pairs it with a fetch allowlist (`sandbox` and `default-src` are separate directives: https://www.w3.org/TR/CSP/#directive-sandbox, https://www.w3.org/TR/CSP/#directive-default-src):

```text
Content-Security-Policy: sandbox allow-top-navigation-by-user-activation; default-src 'none'; script-src 'none'; connect-src 'none'; frame-src 'none'; child-src 'none'; object-src 'none'; font-src 'none'; media-src 'none'; img-src data:; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
```

Scripts are dead twice over (no `allow-scripts`, `script-src 'none'`); nothing loads over the network — the carve-outs are `data:` images and inline styles only, so a self-contained page with inline SVG, `<style>` and `data:` images renders whole; no frame loads and none embeds the page; forms are dead; and the sandbox's opaque origin (no `allow-same-origin`) withholds the yard's API and cookies — the view sets none — from the page. What survives is deliberate: the reader follows a link out by clicking it (`allow-top-navigation-by-user-activation`), with no referrer (`Referrer-Policy: no-referrer`, already set) and no opener window for the page to hold. The exact token set is for the security review to confirm (section 6: every rendering bead carries it). The page opens top-level, by link, never embedded in a yard page: the yard's own pages keep their CSP unchanged, and the no-other-host test still holds, since a navigation is not a fetch. The talk page, which renders every mail file as an `<img>` today (internal/web/templates/talk.html:8-9), must not render page files as images — it skips them or names them without a link, never a broken icon — since mail pages are unopenable until mail viewing is decided. One the yard no longer holds is the Missing line images get, never a broken link.

### 3.4. Footplate shows a page as a row with Open, in the system browser

Where `picture` draws an image today — mail entries and bead notes on cards — a page is a row instead: the note's or mail's words, `page, <size>`, and, for a note's page, Open. Footplate fetches nothing new: `blob` already answers bytes of any held type, over the socket and over a pairing. A note's Open hands the web view's `/blobs/<hash>` URL for the page to the system browser through the `cx.open_url` footplate already uses for clicked links (section 2.3) — read against a footplate setting holding the view's base address, defaulting to the view's default (`http://127.0.0.1:8791/`). That default is why no yard change is needed for the common case: a local yard's view answers there when it runs. When it does not run, or answers nothing, the row says so and how to start it (`yardr web start`), instead of opening nowhere. A yard footplate reaches by pairing is opened the same way once the setting names the address that machine's view is reached by — the proxied or forwarded name, exactly as the person opens the view itself. A mail's page is the same row without Open, saying pages open from notes: the view serves no mail blob (section 3.3), and a `file:` opening would carry no sandbox, so mail Open waits on the mail-viewing decision filed as yardr-k5j6. There is no pixel preview and no embedded engine in this version (question 2 weighs the engine).

### 3.5. Scripts come second, on a separate origin

Static pages — mockups, write-ups, diagrams, static charts — land first, on the same origin, because a fully sandboxed page needs no new listener. Scripted pages — interactive charts, the part of "visualizations" static cannot do — follow on a separate origin: the web view gains a second loopback listener that answers blob bytes only, no yard route at all, fenced by the same loopback/`--host`/421 rules as the view itself (docs/web.md, "Loopback only"), with the proxy documentation saying which second name to give it. Its policy runs inline scripts and nothing else:

```text
Content-Security-Policy: sandbox allow-scripts allow-top-navigation-by-user-activation; default-src 'none'; script-src 'unsafe-inline'; connect-src 'none'; frame-src 'none'; child-src 'none'; worker-src 'none'; object-src 'none'; font-src 'none'; media-src 'none'; img-src data:; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'
Cross-Origin-Resource-Policy: same-origin
```

Scripts run without `allow-same-origin`, so the origin stays opaque even to the sandbox listener itself, which answers no yard route; they reach no yard API, no cookies, no network (`connect-src 'none'` covers fetch, XHR, WebSocket and EventSource), no frames, no workers, no form posts; navigation out is a reader's click only, as in section 3.3. Nothing in the store marks a page scripted — `BlobRef` carries hash, type and bytes only (internal/store/blobs.go:67-72) — so the opt-in lives in the open action, not the page: every page opens static by default, and where the sandbox listener exists each page carries a second action, `run`, opening the same hash there. The reader opts into scripts per open, per page; no author forces them on a reader. That choice is question 6; scripts allowed or not, and the static-first phasing, is question 1; the listener, the header set, the `run` action and the proxy story are bead 4, with the security review as part of done.

### 3.6. What a person would type and see

```sh
$ yardr bead note yardr-9c2k "Footplate head mockup, third pass." --file page.html
note 12 on yardr-9c2k  ◆ 1 page: /home/mckean/.yardr/blobs/9f31…
```

On `/beads/yardr-9c2k` the note's words stand with `page 9f31…` beneath them; following it opens the mockup, scripts dead, in the reader's browser. In footplate the same note on the bead's card is a row — `page, 41 KB` with Open — and Open shows the same bytes in the system browser; the same file on mail is the row without Open, saying pages open from notes. In `--json` the note has `files: [{hash, type: "text/html; charset=utf-8", bytes}]`, as images do.

### 3.7. What a board adds

A page carries one idea; a board lays several out on one surface so they can be read together. The pages do not change for it: a board is an arrangement over pages the yard already holds, each still attached to its note or mail, still versioned by content address. Two shapes fit: a board per bead — the bead's pages laid out beside its notes, in note order under question 7's answer — and a board per yard — pages from anywhere, kept as a surface of their own. People adding to a board is person authoring (question 5) pointed at either shape. Which shape first is question 4; the first version blocks neither, since both arrange the same page items.

## 4. Left out

Real-time co-editing is out: shared cursors and simultaneous typing need presence and a merge story the store has nothing of, and the need as asked is sharing finished pages, not editing together. Comments on a page or a board are out: notes on the bead already discuss whatever the page shows, and a second comment thread would split the discussion. A design system or component library is out: pages are free-form HTML, and any shared styling travels inside each page file until a real repetition earns a library. A canvas editor beyond laying out existing pages — drawing, dragging, resizing on the surface itself — is out: the board arranges pages, it does not author them.

Opening a mail's page, and attaching a page to mail from footplate, are out of this version: both wait on the mail-viewing decision filed as yardr-k5j6, not on this design. An update in place is out, by the mechanism: the content address is the version, so every version is a new blob and nothing rendered earlier changes under its reader. A pixel preview in footplate and rendering a page to an image at upload are out: both need an HTML renderer in the build, and the hermetic options are none — a headless browser is a second program to install, not a library. SVG files as blobs are out for now: the sniffer answers `text/plain` for SVG (run 14 Oct), so taking them needs its own sniffing beside `blobType`, and SVG served as an image is inert while SVG served as a document is active — diagrams travel inline in pages instead. Uploading a page from the web view is out: the view takes no writes without `--as`, and an upload is a write with a file body, a larger route than the version needs. A per-yard page store is out: pages live on notes and mail, where the prune, the caps and the peer rules already govern them.

## 5. Open questions

1. Scripts in pages: static first, scripted second on a separate origin? (a) Static first, as section 3.3, with scripted pages following on the separate origin of section 3.5 (whose opt-in is question 6). Costs: two viewer beads instead of one, and the second listener with its `--host` and proxy story; buys: the version lands without the listener, and static pages are inert by header on the origin that already exists. (b) Scripted from the start on the separate origin. Costs: the listener, the header set and the proxy story all gate the first page; buys: one viewer bead, interactive charts on day one. (c) Static, never scripted. Costs: nothing further; buys: nothing further — interactive charts stay outside the yard, and part of "visualizations" is unanswered. (d) Render each page to an image at upload and show the image. Costs: a renderer in the build or beside it, and everything interactive is dead by construction; buys: viewers change least. The draft's pick is (a): it answers most of "ideas and visualizations shared" at once, and the scripts it defers are the named next bead, not a second design.

2. Footplate: open in the system browser, or embed an engine? (a) System browser through the web view, as section 3.4. Costs: a row with Open reusing `cx.open_url` (section 2.3), a view-address setting, and the view must run and be reachable; buys: no engine, no new dependency, identical pixels on macOS and Linux. (b) Embed a webview (wry). Costs: a new native dependency and two toolkit backends — WebKitGTK system libraries on Linux end the hermetic build — inside a gpui app, plus the sandboxing the view gives for free reimplemented around it; buys: pages inside the window, no view needed. (c) Fetch the bytes and open them as a local file. Costs: no headers on `file:` URLs, so no sandbox and no policy, plus temp-file hygiene; buys: works with no view running. The draft's pick is (a): the view is the yard's renderer, and footplate stays native. No pixel preview in any option: it needs the renderer option (d) of question 1 refused.

3. Do pages cross to a linked yard? (a) As files do today: under the existing `file` kind, within `peer_file_max_bytes`, with `takeFile`'s hash and type checks unchanged. Costs: the consent operators gave for images now covers active content too, and an old yard shows the page as "it did not arrive" until it upgrades; buys: no protocol change, no new kind, and the refusal on old builds is already safe. The trust delta is real but bounded: the bytes cross inert and only the receiving yard's own sandbox runs them, the same sandbox as its local pages. (b) A new consent for pages apart from `file`. Costs: a kind or flag through pairing, `peer allow`, `peer show` and the filing; buys: operators choose images and pages separately. (c) Pages do not cross at first. Costs: a type check on send and a way to know the peer renders pages (`understands` lists kinds, not types); buys: no active content crosses until the sandbox has mileage. The draft's pick is (a): the link's file consent already means "bytes may land" (docs/peers.md: "this says whether bytes may land"), and the sandbox is the receiver's in every case.

4. What shape is the board: per bead or per yard? (a) Per bead first: the bead's pages laid out beside its notes. Costs: a yard-wide surface waits; buys: the board sits where its discussion already is, and needs no new store — it arranges the bead's note files. (b) Per yard first: pages from anywhere on one surface. Costs: a new stored surface with its own membership and pruning; buys: one place for the yard's thinking. (c) Both at once. Costs: both builds; buys: no second decision. The draft's pick is (a): it is arrangement only, over items the first version already defines. The first version is unblocked either way: pages are the board's items under every option.

5. How does a person make a page? The first version is agent-authored (section 3.2), and only note pages open (sections 3.3, 3.4), so person authoring targets notes. (a) Next, footplate attaches HTML files to bead notes: `add_note` in footplate's src/api.rs takes files beside words — `AddNote` over the socket takes bead, text and actor only today (internal/rpc/api.go), while `AddNotedAs` already takes files — and the card's note UI takes a file. Costs: files through the note call plus attach UI; buys: a person shares a page without a terminal, and it opens in both viewers. (b) Next, the web view takes uploads to a note. Costs: a POST route with a file body, `--as` only, under the Origin check — the view's first file write; buys: no app needed. (c) Footplate attaches to mail instead, as it attaches pasted images today. Costs: small Rust UI now — but the page sits unopenable until the mail-viewing decision (yardr-k5j6); buys: nothing until then. The draft's pick is (a): it reuses `put_blob` and the note-adding call footplate already has, and its pages open on day one. Mail authoring follows the mail-viewing decision, not this design.

6. Who opts a page into scripts: the reader per open, or the author per page? (a) The reader, per open, as section 3.5: every page opens static, and a `run` action beside it opens the same hash on the sandbox origin. Costs: two actions per page in each viewer; buys: no store or call-shape change, a safe default, and no author forces scripts on a reader. (b) The author, per page, marked at attach. Costs: the marker stored beside the files on notes and mail (bead 1), carried in peer `file` messages (bead 5), and honored by both viewers (bead 4, which then lands after bead 5); and a marker from a peer yard lets a remote author opt the local reader into scripts. Buys: one click, and author intent travels with the page. (c) No choice: every page is script-capable once bead 4 lands. Costs: nothing; buys: nothing — the static viewer of bead 2 becomes decoration, and opening any page runs its author's scripts. The draft's pick is (a): the sandbox then runs only what the reader asked to run.

7. What lays the board out: note order and an automatic layout, or the author's hand? (a) Note order and an automatic layout: the board is the bead's note pages in note order, in a list or grid the template sets. Costs: no custom arrangement; buys: arrangement only, no new metadata and no new store. (b) An author-set order. Costs: an order store per board — a record beside notes naming which pages in which order — plus UI to set it; buys: a curated sequence. (c) Free positions on a canvas. Costs: positions per item in that store, plus positioning UI; buys: true canvas layout. The draft's pick is (a): the board stays an arrangement over items the first version already defines. If (b) or (c), bead 6 grows the store and the UI.

## 6. The beads it would become

In landing order: 1 → 2 → 3 → 6 → 7, with 5 after beads 1 and 2, 4 after beads 2 and 3 (after bead 5 too if question 6 is (b)), and 8 between 6 and 7 where it exists — bead 8 exists only if question 4 is (c). Beads 2 and 4 render untrusted bytes, so each carries a review of its rendering path by the security lane as part of done, per the bead's constraint — the review confirms the policy is enforced in a real browser, not only present in headers. Mail Open and mail authoring are not among these beads: they wait on the mail-viewing decision filed as yardr-k5j6 (mail images broken on the talk page), which these beads neither depend on nor pre-empt; mail-attached pages stay web-invisible until it is decided, as mail images are today.

1. The yard keeps HTML blobs, attached as images are. Goal: `BlobTypes` takes the HTML type the sniffer answers, `yardr bead note --file` and `yardr mail --file` attach `.html` with no new flag, and the files line says pages apart from images. Where to look: `BlobTypes` and `blobType` in internal/store/blobs.go, `putFiles` in internal/cli/crew.go, the `--file` help in internal/cli/bead_note.go and the mail command, `FilesLine` and `NoteFilesLine` in internal/store/blobs.go, docs/users.md ("An image in mail"). Done when: a `.html` file attaches to a note and to mail with the type the bytes say; a non-HTML file named `.html` is refused; an SVG file is refused (section 4); caps, dedup, prune and the 8-file bounds behave as for images; the files line names pages distinctly in plain text and `--json` carries `text/html; charset=utf-8`; and the help and docs say HTML. If question 6 is (b), the attach commands also take the author's script-intent marker, a flag beside `--file`, and store it beside the files on the note and the mail. Depends on nothing.

2. The web view lists and serves a note's pages, static. Goal: each page stands under its note's words as a link opening the bytes top-level and inert. Where to look: the notes loop in internal/web/templates/bead.html with the `Missing` line as images have, the mail-file loop in internal/web/templates/talk.html (page files skipped or named, never `<img>`), `handleBlob` in internal/web/beads.go (Content-Type from the ref, the page policy for the HTML type replacing the page policy of internal/web/server.go:257), `TestBlobRoute` in internal/web/blobs_test.go, docs/web.md ("One bead", "No other host"). Done when: a note page opens top-level under the policy of section 3.3, with tests asserting the exact header set — scripts dead, and an external image, stylesheet, script, fetch and frame each forbidden by the headers; a page the yard no longer holds is the Missing line; mail pages answer as missing blobs like mail images, and the talk page renders no page file as an image; the no-other-host test passes unchanged; the yard's own pages keep their policy; the docs say so; and the security lane has reviewed the rendering path and confirmed the policy in a real browser.
