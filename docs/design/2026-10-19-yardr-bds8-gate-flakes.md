# Landing-gate flakes under load: one rule for time, a cheaper flaky record, and the fixes each folded bead needs

Design yardr-bds8, proposed 2026-10-19. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

## 1. The question

Thirteen backlog beads filed between 16 and 19 Oct 2026 each record one run of the depot's test gate (`sh .yardr/test`, often with `YARDR_LANDING=1` for a landing) that failed with no behaviour broken and then passed on a rerun or later. Each failure costs the bead it blocked a round trip back to `new` or a `flaky:` line that someone must file as a new bead, and the class grows faster than one-off fixes close it. This design folds the thirteen into one account: what kind of failure each one is, checked against the code as it stands on 19 Oct, the one rule that would have prevented the test failures, what the gate itself should change, and the implementation beads that carry the rest. No code lands with this document.

The thirteen, as filed, fall in three classes. Class A is tests that measure wall-clock time against machine load. Class B is the gate's own tests of its race lock and its subprocesses, in the root package. Class C is the per-package 60-second budget (rule R1 in `docs/testing.md`) failing green packages on a loaded machine. Section 2 checks each bead against the code and regroups two of them; section 6 maps every folded bead to an implementation bead or to the fix that already closed it.

## 2. What exists today

### 2.1 The gate, in the parts that bear on these flakes

The gate is `.yardr/test`. Plainly, in a builder's or reviewer's worktree, it runs gofmt, `go vet`, `go build`, then `go test -race` on the packages the branch changed and everything that imports them. With `YARDR_LANDING=1` the assembly runs the base's copy of the same script on what lands: the same selection plus the six black-box suites that build the tree's binary, linux vet, and, when the selection holds the store, dispatch or bdp packages, those three suites again over the unix socket beside the first run. The whole suite otherwise runs only on a quiet machine, under the dispatcher's event-driven trigger in `internal/dispatch/quiet.go` (rule R6), which holds the machine-wide race lock for its whole length and reports `quiet_passed` or `quiet_failed`.

Three mechanisms in the script matter here, and this design prefers all three over anything new.

The failed-package retry (`again` in `.yardr/test`) runs a failed step's failed packages once more with the same flags. When they pass, the step passes and one line beginning `test: flaky:` names the tests and packages that failed the first time. The comment at that code states the trade plainly: a test that fails one time in two for a real race now gets through a landing half the time, and the flaky line is what makes that visible. Today a builder or reviewer who sees that line files a bead for it; the roles in all three packs (`packs/starter/roles/builder.md`, `packs/contributors/roles/builder.md`, `packs/design/roles/builder.md`, and the three reviewer copies) say to file it from the flaky line, say whether it is the product or the test, and fix it there rather than on the bead it blocked. Thirteen beads in four days is that instruction working as written, at a bead's full price each: shaping, a builder session, two reviews, a landing.

The race lock (`racelocked` in `.yardr/test`) runs one `go test -race` leg at a time on the machine, because five worktrees' race suites side by side on ten cores slow each other past Go's per-package timeout. Waiters queue on timestamped tickets under `$HOME/.yardr/race.queue` and take the lock in arrival order; a dead waiter's ticket is skipped and removed by whoever reaches the front (`front` and `fullclean` in the perl the script embeds), a waiter killed with TERM removes its own ticket and exits 143, and the holder keeps its ticket until it exits so queued runs count it in their place. One hold covers the leg, its failed-package retry and the package-budget re-measurement, shared through `YARDR_RACE_HELD` instead of waiting again. What the lock does not cover is just as important: vet and build wait for nothing, and the socket leg beside a landing's first run is a plain `go test` without `-race`, so it takes no hold and runs beside the race leg on purpose, saving wall time at the price of contention the budget re-measurement then runs inside.

The R1 budget (`packagebudget` and `loadedmachine` in `.yardr/test`, rule R1 in `docs/testing.md`) fails a run when a package's tests take over 60 seconds under `-race`. A package over budget in the leg and not allow-listed — the allow-list today names only `internal/cli` — is run again alone with `-count=1`, still inside the leg's race-lock hold. Over 60 seconds alone on a quiet machine fails the run, naming both times. Since yardr-wq5h landed on 18 Oct (commit a30c501a), over 60 seconds alone on a loaded machine instead passes with a loud line naming both times and the load: `loadedmachine` reads the one-minute load average and the core count (`/proc/loadavg` and `nproc`, else `sysctl vm.loadavg` and `hw.ncpu`, the same readings `contrib/machine-limits` takes) and calls the machine loaded when the average is past the core count. Unknown load still fails. The quiet run (R6) is named as the judge that sees the package again on a quiet machine. The one-minute average and the core count can be overridden through `YARDR_TEST_LOADAVG` and `YARDR_TEST_CORES`, following the script's existing `YARDR_TEST_OWNER` precedent, so the gate's own tests can pin the machine quiet or loaded however the test machine stands.

### 2.2 The time rules that already exist

`docs/testing.md` states seven rules. R1 is the 60-second package budget above. R2 says a test sleeps no more than 500 ms at a site and a poll loop polls a condition with a deadline; a test that waits on time takes a clock it sets, naming the fake clocks the packages already own (the dispatcher's clock, which tests set through `internal/dispatch/export_test.go`'s `SetClock`; `Receiver.SetClock` in `internal/hooks/receiver.go`; the peer clock in the dispatch tests), and a test that must use the real clock is allow-listed with its reason, as six sleep sites are in the script's `longsleeps` table. R4 gives the test line its fields, including the seconds queued on the race lock. R6 is the quiet run. Nothing in those seven rules says, in one place, which of the three ways of waiting a new test should pick — wait for the effect, take an injected clock, or take a deadline from the load — nor how a reviewer checks the pick in a diff. The builder and reviewer roles carry one sentence of it ("wait on the effect, not on wall time", from the yardr-022s design), but a role sentence is not checkable against a test file the way R2's literal sleep scan is.

The code already owns three load readings, none shared. The gate's `loadedmachine` reads the load average against the core count. `contrib/shot/shot_test.go`'s `underLoad` calls the machine loaded when `YARDR_LANDING` is set or the test binary was built with the race detector, and its `windowTimeout` gives a headless-Chrome test ten seconds instead of sixty under load so a stalled Chrome skips quickly instead of spending the full minute (yardr-c2vt). The quiet run's `quietLoad` in `internal/dispatch/quiet.go` reads the same load average for its log line and never fails on it. Any proposal that needs another load reading is new machinery; the ones below reuse these.

### 2.3 Class A checked: tests written against wall-clock time

**yardr-rgm1 and yardr-9enf — `TestPeersDaemonHoldsOrPolls`, already fixed.** Both beads record the same test in `internal/dispatch/peerhold_test.go` failing once in a race leg and passing on the gate's retry. As filed, the test counted peer polls inside a fixed 500 ms window and wanted 3 to 15 of them at 50 ms intervals; under race load fewer than three polls fit in the window. That code no longer exists. Yardr-x51w (commit dc8d4762, landed 18 Oct after both beads were filed) rewrote the first phase to wait for six more polls in whatever time the machine takes, through the same `until` helper the file's other tests use, and to assert only that the six took at least 200 ms: they span five 50 ms pauses, timers fire at or after their deadline and never before, so load can only stretch that span, never shorten it. The second phase still sleeps 500 ms and wants at most one further question while a question is held for a second; a holding daemon asks nothing, and load cannot manufacture a question, so that sleep can only under-count, never over-count. Both beads are closed by x51w, not by anything proposed here, and section 6 maps them so. They still earn their place as the worked example of the rule in section 3: the fix waited for the effect and kept only the one elapsed-time assertion whose direction load cannot falsify.

**yardr-sdb8 — `TestDaemonSkipsAnOlderBuildAndLogsIt`, test-only.** In `internal/dispatch/replace_test.go` the test starts the daemon, sleeps 200 ms, cancels, and then requires exactly one `replace_skipped` event in the store. The daemon checks its binary between passes and on a `CheckBinary` ticker — 10 ms in this test — through `version.Binary.Replacement` in `internal/version/version.go`, which hears of a skipped older build through the `Skipped` callback the dispatcher wires to the event log in `internal/dispatch/dispatch.go`. Twenty ticks fit in 200 ms on a quiet machine; under race load the daemon's goroutine may not be scheduled often enough to reach even the first check before the cancel, so the event the test asserts was never written. Nothing in the product waits on wall time here: the test sleeps instead of waiting for the event it asserts. Its neighbours in the same file already wait properly — one polls the pass stamp until the daemon's first pass lands, another polls the event log for three seconds for `daemon_replaced`. The fix is test-only: wait for the `replace_skipped` event, with a deadline as a fuse, before cancelling, and keep the assertion that the older build was never exec'd.

**yardr-2f9q and the watcher half of yardr-yvq8 — `awaitWatcherSleep`, test-only.** Two tests in `contrib/assembly/watcher_test.go`, `TestMergeLocalKilledWithTermLeavesNoSleepBehind` and `TestMergeLocalIgnoresZeroWatcherPID`, failed in whole-suite race runs at just over ten seconds and passed alone in one to two seconds. Both wait through `awaitWatcherSleep`, which polls the process table with `ps` for the timeout watcher's sleep and fails fatally ("the watcher's sleep never showed in ps") past a ten-second wall deadline. Under whole-suite load, process creation and `ps` itself starve past that deadline; the sleep it looks for is a `/bin/sleep` of about half an hour that has not gone anywhere. The product under test, `contrib/assembly/merge-local`, already records the effect the test needs on disk: its watcher writes its sleep's pid to a nap file under the run's `TMPDIR` before it waits (and holds until that file is non-empty, for the same reason), and the test's own fake `sleep` first on `PATH` writes a record file named with its pid before it execs the real sleep. The zero-PID test already reads that nap file, through a helper that finds it by the pid the `ps` poll returned — the one step that needs `ps` at all. Waiting on either file instead of on process-table visibility makes the deadline a fuse that only fires when the watcher truly never started its sleep. Test-only; `merge-local` does not change.

**yardr-n8ej — `TestHarnessVersion`, test and product.** In `internal/agents/harness_test.go` the test writes a shell script that prints a fixed version at once and asks `HarnessVersion` in `internal/agents/harness.go` for it. `HarnessVersion` runs the harness's version flags under a five-second context (`harnessVersionTimeout`, a variable tests can replace) and returns an empty string on any error, including the timeout. Under race load, starting that shell script took long enough that the five seconds ran out and the test read an empty version; the package took 5.40 s in the failing run against 1.58 s on the retry. The test half is the familiar one: the success case leaves the real five seconds in place while the same test's hanging case replaces the variable with 50 ms, so the success case's bound is whatever load leaves of the product's. The doctor tests solved exactly this in `internal/cli/doctor_test.go`, whose fake tools get thirty seconds with a comment recording that a script's start alone took over two seconds on a loaded machine and an answer was read as a hang. The product half is real and the bead says so: a genuine harness that cold-starts slowly on a loaded yard also gets five seconds, after which the caller proceeds as if there were no version. For this caller the cost of silence is small — the version only annotates a `session_harness_dialog` event in `internal/dispatch/harness_dialog.go`, and is omitted from it when empty — but the bound is the same five seconds that class A4 below shows failing at a higher-stakes caller.

**The server-yard quarter of yardr-yvq8 — the doctor's version probe, product.** `TestServerYardSetsUpAYard` in `contrib/server-yard/server_yard_test.go` runs the real `server-yard` script, which ends with `yardr doctor` and takes its exit status from it. Doctor probes each harness's version flag through `probe` in `internal/cli/needs.go`, under the same five-second bound (`versionTimeout`, likewise a variable tests replace), and a probe that does not answer in time is reported as a hang, which makes doctor name a fault. The fake `claude` on the test's `PATH` is a shell script that echoes its version at once; under whole-suite load its start starved past five seconds, doctor faulted a healthy stand-in, and the script failed. This test cannot stub the bound away, because it drives the built binary, not the package. It is the same product bound as yardr-n8ej at a caller where timing out is not silence but a false fault that fails a setup. One product question covers both bounds; section 5 puts it to the operator, and section 6 splits the two callers into two beads because they live in different packages, fail differently, and either could land without the other.

### 2.4 Class B checked: the gate's own lock and subprocess tests

All three beads in this class are tests of `.yardr/test` itself, in the root package's `yardtest_test.go`, driving fixture copies of the script with a fake `go` and, for the lock tests, the script's real perl queue under a throwaway home. None of them touches product code; two are timing margins, and one is a genuine bug in a test.

**yardr-zaks — `TestYardTestRaceLegWaitsForTheLock`, test-only.** The test holds the race lock itself, lets the fixture run reach its build step, holds the lock three seconds further (allow-listed in `longsleeps` with that reason: so the wait spans whole seconds however slowly the run started), then releases it and probes with non-blocking flocks that neither the race leg nor the budget re-run ever leaves the lock free, finishing with an exact list of the `go` calls and a summary line whose waited field must be at least one second. It failed once inside a gate run whose queue wait was 555 of its 1,109 seconds, then passed focused in 14.5 s; its isolated re-run inside that gate took 15.43 s. The failing assertion was not preserved — the gate prints only the first sixty failure lines of a failed step and the bead records none — but every load-sensitive step in the test is a fixed margin standing in for a synchronisation: the three seconds stand in for "the fixture is queued", and the waited-at-least-one-second summary stands in for the same fact. The queue already publishes that fact as data: a ticket file under the queue directory, and the waiter's own `test: race lock:` status line. Waiting for the ticket before releasing the held lock makes the wait real by construction instead of by margin. Test-only.

**The race-lock quarter of yardr-yvq8 — the TERM-killed waiter's ticket, test, settled.** `TestYardTestRaceLockServesWaitersInOrder` kills a queued waiter with TERM, checks it exits 143, then checks at once that its ticket file is gone. In the failing run that check found the ticket still queued, and the reporter rightly flagged a possible product defect in the script's perl, since a leaked ticket could in principle block the queue. Reading the queue settles it as a test assertion stronger than the product's contract, with a narrow product race worth naming. On TERM the perl's handler removes its own ticket before it exits, so after the waiter's exit the ticket is gone in the normal run of things. But the queue's contract never rests on that removal: every reader of the queue — `front`, `fullclean`, the place counter, the `--race-queue` view — judges a ticket by whether its pid still lives with the start time the ticket recorded, removes dead tickets as it passes them, and skips them in every listing. The same test proves that path deliberately for a waiter killed with KILL, which can run no handler at all. The one window in which a TERM-killed waiter's ticket outlives it is a kill that lands between the ticket file's rename into the queue and the assignment of its name in the perl, where the handler still holds no name to remove; the ticket is then dead by pid and is reaped by the next waiter to reach the front, exactly as a KILL leaves it. So the ticket's presence in the instant after the exit is not a queue failure, and the test should wait for its absence with a deadline, as the watcher tests already wait for stray sleeps to die. That is the verdict: test-only, the product window named and shown harmless because dead-ticket reaping is the designed path, not a fallback. Section 6 gives the bead both the test change and a deterministic reproduction (a stand-in `ps` or a stalled ticket directory) that would convict the perl instead if the ticket proved live, in which case the fix moves to the script.

**yardr-y5zt — race-detector reports in the root package, a bug in one test, the rest unpreserved.** The landing run reported data races in eight root-package tests. One is attributable from the code alone. `TestYardTestRaceLegLockDiesWithOrphan` starts its fixture run with `cmd.Run()` inside a goroutine and, from the test's own goroutine, reads and kills through `cmd.Process` while that start is still in flight; `exec.Cmd` does not allow its fields to be touched concurrently with `Run`, so the race the detector reports on `Cmd` and `Process` is a bug in the test, not load and not the script. It fires only when the ten-second deadline branch is taken — which is also why the report ends "the race leg never reached go test": under load the deadline passed, the test reached for the process handle it had not synchronised, and the detector named the reach. `TestYardTestRaceLegWaitsForTheLock` shares the shape in a weaker form, writing its output and error variables from a `CombinedOutput` goroutine the test reads on its failure paths. The other six named tests run their commands synchronously, and the first run's race output was not preserved beyond the summary, so no honest verdict on them exists yet; races are interleaving-dependent, so a quiet rerun passing proves nothing either way. Section 6 therefore carries one bead that fixes the two unsynchronised tests by construction — start the process where its handle is published, wait for it in the goroutine — and one that reproduces the root package under load with the full race output kept, and fixes whichever side it convicts.
