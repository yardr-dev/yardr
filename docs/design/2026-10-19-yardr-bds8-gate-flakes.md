# Landing-gate flakes under load: one rule for time, a cheaper flaky record, and the fixes each folded bead needs

Design yardr-bds8, proposed 2026-10-19. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

## 1. The question

Thirteen backlog beads filed between 16 and 19 Oct 2026 each record one run of the depot's test gate (`sh .yardr/test`, often with `YARDR_LANDING=1` for a landing) that failed with no behaviour broken and then passed on a rerun or later. Each failure costs the bead it blocked a round trip back to `new` or a `flaky:` line that someone must file as a new bead, and the class grows faster than one-off fixes close it. This design folds the thirteen into one account: what kind of failure each one is, checked against the code as it stands on 19 Oct, the one rule that would have prevented the test failures, what the gate itself should change, and the implementation beads that carry the rest. No code lands with this document.

The thirteen, as filed, fall in three classes. Class A is tests that measure wall-clock time against machine load. Class B is the gate's own tests of its race lock and its subprocesses, in the root package. Class C is the per-package 60-second budget (rule R1 in `docs/testing.md`) failing green packages on a loaded machine. Section 2 checks each bead against the code and regroups two of them; section 6 maps every folded bead to an implementation bead or to the fix that already closed it.

## 2. What exists today

### 2.1 The gate, in the parts that bear on these flakes

The gate is `.yardr/test`. Plainly, in a builder's or reviewer's worktree, it runs gofmt, `go vet`, `go build`, then `go test -race` on the packages the branch changed and everything that imports them. With `YARDR_LANDING=1` the assembly runs the base's copy of the same script on what lands: the same selection plus the six black-box suites that build the tree's binary, linux vet, and, when the selection holds the store, dispatch or bdp packages, those three suites again over the unix socket beside the first run. The whole suite otherwise runs only under rule R6, the dispatcher's event-driven trigger in `internal/dispatch/quiet.go`, which holds the machine-wide race lock for its whole length and reports `quiet_passed` or `quiet_failed`. "Quiet" there is yard-quiet, not load-quiet: `quietReady` (`quiet.go:154-178`) starts a run when at least `quiet_landings` code landings have landed since the last one started, no bead waits in `approved`, and no bead session is live. It never reads the machine's load before starting. That distinction decides how much of R1's load-aware pass R6 can later undo, and section 2.5 and question Q2 carry it through.

Three mechanisms in the script matter here, and this design prefers all three over anything new.

The failed-package retry (`again` in `.yardr/test`) runs a failed step's failed packages once more with the same flags. When they pass, the step passes and one line beginning `test: flaky:` names the tests and packages that failed the first time. The comment at that code states the trade plainly: a test that fails one time in two for a real race now gets through a landing half the time, and the flaky line is what makes that visible. Today a builder or reviewer who sees that line files a bead for it; the roles in all three packs (`packs/starter/roles/builder.md`, `packs/contributors/roles/builder.md`, `packs/design/roles/builder.md`, and the three reviewer copies) say to file it from the flaky line, say whether it is the product or the test, and fix it there rather than on the bead it blocked. Thirteen beads in four days is that instruction working as written, at a bead's full price each: shaping, a builder session, two reviews, a landing.

The race lock (`racelocked` in `.yardr/test`) runs one `go test -race` leg at a time on the machine, because five worktrees' race suites side by side on ten cores slow each other past Go's per-package timeout. Waiters queue on timestamped tickets under `$HOME/.yardr/race.queue` and take the lock in arrival order; the holder keeps its ticket until it exits so queued runs count it in their place. One hold covers the leg, its failed-package retry and the package-budget re-measurement, shared through `YARDR_RACE_HELD` instead of waiting again. What the lock does not cover is just as important: vet and build wait for nothing, and the socket leg beside a landing's first run is a plain `go test` without `-race`, so it takes no hold and runs beside the race leg on purpose, saving wall time at the price of contention the budget re-measurement then runs inside.

Dead tickets are reaped, but not by every reader, and the distinction decides one bead below. In the perl the script embeds, `front` (the oldest-live-ticket scan) unlinks dead tickets ahead of the first live one, `fullclean` (run by a waiter as it takes the flock) unlinks every dead ticket but its own, and `place` (the "Nth in line" counter) unlinks dead tickets it passes on its way to its own ticket. The `--race-queue` view (`show_queue`) does none of that: its comment says so ("Dead tickets are skipped, not removed"), and its loop skips a dead ticket without unlinking it. A waiter killed with TERM or INT runs `cleanup`, which unlinks its own ticket before it exits (143 for TERM, 130 for INT); a waiter killed with KILL can run no handler and leaves a ticket for the next servicing reader to reap.

The R1 budget (`packagebudget` and `loadedmachine` in `.yardr/test`, rule R1 in `docs/testing.md`) fails a run when a package's tests take over 60 seconds under `-race`. A package over budget in the leg and not allow-listed — the allow-list today names only `internal/cli` — is run again alone with `-count=1`, still inside the leg's race-lock hold. Over 60 seconds alone on a quiet machine fails the run, naming both times. Since yardr-wq5h landed on 18 Oct (commit a30c501a, 19:34), over 60 seconds alone on a loaded machine instead passes with a loud line naming both times and the load: `loadedmachine` reads the one-minute load average and the core count (`/proc/loadavg` and `nproc`, else `sysctl vm.loadavg` and `hw.ncpu`, the same readings `contrib/machine-limits` takes) and calls the machine loaded when the average is past the core count. Unknown load still fails. R1's text names the quiet run (R6) as the judge that sees the package again, but the code does not make that run a strict re-judgement. `execQuietRun` (`quiet.go:358-422`) tests the base with the same test command and `YARDR_LANDING=1` (`quiet.go:412`), so its race leg reaches the same `packagebudget`, which calls `loadedmachine` afresh at the alone re-run (`.yardr/test:825-834`). `quietLoad` (`quiet.go:285-305`) only records the one-minute load the run started under, for its log line and result; nothing compares it, gates the start on it, or changes the budget's loaded pass. A package over 60 s alone therefore passes loudly again inside an R6 run whenever the load average is still past the core count at that re-run, exactly as it did at the landing. Holding the race lock removes contention from other gate legs, which makes a load-quiet moment likelier, but work outside the yard and the yard's own non-gate work can keep the average up across successive R6 runs. The strict verdict — over 60 s alone fails — is reached only by a run, landing or R6, whose alone re-run happens at load at or below the core count (or at unknown load, which fails). That residual is real: on a persistently loaded host a genuinely slow package can collect loud passes indefinitely and never face the strict verdict. Section 3.2 does not hide it behind R6, and Q2 puts closing it to the operator. The one-minute average and the core count can be overridden through `YARDR_TEST_LOADAVG` and `YARDR_TEST_CORES`, following the script's existing `YARDR_TEST_OWNER` precedent, so the gate's own tests can pin the machine quiet or loaded however the test machine stands.

### 2.2 The time rules that already exist

`docs/testing.md` states seven rules. R1 is the 60-second package budget above. R2 says a test sleeps no more than 500 ms at a site and a poll loop polls a condition with a deadline; a test that waits on time takes a clock it sets, naming the fake clocks the packages already own (the dispatcher's clock, which tests set through `internal/dispatch/export_test.go`'s `SetClock`; `Receiver.SetClock` in `internal/hooks/receiver.go`; the peer clock in the dispatch tests), and a test that must use the real clock is allow-listed with its reason, as six sleep sites are in the script's `longsleeps` table. R4 gives the test line its fields, including the seconds queued on the race lock. R6 is the quiet run. Nothing in those seven rules says, in one place, which of the three ways of waiting a new test should pick — wait for the effect, take an injected clock, or take a deadline from the load — nor how a reviewer checks the pick in a diff. The builder and reviewer roles carry one sentence of it ("wait on the effect, not on wall time", from the yardr-022s design), but a role sentence is not checkable against a test file the way R2's literal sleep scan is. Section 3 therefore puts the choice inside R2 rather than adding a parallel rule beside it.

The code already owns three load readings, none shared. The gate's `loadedmachine` reads the load average against the core count. `contrib/shot/shot_test.go`'s `underLoad` calls the machine loaded when `YARDR_LANDING` is set or the test binary was built with the race detector, and its `windowTimeout` gives a headless-Chrome test ten seconds instead of sixty under load so a stalled Chrome skips quickly instead of spending the full minute (yardr-c2vt). The quiet run's `quietLoad` in `internal/dispatch/quiet.go` reads the same load average for its log line and never fails on it. Any proposal that needs another load reading is new machinery; the ones below reuse these.

### 2.3 Class A checked: tests written against wall-clock time

**yardr-rgm1 and yardr-9enf — `TestPeersDaemonHoldsOrPolls`, already fixed.** Both beads record the same test in `internal/dispatch/peerhold_test.go` failing once in a race leg and passing on the gate's retry. As filed, the test counted peer polls inside a fixed 500 ms window and wanted 3 to 15 of them at 50 ms intervals; under race load fewer than three polls fit in the window. That code no longer exists. Yardr-x51w (commit dc8d4762, landed 18 Oct 19:40, after both beads were filed) rewrote the first phase to wait for six more polls in whatever time the machine takes, through the same `until` helper the file's other tests use, and to assert only that the six took at least 200 ms: they span five 50 ms pauses, timers fire at or after their deadline and never before, so load can only stretch that span, never shorten it. The second phase still sleeps 500 ms and wants at most one further question while a question is held for a second; a holding daemon asks nothing, and load cannot manufacture a question, so that sleep can only under-count, never over-count. Both beads are closed by x51w, not by anything proposed here, and section 6 maps them so. They still earn their place as the worked example of the rule in section 3: the fix waited for the effect and kept only the one elapsed-time assertion whose direction load cannot falsify.

**yardr-sdb8 — `TestDaemonSkipsAnOlderBuildAndLogsIt`, test-only.** In `internal/dispatch/replace_test.go` the test starts the daemon, sleeps 200 ms, cancels, and then requires exactly one `replace_skipped` event in the store. The daemon checks its binary between passes and on a `CheckBinary` ticker — 10 ms in this test — through `version.Binary.Replacement` in `internal/version/version.go`, which hears of a skipped older build through the `Skipped` callback the dispatcher wires to the event log in `internal/dispatch/dispatch.go`. Twenty ticks fit in 200 ms on a quiet machine; under race load the daemon's goroutine may not be scheduled often enough to reach even the first check before the cancel, so the event the test asserts was never written. Nothing in the product waits on wall time here: the test sleeps instead of waiting for the event it asserts. Its neighbours in the same file already wait properly — one polls the pass stamp until the daemon's first pass lands, another polls the event log for the exec of the new build. The fix is test-only: wait for the `replace_skipped` event, with a deadline as a fuse, before cancelling, and keep the assertion that the older build was never exec'd.

**yardr-2f9q and the watcher half of yardr-yvq8 — `awaitWatcherSleep`, test-only.** Two tests in `contrib/assembly/watcher_test.go`, `TestMergeLocalKilledWithTermLeavesNoSleepBehind` and `TestMergeLocalIgnoresZeroWatcherPID`, failed in whole-suite race runs at just over ten seconds and passed alone in one to two seconds. Both wait through `awaitWatcherSleep`, which polls `watcherSleepers` — the fake sleep's record files for a pid, confirmed by a `ps -p` lookup of that pid — and fails fatally ("the watcher's sleep never showed in ps") past a ten-second wall deadline. Under whole-suite load, process creation and the `ps` confirmation starve past that deadline; the sleep it looks for is a `/bin/sleep` of about half an hour that has not gone anywhere. The product under test, `contrib/assembly/merge-local`, already records the effect the test needs on disk: its watcher writes its sleep's pid to a nap file under the run's `TMPDIR` before it waits (and holds until that file is non-empty, for the same reason), and the test's own fake `sleep` first on `PATH` writes a record file named with its pid before it execs the real sleep. The zero-PID test already reads that nap file, through a helper that finds it by the pid the `ps` poll returned — the one step that needs `ps` at all. Waiting on either file instead of on process-table visibility makes the deadline a fuse that only fires when the watcher truly never started its sleep. The zero-PID test carries a second race that a file wait alone does not close: its test command is `sleep 1` (`watcher_test.go:394`), so if the test goroutine is unscheduled past that second — the same starvation that hid the sleep from `ps` — merge-local finishes, kills its watcher and its sleep through `unwatched`, and removes the nap file before the test ever writes the zero. The fake sleep's record file survives its process, so reading the pid from it afterwards recovers no live watcher, and the zero-PID assertion is never exercised. That test therefore needs its command held alive until the assertion is done, not merely a better observation; B2 specifies the handshake. Test-only; `merge-local` does not change.

**yardr-n8ej — `TestHarnessVersion`, test and product.** In `internal/agents/harness_test.go` the test writes a shell script that prints a fixed version at once and asks `HarnessVersion` in `internal/agents/harness.go` for it. `HarnessVersion` runs the harness's version flags under a five-second context (`harnessVersionTimeout`, a variable tests can replace) and returns an empty string on any error, including the timeout. Under race load, starting that shell script took long enough that the five seconds ran out and the test read an empty version; the package took 5.40 s in the failing run against 1.58 s on the retry. The test half is the familiar one: the success case leaves the real five seconds in place while the same test's hanging case replaces the variable with 50 ms, so the success case's bound is whatever load leaves of the product's. The doctor tests solved exactly this in `internal/cli/doctor_test.go`, whose fake tools get thirty seconds with a comment recording that a script's start alone took over two seconds on a loaded machine and an answer was read as a hang. The product half is real and the bead says so: a genuine harness that cold-starts slowly on a loaded yard also gets five seconds, after which the caller proceeds as if there were no version. For this caller the cost of silence is small — the version only annotates a `session_harness_dialog` event in `internal/dispatch/harness_dialog.go`, and is omitted from it when empty — but the bound is the same five seconds that the next item shows failing at a higher-stakes caller.

**The server-yard quarter of yardr-yvq8 — the doctor's version probe, product.** `TestServerYardSetsUpAYard` in `contrib/server-yard/server_yard_test.go` runs the real `server-yard` script, which ends with `yardr doctor` and takes its exit status from it. Doctor probes each harness's version flag through `probe` in `internal/cli/needs.go`, under the same five-second bound (`versionTimeout`, likewise a variable tests replace), and a probe that does not answer in time is reported as a hang, which makes doctor name a fault. The fake `claude` on the test's `PATH` is a shell script that echoes its version at once; under whole-suite load its start starved past five seconds, doctor faulted a healthy stand-in, and the script failed. This test cannot stub the bound away, because it drives the built binary, not the package. It is the same product bound as yardr-n8ej at a caller where timing out is not silence but a false fault that fails a setup. One product question covers both bounds; section 5 puts it to the operator, and section 6 splits the two callers into two beads because they live in different packages, fail differently, and either could land without the other.

### 2.4 Class B checked: the gate's own lock and subprocess tests

All three beads in this class are tests of `.yardr/test` itself, in the root package's `yardtest_test.go` (with two of the race-report names living in `main_test.go`), driving fixture copies of the script with a fake `go` and, for the lock tests, the script's real perl queue under a throwaway home. None of them touches product code; two are timing margins, and one named test is a genuine bug in a test.

**yardr-zaks — `TestYardTestRaceLegWaitsForTheLock`, test-only.** The test holds the race lock itself, lets the fixture run reach its build step, holds the lock three seconds further (allow-listed in `longsleeps` with that reason: so the wait spans whole seconds however slowly the run started), then releases it and probes with non-blocking flocks that neither the race leg nor the budget re-run ever leaves the lock free, finishing with an exact list of the `go` calls and a summary line whose waited field must be at least one second. It failed once inside a gate run whose queue wait was 555 of its 1,109 seconds, then passed focused in 14.5 s; its isolated re-run inside that gate took 15.43 s. The failing assertion was not preserved — the gate prints only the first sixty failure lines of a failed step and the bead records none — but every load-sensitive step in the test is a fixed margin standing in for a synchronisation: the three seconds stand in for "the fixture is queued", and the waited-at-least-one-second summary stands in for the same fact. The queue already publishes that fact as data: a ticket file under the queue directory, and the waiter's own `test: race lock:` status line. Waiting for the ticket before releasing the held lock makes the wait real by construction instead of by margin. This test's process handling is not part of the race problem below: its goroutine writes `out` and `runErr` and then closes `done` (`yardtest_test.go:1160-1165`), and both the deadline path (lines 1179-1182, which kills and then receives from `done`) and the normal path (lines 1202-1205, which receives before reading either variable) read those variables only after that receive, so the channel close synchronises them. Its only disease is the timing margin, and it stays under yardr-zaks alone. Test-only.

**The race-lock quarter of yardr-yvq8 — the TERM-killed waiter's ticket, test, settled.** `TestYardTestRaceLockServesWaitersInOrder` kills a queued waiter with TERM, checks it exits 143, then checks at once that its ticket file is gone (lines 1765-1775). In the failing run that check found the ticket still queued, and the reporter rightly flagged a possible product defect in the script's perl, since a leaked ticket could in principle block the queue. Reading the queue settles it as a test assertion stronger than the product's contract, with a narrow product race worth naming. On TERM the perl's handler removes its own ticket before it exits, so after the waiter's exit the ticket is gone in the normal run of things. But the queue's contract never rests on that removal: the servicing readers — `front`, `fullclean` and `place` — judge a ticket by whether its pid still lives with the start time the ticket recorded, unlink dead tickets as they service the queue, and skip them in every listing. The read-only `--race-queue` view is the one reader that does not reap: it skips dead tickets and leaves the files where they lie, by design, since a status view must not mutate the queue it reports. The same test proves the reaping path deliberately for a waiter killed with KILL, which can run no handler at all. The one window in which a TERM-killed waiter's ticket outlives it is a kill that lands between the ticket file's rename into the queue in `mkticket` and the assignment of its returned name to `$mine`, where the handler still holds no name to remove; the ticket is then dead by pid and is reaped by the next servicing pass, exactly as a KILL leaves it. So the ticket's presence in the instant after the exit is not a queue failure, and the instantaneous assertion is the bug. The fix must wait for absence in a way that lets servicing happen: in this test the holder still holds the lock while w2 and w3 queue behind it, and a dead ticket at the back of that queue is reached only when the next waiter takes the lock — `front` returning it dead on the way to the front, or `fullclean` unlinking it as that waiter acquires the flock after the test releases the holder. A poll for absence that starts only after the holder has finished therefore finishes (at the latest at w2's acquisition), while a poll taken while the holder still holds, or one that watches through `--race-queue`, can wait forever on a healthy queue; section 6's bead polls after the holder finishes, with a deadline as a fuse, and keeps the exit-143 assertion where it is. That is the verdict: test-only, the product window named and shown harmless because dead-ticket reaping by the servicing readers is the designed path, not a fallback. The bead also carries a deterministic reproduction (a ticket directory stalled between rename and name assignment, or a stand-in `ps` that keeps a dead pid looking live) that would convict the perl instead if the ticket proved live, in which case the fix moves to the script.

**yardr-y5zt — race-detector reports in the root package, a bug in one test, the rest unpreserved.** The bead names nine tests: `TestYardTestRaceLegLockDiesWithOrphan`, and eight further names — `TestYardTestRaceLockIsTheYards`, `TestNoGoCodeNamesGitHub` and `TestNoGoCodeNamesARole` (both in `main_test.go`), `TestYardTestBudgets`, `TestYardTestRerunsFailedPackagesOnce`, `TestYardTestBudgetRerunSharesTheRaceHold`, `TestYardTestRunsAgainWhenTheBuildCacheLostAFile`, and `TestYardTestSelects`. (`TestYardTestRaceLockServesWaitersInOrder` and `TestYardTestRaceLegWaitsForTheLock` are not among the nine.) One is attributable from the code alone. `TestYardTestRaceLegLockDiesWithOrphan` starts its fixture run with `cmd.Run()` inside a goroutine (line 2108) and, from the test's own goroutine, reads and kills through `cmd.Process` (lines 2123, 2162 and 2182) while that start is still in flight; `exec.Cmd` does not allow its fields to be touched concurrently with `Run`, so the race the detector reports on `Cmd` and `Process` is a bug in the test, not load and not the script. It fires only when the ten-second deadline branch is taken — which is also why the report ends "the race leg never reached go test": under load the deadline passed, the test reached for the process handle it had not synchronised, and the detector named the reach. The other eight named tests run their commands synchronously (`CombinedOutput` or `Run` in the test's own goroutine, with no second goroutine touching the command), and the first run's race output was not preserved beyond the summary, so no honest verdict on them exists yet; races are interleaving-dependent, so a quiet rerun passing proves nothing either way. Section 6 therefore carries one bead that fixes the orphan test by construction — start the process where its handle is published, wait for it in the goroutine — and one (B6) that reproduces each of the eight names under a counted load criterion with the full race output kept: at least ten repetitions per name started only while the one-minute load average is past the core count, a preserved report filing that name's fix, and ten silent loaded repetitions recording the name cleared with its count, load range and commit. Quiet repetitions never clear a name. `TestYardTestRaceLegWaitsForTheLock` is not in either bead for race reasons: as shown under yardr-zaks above, its channel already synchronises its output variables.

### 2.5 Class C checked: the R1 budget after yardr-wq5h

Yardr-wq5h landed on 18 Oct at 19:34 (a30c501a). Three of the five budget beads are closed by it on evidence the bead itself holds, one is closed by it only conditionally because its load was never recorded, and one is not closed at all. The judgement for each rests on its own numbers, because "over budget" says nothing until both times and the machine are named — and, after wq5h, until the load at the alone re-run is named too.

**yardr-kscv (`contrib/assembly`) — closed by wq5h.** The gate saw 61 s in the leg and 126 s alone, then 29 s alone minutes later, for a package that did not import the change under test (internal/store and internal/server). An alone run slower than the leg run only load explains, and the package's code was the base's. Seen on yardr-e9f0's first gate run, before wq5h landed. The 29 s alone minutes later is this bead's own strict evidence that the package sits under budget when contention clears, so the close does not rest on a hypothetical loud pass: under wq5h the 126 s re-run would have passed only if `loadedmachine` saw load past the core count at that instant, and any later run at or below the count — a landing, or an R6 run that happens to be load-quiet — would judge the same package by that 29 s shape, not by the 126 s one.

**yardr-dtb1 (`internal/web`) — closed by wq5h only conditionally; no load was recorded.** The same yardr-e9f0 run saw 68 s in the parallel race leg and 61.476 s on the isolated re-run, 1.476 s over the budget, with no `internal/web` file changed and no failing test. The bead records no load average and no core count, and no later alone run at or under 60 s, so this design cannot say wq5h would have passed that re-run. It would have passed only if the one-minute load average at the alone re-run's instant was past the core count; at or below the count, or with the load unreadable, the same 61.476 s still fails, exactly as it did. The margin is small and the two measurements were taken under different contention, which makes the loaded case likely, but likely is not a measurement. The disposition is therefore conditional: closed by wq5h on the condition that the unrecorded load was loaded by `loadedmachine`'s test, with no new bead — a recurrence now prints its load in the loud line (or fails strictly), and either outcome settles what this run left unrecorded. Unlike yardr-kscv, yardr-y3n6 and yardr-1nb4 below, this bead holds no under-budget alone run of its own to close on.

**yardr-y3n6 (`internal/web`) — closed by wq5h.** On yardr-gzy2 (18 Oct): 70 s in the loaded race run and 99 s alone, then 49 s alone immediately afterwards on the same tip, with the depot base at 53 s. A solo time that halves the moment the run ends is a loaded re-measurement, not a slower package. One caveat travels with the close: `loadedmachine` reads the one-minute average, which lags a burst that has already ended, so a very short contention spike can still fail once where wq5h cannot see it; that residue is accepted, because the alternative — failing on an unmeasured guess — is what wq5h removed. A later strict judgement still exists, but only from a run whose alone re-run lands at or below the core count; an R6 run supplies it only when the host happens to be load-quiet then, for the reason section 2.1 gives.

**yardr-1nb4 (root package) — closed by wq5h.** The landing of yardr-n4f9 failed green: 162 s in the race leg and 71 s alone, sending the bead back. The run had waited 544 s for the race lock and other suites read three to eight times their alone times in the leg; the branch changed only a test file in `contrib/isolated-yard`, which cannot alter the root suite's time. The same commit re-run later read 65 s in the run and 36 s alone ("under budget, loaded run"). Seventy-one seconds alone, eleven over, beside that evidence is a loaded re-measurement inside wq5h's threshold shape; today it passes loudly instead of bouncing the bead, provided `loadedmachine` saw load past the core count at that re-run — and the bead's own 36 s alone on the re-run is the strict evidence, so the close, like yardr-kscv's, does not depend on that proviso. No allow-list row for the root package is proposed: the 36 s alone in the bead's own re-run is the number such a row would hide.

**yardr-6tjb (`internal/web`) — not closed; a profiling bead.** On yardr-emh4's landing (18 Oct 19:25, nine minutes before wq5h landed): 61 s in the race leg, then 173 s alone — three times the loaded run, the reverse of R1's load model, in which alone under the lock is the quieter measurement. Nothing web-related landed between the failing run and a plain gate twenty minutes earlier that passed, and the same tree read 55 s under `-race` in a plain gate afterwards. The bead's suggested lead does not survive the tree: `internal/web` drives no headless Chrome — its tests are `httptest` servers and template rendering, and the only PNG bytes in the package are fixtures in `blobs_test.go` — so yardr-c2vt's stalled-Chrome shape cannot be this package's stall. What could make an alone `-count=1` re-run three times slower than its leg is unproven: either uniform contention from work the race lock does not govern (the landing's socket leg runs beside the re-measurement by design, and other yards' work shares the machine), or one test stalling against its own deadline and dominating the package total. The two hypotheses need different fixes — the first is wq5h's loud pass once the load at that instant is known, the second is a test fix — and the bead records no load reading, no per-test times, and no second occurrence. Section 6 gives it a profiling bead that repeats the package alone with per-test timings preserved, and files the fix from what it finds. It is the one Class C bead wq5h does not answer on the evidence held.

## 3. The proposal

The smallest version that answers the question has three parts: one rule written where reviewers already look, no change to how much work the gate runs in parallel, and a cheaper record for the `flaky:` line. Everything else is a test fix in section 6 that the rule would have prevented.

### 3.1 One rule for time, inside R2

Amend R2 in `docs/testing.md` — the rule that already governs sleeps, clocks and the real-clock allow-list — to state the choice in order, instead of adding a new rule beside it. The added sentences, in R2's voice:

> A test waits for the effect it asserts: it polls the condition (a store event, a file, a held question, a ticket) with a deadline that is only a fuse against a hang, never the measurement. Where the code owns the time the test waits on, the test sets that clock — the fake clocks named above — and advances it. A deadline taken from the load is the last resort, and only where the thing waited on is a program outside the test (a harness binary, a browser): there the bound is product code, its failure under load is a product question, and the test stubs the bound long (as the doctor tests stub thirty seconds) instead of inheriting whatever load leaves of it. A count inside a fixed wall-clock window, and a sleep followed by asserting the slept-for event exists, are both the first shape written wrong.

A reviewer checks the pick without running anything, the way R2's sleep scan is checked today: in a diff that adds a test, any new `time.Sleep` over the allow-list scan, any count asserted inside a fixed window, and any sleep-then-assert on the slept-for event needs one of the three shapes named in the diff — the polled condition and its fuse, the set clock, or the stubbed product bound with its bead. The gate's existing `longsleeps` table stays the enforcement for literal sleeps; the new sentences give the reviewer the question to ask about the rest, which today only the role sentence ("wait on the effect, not on wall time") gestures at. Yardr-x51w's peerhold fix is the worked example the rule points at: wait for six polls in whatever time the machine takes, keep the one elapsed assertion (at least 200 ms over five 50 ms pauses) whose direction load cannot falsify.

What each folded test does under the rule is already written in section 2: wait for the event (`replace_skipped`), wait for the file (nap or record file, not `ps`), wait for the ticket (race-lock fixture), stub the bound long (harness-version success case). No test needs the third shape for itself; the third shape is reserved for the two product bounds in section 5, which is why those two are product questions and not test fixes.

### 3.2 The gate: no new load limit, a cheaper flaky record

No limit beyond the race lock is proposed now. The race lock already serialises the one leg that multiplies cost (the `-race` leg, its retry and its budget re-measurement under one hold). The measurements on record argue against spending landing wall time further: the 022s and 635g designs both priced a `-p` cap at roughly 160 s of wall per run against a refinery landing some sixty times a day, and kept the default. Extending the lock to the socket leg or to vet and build would buy quieter budget re-measurements at the same wall-time price on every landing, to defend a budget that wq5h now judges load-aware with a loud line. It must not be defended as "R6 will judge it strictly later": section 2.1 shows R6 judges yard-quiet, not load-quiet, and reaches the same loaded pass, so on a persistently loaded host the strict verdict may never arrive. That gap is priced in Q2 as its own option, separate from parallelism. Whether the remaining contention is worth any parallelism change is a measurement question, and the measurement is already commissioned: t107 brings mckean a week of landing timings on Tue 20 Oct, which has not landed at drafting (19 Oct). Section 5 carries both as open questions with the data named, rather than proposing a cap the timings may not support.

What changes instead is what a `flaky:` line costs. Today it costs a bead each. The proposal: the gate appends every flaky line it prints to one file, `$HOME/.yardr/logs/flaky.log`, one line per event — date, the run's short sha, the test and package names the line already carries — written by the same code in `again` that prints the line, creating the logs directory as the gate already creates the yard home for the lock. A builder or reviewer who sees a flaky line checks that log first (the role sentence in the six builder and reviewer role copies changes to say so): a first occurrence is left in the log and named in the bead's handover note, and a bead is filed only on a repeat — the same test or package again within the log — or at once where the failure shape accuses the product (a race-detector report, a product assertion, a wrong result rather than a timeout). The yardmaster reads the log when shaping and at the R7 re-measurement, where repeat counts become the follow-up beads with their evidence already attached. This keeps the retry's visibility (the flaky line still prints on every run, and the log preserves what the gate's sixty-line failure excerpt drops) while paying a bead's price only where a pattern exists. It reuses the one record the yard already trusts for landing timings, `~/.yardr/logs/refinery.log`, in shape: a plain append-only log under the yard home, greppable, owned by no session.

## 4. Left out

- **A shared load-reading helper for tests.** Three readings exist (gate `loadedmachine`, shot `underLoad`, quiet `quietLoad`) with three different jobs: judge, skip fast, and log. Unifying them would touch the gate, a contrib test and the dispatcher to save no failure in section 2; each bead below reuses the reading already beside it.
- **Raising every deadline that flaked.** A longer `ps` deadline, a longer lock-test margin and a longer harness bound as test constants would silence today's flakes by spending the suite's seconds on every run and would flake again at the next load step. The rule fixes the shape instead; only the two product bounds are raised, and only if the operator takes that option in section 5.
- **An R1 allow-list row for `internal/web` or the root package.** Both read under budget alone in their beads' own reruns (web 49-55 s, root 36 s). A row would hide the next real slowdown to save a loud pass wq5h already grants under load.
- **Removing or widening the failed-package retry.** The retry is what turns a load flake into a visible `flaky:` line instead of a bounced bead; its cost is bounded at one rerun of the failed packages. The problem priced in section 2 is the bead filed per line, not the retry.
- **A product change to the race queue for the TERM ticket.** Dead-ticket reaping by `front`, `fullclean` and `place` is the designed contract, proved in the same test by the KILL case; the `--race-queue` view's skip-without-removing is deliberate for a read-only view. Closing the rename-to-assignment window in the perl would defend an instantaneous assertion no caller needs.
- **Treating yardr-6tjb as a Chrome stall.** There is no Chrome in `internal/web` to stall; the lead is recorded as checked and excluded, so the profiling bead starts from per-test timings instead of from yardr-c2vt's shape.
- **Any change proposed on t107's landing timings.** They are due 20 Oct and are not in; section 5 asks with the data named rather than guessing the gate-parallelism answer a day early.

## 5. Open questions

Each question is the operator's. The option recommended here is marked; nothing else in this document decides it.

**Q1. The two five-second harness-version bounds.** `harnessVersionTimeout` in `internal/agents/harness.go` (silence on timeout; annotates an event) and `versionTimeout` in `internal/cli/needs.go` (a false hang fault on timeout; fails `server-yard` setups through doctor) are both five seconds, and both have now run out under load on stand-ins that answer at once. The same tree already carries two longer precedents: twenty seconds for `Models` in `internal/agents/harness.go`, and forty-five seconds for a real harness call (`tryTimeout` in `internal/cli/needs.go`). Options: (a) keep five seconds in product and fix only the tests (stub long in `internal/agents` as doctor's tests do; accept that `server-yard`'s built-binary test still flakes under load, and that a genuinely slow cold start still reads as no version or as a hang fault); (b) raise both bounds to the twenty-second Models precedent, accepting up to twenty seconds before doctor faults a truly hung harness and the same before a version annotation is given up; (c) make the bounds load-aware, which needs a load reading in product code where none exists today and spends new machinery on two call sites. **Recommended: (b)**, one precedent, no new mechanism; the two callers land as separate beads in section 6 so either can move alone if the operator splits the answer.

**Q2. Any gate load limit beyond the race lock — and whether R6 must ever judge R1 strictly.** Two different costs hide in this one question, and the operator should see them separately. The first is landing wall time under contention. Options: (a) no further limit — wq5h's loud pass carries the budget at landings and the flaky log carries the rest, accepting the residual below; (b) bring the landing's socket leg under the race-lock hold, quieting the budget re-measurement at the price of serialising a leg that today overlaps it; (c) cap `go test -p` for the race leg, priced by the earlier designs at roughly 160 s of wall per run. The second cost is the residual itself: because R6 is yard-quiet, not load-quiet (section 2.1), none of (a)–(c) guarantees a strict R1 verdict — a package can loud-pass at the landing and again in every R6 run while the host stays loaded, so a real slowdown can hide indefinitely behind true load readings. Closing that needs its own option: (d) make R6 strict for R1 — either start the quiet run only once `quietLoad` is at or below the core count (deferring the whole-suite backstop on a busy shared host, possibly for long stretches), or run its `packagebudget` with the loaded pass disabled through a setting the quiet run alone sets (the strict verdict then fails `quiet_failed` loudly on a loaded base, which is the backstop doing its job, at the price of red quiet runs that are load, not regressions, until someone reads the load line beside them). **Recommended: decide the parallelism half on t107's week of landing timings (due Tue 20 Oct, not yet in at drafting)** and take (a) for that half unless those timings show landings, not flakes, paying for contention; decide the strictness half with it, knowing (d) is the only option that ever guarantees the strict verdict, and that taking (a) without (d) accepts the residual openly rather than by the present accident of wording.

**Q3. The flaky record.** Options: (a) keep filing a bead per `flaky:` line (thirteen beads in four days, each at full shaping and review price); (b) the gate-written `$HOME/.yardr/logs/flaky.log` of section 3.2, with beads filed on repeats or product-accusing shapes, and the yardmaster reading the log at shaping and at R7; (c) a counter or table in the store, which the gate in a builder's worktree cannot reach without going through the socket API for a test-logging concern. **Recommended: (b)**; it keeps every occurrence visible and preserved, costs one append in code that already prints the line, and pays a bead's price only for a pattern.
