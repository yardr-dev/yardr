# Setting up a source is one card: apply, account and grants with presets from the pack

Design yardr-7d4e, proposed 2026-10-18. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A source is a service outside the yard, declared by one file. A pack is a way of working as one directory; a pack of kind `source` declares sources and is imported into the yard itself, into no depot. An ask is one question as data on a bead; a run ask (`yardr bead ask --run "<command>"`) proposes one yardr command of a fixed list, and a secret ask (`--secret <source>`) asks for a source's credential, typed unseen and written to a file by the server. A grant is the operator letting a group's sessions or a crew member make a source's calls (`yardr source grant`). The operator is the person who runs the yard. In this document **a preset** is a pack author's named grant suggestion (read only, read plus drafts, everything), **a setup ask** is the new ask this design adds, and **the card** is what it shows the person asked. **A candidate** is a source already in the yard whose account file the card offers to reuse, and **a preset grant** is `source grant <source> --preset <name>`, the plain grant ask naming a preset.

## 1. The question

mckean, 18 Oct 2026 (mail 46659), after setting Google up on the Plantime yard: "how can we avoid running in these issues? maybe a single ask per source with the permission options. not having to click like crazy also providing all the options for the permissions? maybe groups and select all etc. with sane presets". What it took that evening (Plantime yard events, beads yd-106m, yd-xwz6, yd-j6cn, yd-9kp2 and others): a pack-apply run ask per pack, an account secret ask per source (twice over, after the both-names bug yardr-er4c), and a grant run ask per source and kind, read then update — about 25 cards for one Google account, each the same address or the same yes.

## 2. What exists today

### 2.1. The pack-apply run ask

`yardr bead ask <id> "<q>" --run "pack apply <name>"` (design yardr-bht9) proposes applying an embedded pack with no flags. The ask carries the declaration texts and command files read by the yard's server from its own binary (`PackReader` in internal/store/runask_pack.go, registered by the server), never sent by the asker. The card renders the declaration whole in the yard's words: base address, credential names and where the credential goes, every call with kind, method, path, parameters, query and body, and every command with its program and sha256. Since yardr-d860 the card also names the pack's mint: its path under `<home>/sources/<source>/`, its full sha256 and mode 0700. Approving is held to the build, the carried bytes and the yard's sources with their whole destination inventory (`packApplyStale`), and a replacement shows old against new with unified diffs. Carrying out is the server's watcher (internal/server/carry.go, internal/store/carry.go and claim.go): claimed once under the server's boot, applied as the operator, recorded done or failed with what stands. A re-apply that changes nothing applies nothing.

### 2.2. The grant run ask

`yardr bead ask <id> "<q>" --run "source grant <source> read|<call> --group <g> | --crew <c>"` proposes one grant. Its card (`grantCard` in internal/store/runask_list.go) names, for each grantee, the calls the grant is of with their methods and paths: of `read` which calls that is today and that it covers any read call the source is later given, of an update call that it changes something there. The approval is held to the declaration and to each grantee as they were, and runs past what was granted since unless it is held already (`grantStale`). It runs through `GrantSource` (internal/store/sourcecalls.go), which checks the grant against the declaration with `grantable`. `read` is every read call, a later file's included; an update call is granted by its name alone, and there is no word for every update. A grant `--as <user>` is that user's alone to give; the operator is refused it.

### 2.3. The secret ask

`yardr bead ask <id> "<q>" --secret <source>` asks for the credential's names, narrowed by `--env`. Since yardr-er4c an ask with no `--env` asks for what the source needs given: the mint's inputs (`Credential.MintOrStatic()` in internal/store/secretask.go) where the source has a mint, else every name. The answer is typed unseen (`yardr bead answer <id> <ask> --secret`), the server writes it into the env file, and the answer on the bead holds the names given, never the value. Each source's secret ask writes into that source's own file, which the yard chooses; sharing one file across sources is only by hand (`yardr source set <s> env_file=<file>`), as docs/google.md step 3 does for the five Google sources. A credential asked with `--as <user>` lives instead in that user's env file (`User.EnvFile`, or `<home>/users/<name>.env` where the yard chooses one), written by the same writer grown to user files (`keyUser` in internal/store/usernotify.go); it is never in a source's file. A secret ask takes no option, no recommendation and no words.

### 2.4. The plan of a kind-source pack

`pack.Build` (internal/pack/plan.go) plans a kind-source pack with `buildSource`: its declared sources and nothing else — `declared()` and `dropped()` only. It never asks grants: the `calls` step (`CallsAsked` in internal/pack/pack.go, a mapping of source to wanted calls under a depot pack's group or crew member) runs for depot packs alone, which is why every SETUP.md says a pack of kind source asks no grants at import. The planner compares replacements key by key (`declarationDiff` in internal/pack/plan_sources.go) and hashes each command file (`sourceCommands`). What a pack for a depot may say is bounded by key lists (`DeclarationKeys`, `SourceDeclarationKeys` in internal/pack/pack.go). Terminal `pack check` prints the plan and `pack show` prints the pack's setup notes; neither grants anything.

### 2.5. What exists not at all

No pack declares grant presets: the word appears nowhere in internal/pack, internal/source or internal/store. No ask takes more than one pick: an answer holds one option number (`Answer.Option` in internal/store/asks.go), and yardr adds "You decide" to every ask that has options. No card combines a secret with an approval: a secret ask takes no pick and a run ask takes no secret. And no machinery shares one account answer across sources: each secret ask is per source, and the mint's input typed for google-mail is typed again for google-drive.

## 3. The proposal

### 3.1. In one paragraph

One new ask, the setup ask — `yardr bead ask <bead> "<q>" --setup <pack> --crew <name>` — carries the whole setup of a pack's sources as one decision: the apply, the account and the grants. Its options are the pack's presets, picked once, recommended with `--recommend` as on any option ask. Its account is typed unseen on the same card, or picked from the matching accounts the card lists with their addresses. Its carry-out is the pack row's carry-out, then the secret write, then the grants, each step the existing function, recorded done or failed with what stands. A pack update is the same card again, showing the difference. A grantee added later gets one card too: the plain grant ask takes `--preset`. The existing per-step flow — a pack apply card, an account card per source, and a grant card per source and kind — becomes one card per pack; for the four google packs, with their shared account, five sources are set up on four cards with the address typed once, then picked.

### 3.2. The ask

```text
$ yardr bead ask yardr-k3vd "Set up Gmail for the yardmaster?" \
    --setup google-mail --crew yardmaster \
    --context "The yardmaster reads mail to work beads; drafts only, the person sends." \
    --context "The card carries the pack's declaration, its mint, the account and the grants." \
    --recommend 1 --why "reading is the job; drafts can follow"
ask 3101 on yardr-k3vd for mckean: to approve, yardr bead answer yardr-k3vd 3101 <preset> --secret
```

`--setup` names an embedded pack of kind source, with no flags of `pack apply`, as the pack row takes it. `--crew` and `--group` name who the grants are for, repeatable, as the grant row takes them; one is required, since a grant names its grantee. `--recommend` counts the card's preset options as `pack show` prints them (3.4), with `--why` saying why, as on any option ask; no new flag and no type change. `--as` is refused: a grant as a user is that user's alone to give (2.2), and this card is the operator's. A pack carrying sources under different credentials is refused too, naming the existing per-step flow: one card carries one account choice (3.5). The grants the card gives go to the grantee it names; a grantee who comes later gets one preset grant card (3.6): the setup card plus that card are mckean's two asks, to add and to grant. Who may ask, who it is put to and who may approve are the list's, unchanged: a crew member or a user and not a bead's agent, to the operator alone, approved by the operator and never from an agent's pane and never over a link. The store throws away whatever carried bytes, sentences or fingerprints the writer sends, as the pack row does: the server's reading supplies the pack, and the store parses every carried text itself.

### 3.3. The card

The card shows each part exactly as its own card shows it today; bundling changes the number of approvals, not what is shown for any of them. For google-mail, asked as above, with no Google source set up yet:

```text
ask 3101 · open · to mckean · asked by yardmaster · 1m ago
  Set up Gmail for the yardmaster?
  yardmaster says: The yardmaster reads mail to work beads; drafts only, the person sends.
  when you approve, the yard applies the pack, takes the account, and grants the preset you pick, and nothing else:
      yardr pack apply google-mail, the account GOOGLE_ACCOUNT, and the preset's grants to crew yardmaster
  the yard says: pack google-mail (embedded in yardr 06740fc8c90b), of kind source, into the yard: it adds one source and copies 1 command file, and changes nothing else. It makes no hook and sets no credential's file.
  the yard says: source google-mail: its calls go to https://gmail.googleapis.com. Its credential is the variable GOOGLE_TOKEN, sent in the header Authorization: Bearer {credential}. The token is minted per call from GOOGLE_ACCOUNT by google-mint.
  the yard says: call search (read): GET /gmail/v1/users/me/messages. [... each call as the apply card renders it ...]
  the yard says: its mint google-mint is copied to <home>/sources/google-mail/google-mint, sha256 <whole> mode 0700. It runs with the operator's local logins, and a mint_command the operator sets wins over it.
  the yard says: the account GOOGLE_ACCOUNT: type it unseen. It is written to the source's env file, named in the answer, never the value.
  the yard says: grants to crew yardmaster — pick one:
    1. read: may make every read call of the source google-mail (https://gmail.googleapis.com): today that is search, message and thread, and it covers any read call the operator later gives the source.
    2. drafts: may make every read call of the source google-mail (https://gmail.googleapis.com): today that is search, message and thread, and it covers any read call the operator later gives the source. may make the call draft (POST /gmail/v1/users/me/drafts) of the source google-mail (https://gmail.googleapis.com), which changes something there.
    3. You decide: the recommended preset, read, is granted
  the operator can take it back: yardr source rm google-mail; yardr source revoke google-mail <what> --crew yardmaster
  answer with: yardr bead answer yardr-k3vd 3101 <n> --secret
```

In full: the declaration of every source the pack declares, rendered as the apply card renders it (2.1), with the mint's path, full sha256 and the hand-set-wins line; the account line, naming the mint's input names (the yardr-er4c default) or every credential name for a source with no mint, and where the value goes — and, where sources already in the yard hold a matching account, each candidate by source name with its account address, to pick one or type another (3.5); one option per preset, each consequence rendered by the yard from the declarations — each call with method and path, `read` expanded to today's reads with the later-reads line, an update marked as changing something there — and to whom; and the take-backs, `source rm` and `source revoke`. Where google-drive is already set up, the account line of a google-mail setup card reads, for example, `the account GOOGLE_ACCOUNT: already given for google-drive (GOOGLE_ACCOUNT=ops@example.com, in <home>/sources/google-drive.env). Take it with --account google-drive, or type another unseen`, and the card is answered `yardr bead answer <id> <ask> <n> --account google-drive` or `yardr bead answer <id> <ask> <n> --secret`. A preset's `about` is its author's words and is no part of the card, as a declaration's `about` is no part of the apply card (design yardr-bht9): it is printed by `pack show` for the asker. Beside the presets the yard adds "You decide" last, as it adds it to every option ask, which grants the asker's recommended preset. An operator who wants no grants declines the card and applies by terminal. The yard's part is held to 40 lines, counted as the apply card counts them with one line per preset; past it the pack stays on the existing per-step flow, refused with `pack check` named.

### 3.4. Presets in pack.yaml

Presets are pack-level, beside `sources:`, so one card serves a pack whatever its sources: google-docs' two sources take one card, not option groups multiplied. Each preset names, per source, the calls it grants:

```yaml
presets:
  read:
    about: Read mail and threads; write nothing
    grants:
      google-mail: [read]
  drafts:
    about: Read mail, and write drafts the person sends
    grants:
      google-mail: [read, draft]
```

`about` is optional, one line, printed by `pack show` and never on the card (3.3). `grants` maps a source the pack declares to `read` and call names, in the words `source grant` takes: `read` for every read call, an update call by its name, a single read call by its name where a preset wants one without the rest. Pack load refuses what is not so: a source the pack does not declare, a call the declaration does not name, an empty preset, a pack of another kind carrying presets. `pack check` validates them with the plan, and `pack show` prints them numbered in file order — the numbers `--recommend` counts. The same presets are read by the plain grant row: `source grant <source> --preset <name>` (3.6) grants one preset's calls of one source, `--preset` taking the preset's name as `pack show` prints it, not its number. Terminal `pack apply` ignores presets: its grants stay what they are, typed or carded separately. The planner's grant asking for depot packs (`calls`, 2.4) is untouched; presets are the kind-source road, where no grantee stands in the pack and the asker names one.

### 3.5. The account, shared

Two sources share one account answer when they name the same credential and the same mint: the same mint input names, and the same effective mint argv. "Effective" is `MintArgv` (internal/source/command.go): a hand-set mint_command is argv including arguments, so arguments are compared literally — differing arguments break sharing. But a pack-brought mint is a per-source copy under `<home>/sources/<name>/`, so the two sides' program paths always differ; the program position is therefore compared by sha256 of the file's bytes (the four google-mint copies are one text, held so by a test), the arguments literally. A program file the yard cannot read breaks sharing. Both must be minted: a static credential is never shared, since one variable name across two services is coincidence, not sameness.

Candidates are yard-level source files only: the `env_file` of a source already in the yard, holding every shared input name. A credential a user gave for themselves (`--secret <source> --as <user>`, kept in the user's env file) is never a candidate: it is not listed, and it is never reused for another user or for the yard. A source file that resolves to a user-owned file is excluded too: where the candidate's `env_file` path, after `filepath.EvalSymlinks` and `Clean`, equals any user's or crew member's env file, or a default under `~/.yardr/users` or `~/.yardr/crew`, it is not listed, even where a hand-set `env_file` points the source and the user at one file. The card lists each candidate by source name with the shared inputs' values as its file holds them — for the google packs the `GOOGLE_ACCOUNT` address, which the declaration calls "an address, no secret" (packs/google-mail/google-mail.yaml); for github the app id and the key path it mints from (packs/github/github.yaml). Only the shared mint inputs are ever shown, never a static variable, since static credentials never share; and the card is the operator's alone, showing values the operator gave before, with no copy of the ask over a link (Left out). There is no silent reuse, not even with a single match: the answer names a candidate (`--account <source>`) or types another value (`--secret`), exactly one of the two where candidates stand, and `--secret` where none stand.

One account choice per card serves every matching source the pack carries. Where the pack itself carries matching sources not yet in the yard — google-docs' two sources on its first card — one typed value serves them all: the card names the file it will use, the first match's per-source default in the pack's declaration order (for google-docs, `<home>/sources/google-docs.env`), the carry-out writes the value there once, and each matching source's `env_file` points at it. Where the operator picks a candidate, each matching source the pack carries points at the candidate's file instead. A pack carrying sources under different credentials is not set up this way: `--setup` is refused for such a pack, naming the existing per-step flow (Left out). Typing another value on the card keeps its own file: where the source's `env_file` already points at a shared file, the carry-out first leaves it, resetting that source's `env_file` to its per-source default (`source.EnvFile`, `<home>/sources/<name>.env`) before the secret-path write, so the write lands in the source's own file and the sibling's value stands. On a phone the choice is a tap on a candidate or a filled secret field (F1). The approval is held to the candidates as carded: it fingerprints the carded candidate input values (a sha256 over name=value of the shown, non-secret inputs per candidate), not the source settings alone, so a candidate added, removed or changed since refuses it — including a candidate env file changed in place with the same path and source settings. Plain secret asks are unchanged: sharing lives in the setup answer's path, with the matching rule in internal/source for later use. A source removed never takes the file: env files are the yard's and stay, as the hand-shared file of docs/google.md does today.

### 3.6. How an approval runs

The answer picks a preset and settles the account: `yardr bead answer <id> <ask> <n> --secret` to type it, `yardr bead answer <id> <ask> <n> --account <source>` to take a candidate's. A pick with `--secret` or `--account` beside it is new, and allowed on a setup ask only; everywhere else a secret answer still takes no pick. The approval is recorded first, as an approval; the server carries it out once, as the operator, in this order: the apply (the pack row's plan-again, holding and copy), the account (the secret write into the chosen file, or the `env_file` pointed at the picked candidate's), then the picked preset's grants through the preset-grant row's function (below), one call a write. The order is forced: grants and the account write need the source the apply adds, so a failed apply writes nothing further, and a failure anywhere stops the rest and is recorded failed with what stands and the terminal commands that finish it (`pack apply`, `source key`, `source grant`). Stale rules compose the rows': the build and the carried bytes, now including the presets, since the options derive from them; each source with its destination inventory; the sentences, so an account given meanwhile, a candidate added, removed or changed since, or a user told since refuses the approval; each grantee as they were; and grants held since are run past unless held already, as the grant row runs them. An approval from a device travels as run approvals and secret answers travel today, and nothing runs on the phone.

Presets on the plain grant ask: `yardr bead ask <id> "<q>" --run "source grant <source> --preset <name> --crew <c>"` proposes one preset's grants of one source. Its card is the grant card's: each call with method and path, `read` expanded to today's reads with the later-reads line, an update marked as changing something there, with the preset's and the pack's names. The preset is resolved against the embedded packs, through the server's reading of its own binary beside the pack row's; a source no embedded pack declares is granted by name, as today. The approval is held to the preset's bytes with the build, to the source, and to each grantee as they were; `--as` follows the grant's rule, the named user's alone to give. An operator who wants mckean's two-ask shape declines the setup card, applies by terminal, and follows with one preset grant card per grantee.

One window is new and is said plainly: the account's typed value is never stored — in no note, on no ask — so between the approval and the account's write it lives in the server's memory alone, handed from the approval to the carrying out. (The candidate addresses a card shows are values the yard already holds in files, displayed back to the operator who gave them; only the newly typed value travels this window.) A stop inside that window loses it, and the ask is recorded failed naming that the apply stands and the account is asked again, as the secret path already asks again when it wrote the file and could not record it. The window is normally milliseconds, and the failure names exactly what to do.

### 3.7. A pack updated

A setup ask on a pack already applied is the same card again, showing the difference: each source's declaration diff old against new and each command file's old and new sha256 with its unified diff, as the replacement row shows them; the account line reading "given, in `<file>`" where that file holds every name the declaration needs, with typing another still possible (`--secret`, leaving a shared file as 3.5 says) and a candidate's file still to take (`--account`); where the declaration newly needs a name the file does not set, the card names the missing names and the answer types them; and each preset rendered against what the grantee holds — calls held marked held, calls the preset would add marked new. A standing `read` grant covers a read call the update adds, and the card says so beside that call; only an update call the update adds waits on a preset that names it. Picking a preset grants what it names past what is held, and revokes nothing: narrowing stays `source revoke`, proposed on its own card (section 5, decision 3).

### 3.8. What changes in each mechanism

- **Run asks** gain no new row. The setup ask is a new ask kind beside `--run`, because no run ask takes a secret and no run command is three commands. It reuses the pack row's carrying (`AskSource`, the server's `PackReader`, the destination inventory), its stale holding and its carry-out claim (internal/store/claim.go, internal/server/carry.go), and the grant row's sentences and run-past rule. The grant row gains `--preset` (below), resolved through the server's reading of its embedded packs, beside `PackReader`.
- **Secret asks** keep their asking; their answering gains the setup combination. The typed-unseen prompt, the server-side file write and the names-not-values answer are the secret path's, called from the setup carry-out, with `--account <source>` beside `--secret` to take a candidate's file. New beside it: the sibling matching rule (in internal/source, over declarations and effective mint argv), the candidate listing over yard-level source files only, and the leaving rule: a source whose `env_file` points at a shared file gets it reset to its own default before another value is written. `--secret`, `--env` and their refusals are untouched.
- **Pack apply's plan** gains presets at reading and showing: the `presets` key in internal/pack/pack.go with its validation, `pack check` checking them, `pack show` printing them numbered. The planner builds no grant plan for them — the store renders the options from the server's pack reading, as it renders the apply card — and terminal `pack apply` is unchanged. The grant row reads the same presets by name through the server's reading.
- **The grant command** gains `--preset <name>`: in a terminal the CLI expands it from the embedded pack it reads as `pack show` does, and the run row resolves it through the server's reading; each call is granted through `GrantSource` as the operator, exactly as the grant row's approval does. The setup carry-out composes the row's function, so a later grantee's card and the setup card grant the same calls.
- **Asks and answers** gain one flag each: `bead ask --setup` with `--crew`/`--group` and `--recommend` counting presets, and `bead answer <n> --secret` or `<n> --account <source>` together on a setup ask. The single-pick answer shape is untouched: presets are picked one, never several (section 5, decision 2).

## 4. Left out

- **The browser login** (`gws auth login`), which cannot be a card, as the bead says.
- **Grants as a user on this card.** A grant `--as ada` is ada's alone to give; the setup card is the operator's, so per-user setup stays the `--as` secret card and the `--as` grant cards of docs/google.md ("Calling as a user").
- **One card for a whole family of packs.** Four google packs are four cards, joined by the shared account. One card for all four would carry four declarations past the 40-line bound and apply four packs in one carrying out; section 5 records the decision: one card per pack.
- **Multi-select for grants.** Presets are picked one; follow-up grant and revoke rows cover the rest. Decided against in section 5: one preset per card, no multi-select anywhere.
- **A "pick calls" option naming calls in words.** Words are free text; parsing call names from them trades one approval for a refusal loop. The yard-rendered presets plus follow-up rows are the whole choice.
- **Reusing an account without naming it.** Even with a single match the card lists the candidate and the answer picks it; a quicker silent reuse was refused in section 5 (decision 4), since two sources can hold different accounts under the same declarations.
- **Presets for depot packs and in terminal pack apply.** Depot packs ask grants through `calls` at import; terminal `pack apply` takes no preset. Presets are card options for kind-source packs, and one flag on the grant command.
- **A pack-declared default recommendation.** The asker recommends with `--recommend`; a pack default would be one more default to argue about, and the asker knows the grantee.
- **Static-credential sharing.** One variable name across two services is coincidence; each static source asks its own.
- **Packs with several credential groups.** `--setup` is refused for a pack whose sources name different credentials, naming the existing per-step flow; every pack yardr ships carries one group, and per-group choices would need an answer shape this design does not give.
- **Approving in the web view, and any copy of the ask over a link**, as for every run ask. A second approval step (typing the source's name) is refused for the same reason it was refused for the apply row: a device approves.

## 5. Open questions, as decided

Each of these was mckean's to decide, and the first, second and fourth became their own asks on this bead when it reached decide. Asks 7091–7093 were answered by mckean on 18 Oct 2026; the drift rule was decided by yardmaster with no ask; presets on the plain grant ask were proposed to mckean by mail and confirmed (mail 47102). The answers are recorded here and are already folded into section 3 above, so nothing in this section is still open. The critique's remaining items (note 7090, item 2 on mint inputs missing from the old file and item 5 on the fallback wording) are folded into 3.7 and B5, and into 3.1 and 3.3, and are not repeated here.

1. **What should one card cover?** Decided (ask 7091, picked 1): **one card per pack** — google-docs and google-slides are approved together; four cards for Google. Not one card per source (five cards, with docs and slides approved separately while the account is answered once: more approvals for no more information, since one pack is installed as one thing), and not one card for the whole Google family (one approval, but a card carrying four declarations and their diffs past any phone-readable bound, and one carrying out applying four packs, whose failure names a quarter-done yard). mckean's words on granting to a crew member became decision 5.
2. **Presets, or tick each call?** Decided (ask 7092, picked 1): **one preset per card** — no multi-select anywhere, and a missing preset is fixed in pack.yaml. Not presets plus "pick calls" on this card alone (a second answer shape and a second widget in chat and footplate, used by one card), and not multi-select for every ask (changing what an answer is, every view of one, and the peer send of asks).
3. **On drift, do presets only add, or set exact holdings?** Decided by yardmaster, no ask: **presets only add**, as the grant contract does today (`GrantSource` adds, `RevokeSource` is a separate act); narrowing stays `source revoke` on its own card. Not exact holdings, which would let an approval about a pack update silently take access away.
4. **When a second source could reuse an account that is already set, what should the card do?** Decided (ask 7093, picked 1): **show and choose** — the card lists each matching source by name with its account address, and the operator picks one or types a new value into the source's own file; no silent reuse, not even with a single match. mckean added the scoping: a credential a user gave for themselves is never offered and never reused for another user or for the yard, so only yard-level source files are candidates. Not always typing it (the same address retyped on every card), and not silent reuse on a single match (the card would not show which account it took, and two sources can hold different accounts under the same declarations).
5. **Presets on the plain grant ask.** Decided (mail 47102): **`source grant <source> --preset <name> --crew|--group` as a run ask**, and the setup card's grant step composes it, so a later grantee gets one card with the same presets. This follows from mckean's point on ask 7091 that the grant is for a crew member: the setup card plus one preset grant card are the ask to add and the ask for the grants.

## 6. The beads it would become

In the order they would land: B1, then B2, then B7, then B3, B4 and B5; B6 and F1 wait on those they name. Each passes `sh .yardr/test` and updates the pages named. No bead's own tests start an agent: a store in a temporary home, a caller with `WithCaller` where the call needs one, and the isolated yard (`contrib/isolated-yard`) for the one end-to-end trial, never the operator's yard.

**B1. Presets in pack.yaml: read, checked and shown.** Goal: 3.4 — the `presets` key, its validation and its showing. Where to look: the pack reader in internal/pack/pack.go — `presets` is a pack.yaml root key, so the root key list in `reader.pack` beside `sources`, not the declaration key lists (`DeclarationKeys` and `SourceDeclarationKeys` bound declaration files, not pack.yaml); `pack check` and `pack show` in internal/cli/pack.go, the four google packs' pack.yaml gaining their presets. Done when: the reader takes the shape of 3.4 and refuses a source the pack does not declare, a call the declaration does not name, an empty preset and presets on a pack of another kind, each with the file and line; `pack check` reports them and `pack show` prints them numbered in file order; the google packs carry read-only, read-plus-updates and everything presets matching their declarations, and a test holds each preset's calls to the declaration's; docs/packs.md says the key. Depends on nothing.

**B2. The setup ask: asked, carded and approved.** Goal: 3.2, 3.3 and the stale half of 3.6 — everything short of carrying it out. Where to look: `yardr bead ask --setup` in internal/cli/bead_ask.go (the `--crew`/`--group` grantees, `--recommend` counting presets, the refusals of 3.2); the ask's carrying in internal/store beside runask_pack.go (the server's pack reading widened to presets, writer-sent bytes thrown away); the card beside `packApplyCard` and `grantCard` (3.3 whole, the 40-line count with presets, and "You decide" granting the recommended preset); `bead answer <n> --secret` in the answer command, allowed together on a setup ask only; the stale comparison composing build, sources with inventory, sentences and grantees. Done when: asking sends the pack and grantees alone and stores the server's bytes with forged bytes thrown away by a test; the card shows the declaration, the mint with digest, the account line and each preset's yard-rendered calls with grantee, each read by a test against the declarations that made it; a pack past 40 lines, an unknown preset recommendation, and a pack carrying sources under different credentials are refused with a terminal or the per-step flow named, each by a test; an approval is refused stale when the build, bytes, presets, sources, owed-ness or grantees moved, each by a test; the approval records approved-and-not-carried-out and a second approval is refused; docs/chat.md, docs/glossary.md and the ask and answer help say it. Depends on B1.

**B7. Presets on the plain grant ask.** Goal: 3.6's preset grant — `source grant <source> --preset <name> --crew|--group` in a terminal and as a run ask, the card a later grantee gets. Where to look: the grant command in internal/cli/sourcecmd.go (`--preset`, expanded from the embedded pack the CLI reads as `pack show` does); the grant row in internal/store/runask_list.go (`parseGrant` and `grantOf` gaining the flag, `grantCard` rendering the preset's calls as it renders a grant's, `grantStale` holding the approval to the preset's bytes with the build, `runGrant` granting each call); the server's pack reading B2 widened to presets (beside `packReaderFor` in internal/server/packreader.go), resolving the preset by source. Done when: a preset grant card names the preset and the pack and renders each call with method and path as the grant card does; an unknown preset, a source no embedded pack declares, and two packs declaring one source are each refused with the terminal named; the approval runs past grants held since unless held already, as the grant row does, and is refused stale when the preset's bytes, the source or a grantee moved, each by a test; `--preset` with `--as` is the named user's alone to give, as any `--as` grant; the grant help and docs say it. Depends on B1 and B2 (B2 owns widening the server pack reader to presets; B7 reuses it).

**B3. The server carries it out: apply, account, grants.** Goal: the carrying half of 3.6 — once, in order, as the operator. Where to look: the watcher and claim in internal/server/carry.go, internal/store/carry.go and claim.go; the apply step (the pack row's plan-again and holding); the account step (the secret path's write, internal/store/secretask.go, with the value handed in memory from the approval, never stored, or the `env_file` pointed at the picked candidate's); the grants step (B7's preset-grant path, one call a write as the operator); the failure record with what stands and the finishing commands. Done when: an approved setup is carried out once with the apply, the file write and the grants each verified back; a failure at each step stops the rest and records what stands with its finishing command, each by a test; a server stopped between approval and carrying out takes the ask up and finishes it, except the value lost to a stop before the account's write, which is recorded failed naming the account asked again, each by a test; two takers cannot both carry out; a trial in an isolated yard sets google-mail up on one card end to end — pack, account, grants — and `source check` passes. Depends on B2 and B7.

**B4. One account for sources naming the same credential and mint.** Goal: 3.5 — the shared account, shown and chosen. Where to look: the matching rule in internal/source (minted both, same input names, same effective mint argv with the program compared by file bytes and the arguments literally); the setup card's account line (each candidate by source name with its account address, yard-level source files only, never a user's own); the answer's `--account` or `--secret` choice; the carry-out pointing `env_file` at the picked file or writing a typed value into the source's own. Done when: a second google source's card lists the first by name with its `GOOGLE_ACCOUNT` address, and picking it points the new source's `env_file` at that file, verified by `source show`; with a single match the card still lists it and still needs the pick, by a test; a credential a user gave for themselves (`--secret <source> --as <user>`) is never listed, by a test, and a source whose hand-set `env_file` resolves to a user's file is never listed either, by a test with a custom shared path; changing a candidate env file in place (same path, same source settings) refuses the approval stale, by a test; the first setup of google-docs writes one typed value to `<home>/sources/google-docs.env` and points both sources at it, the file named on the card; typing another leaves a shared file for the source's own default before writing, and the sibling still uses its original value; a static source never shares; a hand-set mint shares only where the full effective argv matches, and differing arguments break sharing, each by a test; docs/google.md step 3 says one card per pack, typed once, then picked. Depends on B3.

**B5. A pack updated is one card again.** Goal: 3.7 — the drift card. Where to look: B2's card on an applied pack (declaration diffs, file old-and-new with unified diffs, the account "given" line with its missing names, presets against holdings with held and new marked, the covered-new-read line). Done when: a pack update changing a declaration, a command file and the mint cards each diff as the replacement row does; a preset's held calls read held and its new ones read new; a new read call under a standing `read` grant reads covered with no grant needed, and a new update call reads waiting on its preset; picking a preset grants the new and revokes nothing; where the updated declaration needs a mint input name the old file does not set, the drift card names the missing names and the answer types them, by a test; typing another account value on the drift card leaves a shared file for the source's own default, and the sibling still uses its original value, by a test; taking a candidate's file on the drift card points `env_file` at it, by a test; docs/packs.md says drift is one card. Depends on B2, B3 and B4.

**B6. The yardmaster proposes setup, and the pages say one card.** Goal: the crew asks this way and the docs stop saying 25 cards. Where to look: packs/starter/roles/yardmaster.md where it says what is the operator's to type; docs/google.md steps 2–5, the four SETUP.md files, docs/integrations.md where it lists what a crew member may propose. Done when: the role says a source a pack brings is proposed with `bead ask --setup`, one card, with the grantee and a recommended preset and why, and a grantee who comes later with one preset grant card; the google pages show one card per pack with the address typed once, then picked, and the per-user cards unchanged beside them; the drift card is named where updates are. Depends on B3 and B7 (and B4 and B5 for the pages that name them).

**F1 (footplate). The setup card on a device.** Goal: 3.3 on a phone — the yard's sentences complete, one line per call, command and preset, the account choice on the card (a tap on a candidate takes its file, a filled secret field types another), the preset pick and the approval together, and the readings open, being carried out, ran or failed. Where to look: the run-ask and secret-ask cards there today. Done when: the card shows credential placement, each call's method and path, the mint with digest, each candidate with its address, each preset's calls and grantee, and the take-backs; the texts behind the tap are the ask's own, byte for byte; an approval the yard refuses is shown whole. Depends on B2, B3 and B4.

Not made here: a family card for several packs, multi-select in asks or on the card, presets that narrow holdings, and presets for depot packs. Each is its own step if it is ever wanted.
