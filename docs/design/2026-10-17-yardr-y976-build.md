# A declared call may build its request body with a pack script

Design yardr-y976, proposed 2026-10-17. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A bead is one durable piece of work. A source is a service outside the yard, declared by one YAML file; a declaration's call is one request the yard may make of the service, with its kind (read or update), its parameters, its request's method, path, query and body, and what it keeps of the answer. A pack is a way of working as one directory; a pack of kind source declares sources yardr has no Go for. A command file is a program a declaration names beside its file, which the yard copies under `<home>/sources/<name>/` and runs: the limits, thread, hook and events commands. A grant is who may make which calls of a source. A run ask proposes one yardr command, and its card shows the yard's sentences for what the command changes; the operator approves on the card. The operator is the person who runs the yard. An agent is a bead's session at work. The credential is the secret a source's calls are sent with, read per call from the source's env file, or minted per call from it.

## 1. The question

mckean, 17 Oct 2026 (ask 6830 on yardr-whkk): "A" — extend the source format with per-call build scripts. Three beads are stuck where a substitution-only request template cannot reach: yardr-whkk (one Docs write appending several styled paragraphs needs the doc's end index plus UTF-16 lengths), yardr-ap7t (a Docs replace refusing a multi-match needs a read and a count before sending), and yardr-0kqg (a Gmail draft from to, subject and body needs MIME building and base64url). So: may a declared call build its request body with a pack script, what does the script get and print, and what does the yard show and check of it?

## 2. What exists today

### 2.1. A call is a substitution-only template

A declaration (`source.Parse` in internal/source/declaration.go) holds each call's kind, its scalar parameters (string, int, bool, enum), its request's method, path, query and body, and its answer's select and max. Sending is substitution alone: `fill` in internal/source/call.go replaces each `{name}` with the parameter's value, with no arithmetic, no length, no loop and no conditional, and a body is fixed JSON with marks in it. Parameters are scalar only; a parameter the template never sends is allowed, since the reader holds no parameter to being used. A call's method and path are static text, and so is every key of its query and body. The reader refuses what would fail at every use: an unknown key, a mark for no parameter, a read of any method but GET or POST. A body under a GET is allowed as written. Call names are lowercase words without dots, and `read` is reserved for the grant that covers every read call.

### 2.2. The call path counts, sends and records

`Store.CallSource` in internal/store/sourcecalls.go runs in three parts. A first write tells who calls, checks the grant and the parameters, counts the call against the caller's hourly budget (60 calls, 10 of them updates, unless the source says otherwise), and chooses the update's idempotency key, or finds the one of the try before. The request is then made outside any store transaction: the credential is read for this one call (`ReadCredential`, or `ReadUserCredential` for a call as a user, minting where the file names a mint), and `source.DoKeyed` sends exactly one request and reads its answer. A second write records how it ended. Every call, made or refused, is a `source_call` event: who, which call, how it ended, the names of the parameters given, and the value of each one the declaration marks `log: true` — never the credential, the request's body, the answer, or the address with its values in it. A call the service answers 4xx or 5xx still consumed its count; only a success drops the update's key, so a retry says so by its key for 24 hours.

What `DoKeyed` holds every call to is the same for each: the base's own host and no other, over https (plain http only to this machine, for a stand-in), no redirect followed, 30 seconds (`source.Timeout`), and an answer that is JSON within its bound. Its errors (`CallError`) name the source, the call and the cause, and never a parameter's value, the credential, the request's body or the address with its values in it. Beside `CallSource`, four paths send through `source.Do`: telling a user (`internal/notify/notify.go`), `yardr source check` making the check call, hook registration (`internal/store/runask_hook.go`), and `yardr doctor` trying the check call (`internal/cli/doctorsources.go`).

### 2.3. Pack scripts are commands the yard runs

Beside calls, a declaration names commands: the limits command, thread's reply, posted, read, open, opened and state, hook's normalize, and events' pr and ci, in that order from `Declaration.Commands` in internal/source/command.go. Each is an argv run without a shell. `source.Run` runs one: the JSON object on its stdin, the credential under the name the file gives plus `YARDR_SOURCE_BASE` and PATH and HOME and nothing else (`CommandEnv`), 30 seconds unless told otherwise, at most 64 KiB printed (`MaxCommandOutput`), killed with everything it started past the time, and its answer one JSON object; whatever else happens is a failure whose error ends with the command's stderr. A relative program is a file beside the declaration's file, copied at add and apply time into `<home>/sources/<name>/`, mode 0700 (`CopyCommandFiles`, `CopyCommandFilesFS`, and `WriteCopies` with `VerifyCopies` when a run ask is carried out); an absolute program is the operator's own and is not copied. Telegram's thread script (`packs/telegram/telegram/thread`) is the precedent that matters here: a pack script that makes its own requests to the service with the token from its environment, reading `YARDR_SOURCE_BASE` so a test can point it at a stand-in.

### 2.4. Every showing of a source is driven by its declaration

`yardr source show` prints each call as `call <name> <kind> <METHOD path>` with its parameters, and each command with its argv and its copy's path and full sha256 (`CommandFiles`, `commandFileLine`). `yardr source check` tries the check call where there is one, and of every command says whether its program is there and can be run, running none. A pack's plan lists each declared source's calls as `name (kind)` with each command's program and sha256 (`sourceCommands` in internal/pack/plan_sources.go), what a replacement changes (`declarationDiff`, which compares each call whole, and `commandDiffs` for the files), and who a standing read grant would newly reach (`store.Widened`). A run ask's card says per call what it sends, including the body's JSON (`callSaysWhole` in internal/store/runask_source.go), and per command file its program, argv, whether it is handed the credential (`commandGetsCredential`: thread and events commands are, limits and normalize are not), its sha256 and mode 0700 (`commandSays`); where the installed copies drift from what is carried, the card shows old against new sha256 with diff counts (`AskFileDiff`, from an inventory of `<home>/sources/<name>/`). The carrying out writes exactly the carried bytes and verifies them. Nothing watches the copies continuously: drift of an installed copy from the pack's bytes is found at plan, card and carry time, which compare against the carried bytes; `source check` holds no expected digest to compare, so it finds a missing or non-runnable copy, not drift.

### 2.5. Three precedents bound the shape

First, the store already runs subprocesses on the call path: a minted credential runs the source's `mint_command` (`Mint` in internal/source/mint.go, bounded by `MintTimeout`, 30 seconds) inside `CallSource`, after the count and before the request. Second, the store already knows home: `Store.home` is the directory of `yard.db`, and the pack card's inventory walks `<home>/sources/<name>/` from it. Third, what would fail at every use is refused at parse: `hookRegisterCheck` holds a hook's register call to the calls as read, rather than failing at each registration.

The charter both riders quote is in the package doc of internal/source ("A service is added by its file and no Go") and at the end of packs/google-docs/SETUP.md ("The yard's source format cannot express what is not listed, and the pack does not change yardr").

### 2.6. What the three riders found

On yardr-whkk (note 6828): styling needs absolute ranges; appended text sits at the body's end index plus cumulative UTF-16 lengths; the end index is learnable only by `documents.get`, since `batchUpdate` replies report none; `fill` cannot do the arithmetic; the update path must therefore read with the server-side credential; and the call path runs no pack script today. On yardr-ap7t (note 6832): refusing a multi-match needs the count before sending; Docs has no single-replace, only `replaceAllText`; the 0-occurrences half is fine pack-only, since `occurrencesChanged: 0` says so. On yardr-0kqg (its body): the draft call takes a hand-built base64url message, and replying in a thread needs the thread's last message first. The shared root: each needs a read, some computing, or both, between the agent's parameters and the one request — with the yard's credential, which lives server-side.

## 3. The proposal

### 3.1. In one paragraph

A call may name a `build` command beside its request: the call keeps its kind, method, path, query, parameters and answer, but its body is what its build command prints. The script is a pack script like thread's and normalize's, installed, shown, hashed and drift-checked by the same machinery, and it runs on the `yardr call` path between the credential read and the request, with the call's parameters on stdin and the credential in its environment. It may make its own requests to the base first — the GET before the POST the riders need — as part of the one call, carried by its grant rather than counted or audited of their own. A refusal from the script sends nothing and reads as the script's own words. Grants, limits, audit and idempotency keys work untouched — no new grant kind, no new count — but a built update's grant explicitly carries further than today's: it authorizes the script's unconfined credentialed requests while it builds (expected to be reads of the base, unenforced) and the refusal's service-derived words, disclosed on the card (3.6, 3.8).

### 3.2. The format: one key beside the body

Under a call, beside `request`, a call may name `build`: an argv, a list of strings run without a shell, read by the same `reader.command` every other command goes through, so a relative program is a file beside the declaration's file and stays under it. Unlike every other command, the build program must be relative: the reader refuses an absolute program at parse, since the digest, the card's sha256 and drift against the carried bytes are the only confinement a build script has, and an absolute program is the operator's own, uncopied and unhashed. A call names `body` or `build`, never both: the reader refuses both together. A call with neither still sends no body, as today, and a build on a GET is allowed, exactly as a static body on a GET is today — no new method check. Whether reads may name it at all is 5.2. Nothing else of the file changes: kinds, scalar parameters, the credential, the idempotency header, select and max all mean what they mean today.

### 3.3. What the script gets, and what it prints

The script is handed one JSON object on stdin: `{"params": {name: value}}`, each value typed as the declaration reads it (an int as a number, a bool as a boolean), an optional parameter left out when it was not given. Its environment is `CommandEnv` unchanged: PATH and HOME, the credential's value under the name the file gives (the value the call would be sent with, `EnvOf` of the call's kind: the update credential for an update where those differ), and `YARDR_SOURCE_BASE` from the base, so a test points it at a stand-in as telegram's thread script is pointed. Nothing else of the yard reaches it. It runs in the yard's home, as the thread and limits commands do.

It may make its own requests to the base — that is the point: whkk's script GETs the document for its end index, ap7t's GETs it to count matches, 0kqg's GETs the thread's last message for its reply headers. Those requests are part of the one call, not calls: they are counted nowhere and audited nowhere of their own, as a thread script's requests are part of thread work and a mint's fetch is part of its call. That is an explicit widening of what the outer grant authorizes: a caller granted only the update causes credentialed requests with no `read` grant, no separate count and no separate `source_call` event — the outer call's grant, count and event carry them. The core cannot hold these requests to the declared method and path, or even to the base: a shell script's egress is unconfined, and the base-only, https-only, no-redirect holding of `DoKeyed` guards only the request it sends. What the riders need is GETs of the base, and approved pack bytes are expected to make only those — but the grant as designed authorizes arbitrary credentialed egress while the script builds, including any path and any other host the script phones with the token, and the design claims no enforcement, only approval plus audit (3.8).

It prints the body only: one JSON value on stdout, of any shape a static body may hold, which the core posts exactly as a filled template — same Content-Type, same credential header, same idempotency header. Method, path and query stay in the file: what the card approved as the call's line is what `DoKeyed` sends, under the base-only policy that is never the script's to bend for that request. The script's own requests stand outside that line, as the paragraph above says. The bound is a new constant, `MaxBuildBody` of 1 MiB, equal to `AnswerLimit`: a call may send what it may read. The command bound of 64 KiB is provably too small — whkk's text param runs to 50000 characters and 0kqg's raw message to a million — and a per-call knob for it would be a new setting against simplicity, so the number is fixed and shared.

### 3.4. Running it, between the credential and the request

`CallSource` runs the build after the credential is read and before `DoKeyed` sends, outside any store transaction, as the request is made today. Everything before it — the caller, the grant, the parameter check, the count, the key — runs first and unchanged, so the script only ever sees parameters the declaration allows, and a refused build consumes one of the hour's budget exactly as a call the service answers 4xx does. The runner is `Run`'s sibling in package source, sharing its argv, stdin, environment, directory and stderr rules, with two differences: the answer is one JSON value within `MaxBuildBody` rather than one JSON object, and a non-zero exit is a refusal rather than a failure. `DoKeyed` itself is untouched and template-only; it gains a sibling that takes the ready body instead of filling the template, and `CallSource` picks by whether the call names `build`. The build runs under a timeout; 5.1 sets whether that is a stacked `Timeout` of its own or the call's one shared deadline. Each attempt builds anew; nothing is cached between attempts.

Exit zero posts the printed body. A non-zero exit refuses: nothing is sent, and the caller reads the refusal as the script's stderr, capped at 4 KiB as every command's is — the guard ap7t needs speaks in its own words, for example `3 matches; pass all=true to replace them all`. Breakage — no program, past the time, over the bound, no single JSON value — likewise sends nothing, and reads as the runner's own words naming the command. The audit tells the two apart with two new reasons beside today's: `build_refused` for a refusal, `build_failed` for breakage. The `CallError` contract gains one documented exception: a build message is the pack script's own stderr shown to the caller, and may repeat the caller's parameters back to them, or service-derived metadata the pre-read found (ap7t's count is the point) — an update-only caller reads that metadata with no read grant, explicitly part of what the built call's grant permits. The `source_call` event keeps the reason alone, as it keeps no body and no answer today. A refused or failed build keeps the update's key like any outcome but success, so trying again says so by its key.

### 3.5. Unchanged on purpose

Grants cover a built call by name as any call — and a built read by the read word too, where 5.2 allows one, since `Covers` grants a read by kind or by name and an update only by name. The mechanism is unchanged and no caller needs a second grant; what is wider is the meaning of the one grant: for a built call it explicitly includes the script's unconfined credentialed requests while it builds and the refusal's service-derived words, disclosed where the grant is approved (3.6). Limits count one attempt as one call. The audit records who, which call, how it ended and the declared parameter names, with the new reasons as its statuses. Idempotency keys are chosen before the build and dropped only on success. The answer still passes through select and max, `--as` still reads the named user's credential for the script's environment, and `--note` still notes what the service answered. The request `DoKeyed` sends still goes to the base's own host over https with no redirect followed.

### 3.6. What source show, the plan and the card show

A build command joins `Declaration.Commands` with the key `call.<name>.build` — unambiguous, since call names hold no dots — after the events commands. Because the program is always relative (3.2), everything that walks the commands then carries it with no new path and no operator-owned exception: `CheckCommandFiles` and the `CopyCommandFiles` family install it; `CommandFiles` shows its path and sha256; the pack planner hashes it and diffs it (`sourceCommands`, `commandDiffs`); the apply card inventories it against the installed copies and shows old against new with diff counts; the carrying out writes and verifies exactly the carried bytes; and `source check` says whether its program is there and can be run, running none. Pack drift reads as it reads for every command file: content drift from the carried bytes is found at plan, card and carry time, watched nowhere continuously; `source check` finds a missing or non-runnable copy, not drift; and the installed copy is read fresh at each call, never cached.

Four places learn the new key by shape. `yardr source show` prints under each built call its build argv and the copy's file line, by the existing `CommandFile` rendering. The plan's per-call summary stays `name (kind)`; the commands beside it say the rest. The card's per-call line for a built call says it builds its body with its command, run with the credential at each call and free to make its own requests with it while it builds — the unconfined egress the grant carries (3.8) — in place of the body's JSON; the file line with sha256 and mode 0700 follows from `commandSays` once `commandGetsCredential` matches build keys, which are handed the credential like thread's. A replacement's call-level change shows through `declarationDiff` on its own, since the call's JSON now holds the argv, and `Widened` needs no change.

### 3.7. The static paths that send the template

Telling a user, the check call (`source check` and `yardr doctor` both send it), and hook registration send through `source.Do`, which fills the file's template and runs no script. A build named on one of those calls would either be refused at parse — in the reader, beside the checks those references already carry (three checks: the check call, notify's call, hook register's call), each error naming the path that sends the template — or honored by threading home through `Do` so every path builds. 5.3 picks; the `yardr call` path builds either way.

### 3.8. The trust line, for review-security

A build script is the same class as a thread script: pack bytes, approved by the operator on a card (or in a terminal) that shows the program and its sha256, run outside any agent's pane with the yard's credential and free to make its own requests. Its running is the mint command's: in the server process, on the call path, after the grant and the count. What is new against thread scripts is the caller and the grant it rides on: an agent's parameters, not a delivery or an operator's reply — validated against the declaration before the script runs, so unknown, missing, over-long and off-pattern values never reach it — and a per-call grant that now explicitly includes unconfined credentialed requests while the script builds. What the script prints as the body goes only to the declared method and path, never anywhere it chooses; but the script's own requests are confined by nothing: a buggy or malicious pack script could request any path, or phone elsewhere with the token, exactly as a thread script could today — any side effects such requests cause ride on the caller's grant of the built call. The confinement is approval plus audit — the sha256 on the card over bytes that are always pack files, never operator-owned (3.2), the per-built-call line disclosing the unconfined egress, the `source_call` event per attempt, review of embedded packs in the repository — not filtering, and the design claims nothing stronger.

What the caller learns beyond today's answer is the refusal text, which is pack-authored and operator-approved: ap7t's "3 matches" is metadata of the same kind as `occurrencesChanged`, which an update-granted caller reads today with no read grant — but the resemblance ends at the example: `occurrencesChanged` arrives in the granted call's own answer, while the count is service content fetched without a read grant, and this design says so instead of claiming no bypass. Stated plainly: a built update's grant authorizes unconfined credentialed requests the caller could not make directly, and service-derived words in a refusal, with neither a separate read grant nor a separate event. The pre-read content otherwise never leaves the server except as shaped into the body or the refusal by approved bytes. The alternative — refusing build-time requests, or demanding the caller also hold `read` — would keep the grant's meaning narrow at the price of the riders: whkk and ap7t cannot build without reading, and a read grant on every updater spreads further than the one disclosed line on the card. Against the review-security list: the new caller reach is the granted call's method and path with a script-built body, plus the script's unconfined credentialed requests while it builds and the refusal's words; no check is loosened (`maySource` and the grant checks run first, unchanged) — the grant's meaning is wider, and the card discloses it where it is approved; outside text (the pre-read answer) is data to the script, and reaches the caller only through the service's own answer and the refusal; no credential is ever in an event, and refusal text — which may hold the caller's own values — goes to the caller alone, never into the event; files are written by the existing copy machinery at its modes and paths; nothing new listens; no new dependency — curl, jq or an interpreter are the pack's choice on the operator's machine, and each tool a rider's script calls is the checklist's existing item on that rider's bead, not here.

### 3.9. The charter still holds

The core learns one generic mechanism — run an argv, post the JSON it prints — and names no service anywhere in it: no `if source ==`, no per-service branch, no new package. Docs ranges, UTF-16 lengths, MIME and base64url live in the packs' scripts, carried, hashed and copied as data the core never reads for meaning. The format stays declarative about permission — calls, grants, limits — and delegates encoding to the pack, which is the same line today's commands already draw: to the core, a thread script is opaque bytes with a shape. The package doc's list of what a file cannot say stays true: a request that must be signed, an answer in pages, anything that is no JSON over HTTPS are still not declared sources. What honestly changed is one precedent, the one mckean accepted in ask 6830: request construction was template-only, and now a call may delegate its body. `SETUP.md`'s "the pack does not change yardr" still holds — the pack uses a yardr mechanism — but the format grew one careful key to offer it, and the design says so out loud.

### 3.10. What a person types and sees

The declaration names the script where the body was:

```yaml
  write:
    kind: update
    about: Append paragraphs at the end, each with its style
    params:
      docId: { type: string, pattern: "^[A-Za-z0-9_-]+$", max: 200, log: true }
      paragraphs: { type: string, max: 60000 }
    request:
      method: POST
      path: /v1/documents/{docId}:batchUpdate
    build: [google-docs/build-write]
    answer: { select: [documentId, replies] }
```

`yardr source show google-docs` prints under the call its build line and the copy's file line; the pack plan and the apply card show the command file with its sha256 beside the call it builds for. An agent's guarded call reads as the guard wrote it:

```text
$ yardr call google-docs replace docId=abc find="lunch" with="dinner"
source google-docs, call replace: 3 matches; pass all=true to replace them all
```

and nothing was sent. The `source_call` event on the bead says who, `replace`, and `build_refused`.

## 4. Left out

List parameters. whkk's paragraphs cross as one JSON string the script parses and validates, refusing garbage. A list type is its own format change — CLI syntax, validation, `fill`, brief lines — and build does not need it. Fixed slots (`text1`, `style1`, …) were considered and rejected: an arbitrary cap the JSON string does not have.

Method, path or query from the script. The body only: the call's line on the card and in the grant stays what `DoKeyed` sends, and the base-only policy stays the core's for that request, never the script's to bend.

Egress confinement for scripts. No sandboxing, no allowlist, no holding build-time requests to GET or to the declared path: the same exposure thread scripts have today, held by the same approval and audit. A rule the core cannot enforce would be a convention wearing a check's name.

Separate grants, counts or audit entries for build-time requests. The outer call's grant, count and event carry them: the core cannot count what a subprocess chose to fetch, so a separate count would be the script's own report, unenforced. The grant's wider meaning is disclosed on the card instead (3.6, 3.8).

Continuous drift watching. Installed copies are checked at plan, card, carry and `source check` time, as every command file is; no watcher is proposed.

Caching built bodies or pre-reads. Each attempt builds anew: a GET per attempt is the honest cost, and a cached body would be a stale write wearing a fresh attempt's key.

Bodies over 1 MiB, and streaming. The bound is the bound; the services' own caps still apply past it.

A structured refusal protocol. One refusal shape — stderr text — is all ap7t's guard needs; exit codes per meaning would be a second protocol beside the words.

Build on the check, notify and hook-register paths, unless 5.3 says otherwise: those calls are the pack author's static choice, and `Do` stays template-only.

## 5. Open questions

### 5.1. One stacked timeout, or one shared deadline?

Option A: the build runs under its own stacked `Timeout` (30 seconds), after the mint's and before the request's, for a worst case near 90 seconds on a minted built call. It costs the wait in the worst case and nothing in plumbing: `Run`'s default, as the mint stacks today. Option B: build and request share the call's one 30-second deadline. It costs deadline threading through the build into `DoKeyed`, and either the build or the request can starve the other on a slow service. I would take A: the worst case is rare and honest, and the mechanism beads change no signature to get it.

### 5.2. May a read name build, or updates only?

Option A: any call may name it. The mechanism is kind-agnostic, so this costs no check, and a POST read with a computed body (a search, GraphQL) stays possible. It costs the oddity of a built GET, whose script reads only for a body the method barely uses. Option B: updates only, refused at parse for a read. It costs one check and keeps reads substitution-only, at the price of reopening the question the first computed read arrives. I would take A, by generalization: one rule for every call, and the odd shape is the pack author's to avoid.

### 5.3. Refuse build on the static paths, or honor it everywhere?

Option A: the reader refuses `build` on the check call (which `source check` and `yardr doctor` both send), notify's call and hook register's call — three checks covering the four static paths — each error naming the path that sends the template. It costs three small checks, in the style of `hookRegisterCheck`, and those calls stay the pack author's static choice. Option B: thread home through `Do` and `DoKeyed` so every path builds — notify, check, registration and doctor included. It costs a signature change on two core functions and every test that calls them, for paths whose calls want no build today. I would take A: refuse at parse what the path cannot serve, and reopen B the day a notify or register call needs computing.

## 6. The beads it would become

In landing order. The first two are the mechanism; the last three are the riders, reshaped here — their bodies stay as written until the yardmaster reshapes them from this section after the decision.

1. **The build key: format, runner and the call path.** Goal: a call may name `build`, and `CallSource` runs it between the credential read and the request, refusing and recording as section 3 says. Where to look: `Call.Build` and `Commands` in internal/source (declaration.go, command.go), the new runner beside `Run`, the `DoKeyed` sibling in call.go, the wiring in `CallSource` in internal/store/sourcecalls.go, the parse refusal of an absolute build program (3.2), and the parse refusals of 3.7 as 5.3 decides them. Done when: goldens over a fixture declaration pin the stdin, the environment, the posted body, a refusal, and each breakage; a stand-in round trip builds against `YARDR_SOURCE_BASE`; `.yardr/test` passes. Depends on nothing.

2. **The build key: show, plan and card.** Goal: `source show` prints each built call's build argv and file line, the pack plan hashes and diffs the script, and the apply card says per built call that it builds its body with its command — run with the credential at each call and free to make its own requests with it while it builds — with the file's sha256 and the credential handed. Where to look: internal/cli/sourcecmd.go, internal/pack/plan_sources.go, `commandGetsCredential` and `callSaysWhole` in internal/store/runask_source.go, and one paragraph in docs/integrations.md beside the check-call section. Done when: goldens pin the show lines, the plan lines and the card lines for a built call, including the egress disclosure and a replacement's file diff; `.yardr/test` passes. Depends on 1.

The old text/style/start/end form is replaced, not kept: one call holds one body shape. Where to look: packs/google-docs/google-docs.yaml, the new script beside it, packs/google_test.go, SETUP.md's try step.
