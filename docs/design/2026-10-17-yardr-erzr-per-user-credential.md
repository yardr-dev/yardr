# A source's credential per user, and a grant that calls as that user

Design yardr-erzr, proposed 2026-10-17. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A source is a service outside the yard, declared by one file; a crew member is one of the yard's always-on agents; a user is a person of the yard, and the operator is the user who runs it; a grant (`yardr source grant <source> read|<call> --crew|--group`) is the record that lets a crew member or a group's sessions make a declared call (`yardr call <source> <call>`); an ask is one question as data on a bead, and a secret ask (`yardr bead ask --secret <source>`) is the ask whose typed answer is written to a file by the yard's server and shown to nobody. docs/glossary.md has all of yardr's words. In this document **a holder** is whoever a credential belongs to — the source, a crew member or a user — **called as** is the user whose credential one `yardr call` is made with, and **the mint** is the command a source's `mint_command` names, which turns named inputs into a short-lived token per call.

## 1. The question

mckean, 17 Oct 2026 (mail): "googel cli, it would make sense to have an env per user, and then granting you access for a users google stuff". Today the `google` pack declares four sources whose credential is minted per call from one gws login on this machine, so the yard has one Google identity, the operator's, and every grant calls as it. What is wanted, generic across services and with Google first, is that a source can be called as a user of the yard, with that user's own credential, and that someone grants a crew member or a group the right to call it as that user.

## 2. What exists today

### 2.1. A declared source and the one place its calls are made

A source is one YAML file, read by `source.Parse` in internal/source/declaration.go into a `Declaration`: its `base` address, its `credential` (`env`, the variable the credential is in; `header`, where it goes; `update_env`, a second variable for update calls; `mint`, the names that together select a minted credential; `in_path`, where the service takes the credential in the request path), and its `calls`, each `read` or `update` with its parameters and its request. The store keeps the declaration's whole text and four settings in the `Source` record in internal/store/sources.go: `EnvFile`, `MintCommand`, `CallsPerHour` and `UpdatesPerHour`. The pack is `packs/google/pack.yaml`, of kind `source`, declaring `google-mail` (Gmail read and drafts, sends nothing), `google-drive` (files listed and read, folders and empty Docs and Slides made), `google-docs` and `google-slides` from `packs/google/google-mail.yaml`, `google-drive.yaml`, `google-docs.yaml` and `google-slides.yaml`. Each names the same credential shape: `env: GOOGLE_TOKEN`, the header `Authorization: Bearer {credential}`, and `mint: [GOOGLE_ACCOUNT]`. So the file a call reads holds one address, `GOOGLE_ACCOUNT`, and no token is kept anywhere; a token is minted per call.

Every declared call is made by the yard's server, in `Store.CallSource` in internal/store/sourcecalls.go. The server reads the credential once, for that call, through `Declaration.ReadCredential` in internal/source/credential.go from the source's one `EnvFile`, and calls `source.DoKeyed` in internal/source/call.go. The credential is kept nowhere: it is in no pane's environment, no brief and no event. `ReadCredential` in turn uses `Declaration.SelectCredential`, which reads that one file and applies one precedence, in `Credential.Select` in internal/source/mint.go: when the file sets every name under `mint`, the mint's inputs are returned for `Mint` and the static variable is ignored; one of them alone is refused; otherwise the value of the variable `EnvOf(kind)` is used as it is set, the read variable for a read call and `update_env` for an update where the file names one. `Mint` runs the source's `MintCommand`, one line split on spaces without a shell, with `{inputs, scope}` on stdin for `{token, expires_at}`, keeps the token in this process's memory alone, keyed in `mintKey` by the source, the command, a hash of the inputs and the scope, and asks again shortly before it expires. Its environment is `PATH`, `HOME` and `YARDR_SOURCE_BASE` and nothing else. `CredentialState` says in words where every variable is set, and never holds a value. `yardr source key <name>` and `yardr source set <name> env_file=<file>` and `mint_command=<program>` are how a person sets that file and that command (internal/cli/sourcecmd.go); what the file holds is never in the store, an event or a log.

`contrib/google-mint/google-mint` is the mint command the google pack's setup names. It reads `GOOGLE_ACCOUNT` from its inputs, checks that `gws auth status` answers that same account, takes the client id, client secret and refresh token from `gws auth export --unmasked`, and exchanges them at Google's token endpoint for an access token. No copy of a secret is stored: the three are held in that process's memory alone, sent in the exchange's body, and never printed or written. It needs `gws` and `curl` on `PATH`. gws's own help (run on this machine, `gws --help`) lists `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` as "Override config directory (default: ~/.config/gws)" beside `GOOGLE_WORKSPACE_CLI_CREDENTIALS_FILE` and the client id and secret variables, and `gws auth login --help` shows it takes `--services` and `--scopes`. As shipped, the script chooses no config directory, so gws reads the one default login in `~/.config/gws` whatever `GOOGLE_ACCOUNT` names, and the script refuses when that login is for another account.

### 2.2. The grants a call is checked against

Who may make which call is a record of its own, `SourceGrant` in internal/store/sourcecalls.go, in the bucket `bSourceGrants` under the key `<source>\x00group|crew\x00<name>`. A grant holds the source, one grantee (a group, and so each session it starts, or one crew member), the calls it covers (`read`, the word `GrantRead` for every read call of the source, the ones a later file adds included, or one call by its name, which is the only way an update call is granted), when it was given and by whom. `Grantee` is either `Group` or `Crew`. Giving one is the operator's: `GrantSource` checks `checkGrantSource`, which is `maySource` marked askable, and `RevokeSource` may be run by anyone, as narrowing a grant may. `yardr source grant` and `yardr source revoke` in internal/cli/sourcecmd.go take `--group` and `--crew`, each repeatable, and no other word for whom the call is made as. A crew member that needs a grant proposes it with a run ask, `yardr bead ask <id> "<question>" --run "source grant crm note --crew yardmaster"`: the card in internal/store/runask_list.go names each call with its method and path, says of `read` which calls that is today and that it covers read calls the source is later given, and of an update call that it changes something there; the approval is held to the declaration, to the source's `env_file` and `mint_command`, and to each group and crew member as they were when the card was written. `yardr source show <name>` prints each call with who may make it, `yardr crew show <name>` prints `may call <source>: <calls>` for that crew member, and `yardr group list` has the same in its `CALLS` column.

Who is calling is told by the server before the caller's word, in `sourceCallerIn` in internal/store/sourcecalls.go: the session whose pane the command runs in, which gives its group and its bead; else the crew member whose pane it is; else the session `$YARDR_SESSION` names; else the actor, a crew member by its name or the operator. The operator may make any call, to try it; any other person makes none; a session that has ended calls nothing; and a session whose bead came from a linked yard calls nothing whatever its group is granted (`fromPeer`). `may` then holds the caller to its grant. Every call, made or refused, is a `source_call` event written by `sourceCalled`: `source`, `call`, `kind`, `by` (who called, in words), the session and group or the crew member, `status`, the milliseconds and bytes, the names of the parameters given and the value of each the file marks `log: true`, and `attempt` from 2 for an update sent again. It never holds the credential, the request, the answer or the address with its values in it. One caller makes 60 calls of a source in an hour (`calls_per_hour`), 10 of them updates at most (`updates_per_hour`), counted in `bSourceCalls` under `<source>\x00session|crew|user\x00<id>`. `yardr call --list` and a session's brief print what the caller may call in the same way, each call as its command with an update marked.

### 2.3. The three files a credential is kept in today

Values are kept in env files, files of `KEY=VALUE` lines of mode 0600, and the store keeps each file's path and never its content. Three holders have one today, and they are read in three different places, which is the fact any per-user design has to start from:

| holder | whose file | who names the variable | who reads the file, and when |
|---|---|---|---|
| a declared source's credential | `Source.EnvFile`, or `<home>/sources/<name>.env` where `yardr source key` writes one (`source.EnvFile` in internal/source/credential.go); the google pack's setup shares one, `~/.yardr/sources/google.env`, across its four sources | the declaration: `credential.env`, `credential.update_env`, or the inputs under `credential.mint` | the server, for one `yardr call` (`ReadCredential`, above) |
| a user's own address in a source that tells people | `User.EnvFile`, or `<home>/users/<name>.env` where `yardr user key` writes one (`userEnvFile` in internal/store/usernotify.go) | the declaration's `notify.address.env` (for Telegram, `TELEGRAM_CHAT_ID`) | the server, at each send through that source (`KeyUser`'s file, read where the notify path reads it) |
| a crew member's outbound credentials | the crew member's `env_file`, or the lines its `env_command` prints (docs/crew.md, "Outbound credentials") | nothing: every line of the file is loaded | the runner, when it starts the pane: the lines join the agent's pane environment, and the commands the yard runs in the source's threads read the credential from that environment (`Credential` and `CredentialFrom` in internal/hooks, through `Credential.Select`) |

A user's record is `User` in internal/store/users.go: a name and an inbox, the source that tells them outside the yard (`notify`), the path of that env file, which parts they are told of (`tell`), who they are in each source (`identities`, set by `yardr user identity`, as a crew member's is), and their subscriptions. The store has three ways of writing a value into one of those files without anyone writing the file by hand, all through `config.WriteEnvFile` in internal/config/envfile.go, which replaces or adds the line of each given name, keeps every other line and comment, writes the new content whole to a second file beside it created with mode 0600, syncs it and renames it into place, and refuses a file that is not regular or that anyone but its owner can read or write. They are `KeySource` for a source's credential, `KeyUser` in internal/store/usernotify.go for a user's own address in a source (exactly the one variable its `notify` key names, and refused for a source with no `notify` key), and `GiveSecret` in internal/store/secretask.go, which answers a secret ask by writing the value and then recording an answer note that holds the names and never the value. The first two have terminal forms, `yardr source key` and `yardr user key`; the third is the card form of the first two and of two more (a hook's signing secret, and a waiting login's input).

### 2.4. Secret asks: what a card can ask for today

`yardr bead ask <bead> "<question>" --secret <source>` asks the operator for a declared source's credential. `AskSecret` in internal/store/secretask.go is where such an ask's answer goes: the source, the variables `Env` (every variable of its credential when the asker narrowed to none, in the declaration's order), the host of the source's calls, and, where set, one of three marks that change where the value goes instead. `User` makes it an ask for that user's own address in a source that tells people (`--secret <source> --for-user <user>`): `Env` is the one variable the source's `notify` key names, the ask is for that user or the operator for them (`askedAddress`, checked with `mayTell`, the same check that guards where a user is told), and `GiveSecret` writes it into that user's env file by `keyUser`. `Hook` makes it a hook's signing secret, and `Login` a waiting login's input; both are the operator's alone. With no mark it is the source's credential, and `askedSecret` refuses anyone but the operator as the one asked, a source the yard does not have, one that names no credential, and a name the declaration does not have; the asker never names a path and never invents a name. `Line` is what a card says such an ask asks for, in the yard's words and never the asker's: "a secret: `GOOGLE_ACCOUNT` and `GOOGLE_TOKEN`, for the source google-mail (https://gmail.googleapis.com)", or for a user's address the same with "…`TELEGRAM_CHAT_ID`, mckean's own address in the source telegram (…); mckean is told through telegram once it is given and `yardr user set mckean notify=telegram` is run". A secret ask takes no option, no recommendation and no about-beads, is not sent to a peer, and `AddAnswer` refuses a pick, words and a decline's words on it, so a client that does not know the field yet cannot put a value in a note. Giving again is allowed while the ask is not declined, and each giving is a note with the names.

A crew member's own credential for a source is the one holder with no card: that is bead yardr-0tew, in `new`. It proposes `--for-crew <crew member>` beside `--for-user` on `bead ask --secret`, the names from the source's credential as `--secret` takes them (`--env` narrows), the value into the crew member's `env_file` or with none set into `~/.yardr/crew/<name>.env`, which is then set as `crew set env_file` sets it, asked of the operator only, and with the answer saying the running process sees the new value only at its next start. What it serves is not `yardr call` but the pane path of the third row of the table in 2.3: `yardr reply` and `yardr thread` read the caller's own credential from the pane's environment (`Credential` in internal/hooks/reply.go and the declared thread commands in internal/hooks/declared.go, which resolve a minted credential from the acting environment with the thread or the place as scope). It does not touch the server's caller, grant or counting, and nothing in it names a user.

Two other per-user namings in the code are not this. A crew member may serve particular users, with `for=<users>` and `env_for_<user>=<file>` on its config (`Serves`, `EnvFor` and `HasConversation` in internal/store/crew.go): `env_for_<user>` names the env file a conversation session with that user runs under, loaded into that session's pane at its start, under every file of a crew member as it is at a start. And a group's `login_for=<user>` (docs/groups.md) declares whose harness login a group's panes burn, for quota and billing. Neither is a credential for a call of a source, and neither is read by the server.

### 2.5. The google pack's setup today

`packs/google/SETUP.md` has seven steps, all typed in a terminal, and the pack is not applied on this yard yet, partly because they are. They are, with who does them as the file says:

1. **The gws login.** `gws auth status`, and where its scopes lack one of the four (`gmail.modify`, `drive`, `documents`, `presentations`), `gws auth login -s gmail,drive,docs,slides` again. The machine holds one login in `~/.config/gws`, and its account is what every source mints from.
2. **The pack.** `yardr pack apply google`, which declares the four sources and nothing else, and asks no grants at import: a pack of kind `source` never carries a grant (`pack.yaml`: "A pack of kind source asks no grants at import, so the operator grants what a crew member may call afterwards").
3. **The account.** `umask 077`, `printf 'GOOGLE_ACCOUNT=%s\n' '…' > ~/.yardr/sources/google.env`, `chmod 600`, and `yardr source set $s env_file=~/.yardr/sources/google.env` for each of the four sources.
4. **The mint.** `install contrib/google-mint/google-mint ~/bin/` from `main`, and `yardr source set $s mint_command=$HOME/bin/google-mint` for each source.
5. **The grants.** For each source, `yardr source grant $s read --crew yardmaster`, and each update call by its name: `google-mail draft`, `google-drive folder`, `doc` and `slides`, `google-docs write`, `google-slides slide`.
6. **Check it.** `yardr source check google-drive`, whose check call lists the drive's files, and `yardr source check google-mail`, which names no check call and so looks the credential over and sends nothing.
7. **Try it.** As the operator, who may make any call: `yardr call google-mail search q="from:me" maxResults=5`, a message read, a draft, a folder and a doc written into.

Of these, two already have a card by other work and two never will have the same shape. Applying a pack of kind `source` is a run ask today (`yardr bead ask --run "pack apply google"`, design yardr-bht9: the card carries the declaration's whole text and each command file's bytes). A source grant is a run ask today (2.2). Setting `env_file` and `mint_command` is operator-alone and not a run ask (`sourceSetAsk` in internal/store/sources.go marks only the two per-hour limits askable), setting a source's credential is asked for with a secret ask, and `yardr source check` and `yardr call` are the operator's terminal commands to try a source with; none of the four is a card. The Telegram trial (yardr-b6sq) set that shape: everything that reached the operator reached him as a card, and each step that still needed a terminal was filed as a bead — yardr-0tew is the one it filed for the crew credential.

### 2.6. What is already decided about the edges of this

Three standing decisions bound the design. Integrations are packs and no trick in the core for one product (mem-hz71), so nothing in the proposal names Google, Gmail or gws outside `packs/google`, `packs/google/SETUP.md` and `contrib/google-mint`. Nothing that acts crosses a yard's link — a move, a release, an operator's command, a setting, a secret: each is done in a yard, by an actor of that yard, under that yard's checks — and a secret crosses least of all (design yardr-r6jh, and design yardr-0qs5, which built the secret ask on it). And custody stays "not shown unasked": a value is in the file the server reads and in no note, event, mail, brief or pane (2.1, 2.3). A design that put a second person's login on another machine, or called a source here with a credential kept there, would cross the first of these, so it is not proposed below; section 4 says what is left instead.

## 3. The proposal

### 3.1. In one paragraph

One new word, `--as <user>`, carries the whole design, and it means the same at its three places: whose credential is stored, whose it may be used by, and whose a call is made with. A user's credential for a source lives in that user's env file, under the names the source's declaration names — for the google sources the one mint input `GOOGLE_ACCOUNT`, set once in `~/.yardr/users/<user>.env` and serving all four — written there by a secret ask that names the user, through the same writer that writes the user's address today. A grant gains the word: `yardr source grant google-mail read --crew yardmaster --as mckean` is a grant of that call made with mckean's credential. A call gains it: `yardr call google-mail search --as mckean` is made with the credential in mckean's file, and without it a call is made with the source's own, exactly as today. Each place is carried by a mechanism that exists — the secret ask and its writer for storing, the grant record for who may, and the server's one call path, which changes only which env file it reads the credential from, which grant it holds the caller to, and which user the update call's idempotency key names beside the caller; the mint command, its contract, and the token cache are unchanged, because the mint's inputs are all that differ per user. Who gives each part was decided by mckean on 17 Oct 2026 (section 5): a grant `as` a user is that user's to give, a per-user credential is asked of that user or of the operator for them, and the operator's own `--as` credential is kept apart from the source's, so the operator walks the user flow himself as its first user.

### 3.2. The three holders, one shape for storing and three for using

Per-user is the third holder beside source and crew, and the answer is one model for storing, not one for using, because the three are used in three different places (2.3) and a model that merged them would merge a pane that must hold a token to answer in a thread with a server that must hold none to make a call.

For storing, the model is one: a credential is a set of names from a declaration, a value for each in a file the server alone writes through `config.WriteEnvFile`, and a card that holds the names and never a value. That is what `--secret <source>` does for a source today; yardr-0tew extends it to a crew member, and this design extends it to a user. The three differ only in which file the server chooses — the source's, the crew member's, or the user's — and in the check that says who may give it. A builder who has read one of the three has read the shape of all of them.

For using, the three stay apart. A source's credential is read by the server per `yardr call`, from the source's file. A crew member's is loaded into its pane per start, for `yardr reply` and `yardr thread`. A user's is read by the server per `yardr call --as`, from the user's file, for that one call and kept nowhere, exactly as a source's is. Nothing about the second changes: a crew member that answers in a source still speaks with its own credential, and a call `as` a user is not a way to reply as them. One precedence belongs to the crew alone and does not carry over: a crew member's `env_command` wins over its `env_file` for a name both set (docs/crew.md, "Secrets from a provider"), because both are that crew member's; a user has no `env_command`, so a per-user credential has no second source to win over its file, and the only precedence inside it is the credential's own, mint over static (2.1).

### 3.3. Where a user's credential lives

In the user's env file: `User.EnvFile`, or with none set `<home>/users/<name>.env`, the file `yardr user key` writes today. That file is already "what a source needs of that person, read by the server at each use": it holds a user's address in a source that tells people, and this proposal has it hold that user's credential for a source too, under the names that source's declaration names. Nothing new is set up to hold it: no new setting on `User` or on `Source`, no new file, and no per-source file. Three consequences follow, and the proposal takes all three.

First, one entry serves every source that names the same variable. The four google sources name one mint input, `GOOGLE_ACCOUNT`, so one line in `~/.yardr/users/mckean.env` mints all four as mckean. Where two sources name the same credential variable with different values for one user, they share it in that user's file as they would in the source's (2.5's four sources share one `google.env` the same way): a variable has one value per file, and a service whose sources would disagree must name different variables in its declarations. That is a bound a declaration author already works under for the source's file, and the proposal does not lift it (section 4).

Second, the names a call reads are exactly the names a call reads from the source's file: `Credential.Select`'s precedence, unchanged. Where the user's file sets every name under `mint`, the token is minted from them; one of them alone is refused; otherwise the variable of the call's kind is used as it is set. So a static credential per user is the variable `credential.env` (and `credential.update_env` for an update) in the user's file, and a minted one is its mint inputs with the static variable as the fallback, as today.

Third, a file that is not set is not read, as a source's is not. A user whose record names no `env_file` has no credential per user wherever a file stands at the default path, and the refusal says what gives one (3.6). The server chooses the path, as it does for each holder today: nothing a caller sends is a path.

### 3.4. Giving a user's credential: the secret ask, and the terminal form

The card form:

```text
$ yardr bead ask yardr-k3vd "Your Google account for your mail?" \
    --secret google-mail --as ada \
    --context "The yard will read your Gmail as you when the yardmaster is granted it as you." \
    --context "It is the account address google-mint will mint from: the address alone, no token."
ask 2901 on yardr-k3vd: a secret, GOOGLE_ACCOUNT of the source google-mail, as ada
```

`--as <user>` beside `--secret <source>` is new, and it is deliberately not `--for-user`, whose meaning stands (2.4): `--for-user` asks for the address a source that tells people reads of a user's file, and `--as` asks for the credential a `yardr call` as that user reads of the same file. A source may have both to ask for — Telegram has a bot credential and an address — and the two flags keep the two apart. What the store keeps is `AskSecret` with a new field, `As`, holding the user's name; `User`, `Hook` and `Login` are unset. The names asked for are the ones a call as that user would mint or use, and `--env` narrows them as it does today: every name under `mint` where the credential is minted (`GOOGLE_ACCOUNT` for the google sources), else `credential.env` and `credential.update_env` where it names one. The static variable of a minted credential (`GOOGLE_TOKEN`) may be asked for only when `--env` names it, as today a caller may narrow to any name the declaration has. The card's line, in the yard's words and never the asker's, is:

```text
a secret: GOOGLE_ACCOUNT, ada's own credential for the source google-mail (https://gmail.googleapis.com), read as ada when a call is made --as ada
```

Who the ask is for was decided (section 5, question 4): that user, or the operator for them, as a user's own address is asked for today. The one check `askedSecret` makes of `To` for an `--as` ask is therefore `askedAddress`'s: the named user or the operator may be asked, and nobody else. The refusals are a source the yard does not have, one that names no credential, a user the yard does not have, and a name the declaration does not have. It takes no option, no recommendation and no about-beads, and nothing of it leaves the yard, as every secret ask.

Giving writes into the user's env file through the same writer as `keyUser`, in the same order — the checks, the answer note put and not yet committed, the file written beside itself and renamed last — so the store never says "gave" of a value the file does not hold, and what a commit that fails after the rename leaves is what it leaves of a source's credential (the value in the file, and for a user who had no `env_file` none set still; give it again, and it ends as one giving that worked). The writer is `keyUser` itself, grown to take which set of names a giving is for: the one its `notify` names for an address, or the credential's (its `Variables`, narrowed by the ask) for a credential, with no `notify` required in the second case, since a source that can be called `as` a user need tell nobody. It records the answer under the same sentence form either way, `ada gave GOOGLE_ACCOUNT for the source google-mail, as ada`. The value is in the file and nowhere else, as every giving's is.

The terminal form is the same giving typed, for an operator setting up a source they hold the account of, and for a script:

```text
$ yardr source key google-mail --as ada
GOOGLE_ACCOUNT for ada's credential for the source google-mail (nothing is shown as you type):
ada gave GOOGLE_ACCOUNT · it is set in ~/.yardr/users/ada.env · yardr source check google-mail --as ada
```

It is `yardr source key` with `--as <user>`: the names are the credential's as above (with `NAME`s on the command narrowing, as today), the value is read without echo or as `NAME=value` lines on standard input, and `KeySource`'s place is taken by the grown `keyUser` write through a new store call beside `KeyUser`. `yardr source key <name>` without `--as` is unchanged. No new command is proposed for setting the file's path: `yardr user set <user> env_file=<file>` names a file a person keeps themselves, as it does for the address today, and the yard chooses the default where none is named.

### 3.5. A mint per user

The mint needs no change of contract, of command or of cache: only of which file its inputs are read from. `SelectCredential` already returns the mint's inputs without running anything, and `Mint` already mints from inputs it is handed and caches by a hash of them, so two users' `GOOGLE_ACCOUNT`s mint two tokens and never share a cached one. What is new is that `CallSource` (3.7) selects from the user's file where `--as` names one. The token is handed to the call under `credential.env` and kept in memory alone, per call, as today.

What differs per service is how its mint command finds that user's login, and that stays the service's, outside product code. For gws it is the config directory: gws reads one login from `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` where that variable is set, else `~/.config/gws` (2.1). `contrib/google-mint` today sets no directory and so always mints the default login, refusing another account. The proposal changes only that script: where the account it is given is the default login's, it runs gws as today; where it is not, it runs its `gws auth status` and `gws auth export --unmasked` with `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` set by the script itself, for that run of gws alone, to that account's directory, and refuses where that directory holds no login or one for another account, saying which account it looked for and the command that makes its login. That variable is the script's own setting for the program it starts, not a name under `credential.mint`: it is never declared in a source file, never read from an env file, and never an input `Mint` is handed, so `Credential.Select` in internal/source/mint.go — which, once any name under `mint` is set in a file, requires every name there and refuses a file that sets one alone — is untouched, and no file that is complete today becomes incomplete. The one input stays `GOOGLE_ACCOUNT`, in the source's file for the yard's own account and in a user's file for theirs, and each of the two is given exactly as it is given today, by the card or the terminal form of 3.4 for a user and by `yardr source key` for the source — neither gains a second name to give, and nothing already set up is asked again. Where that account's directory stands was decided (section 5, question 2): beside gws's own login, at `~/.config/gws-accounts/<account>`, derived by the script from the account it is given. That place is the google pack's to declare, not a yardr-wide rule: it lives in `contrib/google-mint` and `packs/google/SETUP.md`, and another service's mint names its own. It changes no declaration. Nothing in yardr's core depends on it, and `google-mint`'s answer is the same `{token, expires_at}` either way, with the refresh credentials held in its memory alone and never printed, as today.

Where the second login comes from is therefore one interactive step per user, done once on this machine: a login made with that account's directory, in a browser, as section 3.8 lists. A person who is not on this machine cannot do it here, and this design puts nothing of theirs here: see section 4 and question 3 in section 5. The scopes their login must hold are the four the pack already lists (`gmail.modify`, `drive`, `documents`, `presentations`), and a login without one answers 403 on the calls that need it, as the one login does today.

### 3.6. The grant

```text
$ yardr source grant google-mail read --crew yardmaster --as ada
crew member yardmaster may call google-mail as ada: read

$ yardr source grant google-mail draft --crew yardmaster --as ada
crew member yardmaster may call google-mail as ada: read, draft (update)
```

`SourceGrant` gains one field, `As`, a user's name, empty for every grant given before and for every plain grant still. The bucket key does not change for a plain grant: a grant with `As` empty keeps the key it has today, `Grantee.key(src)` in internal/store/sourcecalls.go, `<source>\x00group|crew\x00<name>`, and its stored record gains no new key and needs no migration — the new `As` field reads as empty in a record written before it. Only a grant with `As` set appends it, `<source>\x00group|crew\x00<name>\x00<as>`, so a grantee's grant `as` one user and its grant as another are two records, and `read` `as ada` is covered by nothing else. `grantSource` and `RevokeSource`, which today load and delete by `to.key(src)` alone, take the key from the grant they are writing or removing — the old key when `As` is empty, the appended key when it is not — and `grantsOf`, which scans the prefix `<source>\x00`, already reaches both kinds, as does `dropSourceRecords`, which deletes by that prefix when a source is removed. A persisted-store regression holds this: a store holding a plain grant under its old key and old record, reopened on the new code, still shows that grant covering its plain call, and granting and revoking plainly still address that same record, while a new `as` grant is a second record beside it. Granting the same word twice for the same grantee and the same `as` is the one record, as today. `Covers` holds a call when the grant's calls cover it and the grant's `As` is the call's `As`: a plain grant covers a plain call and no `as` call, and an `as` grant covers that user's calls and no other. `read` still covers every read call the source is later given — `as` that user — and an update is still granted by its name alone. The hourly limits keep their numbers (60 calls, 10 of them updates) and their counting: per caller, as today (section 5, question 5), so a crew member's calls plain and `as` any number of users share the one budget and the count's key is unchanged.

Giving and taking back take the word in the same place: `yardr source grant <source> read|<call> --crew|--group <who> [--as <user>]`, and `yardr source revoke <source> read|<call> --crew|--group <who> [--as <user>]` takes back by the same words, and anyone may take one back, as anyone may narrow a grant today. Revoking a grant stops the next call: the grant is checked before any credential is read, so a token already minted in memory is not reached. The run ask takes the word too: the row's use line becomes `yardr source grant <source> read|<call> --group <group>|--crew <crew member> [--as <user>]`, its card names the user beside the grantee — "crew member yardmaster may make read of the source google-mail as ada: it reads ada's mail with the credential in ada's env file" — and the approval is held, as every grant approval is, to the declaration, the source's `env_file` and `mint_command` as they stood, and to each group, crew member and user as they were. Who gives an `as` grant was decided (section 5, question 1): the user whose credential it is, and nobody else — "you as a user will trust the system more" (mckean). The check stands in `checkGrantSource` beside the plain grant's: a plain grant keeps `maySource` (the operator), and a grant with `As` set instead requires the actor to be that user. In practice the user gives it on a card: the source-grant run ask with `--as <user>` is addressed to that user and is theirs to approve, as a `user set tell=` run ask is that user's today ("this command is ada's to approve"), and the yard runs it as the one who approves, so the check passes on the approver's name. The operator cannot give an `as` grant, at a terminal or by approving the card for them: a typed `yardr source grant … --as ada` by the operator is refused with the card that asks ada. Taking one back stays as narrowing a grant stays: anyone may revoke, the user included, and the card's "back" line is the revoke command with `--as`.

Seen where grants are seen today, with the word said:

```text
$ yardr source show google-mail
google-mail  https://gmail.googleapis.com
  credential: GOOGLE_ACCOUNT is set in ~/.yardr/sources/google.env, minted with /Users/me/bin/google-mint
  credential as ada: GOOGLE_ACCOUNT is set in ~/.yardr/users/ada.env
  call search  read  GET /gmail/v1/users/me/messages
    may be called by crew member yardmaster, crew member yardmaster as ada
  call draft  update  POST /gmail/v1/users/me/drafts
    may be called by crew member yardmaster as ada

$ yardr crew show yardmaster
  may call google-mail: search, message, thread
  may call google-mail as ada: search, message, thread, draft (update)
```

`yardr source show` reads each user's file only for whether the names are set, as it reads the source's, and never a value; a user with no file, or a file without the names, is said so with the command that gives one. `yardr group list`'s `CALLS` column says the same for a group, `google-mail as ada: read`, and `yardr user show ada` gains one line naming which of the yard's sources hold a credential of hers, by name — never the value, and never the account, which is in her file and not yardr's to print. Removing a source removes its `as` grants with its plain ones (`dropSourceRecords`). Removing a user (2.3: theirs alone to ask for, the operator's to do) removes more than the refusal a missing record would give on its own, because a name is reusable: a user added again under the same name (internal/store/users_test.go holds that a second user of a name starts with none of the first's mail) must not find the first's access waiting. So `deleteUser` in internal/store/users.go first works out the one file it would have to clear, and refuses the removal whole where clearing it would take another user's credential or address with it. That file is the user's effective file: `User.EnvFile` where the record names one, and otherwise the yard's default `userEnvFile(home, name)` where the yard chooses one for the name; a user whose name carries a path separator and who names no file has no file to clear, and only their grants and record go. Before any grant is deleted and before the file is touched, `deleteUser` compares that file's resolved path with the effective file of every other user, worked out by the same rule. A resolved path is `config.ExpandPath`'s — a leading `~/` made the home and the result made absolute and cleaned — with a symbolic link evaluated where the file stands, so `~/users/ada.env`, its absolute spelling and a link to it count as the one file; the comparison is on the records, whether the file stands today or not. This catches a sharing the stored strings do not show: one user's custom `env_file` pointing at another's default, as well as two custom spellings of one file. Today nothing refuses that sharing — `SetUser` in internal/store/usernotify.go stores `env_file` as given, and the command in internal/cli/users.go checks only that the file can be read — and this proposal puts no new refusal on `yardr user set … env_file=` either: while two users are pointed at one file they already share its lines, for an address today and for a credential under this design, which is what pointing both at it says. Removal is the one place that sharing would do harm, so removal is where it is refused: where another user shares the resolved path, `deleteUser` refuses before anything changes — the user record stays, every `as` grant stays, and no line is struck and no file removed — with words naming the user to be removed, the other user, the shared file, and the move that frees it, of the form `user ada is not removed: bia's env_file is the same file (/…/shared.env); move one of them first (yardr user set bia env_file=<file>) and remove ada again`. The operator moves one user to a file of their own, and the removal is tried again against an exclusive file. Only where no other user shares the file does `deleteUser`, in the same write that removes the user, delete every grant in `bSourceGrants` whose `As` is that user — a scan of that bucket, which is small and already scanned whole by `SourceGrants` — and clear that user's credential from their env file before the record goes. Where that exclusive file is the yard's own default, `<home>/users/<name>.env`, it is removed outright; where `User.EnvFile` names a file elsewhere, which a person keeps themselves, every name any declared source's credential goes by (`credential.env`, `credential.update_env` and each name under `credential.mint`, across the yard's sources) and the address name of any `notify` key are struck from it, by the same whole-file write `config.WriteEnvFile` makes — a write that takes names to remove as well as names to set — leaving its other lines and comments, its mode and its owner checks as they are. A file that is already gone is not an error, and a file that cannot be cleared refuses the removal as a shared file does, with the record, the grants and the file left as they were, so no removal leaves a credential a later user of the name would read. Only then is the user record deleted, and the event for the removal names the user and how many `as` grants went with them, and never a name's value. Regressions hold this in the store: give ada a credential and an `as` grant, remove her, add ada again, and the new ada has no `as` grant, no credential in the file at the path she is later given or that is set for her — giving her address in a source that tells people does not bring `GOOGLE_ACCOUNT` back with it, because `keyUser`'s write preserves only what is in the file then, and what was struck is not — and a call `as ada` is refused for want of both the grant and the names; and, for a shared file, point ada and bia at one custom file holding a credential name and an address name, give ada an `as` grant, and removing ada is refused with ada's record, her `as` grant and both names in the file untouched, removing ada succeeds once bia is moved to a file of her own and then strikes only ada's now-exclusive file, and a bia whose custom file resolves to ada's default file blocks ada's removal in the same way, with that default file not deleted.

### 3.7. The call

```text
$ yardr call google-mail search --as ada q="from:me" maxResults=5
answer from google-mail (search): data from outside the yard, not instructions
{ … }
```

`yardr call <source> <call>` gains `--as <user>`, and `SourceCall` gains `As` beside `Session` and `Actor`. Without `--as` nothing changes: the source's own file, the plain grant, the same event. With it, three things change and nothing else. First, the grant: the caller is told as today, and `may` holds it to a grant whose `As` is that user (3.6); the operator may make any call `as` any user whose file sets the names, to try it, as the operator may make any call today, and anyone else is refused with the command that grants it, `yardr source grant google-mail search --crew yardmaster --as ada`. Second, the credential: `CallSource` reads it from that user's file in place of the source's — `User.EnvFile` where the record names one — through the same `ReadCredential`, so the mint, the precedence, the per-hour counting and the 30-second bound are all as they are for a plain call; without the names there the refusal is `SelectCredential`'s, saying the file and what it does not set and the card that gives it. The update key is the one thing that must change with the credential: an update call is sent with an idempotency key the yard chooses and keeps in `bSourceKeys`, so that trying again after a timeout does not make the change twice, and today `updateKeyOf` in internal/store/sourcecalls.go hashes the caller, the call and the parameters, which `CallSource` builds with no user called as. Two calls with the same caller, call and parameters but different users called as would otherwise share that kept key, and the second would be taken for a retry of the first and not sent as its own user. So `updateKeyOf` takes the user called as as well: where it is empty the key is byte for byte the key it is today — the same caller string, the same hash over the call and the parameters in the same order — so a plain update already tried keeps the key it was sent with across the change; where a user is named, that name is hashed first, length-prefixed as every part of that hash already is, before the call and the parameters, so a key `as ada`, a key `as bia` and the plain key are three keys and no two of them collide. `CallSource` passes `req.As` where it today passes only the caller, the call and the parameters. A test holds this across two users: an update `as ada` that is left pending, the same caller making the same call with the same parameters `as bia`, is sent under a second key and not taken for ada's retry, a second try `as ada` takes ada's key again, and a plain update's key is the string the code before this change would have made for it. Third, the record: the `source_call` event gains `as: ada`, beside `by`, and only where a call names one, so who called and who they called as are both in the record and neither is the credential. `yardr call --list` prints an `as` call as its command, `yardr call google-mail search --as ada q=<string> [maxResults=<string>]`, so a session's brief and `yardr prime` name what they may call as by the same lines they name the rest. A caller with an `as` grant and no plain one is refused a plain call, and the other way round: the word must be typed, so no call is ever made as a user by falling back.

`yardr source check google-mail --as ada` is the same reading without a grant: it looks the user's credential over as `check` looks the source's, and makes the source's check call with it where the file names one, saying it was made as ada. It is the operator's, as `check` is.

Two things the earlier draft left implicit are said out loud here. A person must already be a user of the yard before anything can be asked of them or granted as them — `--secret … --as ada` and `source grant … --as ada` both refuse a name the yard has no user for — so adding the user comes first, and it is a card: `yardr user add <name>` is a run ask today (2.4's list in internal/store/runask_more.go). And no source is pointed at a shared file by a card: `yardr source key` chooses and records a per-source default, `<home>/sources/<name>.env`, where a source names no `env_file` (internal/store/sources.go), and setting `env_file` stays the operator's typed setting, so the card way below gives each source its own file and its own card, and the shared `~/.yardr/sources/google.env` of today's SETUP.md becomes the typed way beside it, not the way the cards take.

## 4. Left out

**Calling a source here with a credential kept on another machine.** A person on another machine has their own yard, and a call in this yard reads a file in this yard's home (2.6). Routing a `yardr call --as <user>` to their yard over a peer link, and bringing the answer back, would send a command to act across a link, which a standing decision forbids, and would put the answer in two yards' records. The way to the same end today is mail: the crew member asks that person, in their yard, to read the thing there. This was settled without an ask (section 5, question 3): cross-yard execution stays out, and a narrower form would be a design of its own if a person with a second yard ever wants it.

**The crew member's credential, and any change to it.** yardr-0tew carries it, in build, and this design adds nothing to it: not its card (which is that bead's `--for-crew`), not whether its approval restarts the crew member, and not a way to call `reply` or `thread` as a user, which would be a credential in a pane that must not hold one of a person's. A crew member speaks in a thread with its own credential before this design and after it.

**A per-source-per-user file, or more than one value of a name for one user.** One user's file holds one `GOOGLE_ACCOUNT`, one `CRM_TOKEN`. A service that needs two accounts of one person at one source, or two values of one variable at two sources, names different variables in its declarations or is not served per-user (3.3). A directory of files per user and source would need its own naming, its own writer and its own showing in `source show`, for a case no source in the yard has.

**Several accounts of one user, and a user calling `as` themself.** One `As` names one user and that user has one credential per source (3.3). A person who runs yardr with their own name is not a `yardr call` caller today (a caller is a session, a crew member or the operator, 2.2), and this design does not make them one: they give their credential and are called as, they do not call.

**Naming the account, or the login directory, in the store or a declaration.** `GOOGLE_ACCOUNT`'s value is the address of the account whose mail would be read, and it is kept in the file with the rest of the credential. A setting that named it would print it in `source show`, `events` and backups, and a declaration key for gws's directory would put one service's layout in the format every service is declared in (2.6). `source show` says the names are set, and `google-mint` refuses a login for another account by name in its error, which is where the address is needed and the one place it is said.

**Work around it, also left out:** no per-user `calls_per_hour` or `updates_per_hour` settings (the limits stay the source's, counted per caller as decided), no expiry shown beside `credential as <user>` beyond what a `check --as` mints to say, no eviction of a minted token from the server's cache when a grant is revoked or a file rewritten (the grant is checked before the mint is reached, and a changed account hashes to a new cache entry; a rewritten login's own token cache is gws's, read at the next mint after the cached token's life), and no copy of the source's existing value into a user's file instead of typing it again, which yardr-0tew also leaves out: one file feeding another is a second change.

## 5. Open questions, as decided

Each of these was mckean's to decide, and each became its own `yardr bead ask` on this bead, as mem-xyzn holds. All were answered on 17 Oct 2026 (asks 6534–6538); the answers are recorded here and are already folded into section 3 above, so nothing in this section is still open. Question 3 was settled without an ask, by the standing decision of 2.6, as the critique noted.

1. **Who may give a grant `as` a user?** Decided (ask 6534): **the user whose credential it is** — "I like the idea of this with multiplayer, meaning you as a user will trust the system more" (mckean). Not the operator, and not either. This costs the second approval path named when the question was asked: an `--as` grant card sits in that user's decisions, and the operator cannot approve it for them (3.6). The plainer rule (the operator alone, as every grant today) was the recommended answer and was not taken; it can still not be added later without changing who may give, so builders should not leave an operator leg in `checkGrantSource` for `As` grants. That refusal guards against mistakes, not against intent, like the yard's other operator rules: outside a pane the actor is the caller's word (`notOperator` in `internal/store/users.go`), so a terminal that claims the user's name satisfies the check, and on one machine the operator can read every user's credential file anyway.
2. **Where does a second person's gws login live on this machine?** Decided (ask 6535): **beside gws's own login, `~/.config/gws-accounts/<account>`** — with mckean's gloss that "how this is handled can be part of the pack". So the place is declared by the google pack (in `contrib/google-mint` and its SETUP.md), not by a yardr-wide rule, and no name is added under `credential.mint` or to any env file: the script sets `GOOGLE_WORKSPACE_CLI_CONFIG_DIR` for the gws it starts, and a file holding only `GOOGLE_ACCOUNT` stays complete (3.5). A yard backup therefore does not carry a second person's refresh token.
3. **Is a person on another machine in scope at all?** Settled, no ask: **no.** A user with no login on this machine cannot be called as here, and the refusal says so (section 4). Anything narrower would be a design of its own against the standing decision of 2.6, filed only when a person with a second yard wants it.
4. **Who is a per-user credential asked of?** Decided (ask 6536): **that user, or the operator for them**, as a user's own address is asked for today (`askedAddress`, 3.4).
5. **Are the hourly limits per caller, or per caller and `as`?** Decided (ask 6537): **per caller.** A crew member's 60 calls an hour are all it has however it calls; the count's key is unchanged (3.6).
6. **The operator called as: the source's credential, or a separate user one?** Raised by the critique and decided (ask 6538): **keep them apart** — "cleaner, and we can go through the flow" (mckean). `--as mckean` reads the operator's user file and its own login, set up by the same cards as any user's (3.8); the source's credential never stands for the operator as a user, even though today it is the same person and the same account.

## 6. The beads it would become

### B1. A user's credential for a source, given on a card (`--secret <source> --as <user>`)

Goal: `yardr bead ask --secret <source> --as <user>` asks for the names a call as that user reads, asked of that user or of the operator for them as decided (question 4, `askedAddress`'s check), and `GiveSecret` writes them into that user's env file holding names, never values; `yardr source key <source> --as <user>` is the same giving typed. New `AskSecret.As`, `keyUser` grown to take which set of names a giving is for, the card line and the refusal set of 3.4.
