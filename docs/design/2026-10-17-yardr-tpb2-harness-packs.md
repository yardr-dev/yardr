# A harness is a pack kind, imported and updated like a source pack

Design yardr-tpb2, proposed 2026-10-17. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A **harness** is the agent program yardr starts in a pane (Claude Code, Codex, Kimi); its **kind** is the name herdr starts it by (`claude`). What yardr knows of a kind beyond what herdr knows is kept in one file per kind, `harnesses/<kind>.yaml` — the **harness file**. A **pack** is a way of working as one directory, imported into a depot or into the yard itself (`yardr pack apply`, docs/packs.md); a pack yardr ships inside its binary is a **built-in** pack, as telegram is. The **operator** is the person who runs the yard. In this document **the card** is the plan `yardr pack check` prints and `yardr pack apply` asks to confirm, and **an override** is a yard's own import of a harness pack where the binary already carries one for the kind.

## 1. The question

mckean, 17 Oct 2026 (pane): "the yardr/harness mapping must be kept up to date; externalize it as a pack or another primitive, so it is easy to update for harness changes, to hold mappings for several versions of a harness, and to add new harnesses." Today the mapping ships inside the yardr binary: changing it for a harness's new version means editing `harnesses/<kind>.yaml` and cutting a yardr build, and a yard cannot add a kind yardr has no file for or correct one it has. The question is whether a pack can carry the harness file as it carries a source's declaration, what the card must show for a file that decides which keys yardr types into agents' panes and which flags agents start with, how one file serves several versions of a harness, how a yard learns a newer harness pack exists, and what adding a new harness still needs in code.

## 2. What exists today

### 2.1. The harness files and their one reader

`harnesses/<kind>.yaml` — seven kinds today (claude, codex, grok, kimi, muse, opencode, pi) — is embedded in the binary (`harnesses/harnesses.go`, `//go:embed *.yaml`) and read once at process start into the package global `agents.Harnesses` (`internal/agents/harness.go:298`), which panics on a file that does not parse, "a fault of the build, which TestHarnessFiles finds". `Load` (harness.go:343) takes any `fs.FS`, decodes with `KnownFields(true)` — a key the struct has no field for is an error — and runs `check()` (harness.go:389), which refuses a file whose `version` is not `FileVersion` (1), whose kind is no kind herdr starts (`IsKind`, harness.go:393), or whose fields are half given. The struct `Harness` (harness.go:33) holds: `label`, `provider`, `aliases`, `install` (printed, never run), `fetch` (one file of one version at its maker's address with its sha256; printed, never fetched by yardr — for a program that fetches), `trust` (the folder-trust dialog yardr answers: `dialog`, `answer`, `cursor`), `marks` (what its pane is read by), `flags` (`model`, `unattended`, `version`, `one_shot`, `always`, and `permissions`, the named flag sets a person picks from), `offers` (models suggested to pick), `model` (where the session's reported model is read), `errors`, `dialogs` (questions it draws in place of its input, told of and never answered — but see 2.2 for one exception), `login` (its login screen's lines), `login_recipe`, `background`, `hints`. `yardr harness list` and `yardr harness show <kind>` print what the files say (internal/cli/harness.go); docs/groups.md, "What yardr knows of a kind", is the field-by-field reference and says outright: "There is one set of files, the one in the binary: a yard cannot add to it or replace one."

### 2.2. Who reads the file, and for what

The herdr runner (internal/runner) answers the trust dialog at agent start and in the dispatcher's later passes (trust.go: `trustEntry` takes the kind's `trust` unless the config says `trust=false`; `acceptTrust` sends `down` at most four times and `enter` only when the screen holds the dialog's text at a line's edge, the accepting answer as an exact line, and the cursor on it — a dialog that changed shape is left for a human). The runner assembles an agent's arguments (herdr.go `agentArgs`, :751): the group's `args`, the file's `flags.always` appended whatever the group says (:756), `{socket}` and `{workdir}` filled in, and the model flag from `flags.model` appended in place of the group's own whenever a model is configured (:785-806). It reads panes by the file's `marks` (herdr_screen.go; the fallback for a kind with no file is the hardcoded `❯`/`›`, herdr_screen.go:46), reports dialogs it finds (herdr_screen.go `InputDialog`, :375 — with one hardcoded exception: a dialog whose word is `auto_mode_setup` is dismissed with Esc, :395), and recognizes the login screen by `login`. The daemon (internal/dispatch) matches a stopped agent's tail against `errors` (`HarnessError`, harness.go:154) and `background`, and reads the model by `model`. The command line offers the file's permission presets in the `group add` form (groupform.go `agentPermissions`), fills `--bind group.args=<label>` from one (`presetArgs`, internal/cli/pack.go:1215), gives the yardmaster `flags.unattended` at `yardr init` (init.go:584), and runs the executable outside a pane by `flags.version` (doctor's probe, needs.go:602) and `flags.one_shot` (doctor's `--try` and the onboarding's one real call, needs.go:500, start.go:258 — both on a person's yes only).

What a file can never say, because it is code and not data: how a kind lists its models (`modelLists`, harness.go:284 — "code, not something a file can say"), the executable's name when it is not the kind (`executables`, models.go:305), the display order and the default kind (`order`, harness.go:312; `DefaultKind`, harness.go:26), the Esc dismissal of the one known dialog (keyed by its word, which a file names), and Kimi's hooks-file parsing (cli/kimihooks.go). A kind herdr starts that has no file is started all the same, as the zero `Harness`: no marks, no error lines, no flags (docs/groups.md).

### 2.3. Packs: kinds, import, the card, the record

A pack is a directory with a `pack.yaml` (internal/pack/pack.go). Its `kind` is a depot kind (`git` or `dir`), `source` (`KindSource`, pack.go:236 — imported into the yard itself, into no depot, carrying sources alone: telegram is the model), or unset. `yardr pack apply <pack>` (internal/cli/pack.go) resolves its argument (`resolvePack`, pack.go:126): a URL is fetched one file at a time (`pack.URLFS`; docs/packs.md:258 gives `https://yardr.dev/packs/starter/` as the shape — a plain static directory, no registry protocol), a path is read as a directory, and a bare word is looked up in the yard's import records first — the record re-read from its recorded `Source`, an embedded one re-read from the current binary — and in the binary's built-ins second (`packs.FS`, packs/packs.go:25: starter, dir, contributors, design, linear, github, google, pushover, telegram). An import record (`store.PackImport`, internal/store/packs.go:26) holds the source, the time, who applied it, and each installed object's sha256; it is what a bare name resolves to, so a yard's import already overrides a built-in pack of the same name. The plan (`pack.Build`) and its printing (`printPlan`, pack.go:1626) are the card: every object with its action and diffs, what the import would ask, and — for a kind-source pack — each declared source with each command file's sha256. `yardr pack show <pack>` prints the pack's setup notes, "from the pack, not checked by yardr". Applying is confirmed in a terminal or given `--yes`; the parts only the operator may grant — adding a source, opening threads, grants, exposure — are refused to anyone else with the reason named and the rest of the import done (pack.go:743-774). A file edited by hand since the last import is not overwritten without `--yes` (`EditedFiles`). Since design yardr-bht9 landed, `yardr pack apply <name>` of a built-in pack whose plan asks nothing can also be proposed as a run ask and approved on a card (`internal/store/runask_pack.go`), held to the build and the carded bytes; every other form of the command stays "the operator's alone, typed in a terminal".

There is no update mechanism for any pack: no version check, no registry, no `pack update`. A re-apply of a name re-reads its recorded source or the current binary, and the plan shows what changed as `old -> new` diffs and changed sha256s. Hosted yards (design yardr-bwm2, docs/design/2026-10-14-yardr-bwm2-hosted-v0.md) receive a new yardr by deploy: the container image is rebuilt and recreated, or `yardr upgrade` runs on the droplet with the release archive from yardr.dev.

The public pack directories are copied by yardr.dev's `scripts/sync-packs`, which takes a yardr checkout and rewrites `public/packs/` and the site's pack catalog. Its `PACKS` list names seven packs today, not the harnesses, and it accepts a flowless pack only when its kind is `source`. The pack index (`src/pages/packs/index.astro`) treats every other kind as a flow pack and reads its first flow; the detail page (`src/pages/packs/[name].astro`) gives every non-source pack a depot import; and `src/lib/packs.ts` requires a one-line description per listed pack. The release flow makes a GitHub release from the release bead's body, and its publish stage (`contrib/release/stage`) files a yardr.dev bead for `scripts/sync-release` alone: release archives, not packs. Thus neither editing a pack nor cutting a release currently publishes a changed pack at its yardr.dev address.

## 3. The proposal

### 3.1. In one paragraph

A harness file becomes a pack of a new kind, `harness`: one pack per kind, named as the kind, carrying today's file unchanged. The seven files move from `harnesses/` into `packs/<kind>/` and become built-in packs exactly as telegram is a built-in pack: embedded, importable by name, and overridable. A yard's own `yardr pack apply claude` from a directory or a URL records the import, and the yard reads the import before the built-in, as a bare pack name already does. One security boundary qualifies the override: fields that make yardr act without a fresh choice by a person — today `trust`, which types an answer, and `flags.always`, which adds arguments to every agent — always come from the reviewed built-in, never from imported bytes. An import that tries to change either is refused; a new kind has neither behavior until a yardr release adds it. Every other field overrides whole. Applying is the operator's alone, in a terminal, on a card that inventories every dialog yardr answers and every harness-controlled argument yardr passes to the executable, then shows the import's diff against the built-in. The installed file is read only at the sha256 the import recorded. Several versions of a harness are served by tolerant lists rather than version-keyed sections. A changed pack is announced in the release notes and published at its yardr.dev address by the release's site-sync step; a yard whose import differs from the build's built-in is told so by `yardr harness list` and doctor. A yard with no override rides each yardr build, and a hosted yard rides each deploy. Adding a harness for a kind herdr already starts takes a pack alone for its passive and person-chosen behavior; automatic trust answers, implicit arguments, and the behavior that is code today still take code.

### 3.2. The pack and its file

A pack of kind harness is one directory:

```text
packs/claude/
  pack.yaml      # name: claude · kind: harness · harness: claude.yaml
  claude.yaml    # today's harnesses/claude.yaml, comments and all
```

`pack.yaml` names its one harness file under a `harness` key (the reader's file glob cannot be reused as is: `Load` reads every `*.yaml` it finds, and would read `pack.yaml` itself). The file is today's format, `version: 1`, checked by the same rules a built-in is checked by; 3.4 adds the import's two build-pinned fields. A kind harness pack carries nothing else: no flows, groups, crew or sources — as a kind-source pack carries sources alone, this kind carries one harness file alone — and it imports into the yard, into no depot. The `harnesses/` directory and package go away; `packs.FS` gains the seven kinds, and the built-in harness set is `Load` over each embedded pack's directory. Everything that pins the embedded packs — the docs table test, the consistency tests, the run-ask card's embedded-only rule — covers them from then on, and the harness-specific golden tests (`TestHarnessFiles`, the docs tables of internal/agents) move to the packs' new home unchanged in what they assert.

`yardr pack apply claude` on a yard with no import of it imports the built-in and changes nothing the yard reads — the record is what later overrides and drift reports hang from. `yardr pack apply ./claude/` or a URL imports that file instead. `yardr pack list` shows harness imports among the records; `yardr pack show claude` prints setup notes as for any pack — a harness pack carries none. `yardr harness show claude` stays the reader of the effective file and gains lines naming the import's source and date and saying that `trust` and `flags.always`, where present, come from the build.

### 3.3. The card

`yardr pack check claude` prints, and `yardr pack apply claude` asks to confirm, a card with two parts. The first is the **complete effective behavior**, including unchanged fields, so no dialog or argument is hidden by a diff summary:

- the kind, its label, provider, aliases, file version, and where the pack came from;
- **every dialog yardr answers**: the folder-trust dialog's three strings whole — the text that marks it, the exact answer typed, the cursor — or that it answers none, each marked `from the build`; every entry in `dialogs` and `login` is also shown and marked as reported, never answered, as is the hardcoded Esc dismissal of `auto_mode_setup`;
- **every harness-controlled argument yardr passes to the harness's executable**, grouped by the command that uses it: `flags.always` whole for every agent (marked `from the build`), `flags.model` for a configured model, `flags.unattended` whole for `yardr init` and the forms, every permission preset with its label, arguments and description, `flags.version` for doctor's probe, `flags.one_shot` for doctor's `--try` and onboarding's permitted real call, and `login_recipe.argv` plus every login method's label and arguments for `yardr harness login`;
- `fetch` whole: `verified.from` and `verified.on`, `version`, destination `path`, installer `run` arguments, and every operating-system/architecture target's `url`, `sha256`, `size` and optional archive `member`;
- the rest of the file whole: `install`; `login_recipe`'s verification, `open_url` and `input`; the error lines with their reasons, the background lines, marks, model source, offers and hints.

The second part, for a kind the build already carries, is the **diff against the built-in**, field by field, `old -> new` as `printPlan` already renders a changed object. For a new kind it is the whole candidate. A difference in `trust` or `flags.always` is not an applyable card: `pack check` refuses it and prints that difference with the build-pinned rule. Thus the card discloses even behavior that is unchanged, and a permitted change cannot hide inside a file the operator is assumed to know.

A harness pack is never on the run-ask list: `yardr pack apply <name>` stays askable for the packs yardr-bht9 admitted, and a kind harness pack keeps the refusal "the operator's alone, typed in a terminal". Open question 3 asks whether that holds for good.

### 3.4. What an imported harness pack may never do, and what enforces it

The security boundary is between the reviewed built-in bytes in the binary and bytes a yard imports. A release can already change both code and built-in data; an import must not acquire the same authority. The general rule is that **a field that acts without a fresh choice by a person is build-pinned**. Today those fields are `trust` and `flags.always`; a future field of that kind joins the same rule rather than acquiring a special case of its own. The concrete nevers are:

- **An import never supplies an answer to a permission prompt, or to any other dialog.** `internal/runner/trust.go` takes `trust` only from the built-in for the kind. For an override to be valid its `trust` must repeat the built-in's three strings exactly, but even then the runner reads the built-in's copy, not the import's; a new kind with no built-in must have no `trust`. The import check rejects any other value, and the effective-set check rejects it again rather than activating it. Consequently arbitrary imported strings never reach `trustAnswer` or `acceptTrust`: an import cannot name an MCP-server approval, a tool-permission prompt, or a lookalike at first start. Only the built-in's reviewed folder-trust entry retains today's exact screen match and `down`/`enter` behavior. The dispatcher's pre-work window remains useful defense in depth, but it is **not** the permission-prompt wall and this design does not claim that it is. Every other dialog is still reported and left for a person; the one hardcoded Esc dismissal is unchanged. Open question 1 asks whether this build-pinned cost is acceptable.
- **An import never adds an implicit argument, widening or otherwise.** `flags.always` is also taken only from the built-in: an override must repeat that argument sequence exactly, and a new kind must have an empty one. This needs no classification of a future flag's meaning — an unknown argument is refused precisely because it is new to the built-in. As a check on the reviewed built-ins themselves, `Harness.check` also refuses an `always` argument repeated in that built-in's `unattended` or permission presets, the arguments yardr already knows make an agent ask less. `unattended` remains something a person sees at init or in `group add`, and a permission preset takes effect only where a person picks it. The card discloses those choices; no pack selects one.
- **A harness file never names an arbitrary program or file for yardr to run.** The schema has no such field: `install` is printed and never run, `fetch` is data for a separate fetching program and is never fetched or run by yardr, and the decoder refuses every key the struct does not know. The login recipe can add arguments only to the harness executable that a person explicitly asks `yardr harness login` to start.
- **Applying a harness pack is the operator's, whole.** Today's packs let anyone apply and skip the operator-only parts; a harness pack has no safe remainder, so the store refuses the import to anyone but the operator, as `maySource` refuses a source, with the operator named.
- **What is in effect is what was carded.** The installed copy supplies the overridable fields only at the sha256 the import record holds; the current build supplies the two build-pinned fields, as the card says. A copy edited by hand since is no override — the built-in serves, and the yard tells of it (an event, a doctor fault, the mark in `yardr harness list`). A re-apply over a hand-edited copy keeps today's `--yes` rule. A record from a URL or directory is re-read from its source on re-apply, as every pack's is; the record's hashes are what the yard runs meanwhile.

### 3.5. The effective harness set

The package global that panics at process start does not survive a yard being able to override a file: a bad override cannot be a build fault. `agents.Load` stays pure — it takes an `fs.FS` today — and the effective set is built one level up, where the yard's home and store are in reach (internal/agents must stay below the store: the store already imports it for `IsKind`). The rule is the pack system's own with 3.4's security qualification: the yard's import of a kind wins for every overridable field; the current built-in supplies `trust` and `flags.always`; otherwise the whole built-in serves; a kind with neither is the zero `Harness`, as today. Thus a deploy can correct the build-pinned behavior even while an older override supplies the passive mappings. An override whose installed file fails the harness checks, changes either build-pinned field, or whose bytes are not the record's sha256 is refused as 3.4 says — the built-in serves and the yard tells of it; it is never half read, and no process panics on it. Readers that run with no yard at all — `yardr harness list` and doctor on a home with no yard are in the no-onboarding set — read the built-ins, as today. `yardr harness list` gains, per kind, the file's source and drift: `from pack claude, imported 17 Oct from ./claude/`, and where the build's built-in differs from the yard's, `the build carries a different claude: yardr pack check claude shows what would change`. Doctor repeats that local comparison; the release notes of 3.6 are what announce a change to someone who never runs either command.

### 3.6. Versions and updates

**Several versions of one harness are one file's lists, not one file per version.** The file's idiom is already tolerant: `errors`, `dialogs`, `login` and `background` are lists of patterns tried in order, so a file serves every harness version that prints any of its lines; `offers` is a suggestion, not a check, and a wrong model id fails loudly at the first session; `flags.version` drives doctor's probe rather than a comparison. `fetch` is the place a version is unavoidable: it pins the newest verified release's bytes to a sha256, and an older harness installed by hand is unaffected. Where tolerance breaks for an overridable field is `marks`: single strings a harness version could change incompatibly. Follow the patterns' precedent when that happens — the field gains alternates rather than version-keyed sections, and the runner matches whichever the pane shows. `trust` can gain the same alternates only in a built-in, because it is build-pinned; a version that needs different `flags.always` also needs a built-in change. A version key would be forced only by a change no list can hold — other flags that differ per version, say — and that is a `version: 2` of the file format, `FileVersion`'s existing seam, not this design's. See section 4.

**How a yard learns a newer harness pack exists, and where the manual file comes from.** Nothing polls. The release flow cuts a GitHub release whose notes are the release bead's body (contrib/release/stage, the build stage), and a harness fix too urgent for the next feature release is cut as a patch release whose notes say what changed. The release's publish stage gains a second site bead beside today's `sync-release` bead: it asks yardr.dev to run `scripts/sync-packs` from a clean checkout at that release's tag. B4 makes that script copy the seven harness packs and the pack pages accept their flowless kind; B5 wires the release step. When that site bead lands and deploys, `https://yardr.dev/packs/claude/` and its peers serve the files from the release the notes name. The stable address is therefore a real manual update source, not a claim that copying a file notifies anyone. An operator who reads the notes can run `yardr pack check https://yardr.dev/packs/claude/` and then apply that URL without upgrading yardr. A yard with no override instead rides the build — `yardr upgrade`, or a hosted yard's deploy — and a yard with an override sees the drift line and can re-base from the new built-in. Open question 2 asks whether this discovery story is enough.

**A new harness by pack alone.** The gate stays herdr's: `check()` refuses a file whose kind herdr does not start, so a pack can teach yardr a kind from the twenty-four herdr knows (`HerdrKinds`, models.go:22) that yardr has no file for — write the file, apply the pack, and the kind has marks, person-chosen flags, error lines and offers with no yardr build. It has no automatic trust answer or implicit `always` argument. What still takes code is a built-in change for either of those automatic behaviors, and what is code today: a kind herdr does not start (herdr's to learn); listing the kind's models (`modelLists`); an executable named other than the kind (`executables`); a place in the display order; kind-specific reading like Kimi's hooks file; and the golden tests and doc tables that enumerate kinds by name.

## 4. Left out

- **Version-keyed sections of the file format** (a `versions:` map, or one file per harness version). Tolerant lists cover the drift yardr has met so far; the seam for the rest is `FileVersion`, and a v2 is designed when a harness forces it, not before.
- **An update command, a check against yardr.dev, or a registry protocol.** No pack has one; release notes announce, the drift line compares, and re-apply updates. A push of "a newer claude pack exists" is a yard phoning home, which yardr does not do.
- **Harness packs on the run-ask list** (the card of yardr-bht9, from a device). Terminal-only at first; open question 3 asks whether for good.
- **A semantic classifier of pane text or harness flags.** Text matching cannot prove that an arbitrary dialog is folder trust rather than an MCP-server or tool-permission approval, and a string yardr has never seen cannot be classified as access-widening or safe. The design therefore build-pins the fields that act without a fresh choice instead of pretending a classifier exists. A learned or crowd-sourced classification would be a registry by another name, with its freshness problems on top.
- **Signed packs or provenance beyond the record.** The record already holds the source and every installed file's sha256; who may vouch for a pack is a question for packs generally, not for this kind.
- **Per-depot or per-group harness files.** One effective file per kind per yard; a group that needs different flags has `args`, as today.
- **Answering any dialog but the built-in's folder-trust one**, and typing into the login screen. Both stay code's refusals, unchanged.
- **Idle, working, blocked, done.** Herdr's to decide from its own files, today and after; no harness file speaks of it.

## 5. Open questions

Each is for mckean at decide, as its own ask on the bead.

**1. Should `trust` stay build-pinned, or may an import supply the keys yardr types?** Option A, build-pinned as proposed: an override must repeat the built-in's `trust`, the runner reads only that built-in value, and a new kind has no automatic answer. The cost is real: a changed folder-trust dialog, and automatic trust for a new kind, still need a yardr release; a URL pack cannot fix that one field between releases. Option B, let an import replace `trust`: folder-trust updates become as easy as the other mappings, but arbitrary strings can match an MCP-server or tool-permission approval even before the first work. The card and operator-only apply disclose that answer; they cannot enforce the bead's "never answer a permission prompt" boundary, so B requires deliberately relaxing that requirement. I would take A: it preserves an enforceable security guarantee, and the release mechanism still delivers the fix to every yard that upgrades or deploys.

**2. Are the release notes and drift line enough for a yard to learn a newer harness pack exists?** Option A, as proposed: the release notes announce a changed pack (a patch release for an urgent one), B4/B5 publish its exact files at the named yardr.dev address, and `yardr harness list` and doctor say when the build's built-in differs from the yard's import. The cost: a yard that never upgrades, never reads the notes and never runs those commands never learns; every yardr release also gains a pack-sync site bead beside its release-archive bead. Option B: a command that fetches yardr.dev's harness packs and says what is newer. The cost: a network fetch on a command's say-so and a version-comparison protocol for harnesses alone. I would take A.

**3. Should a harness pack stay off the run-ask list for good?** Option A, as proposed: applying one is typed in a terminal, where the complete inventory, diff and files stand beside it; the run-ask card admits no harness pack. The cost: an operator with no shell — the hosted case yardr-bht9 answered for source packs — cannot re-base an override from a device; such an operator rides the build's built-ins by deploy and never holds an override, so the cost is nil until a hosted yard wants its own harness file. Option B: admit built-in harness packs to the row, with 3.3's card held to the run-ask bounds, as yardr-bht9 did for packs whose plan asks nothing. The cost: an approval from a phone that steers every agent the yard starts, on a card whose every line must be read. I would take A, and revisit if a hosted yard ever imports one.

## 6. The beads it would become

In safe landing order. B1, B2, B3, B5 and B6 are yardr beads and pass `sh .yardr/test`; B4 is in yardr.dev and passes that depot's test command. B2 depends on B1; B3 depends on B2, so no override becomes effective before the security checks; B4 depends on B1; B5 depends on B4, so the release never files a sync the site cannot perform; B6 is last.

**B1. The pack kind harness, the seven built-ins, and the complete card.** Goal: `kind: harness` exists; a harness pack is one `pack.yaml` (`name` the kind, `harness` its file) and one harness file; the seven files move from `harnesses/` to `packs/<kind>/` unchanged in content and become built-in packs; `yardr pack check` and `yardr pack apply` read, validate, card and record them without making a yard override effective yet; `harnesses.FS` and its package go away and the built-in harness set is read from `packs.FS`. Where to look: `Kinds` and the kind rules (internal/pack/pack.go:228, :545-656) — a harness pack carries its one file and no flows, groups, crew or sources; the plan's object kinds (internal/pack/plan.go) gain the harness object; `printPlan` (internal/cli/pack.go:1626) gains 3.3's complete inventory and diff, including every login and fetch field; the reader's harness-file validation reuses `agents.Load`'s checks on the named file rather than a glob; `packs.FS` and its consts (packs/packs.go:25-54); the embedded-pack consistency tests (packs/packs_test.go) and the docs table row they enforce; `TestHarnessFiles` and the doc-table tests (internal/agents), moved to the files' new home. Done when: `yardr pack check claude` prints every dialog and harness-controlled argument of 3.3, all fetch and login fields, and the diff against the built-in; `yardr pack apply ./x` with a malformed harness file is refused with the file and reason; the import records each file's sha256; a harness pack naming flows, groups, crew or sources is refused; the tests that pinned `harnesses/` pass against `packs/`. Depends on nothing.

**B2. Operator-only imports and build-pinned automatic behavior.** Goal: the store refuses a harness import to anyone but the operator; pack validation refuses an override whose `trust` or `flags.always` differs from the embedded built-in, and refuses either field for a kind with no built-in; `Harness.check` refuses a built-in whose `always` repeats one of its own `unattended` or permission-preset arguments. Where to look: the operator check beside `maySource` (internal/store/sources.go) and the plan's operator-only refusals (internal/cli/pack.go:743-774) — for this kind the refusal is whole, not a skip; `Harness.check` (internal/agents/harness.go:389) and the harness-pack validation B1 added for the comparison against the built-in. Done when: a non-operator apply is refused with the operator named and applies nothing; an import naming an MCP-server or tool-permission approval as `trust` is refused even though the session has never worked; an unknown `flags.always` argument absent from every unattended and permission list is refused, as is any `always` on a new kind; the seven built-ins pass. These tests pin the security boundary itself, not merely the pre-work window. Depends on B1.

**B3. The effective harness set.** Goal: 3.5 — the yard's import wins for overridable fields at the record's sha256, while `trust` and `flags.always` come only from the current built-in; an invalid or tampered override yields the built-in plus the event, doctor fault and `harness list` mark; the package global and its panic go; `harness show` and `harness list` name the source and drift; yardless readers read the built-ins. Where to look: `agents.Harnesses`, `byName`, `Lookup` (internal/agents/harness.go:298-331) and each caller — the runner (trust.go, herdr.go's `agentArgs`, herdr_screen.go), the daemon's dispatch (harness.go), the CLI (init.go, groupform.go, needs.go, harness.go) — threaded a resolved set from where home and store are in reach; `store.PackImport` for the records; `Config.Pack` (internal/config) for the installed copy. Done when: an applied override is what `harness show` prints and what a started agent's overridable behavior follows; a fixture that bypasses apply validation with an unsafe recorded import still cannot make `trustEntry` return imported strings or `agentArgs` append an imported `always` argument; editing the installed copy returns the kind to the built-in with the event and doctor fault; a yardless `harness list` reads the built-ins; no process panics on any yard file. Depends on B2.

**B4. Publish harness packs on yardr.dev.** Goal: `scripts/sync-packs <checkout>` copies the seven harness packs and accepts `kind: harness` with no flows, and the site presents them as yard-level packs rather than trying to draw a flow. Where to look: the script's `PACKS` list and flowless-kind check; `src/pages/packs/index.astro`, which currently reads `flows[0]` for every non-source pack; `src/pages/packs/[name].astro`, whose import commands need the source pack's no-depot form for harnesses too; `src/lib/packs.ts`, which needs a one-line description for each new listed pack. Done when: running the script against a clean yardr checkout at a tag containing B1 writes `public/packs/<kind>/pack.yaml` and the harness file for all seven kinds; the site build and depot tests pass; each generated harness page offers its `https://yardr.dev/packs/<kind>/` import without `--depot` and links the actual files. Depends on B1.

**B5. Make every yardr release publish its harness packs.** Goal: the release's publish stage files a yardr.dev pack-sync bead beside the existing release-archive bead, and the release instructions require the notes to name each changed harness pack's stable yardr.dev address. Where to look: `publish` in `contrib/release/stage` — the second bead is for `PRODUCT=yardr` only, names the release tag and tells the site builder to run `scripts/sync-packs` from a clean checkout at that tag; the other products using this script keep their one sync bead; `docs/install.md`, "Making a release", for the notes convention. Done when: the stage's test with a stand-in `yardr` records both yardr.dev beads, the pack bead's body names the exact tag and script, a non-yardr product files no pack bead, and the release documentation says how an operator finds the manual-update URL in the notes. Depends on B4.

**B6. The pages.** Goal: the yardr docs say the new shape. Where to look: docs/groups.md — "What yardr knows of a kind" gains where a kind's file comes from, and the passage "There is one set of files, the one in the binary: a yard cannot add to it or replace one" is rewritten; docs/packs.md gains the kind in its table and a section with the card's shape, build-pinned fields and nevers; docs/glossary.md gains **harness** (today it has no entry for harness, kind or trust); the AGENTS.md install table where it speaks of harness checks, if it needs it. Done when: a reader of docs/groups.md learns the override order, which fields never override, the drift line and the manual update path; `TestDocsPackTableNamesEveryEmbeddedPack` and the doc-table tests pass. Depends on B3 and B5.
