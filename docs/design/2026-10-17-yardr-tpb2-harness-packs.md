# A harness is a pack kind, imported and updated like a source pack

Design yardr-tpb2, proposed 2026-10-17. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A **harness** is the agent program yardr starts in a pane (Claude Code, Codex, Kimi); its **kind** is the name herdr starts it by (`claude`). What yardr knows of a kind beyond what herdr knows is kept in one file per kind, `harnesses/<kind>.yaml` — the **harness file**. A **pack** is a way of working as one directory, imported into a depot or into the yard itself (`yardr pack apply`, docs/packs.md); a pack yardr ships inside its binary is a **built-in** pack, as telegram is. The **operator** is the person who runs the yard. In this document **the card** is the plan `yardr pack check` prints and `yardr pack apply` asks to confirm, and **an override** is a yard's own import of a harness pack where the binary already carries one for the kind.

## 1. The question

mckean, 17 Oct 2026 (pane): "the yardr/harness mapping must be kept up to date; externalize it as a pack or another primitive, so it is easy to update for harness changes, to hold mappings for several versions of a harness, and to add new harnesses." Today the mapping ships inside the yardr binary: changing it for a harness's new version means editing `harnesses/<kind>.yaml` and cutting a yardr build, and a yard cannot add a kind yardr has no file for or correct one it has. The question is whether a pack can carry the harness file as it carries a source's declaration, what the card must show for a file that decides which keys yardr types into agents' panes and which flags agents start with, how one file serves several versions of a harness, how a yard learns a newer harness pack exists, and what adding a new harness still needs in code.

## 2. What exists today

### 2.1. The harness files and their one reader

`harnesses/<kind>.yaml` — seven kinds today (claude, codex, grok, kimi, muse, opencode, pi) — is embedded in the binary (`harnesses/harnesses.go`, `//go:embed *.yaml`) and read once at process start into the package global `agents.Harnesses` (`internal/agents/harness.go:298`), which panics on a file that does not parse, "a fault of the build, which TestHarnessFiles finds". `Load` (harness.go:343) takes any `fs.FS`, decodes with `KnownFields(true)` — a key the struct has no field for is an error — and runs `check()` (harness.go:389), which refuses a file whose `version` is not `FileVersion` (1), whose kind is no kind herdr starts (`IsKind`, harness.go:393), or whose fields are half given. The struct `Harness` (harness.go:33) holds: `label`, `provider`, `aliases`, `install` (printed, never run), `fetch` (one file of one version at its maker's address with its sha256; printed, never fetched by yardr — for a program that fetches), `trust` (the folder-trust dialog yardr answers: `dialog`, `answer`, `cursor`), `marks` (what its pane is read by), `flags` (`model`, `unattended`, `version`, `one_shot`, `always`, and `permissions`, the named flag sets a person picks from), `offers` (models suggested to pick), `model` (where the session's reported model is read), `errors`, `dialogs` (questions it draws in place of its input, told of and never answered — but see 2.2 for one exception), `login` (its login screen's lines), `login_recipe`, `background`, `hints`. `yardr harness list` and `yardr harness show <kind>` print what the files say (internal/cli/harness.go); docs/groups.md, "What yardr knows of a kind", is the field-by-field reference and says outright: "There is one set of files, the one in the binary: a yard cannot add to it or replace one."

### 2.2. Who reads the file, and for what

The herdr runner (internal/runner) answers the trust dialog at agent start and in the dispatcher's later passes (trust.go: `trustEntry` takes the kind's `trust` unless the config says `trust=false`; `acceptTrust` sends `down` at most four times and `enter` only when the screen holds the dialog's text at a line's edge, the accepting answer as an exact line, and the cursor on it — a dialog that changed shape is left for a human). The runner assembles an agent's arguments (herdr.go `agentArgs`, :751): the group's `args`, the file's `flags.always` appended whatever the group says, `{socket}` and `{workdir}` filled in, the model flag from `flags.model`. It reads panes by the file's `marks` (herdr_screen.go; the fallback for a kind with no file is the hardcoded `❯`/`›`, herdr_screen.go:46), reports dialogs it finds (herdr_screen.go `InputDialog`, :375 — with one hardcoded exception: a dialog whose word is `auto_mode_setup` is dismissed with Esc, :395), and recognizes the login screen by `login`. The daemon (internal/dispatch) matches a stopped agent's tail against `errors` (`HarnessError`, harness.go:154) and `background`, and reads the model by `model`. The command line offers the file's permission presets in the `group add` form (groupform.go `agentPermissions`), fills `--bind group.args=<label>` from one (`presetArgs`, internal/cli/pack.go:1215), gives the yardmaster `flags.unattended` at `yardr init` (init.go:584), and probes `flags.version` and `flags.one_shot` in doctor (needs.go).

What a file can never say, because it is code and not data: how a kind lists its models (`modelLists`, harness.go:284 — "code, not something a file can say"), the executable's name when it is not the kind (`executables`, models.go:305), the display order and the default kind (`order`, harness.go:312; `DefaultKind`, harness.go:26), the Esc dismissal of the one known dialog (keyed by its word, which a file names), and Kimi's hooks-file parsing (cli/kimihooks.go). A kind herdr starts that has no file is started all the same, as the zero `Harness`: no marks, no error lines, no flags (docs/groups.md).

### 2.3. Packs: kinds, import, the card, the record

A pack is a directory with a `pack.yaml` (internal/pack/pack.go). Its `kind` is a depot kind (`git` or `dir`), `source` (`KindSource`, pack.go:236 — imported into the yard itself, into no depot, carrying sources alone: telegram is the model), or unset. `yardr pack apply <pack>` (internal/cli/pack.go) resolves its argument (`resolvePack`, pack.go:126): a URL is fetched one file at a time (`pack.URLFS`; docs/packs.md:258 gives `https://yardr.dev/packs/starter/` as the shape — a plain static directory, no registry protocol), a path is read as a directory, and a bare word is looked up in the yard's import records first — the record re-read from its recorded `Source`, an embedded one re-read from the current binary — and in the binary's built-ins second (`packs.FS`, packs/packs.go:25: starter, dir, contributors, design, linear, github, google, pushover, telegram). An import record (`store.PackImport`, internal/store/packs.go:26) holds the source, the time, who applied it, and each installed object's sha256; it is what a bare name resolves to, so a yard's import already overrides a built-in pack of the same name. The plan (`pack.Build`) and its printing (`printPlan`, pack.go:1626) are the card: every object with its action and diffs, what the import would ask, and — for a kind-source pack — each declared source with each command file's sha256. `yardr pack show <pack>` prints the pack's setup notes, "from the pack, not checked by yardr". Applying is confirmed in a terminal or given `--yes`; the parts only the operator may grant — adding a source, opening threads, grants, exposure — are refused to anyone else with the reason named and the rest of the import done (pack.go:743-774). A file edited by hand since the last import is not overwritten without `--yes` (`EditedFiles`). Since design yardr-bht9 landed, `yardr pack apply <name>` of a built-in pack whose plan asks nothing can also be proposed as a run ask and approved on a card (`internal/store/runask_pack.go`), held to the build and the carded bytes; every other form of the command stays "the operator's alone, typed in a terminal".

There is no update mechanism for any pack: no version check, no registry, no `pack update`. A re-apply of a name re-reads its recorded source or the current binary, and the plan shows what changed as `old -> new` diffs and changed sha256s. Hosted yards (design yardr-bwm2, docs/design/2026-10-14-yardr-bwm2-hosted-v0.md) receive a new yardr by deploy: the container image is rebuilt and recreated, or `yardr upgrade` runs on the droplet with the release archive from yardr.dev.

## 3. The proposal

### 3.1. In one paragraph

A harness file becomes a pack of a new kind, `harness`: one pack per kind, named as the kind, carrying today's file unchanged. The seven files move from `harnesses/` into `packs/<kind>/` and become built-in packs exactly as telegram is a built-in pack: embedded, importable by name, and overridable — a yard's own `yardr pack apply claude` from a directory or a URL records the import, and from then on the yard reads the kind's harness file from its import, as a bare name already resolves to the yard's record before the binary. Applying one is the operator's alone, in a terminal, on a card that names every dialog yardr would answer and every flag an agent would start with, and shows an override as a diff against the built-in it replaces. What runs is what was carded: the installed file is read only at the sha256 the import recorded. Several versions of a harness are served by the file's existing habit — lists of patterns that tolerate whatever of them a version prints — and no version key is added. A yard learns of a newer harness pack from `yardr harness list` and doctor, which say when a yard's import differs from the build's built-in; a yard with no override rides each yardr build, and a hosted yard rides each deploy. Adding a harness for a kind herdr already starts takes a pack alone; what still takes code is what is code today.

### 3.2. The pack and its file

A pack of kind harness is one directory:

```text
packs/claude/
  pack.yaml      # name: claude · kind: harness · harness: claude.yaml
  claude.yaml    # today's harnesses/claude.yaml, comments and all
```

`pack.yaml` names its one harness file under a `harness` key (the reader's file glob cannot be reused as is: `Load` reads every `*.yaml` it finds, and would read `pack.yaml` itself). The file is today's format, `version: 1`, checked by the same rules a built-in is checked by (3.4 adds two). A kind harness pack carries nothing else: no flows, groups, crew or sources — as a kind-source pack carries sources alone, this kind carries one harness file alone — and it imports into the yard, into no depot. The `harnesses/` directory and package go away; `packs.FS` gains the seven kinds, and the built-in harness set is `Load` over each embedded pack's directory. Everything that pins the embedded packs — the docs table test, the consistency tests, the run-ask card's embedded-only rule — covers them from then on, and the harness-specific golden tests (`TestHarnessFiles`, the docs tables of internal/agents) move to the packs' new home unchanged in what they assert.

`yardr pack apply claude` on a yard with no import of it imports the built-in and changes nothing the yard reads — the record is what later overrides and drift reports hang from. `yardr pack apply ./claude/` or a URL imports that file instead. `yardr pack list` shows harness imports among the records; `yardr pack show claude` prints setup notes as for any pack — a harness pack carries none. `yardr harness show claude` stays the reader of the effective file and gains one line: where the file came from — the build, or the pack's import with its source and date.

### 3.3. The card

`yardr pack check claude` prints, and `yardr pack apply claude` asks to confirm, a card that for a harness pack says, in these words' worth of detail:

- the kind, its label, its file version, and where the pack came from;
- **every dialog yardr would answer**: the trust dialog's three strings whole — the text that marks it, the exact answer typed, the cursor — or that it answers none;
- **every flag an agent would start with**: `flags.always` whole (added to every agent of the kind, nobody asked), `flags.unattended` whole (what `yardr init` gives and the forms preselect), and each permission preset with its label and its args whole (offered, and chosen by a person — a pack never picks one);
- `fetch` whole — the address, the version, the sha256 — since a fetching program would install exactly those bytes as the agent;
- every pattern list whole: the error lines with their reasons, the login screen's lines, the dialogs told of, the background lines; the marks; the model source; the offers.

For a kind the build already carries, the card is the **diff against the built-in**, field by field, `old -> new` as `printPlan` already renders a changed object — so an added flag, a widened answer or a moved fetch address is a line of its own and cannot hide inside a file the operator is assumed to know. For a kind the build does not carry, the card is the whole content as listed above.

A harness pack is never on the run-ask list: `yardr pack apply <name>` stays askable for the packs yardr-bht9 admitted, and a kind harness pack keeps the refusal "the operator's alone, typed in a terminal". Open question 3 asks whether that holds for good.

### 3.4. What a harness pack may never do, and what enforces it

The file steers every agent the yard starts, so the rules are stated as nevers, each with its enforcement:

- **A harness file never answers anything but its trust dialog, and never answers a permission prompt.** Only `internal/runner/trust.go` sends keys on a file's say-so, and it sends them only when the screen matches exactly: the dialog's text at a line's edge, the accepting answer as a whole line, the cursor on it, at most four cursor moves. Every other dialog a file names is told of and left for a person (`InputDialog`); the one dismissal, Esc for the word `auto_mode_setup`, cancels an offer and widens nothing. This is code, and no file changes it. The residual risk is not in the matching but in the strings: an override could name a permission prompt's text as its `trust`. Against that: the card shows the three strings whole and diffs them against the built-in, and applying is the operator's alone. Open question 1 asks whether the core should go further and refuse an override that changes `trust` at all.
- **A harness file never starts an agent with a flag that widens access unless a person chose the flag.** `unattended` is printed in `group add --help` and given at `yardr init`, where a person sees it; a permission preset takes effect only where a person picks it (the form, `--bind`). The one field that acts with nobody asked is `flags.always`, so `check()` gains a rule: `always` may not repeat an argument of the file's own `unattended` or of any of its permission presets — a widening rides a person's choice, never the file's default. (Today's seven files pass it: Codex's `always` is `--no-daemon` and its update check off, which no preset carries.) The card shows `always` whole regardless.
- **A harness file never names a program or a file for the yard to run.** The schema has no such field: `install` is printed and never run, `fetch` is printed and never fetched by yardr, and the decoder refuses every key the struct does not know. The card shows `fetch`'s address and sha256 whole, since what a fetching program installs is what the file says.
- **Applying a harness pack is the operator's, whole.** Today's packs let anyone apply and skip the operator-only parts; a harness pack has no safe remainder — every field of it steers every agent — so the store refuses the import to anyone but the operator, as `maySource` refuses a source, with the operator named.
- **What is in effect is what was carded.** The effective file is the installed copy read at the sha256 the import record holds for it; a copy edited by hand since is no override — the built-in serves, and the yard tells of it (an event, a doctor fault, the mark in `yardr harness list`). A re-apply over a hand-edited copy keeps today's `--yes` rule. A record from a URL or directory is re-read from its source on re-apply, as every pack's is; the record's hashes are what the yard runs meanwhile.

### 3.5. The effective harness set

The package global that panics at process start does not survive a yard being able to override a file: a bad override cannot be a build fault. `agents.Load` stays pure — it takes an `fs.FS` today — and the effective set is built one level up, where the yard's home and store are in reach (internal/agents must stay below the store: the store already imports it for `IsKind`). The rule is the pack system's own: the yard's import of a kind wins; otherwise the built-in serves; a kind with neither is the zero `Harness`, as today. An override whose installed file fails the harness checks, or whose bytes are not the record's sha256, is refused as 3.4 says — the built-in serves and the yard tells of it; it is never half read, and no process panics on it. Readers that run with no yard at all — `yardr harness list` and doctor on a home with no yard are in the no-onboarding set — read the built-ins, as today. `yardr harness list` gains, per kind, the file's source and drift: `from pack claude, imported 17 Oct from ./claude/`, and where the build's built-in differs from the yard's, `the build carries a different claude: yardr pack check claude shows what would change` — that line is 3.6's whole update mechanism for a yard with an override, and doctor repeats it.

### 3.6. Versions and updates

**Several versions of one harness are one file's lists, not one file per version.** The file's idiom is already tolerant: `errors`, `dialogs`, `login` and `background` are lists of patterns tried in order, so a file serves every harness version that prints any of its lines; `offers` is a suggestion, not a check, and a wrong model id fails loudly at the first session; `flags.version` drives doctor's probe rather than a comparison. The fields that name one version exactly are the ones that must: `fetch` pins bytes to a sha256, which is a version by construction and the one place a version is unavoidable — it names the newest version whose fetch was verified, and an older harness installed by hand is unaffected. Where tolerance breaks is `trust` and `marks`: single strings a harness version could change incompatibly. The proposal is to follow the patterns' precedent when that happens — the fields gain alternates (a second accepted string beside the first) — rather than version-keyed sections: the runner matches whichever the pane shows, as it already matches whichever pattern a version prints. A version key would be forced only by a change no list can hold — flags that differ per version, say — and that is a `version: 2` of the file format, `FileVersion`'s existing seam, not this design's. See section 4.

**How a yard learns a newer harness pack exists.** Nothing is pushed and nothing polls. Three roads, all existing mechanisms: a yard with no override rides the build — `yardr upgrade`, or a hosted yard's deploy (the rebuilt image, or `yardr upgrade` on the droplet, both of yardr-bwm2), carries the new built-in and the yard reads it from then on; a yard with an override sees the drift line in `yardr harness list` and doctor (3.5) and re-bases with `yardr pack check claude` and `yardr pack apply claude`, the card showing the diff; and a fix that cannot wait for a release ships as a file at a stable address — `https://yardr.dev/packs/claude/`, the plain static directory a URL import already reads — and is imported by URL. Publishing that directory is the release process's, not the yard's.

**A new harness by pack alone.** The gate stays herdr's: `check()` refuses a file whose kind herdr does not start, so a pack can teach yardr a kind from the twenty-four herdr knows (`HerdrKinds`, models.go:22) that yardr has no file for — write the file, apply the pack, and the kind has marks, flags, error lines and offers with no yardr build. What still takes code is what is code today: a kind herdr does not start (herdr's to learn); listing the kind's models (`modelLists`); an executable named other than the kind (`executables`); a place in the display order; kind-specific reading like Kimi's hooks file; and the golden tests and doc tables that enumerate kinds by name.

### 3.7. What a person types and sees

```text
$ yardr pack apply ./harness-claude/     # an override, as the operator, in a terminal
pack claude (./harness-claude/, commit 9f2c1e0), of kind harness, into the yard
  harness claude: change — replaces the build's built-in
    trust.answer: "Yes, I trust this folder" -> "Yes, I trust this folder, and remember"
    flags.always: [] -> [--some-new-flag]
    errors: 14 patterns -> 15
    (11 fields unchanged)
  ...
Apply pack claude to the yard? 1 object to write or remove.

$ yardr harness list
KIND   HARNESS       FILE   SOURCE
claude Claude Code   v1     pack claude, imported 17 Oct from ./harness-claude/ — the build carries a different claude: yardr pack check claude shows what would change
codex  Codex         v1     the build
...
```

(The exact lines are the builder's; the content — kind, source, drift — is the design's.)

## 4. Left out

- **Version-keyed sections of the file format** (a `versions:` map, or one file per harness version). Tolerant lists cover every drift yardr has met so far; the seam for the rest is `FileVersion`, and a v2 is designed when a harness forces it, not before.
- **An update command, a check against yardr.dev, or a registry protocol.** No pack has one; the drift line and re-apply are the mechanism, and a push of "a newer claude pack exists" is a yard phoning home, which yardr does not do.
- **Harness packs on the run-ask list** (the card of yardr-bht9, from a device). Terminal-only at first; open question 3 asks whether for good.
- **Signed packs or provenance beyond the record.** The record already holds the source and every installed file's sha256; who may vouch for a pack is a question for packs generally, not for this kind.
- **Per-depot or per-group harness files.** One effective file per kind per yard; a group that needs different flags has `args`, as today.
- **Answering any dialog but the trust one**, and typing into the login screen. Both stay code's refusals, unchanged.
- **Idle, working, blocked, done.** Herdr's to decide from its own files, today and after; no harness file speaks of it.

## 5. Open questions

Each is for mckean at decide, as its own ask on the bead.

**1. May an override change `trust` — the keys yardr types into the pane?** Option A, yes, as proposed: the card shows the dialog, the answer and the cursor whole and diffs them against the built-in, and applying is the operator's alone. The cost: the card is the only wall between a bad override and keys typed into every agent's pane — a reader who skims it approves whatever answer it names. Option B, no: an override that changes `trust` is refused, and the trust strings come from the build alone. The cost: the trust dialog is the one thing that blocks every start of a kind, and a harness release that changes it leaves every overriding yard stuck until a yardr release ships the new strings — exactly the update this design exists to make easy. I would take A: the diff makes a changed answer the loudest line on the card, and B re-couples the most volatile string in the file to the release cycle.

**2. Is the drift line enough for a yard to learn a newer harness pack exists?** Option A, as proposed: `yardr harness list` and doctor say when the build's built-in differs from the yard's import; nothing polls. The cost: a yard that never upgrades yardr and never runs those commands never learns — but such a yard updates nothing else either. Option B: a command that fetches yardr.dev's harness packs and says what is newer. The cost: a network fetch on a command's say-so, an address to keep alive, and a protocol of one for harnesses alone. Option C: release notes only. The cost: invisible to a hosted operator who never reads them — though a hosted yard rides each deploy and needs no line. I would take A.

**3. Should a harness pack stay off the run-ask list for good?** Option A, as proposed: applying one is typed in a terminal, where the diff and the files stand beside it; the run-ask card admits no harness pack. The cost: an operator with no shell — the hosted case yardr-bht9 answered for source packs — cannot re-base an override from a device; such an operator rides the build's built-ins by deploy and never holds an override, so the cost is nil until a hosted yard wants its own harness file. Option B: admit built-in harness packs to the row, with 3.3's card held to the run-ask bounds, as yardr-bht9 did for packs whose plan asks nothing. The cost: an approval from a phone that steers every agent the yard starts, on a card whose every line must be read. I would take A, and revisit if a hosted yard ever imports one.

## 6. The beads it would become

In the order they would land; each passes `sh .yardr/test`. B2 and B3 both depend on B1 and are independent of each other; B4 is last.

**B1. The pack kind harness, and the seven built-ins.** Goal: `kind: harness` exists; a harness pack is one `pack.yaml` (`name` the kind, `harness` its file) and one harness file; the seven files move from `harnesses/` to `packs/<kind>/` unchanged in content and become built-in packs; `yardr pack check` and `yardr pack apply` read, validate, card and record them; `harnesses.FS` and its package go away and the built-in harness set is read from `packs.FS`. Where to look: `Kinds` and the kind rules (internal/pack/pack.go:228, :545-656) — a harness pack carries its one file and no flows, groups, crew or sources; the plan's object kinds (internal/pack/plan.go) gain the harness object; `printPlan` (internal/cli/pack.go:1626) gains 3.3's card, diffed against the built-in where there is one; the reader's harness-file validation reuses `agents.Load`'s checks on the named file rather than a glob; `packs.FS` and its consts (packs/packs.go:25-54); the embedded-pack consistency tests (packs/packs_test.go) and the docs table row they enforce; `TestHarnessFiles` and the doc-table tests (internal/agents), moved to the files' new home. Done when: `yardr pack check claude` prints the card of 3.3 with the diff against the built-in; `yardr pack apply ./x` with a harness file that fails a check is refused with the file and reason; the import records each file's sha256; a harness pack naming flows, groups, crew or sources is refused; the tests that pinned `harnesses/` pass against `packs/`. Depends on nothing.

**B2. The effective harness set.** Goal: 3.5 — the yard's import of a kind wins over the built-in, read at the record's sha256; a failed or tampered override yields the built-in plus the event, the doctor fault and the `harness list` mark; the package global and its panic go; `yardr harness show` and `harness list` name the source and the drift; yardless readers read the built-ins. Where to look: `agents.Harnesses`, `byName`, `Lookup` (internal/agents/harness.go:298-331) and each caller — the runner (trust.go, herdr.go's `agentArgs`, herdr_screen.go), the daemon's dispatch (harness.go), the CLI (init.go, groupform.go, needs.go, harness.go) — threaded a resolved set from where home and store are in reach; `store.PackImport` for the records; `Config.Pack` (internal/config) for where the installed copy stands. Done when: an applied override is what `harness show` prints and what a started agent's flags follow; editing the installed copy by hand returns the kind to the built-in with the event recorded and doctor naming it; a yardless `harness list` reads the built-ins; no process panics on any file of the yard's. Depends on B1.

**B3. The operator's alone, and the `always` rule.** Goal: 3.4's two new enforcements — the store refuses a harness import to anyone but the operator, with the operator named; `check()` refuses a file whose `flags.always` repeats an argument of its own `unattended` or of any permission preset. Where to look: the operator check beside `maySource` (internal/store/sources.go) and the plan's operator-only refusals (internal/cli/pack.go:743-774) — for this kind the refusal is whole, not a skip; `Harness.check` (internal/agents/harness.go:389) for the flag rule. Done when: a non-operator apply of a harness pack is refused with the operator named and applies nothing; a file crossing the `always` rule fails `pack check` with the argument named; the seven built-ins pass. Depends on B1.

**B4. The pages.** Goal: the docs say the new shape. Where to look: docs/groups.md — "What yardr knows of a kind" gains where a kind's file comes from, and the passage "There is one set of files, the one in the binary: a yard cannot add to it or replace one" is rewritten; docs/packs.md gains the kind in its table and a section with the card's shape and the nevers; docs/glossary.md gains **harness** (today it has no entry for harness, kind or trust); the AGENTS.md install table where it speaks of harness checks, if it needs it. Done when: a reader of docs/groups.md learns the override order, the drift line and the security rules; `TestDocsPackTableNamesEveryEmbeddedPack` and the doc-table tests pass. Depends on B2 and B3.
