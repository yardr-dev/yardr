# A harness is a pack kind, imported and updated like a source pack

Design yardr-tpb2, proposed 2026-10-17. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A **harness** is the agent program yardr starts in a pane (Claude Code, Codex, Kimi); its **kind** is the name herdr starts it by (`claude`). What yardr knows of a kind beyond what herdr knows is kept in one **harness file** per kind. A **pack** is a way of working as one directory, imported into a depot or into the yard itself (`yardr pack apply`, docs/packs.md); a pack yardr ships inside its binary is a **built-in** pack, as telegram is. The **operator** is the person who runs the yard. In this document **the card** is both the plan `yardr pack check` prints and the card a run ask shows in footplate, and **an override** is a yard's import of a harness pack from a directory or URL where the binary already carries one for the kind. A **build-pinned** field always comes from the running build, never from imported bytes in effect.

## 1. The question

mckean, 17 Oct 2026 (pane): "the yardr/harness mapping must be kept up to date; externalize it as a pack or another primitive, so it is easy to update for harness changes, to hold mappings for several versions of a harness, and to add new harnesses." Today the mapping ships inside the yardr binary: changing it for a harness's new version means editing `harnesses/<kind>.yaml` and cutting a yardr build, and a yard cannot add a kind yardr has no file for or correct one it has. The question is whether a pack can carry the harness file as it carries a source's declaration, what the card must show for a file that decides which keys yardr types into agents' panes and which flags agents start with, how one file serves several versions of a harness, how a yard learns a newer harness pack exists, and what adding a new harness still needs in code.

## 2. What exists today

### 2.1. The harness files and their one reader

`harnesses/<kind>.yaml` — seven kinds today (claude, codex, grok, kimi, muse, opencode, pi) — is embedded in the binary (`harnesses/harnesses.go`, `//go:embed *.yaml`) and read once at process start into the package global `agents.Harnesses` (`internal/agents/harness.go`), which panics on a file that does not parse, a fault of the build that `TestHarnessFiles` finds. `Load` takes any `fs.FS`, decodes with `KnownFields(true)`, so a key the struct has no field for is an error, and runs `check()`, which refuses a file whose `version` is not `FileVersion` (1), whose kind is no kind herdr starts (`IsKind`), or whose fields are half given. The struct `Harness` holds: `label`, `provider`, `aliases`, `install` (printed, never run), `fetch` (data for a separate fetching program, never fetched by yardr), `trust`, `marks`, `flags`, `offers`, `model`, `errors`, `dialogs`, `login`, `login_recipe`, `background`, and `hints`. `yardr harness list` and `yardr harness show <kind>` print what the files say (internal/cli/harness.go); docs/groups.md, "What yardr knows of a kind", is the field-by-field reference and says: "There is one set of files, the one in the binary: a yard cannot add to it or replace one."

The trust shape has just gained two relevant pieces on main, from yardr-k9ew and yardr-tzkk. `trust.answers` accepts one string or a list, with the old `answer` still read as one, so Kimi 2.1.1's `Trust this folder` and 2.2.0's `Trust and continue` coexist. `trust.env` holds `KEY=VALUE` entries that let a harness skip the dialog; Kimi 2.2.0's is `KIMI_CODE_TRUST_WORKSPACE=1`. `internal/dispatch/harness_dialog.go` raises `session_harness_dialog` when a session at its first prompt shows the known dialog with none of its known answers: it names the kind, installed harness version, dialog and pane tail, and the runner types nothing.

### 2.2. Who reads the file, and for what

The herdr runner (internal/runner) answers the trust dialog at agent start and in the dispatcher's later passes. `trustEntry` takes the kind's `trust` unless the config says `trust=false`; `trustAnswer` requires the dialog text, an accepting answer as an exact line, and the cursor on that answer; `acceptTrust` sends `down` at most four times and `enter` only on a selected answer. `agentEnv` adds `TrustEnv`: the configured values when automatic trust is allowed, or empty values under `trust=false`, so an inherited environment or env file cannot leave a trust bypass enabled. The runner assembles an agent's arguments in `agentArgs`: the group's `args`, the file's `flags.always` appended whatever the group says, `{socket}` and `{workdir}` filled in, and the model flag from `flags.model` appended whenever a model is configured. It reads panes by `marks`, reports `dialogs` and the login screen without answering them, and has one hardcoded Esc dismissal for `auto_mode_setup`.

The daemon (internal/dispatch) matches a stopped agent's tail against `errors` and `background`, reads the model by `model`, and runs `flags.version` with a five-second timeout to name a version in `session_harness_dialog`. The command line offers the file's permission presets in the `group add` form (`agentPermissions`), fills `--bind group.args=<label>` from one (`presetArgs`), gives the yardmaster `flags.unattended` at `yardr init`, and runs the executable outside a pane by `flags.version` (doctor's probe) and `flags.one_shot` (doctor's `--try` and onboarding's one real call, both on a person's yes). `yardr harness login` runs `login_recipe.argv` plus the chosen method's `args` (`internal/cli/harnesslogin.go`). `fetch` includes verification source and date, version, destination path, optional installer arguments, and per-target URL, sha256, size and archive member (`internal/agents/fetch.go`); yardr only prints it for the separate program that performs a fetch.

What a file can never say, because it is code and not data: how a kind lists its models (`modelLists`), the executable's name when it is not the kind (`executables`), the display order and default kind (`order`, `DefaultKind`), the Esc dismissal of the one known dialog, and Kimi's hooks-file parsing (cli/kimihooks.go). A kind herdr starts that has no file is started all the same, as the zero `Harness`: no marks, no error lines, no flags.

### 2.3. Packs: kinds, import, the card, and the record

A pack is a directory with a `pack.yaml` (internal/pack/pack.go). Its `kind` is a depot kind (`git` or `dir`), `source` (imported into the yard itself, carrying sources alone, as telegram does), or unset. `yardr pack apply <pack>` resolves its argument in `resolvePack` (internal/cli/pack.go): a URL is fetched one file at a time (`pack.URLFS`), a path is read as a directory, and a bare word is looked up in the yard's import records first and the binary's built-ins second. The record is re-read from its recorded `Source`; an embedded record is re-read from the current binary. An import record (`store.PackImport`, internal/store/packs.go) holds the source, time, actor, and each installed object's sha256. Thus a yard's directory or URL import already overrides a built-in pack of the same name, while an embedded import follows the running build.

The plan (`pack.Build`) and its printing (`printPlan`) are the terminal card: every object with its action and diffs, what the import would ask, and, for a kind-source pack, each declared source with each command file's sha256. `yardr pack show <pack>` prints the pack's setup notes, "from the pack, not checked by yardr". Applying is confirmed in a terminal or given `--yes`; the parts only the operator may grant are refused to anyone else with the reason named and the rest of the import done. A file edited by hand since the last import is not overwritten without `--yes`.

Since design yardr-bht9 landed, `yardr pack apply <name>` of an embedded source pack, or an embedded depot pack whose one standing plan asks nothing, can also be proposed as a run ask and approved on a card. `internal/store/runask_pack.go` and `internal/server/packreader.go` make that card from the server's own embedded bytes, never from a directory, URL or earlier import's record; writer-supplied content is discarded. `internal/server/carry.go` rebuilds and applies the approved embedded pack as the operator, holding the approval and carrying out to the carded build, bytes and yard state. Existing line and payload bounds refuse a card that cannot be read whole rather than truncating it. Only the operator may approve a run ask.

### 2.4. Publication, releases, and installs

There is no update mechanism for any pack: no version check, registry, or `pack update`. A re-apply of a name re-reads its recorded source or the current binary. The public pack directories are copied by yardr.dev's `scripts/sync-packs`, whose fixed `PACKS` list names no harnesses and which accepts a flowless pack only when its kind is `source`. Its pack index and detail pages treat other kinds as flow packs. The release flow makes a GitHub release from the release bead's body, and its publish stage (`contrib/release/stage`) files a yardr.dev bead for `scripts/sync-release` alone: release archives, not packs. Neither editing a pack nor cutting a release currently publishes a changed pack at its yardr.dev address.

`yardr upgrade` installs a build, restarts the yards it covers, and checks their health (`internal/cli/upgrade_flow.go`); its existing mail helper tells the yardmaster and operator of failures, not of harness changes. Hosted yards (design yardr-bwm2, docs/design/2026-10-14-yardr-bwm2-hosted-v0.md) receive a new yardr by deploy: a container is rebuilt and recreated over the same home, or `yardr upgrade` runs on a droplet. In both forms the yard's server starts the new build and opens the existing store (`internal/server/server.go`, `serve`). No current record says which built-in harness bytes an import last saw, and no server-start path reports harness drift.

## 3. The proposal

### 3.1. In one paragraph

A harness file becomes a pack of a new kind, `harness`: one pack per kind, named as the kind, carrying today's file. The seven files move from `harnesses/` into `packs/<kind>/` and become built-in packs exactly as telegram is a built-in pack: embedded, importable by name, and overridable. A yard's directory or URL import supplies the fields that recognize and report a harness, plus the answers to its built-in folder-trust dialog; an embedded import follows the current build. The running build always supplies every field that yardr itself turns into harness arguments or login commands, and the trust dialog's text, cursor and environment. Only `trust.answers` crosses the boundary from an import into automatic action. Applying is operator-only, in a terminal or on an embedded pack's run-ask card, with every dialog, argument, login command and download shown whole. Several harness versions are served by tolerant lists rather than version-keyed sections. Release notes announce changed packs and the release publishes their exact files at stable yardr.dev addresses; after an install or hosted deploy, a server start mails the yardmaster when the new built-in would change fields an override controls. `yardr pack check <kind> --builtin` makes the local comparison and `yardr pack apply <kind> --builtin` adopts the built-in. A yard with no override rides each build or deploy. Adding a harness for a kind herdr already starts takes a pack alone for its passive mappings; automatic behavior and the behavior that is code today still take code.

### 3.2. The pack and its file

A pack of kind harness is one directory:

```text
packs/claude/
  pack.yaml      # name: claude · kind: harness · harness: claude.yaml
  claude.yaml    # today's harnesses/claude.yaml, comments and all
```

`pack.yaml` names its one harness file under a `harness` key; the reader's current file glob cannot be reused because it would read `pack.yaml` too. The harness file keeps format `version: 1`, including the landed `trust.answers` and `trust.env`, and is checked by the same rules a built-in is checked by. A kind-harness pack carries nothing else: no flows, groups, crew or sources. Like a kind-source pack, it imports into the yard and into no depot. The `harnesses/` directory and package go away; `packs.FS` gains the seven kinds, and the built-in harness set is `Load` over each embedded pack's named harness file. The harness-specific golden tests and documentation-table tests move to the packs' new home without weakening what they assert.

`yardr pack apply claude` with no standing override records an embedded import and changes nothing the yard reads; later builds continue to supply the whole file. `yardr pack apply ./claude/` or a URL records an override. `yardr pack list` shows harness imports among the other records. `yardr pack show claude` prints setup notes as for any pack; a harness pack carries none. `yardr harness show claude` remains the reader of the effective file and gains its source and import date. It marks `flags`, `login_recipe`, and the trust dialog, cursor and environment as coming from the build, and names the source of the effective trust answers.

### 3.3. The card

`yardr pack check claude` prints, and `yardr pack apply claude` asks to confirm, a card with two parts. The first is the **complete effective behavior after this import**, including unchanged fields, so no dialog, argument or download is hidden by a diff summary:

- the kind, label, provider, aliases, file version, and where the pack came from;
- **every dialog yardr answers or deliberately bypasses**: the built-in folder-trust `dialog` and `cursor`, the effective `trust.answers` whole with their source, every `trust.env` entry whole and marked `from the build`, or that the kind answers and bypasses none. Every entry in `dialogs` and `login` is shown and marked as reported, never answered, as is the hardcoded Esc dismissal of `auto_mode_setup`;
- **every harness-controlled argument yardr passes to the harness executable**, all marked `from the build`: `flags.always`, `flags.model`, `flags.unattended`, `flags.version`, `flags.one_shot`, and every permission preset with its label, arguments and description, grouped by the command that uses them;
- **the whole login recipe**, marked `from the build`: verification source and date, `argv`, every method's label and arguments, `open_url`, and `input`;
- **`fetch` whole**: `verified.from` and `verified.on`, `version`, destination `path`, installer `run` arguments, and every operating-system/architecture target's `url`, `sha256`, `size` and optional archive `member`;
- the rest of the file whole: `install`, marks, model source, offers, error lines with their reasons, background lines, and hints.

The second part, for a kind the build already carries, is the **diff against the current built-in**, field by field, `old -> new` as `printPlan` renders a changed object. For a new kind it is the whole candidate. A difference in a build-pinned field is not an applyable card: `pack check` refuses it and prints that difference with the build-pinned rule. Only `trust.answers` may differ inside `trust`.

An embedded harness pack joins the existing `yardr pack apply <name>` run-ask row. The server's reading, the stored card, approval staleness and carrying out use the same complete inventory and the same embedded bytes as the terminal card; the harness file and its unified diff are carried for the view's expanded text, while every behavior remains in the yard's own card sentences. Existing card line and payload bounds still apply: a harness whose complete card does not fit is refused, never shortened. A directory or URL harness pack is not added to this row, because the existing mechanism cards only bytes embedded in the server. Approving remains the operator's alone; a changed build, pack bytes, or standing override makes the approval stale, and the server applies only what was carded.

### 3.4. What an imported harness pack may never do, and what enforces it

The security boundary is between the reviewed built-in bytes in the binary and bytes a yard imports. A release can already change both code and built-in data; an import must not acquire the same authority. The general rule is that **a field that yardr itself turns into a harness command, a trust-bypassing environment, or the identity of a dialog yardr answers is build-pinned**. The only exception is the list of accepting answers within the built-in folder-trust dialog. The concrete rules are:

- **An import never supplies an argument that yardr passes to a harness executable.** The whole `flags` block is build-pinned: `always`, `model`, `unattended`, `version`, `one_shot`, and every permission preset, including labels and descriptions that could otherwise misrepresent built-in arguments. The whole `login_recipe` is build-pinned for the same reason: its `argv` and method arguments become a command, and its labels must describe that same command. At apply, an override must repeat the current built-in's values for these blocks, and a new kind with no built-in must leave them empty. An unknown access-widening argument is therefore refused as a difference whether it appears in `always`, `model`, `unattended`, a permission preset, a version or one-shot probe, or a login method. No semantic classification of a flag is pretended. As a check on the reviewed built-ins themselves, `Harness.check` also refuses an `always` argument repeated in that built-in's unattended or permission-preset arguments, the arguments yardr already knows make an agent ask less.
- **An import may change only the answers, never which dialog or bypass yardr uses.** `trust.dialog`, `trust.cursor` and `trust.env` are build-pinned. At apply, a kind with a built-in trust entry requires those fields to repeat the built-in and requires a nonempty `answers`; a kind without one permits no `trust`. At run time the runner receives a `Trust` assembled from the current built-in's dialog, cursor and environment plus the imported answers. Imported bytes never reach `agentEnv` as trust entries and can never point `trustAnswer` or `acceptTrust` at an MCP-server approval, a tool-permission prompt, or another dialog. The existing exact-answer and cursor checks still govern keys, and the dispatcher's first-prompt window remains defense in depth rather than the claimed wall. An answer the effective list does not know still raises `session_harness_dialog` and sends nothing; its hint names the effective pack's `trust.answers` and the source shown by `harness show`, not the removed `harnesses/` path.
- **A harness file never names an arbitrary program or file for yardr to run.** The schema has no such field: `install` is printed and never run, and the decoder refuses unknown keys. `fetch` remains data for a separate fetching program, with its complete source, checksum and installer arguments disclosed on the card; yardr does not fetch or execute it. A login command comes only from the build-pinned recipe and only when a person explicitly runs `yardr harness login`.
- **Applying a harness pack is the operator's, whole.** Today's packs let anyone apply and skip the operator-only parts; a harness pack has no safe remainder, so the store refuses the import to anyone but the operator, as `maySource` refuses a source, with the operator named. A run ask does not weaken this: its approval and carrying out are already operator-only.
- **What is in effect is what was carded.** For a directory or URL override, the installed copy supplies overridable fields only at the sha256 the import record holds. A copy edited by hand since is no override: the built-in serves, and the yard tells of it through an event, a doctor fault, and the mark in `yardr harness list`. A re-apply over a hand-edited copy keeps today's `--yes` rule. An embedded import reads the current binary rather than an old installed copy.

Build-pinning has separate apply-time and read-time rules so an upgrade does not break an old override. Apply refuses a candidate whose pinned fields differ from the build against which it is carded. Once recorded, however, the resolver never reads those pinned fields from the import at all and does not reject them merely because a later build changed them. The later build's flags, login recipe, trust dialog, cursor and environment take effect automatically, while the old import continues to supply only its overridable fields and trust answers. A candidate published by a newer release whose pinned fields differ from the running build is refused at a new apply; that update needs the upgrade or deploy. A pack whose changes are confined to answers or recognition fields remains applicable by URL when its pinned fields match the running build.

### 3.5. The effective harness set and built-in comparison

The package global that panics at process start does not survive a yard being able to override a file: a bad override cannot be a build fault. `agents.Load` stays pure, and the effective set is built one level up, where the yard's home and store are in reach; internal/agents must stay below the store because the store already imports it for `IsKind`. The resolver applies the same file and whole-set checks as `Load`, including kind and alias conflicts.

For a directory or URL override whose installed bytes match the record, the yard's file wins for every overridable field. The current built-in supplies `flags`, `login_recipe`, and the trust dialog, cursor and environment; the import supplies `trust.answers`. If an old import has no answers where a new built-in has a complete trust entry, the built-in's answers serve too; imported answers can act only within a current built-in trust entry. A kind with no built-in gets zero pinned fields, and a kind with neither file is the zero `Harness`, as today. An embedded import or a yard with no import reads the whole current built-in. An invalid or tampered override is never half read and never panics a process: the whole built-in serves and the yard reports it; with no built-in, the zero `Harness` serves. Readers with no yard read the built-ins, as today.

`yardr harness list` gains, per kind, the effective file's source and drift: `from pack claude, imported 17 Oct from ./claude/`. Drift means that adopting the current built-in would change fields the override controls; differences confined to build-pinned fields are not drift because those changes are already in effect. Doctor repeats the same local comparison. The line names two working commands:

- `yardr pack check <kind> --builtin` resolves the named embedded pack directly, bypassing the recorded directory or URL, and shows what adopting the current built-in would change. Bare `yardr pack check <kind>` keeps today's recorded-source behavior.
- `yardr pack apply <kind> --builtin` applies that embedded pack after the same operator card and records an embedded source. This is the re-base command: it adopts the whole built-in and ends the override; it is not a three-way merge of local changes. An operator who wants to keep changes reads the diff, edits the pack's source, and re-applies that source.

`--builtin` is a general pack-resolution flag rather than a harness-only command, because the recorded-source ambiguity already exists for every built-in pack. The run-ask row needs no flag: its server reading is already explicitly embedded.

### 3.6. Versions, updates, and new harnesses

**Several versions of one harness are one file's lists, not one file per version.** The file's idiom is already tolerant: `errors`, `dialogs`, `login` and `background` are lists of patterns tried in order, so a file serves every harness version that prints any of its lines. `trust.answers` now has the same shape, and an import may extend or replace that list while retaining old answers for old versions. `offers` is a suggestion, not a check, and a wrong model id fails loudly at the first session. `fetch` is the place a version is unavoidable: it pins the newest verified release's bytes to a sha256, and an older harness installed by hand is unaffected. Where tolerance breaks for an overridable field is `marks`: single strings a harness version could change incompatibly. Follow the patterns' precedent when that happens — the field gains alternates rather than version-keyed sections, and the runner matches whichever the pane shows. A changed trust dialog, cursor or environment, any changed flag, and a changed login recipe need a built-in change because they are build-pinned. A version key would be forced only by a change no list can hold in an overridable field; that is a `version: 2` of the file format, `FileVersion`'s existing seam, not this design's.

**Release notes announce, the release publishes, and an install tells the yardmaster.** Nothing polls yardr.dev. The release flow cuts a GitHub release whose notes name each changed harness pack; an urgent harness fix gets a patch release. The release's publish stage gains a second site bead beside today's `sync-release` bead, asking yardr.dev to run `scripts/sync-packs` from a clean checkout at that release's tag. The site sync copies the seven harness packs and its pages accept their flowless kind, so `https://yardr.dev/packs/claude/` and its peers serve the files from the release the notes name. An operator who reads the notes can check and apply that URL manually, subject to the pinned-field compatibility rule above. A yard with no override rides the build or hosted deploy.

The install itself is the other discovery event. A directory or URL import record gains the sha256 of the built-in harness file it last saw, set when the import is applied. On server start, a changed current built-in hash makes the server run the local drift comparison once. One store write advances that marker and, only when adopting the new built-in would change fields the override controls, mails the yardmaster. The mail names the kind, import source, build, and `yardr pack check <kind> --builtin`; it does not apply anything. A restart with the same built-in does nothing, a built-in change confined to pinned fields sends no mail because it is already effective, and a yard with no override sends none. A missing marker in an existing record is treated as unseen once, so the release that adds this mechanism cannot leave old overrides silent. Because this check lives in server start rather than only in `yardr upgrade`, a hosted container recreate follows the same path. The yardmaster can tell the operator or propose the embedded pack's run ask for the card-based re-base.

**A new harness by pack alone.** The gate stays herdr's: `check()` refuses a file whose kind herdr does not start, so a pack can teach yardr a kind herdr knows that yardr has no file for. Write the file, apply the pack, and the kind has marks, model suggestions and reporting, error and dialog reporting, login-screen recognition, background lines, and install and fetch data with no yardr build. With no built-in it has no harness-file flags, login recipe, automatic trust answer, or trust-bypassing environment; a person's explicit group `args` remain the yard's own mechanism, as today. What still takes code is a built-in change for those pinned behaviors, and what is code today: a kind herdr does not start, listing the kind's models (`modelLists`), an executable named other than the kind (`executables`), display order and default, kind-specific reading like Kimi's hooks file, and the golden tests and documentation tables that enumerate kinds by name.

### 3.7. What a person types and sees

```text
$ yardr pack apply ./harness-claude/     # an override, as the operator, in a terminal
pack claude (./harness-claude/, commit 9f2c1e0), of kind harness, into the yard
  harness claude: change — overrides the build's built-in
  effective behavior (unchanged fields included):
    trust: dialog and cursor from the build; answers from this import;
      env from the build, every entry printed whole
    flags, from the build: always, model, unattended, version, one_shot,
      and every permission preset with label, args and description printed whole
    login_recipe, from the build: verification, argv, every method, open_url and input
    fetch: verification, version, path, run, and every target's url, sha256, size and member
    every remaining field: printed whole
  changes against the build:
    trust.answers: ["Yes, I trust this folder"] -> ["Yes, I trust this folder", "Trust this workspace"]
    errors: 14 patterns -> 15
Apply pack claude to the yard? 1 object to write or remove.

$ yardr harness list
KIND   HARNESS       FILE   SOURCE
claude Claude Code   v1     pack claude, imported 17 Oct from ./harness-claude/ — the built-in changes fields this import controls: yardr pack check claude --builtin compares; yardr pack apply claude --builtin adopts it
codex  Codex         v1     the build
...

$ yardr pack check claude --builtin
pack claude (embedded in yardr d5d43156…), of kind harness, into the yard
  …the same complete card, with the standing override as old and the built-in as new…
```

On footplate, a run ask for `yardr pack apply claude` shows the same complete card from the server's embedded claude pack. The operator's approval applies exactly that build; a directory or URL override still begins in a terminal. After a deploy that changes claude's overridable built-in fields, the yardmaster receives one mail naming the drift and the `--builtin` comparison command. The exact rendering is the builder's; the content and the enforcement are the design's.

## 4. Left out

- **Version-keyed sections of the file format** (a `versions:` map, or one file per harness version). Tolerant lists cover the drift yardr has met so far; the seam for the rest is `FileVersion`, and a version 2 is designed when a harness forces it.
- **An update command, a check that polls yardr.dev, or a registry protocol.** Release notes announce, server start notices a changed built-in, and explicit check or apply commands update. A push of "a newer claude pack exists" is a yard phoning home, which yardr does not do.
- **Directory or URL packs on the run-ask row.** The existing row's security comes from reading the server's embedded bytes and holding approval to them. Hosted yards receive new built-ins by deploy and can adopt them on a card; a custom directory or URL import still starts in a terminal.
- **A semantic classifier of pane text, environment entries, or harness flags.** Text matching cannot prove that an arbitrary dialog is folder trust, and an argument yardr has never seen cannot be classified as safe. Only `trust.answers` is importable into automatic action; flags and login recipes stay build-pinned rather than acquiring a pretend classifier.
- **An automatic merge of an override with a new built-in.** `pack apply <kind> --builtin` adopts the built-in and ends the override. Preserving local changes is a human edit informed by the card, not a three-way merge with no ownership rules.
- **Signed packs or provenance beyond the record.** The record already holds the source and installed file's sha256; who may vouch for a pack is a question for packs generally, not for this kind.
- **Per-depot or per-group harness files.** One effective file per kind per yard; a group that needs different arguments has `args`, as today.
- **Answering any dialog but the built-in folder-trust one**, and typing into the login screen. Both stay code's refusals, unchanged.
- **Idle, working, blocked, done.** Herdr decides these from its own files, today and after; no harness file speaks of them.

## 5. Open questions

mckean answered all three questions on 17 Oct 2026 (asks 6724, 6725 and 6727; answers 6728–6730). None remains open; the proposal follows his picks.

**1. May an imported pack change which answer yardr picks in a harness's trust dialog?** Option A, answer only: an import may change or add answers, never the dialog text; this keeps the reason for the design — Kimi's renamed answer can be fixed by a pack — while the core still answers only the build's known dialog. Option B, pin all of trust: simpler, but a renamed answer still needs a release, despite yardr-tzkk's clear fault. Option C, make dialog and answer importable: most flexible, but the card is the only wall against naming a permission prompt as trust. I recommended A. **Decided: A.** The design also keeps the cursor and trust-bypassing environment with the build's dialog; they are part of which dialog is answered or skipped, not which accepting answer is chosen.

**2. Are release notes plus a drift line enough for a yard to learn of updates?** Option A, enough: no new runtime notification, but a yard that upgrades without reading notes or running `harness list` learns nothing. Option B, also tell the operator: after an install, a yard whose import differs from a newer built-in mails the yardmaster; it uses an event the yard already has and costs one local comparison and marker. I recommended B. **Decided: B.** The mail is to the yardmaster, who can involve the operator and propose the card; nothing applies automatically.

**3. Should applying a harness pack stay terminal-only, or may it use a card too?** Option A, terminal-only: keeps a consequential change at a desk but means a hosted operator with no terminal cannot apply one. Option B, a card too: operator-only, showing every flag, login command and download whole, using footplate's existing run-ask surface. I recommended B. **Decided: B.** The existing embedded-only bound of that surface stays; this decision does not introduce URL fetching into run asks.
