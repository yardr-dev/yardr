# Limits by provider, not by harness kind: a group may say provider=<name>

Design yardr-t5ts, proposed 2026-10-12. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

Design for bead yardr-t5ts (flow `design`, stage `draft`). A yard is one installation of yardr; a group is who works a stage; a runner is how a group's work starts, and `herdr` is the runner that starts an agent; a harness is the agent program herdr starts (claude, codex, kimi, pi); a harness kind is which one. A **provider** in this document is the subscription a harness's usage bills to, named by the name a limits command takes for it (`zai`, `kimi`); a **limits source** is a declared source whose file has a `limits` key, naming the operator's command that says what such a subscription still carries; the **kinds table** is that key's `kinds` map. Signalbox is the 3D yard, a view of its own in a second depot; its **silo** (a tower in the picture) is one provider's quota as the page draws it. See docs/glossary.md for all of yardr's words.

## 1. The question

mckean, 8 Oct 2026, from airy: "my friend uses z.ai but via pi harness, so the signal box draws the silo for the harness instead of the subscription". Today a limits source's kinds table maps a harness kind to a provider's name, so one pi subscription per yard works; but a kind can front several subscriptions (pi with Z.ai in one group, pi with OpenAI in another), and then the subscription is the group's, not the kind's. The bead asks for a `provider` setting on a herdr group that wins over the kinds table for that group, for `yardr limits` and the daemon to resolve it, and for clients to read it.

This bead is older than much of what it speaks of, so first, what of it is already built, what another design already decided, and what is left.

**Already built.** The limits machinery exists and is keyed by kind end to end: the `limits` key with its kinds table (`internal/source/declaration.go`, `Limits.Argv` substituting `{provider}`); `limits.Ask` asking the first source that lists the kind (`internal/limits/limits.go`); `yardr limits [kind]` asking per kind in use with `unmapped` for the rest (`internal/cli/limits.go`); the daemon's `rate_limited` path asking for the harness's kind when it raises `session_harness_error`, keeping the answer 60 seconds and waiting for a window that resets within six hours (`internal/dispatch/harness_limits.go`, `internal/dispatch/harness_reset.go`, docs/groups.md); doctor noting a kind in use that no source answers for (`limitsPart` in `internal/cli/limits.go`); and `GET /limits` answering what the command answers (`internal/web/limits.go`). Group settings already work as the bead wants a new one to: `yardr group set <name> key=value` (bare pairs, not `--set`) writes runner config the store holds to `ConfigKeys` (`internal/store/configkeys.go`, `internal/cli/ops.go`).

**Already decided by another design.** Design yardr-zyzp (2026-10-11-yardr-zyzp-web-serve-ui.md) was withdrawn the day it was decided: "signalbox stays a view of its own and yardr does not serve another front end's files. Only GET /limits (bead 2) was built." It established what this bead's API paragraph must now follow: "The view's JSON is the yard's read API", and "signalbox already follows the view", reading `/depots`, `/flows`, `/groups`, `/routes`, `/crew`, `/peers`, `/beads`, `/sessions`, `/deps` and the `/events` stream from `yardr web` (verified still true in signalbox's `scripts/yard.mjs`). Memory mem-hzpk holds the line: "What both need belongs in the API." Memory mem-hz71 holds that integrations are packs and the limits command stays the operator's alone; mem-j0y0 allows breaking changes with no upgrade paths; mem-htz2 prefers the mechanism that exists.

**What is left.** The bead's question itself: no per-group provider exists anywhere (verified: `ConfigKeys` has `kind`, `model` and the rest, but no `provider`; `limits.Ask` takes a kind; signalbox's `providers()` in `src/layout.ts` still returns the kinds of the agent-running groups and crew). Four of the bead's pointers have gone stale with age, and the proposal corrects them: signalbox reads the web API, not the socket API (docs/api.md has no groups call at all: `Settings`, `Crew` and the rest in `internal/rpc/api.go`, no `Groups`); `group set` takes bare `key=value`, `--set` is on `group add` and `crew add`; the accepted config keys live in `internal/store/configkeys.go`, not `internal/store/routing.go`; and `yardr limits` is documented in docs/integrations.md ("Say what a subscription still carries"), docs/groups.md and docs/web.md — there is no docs/limits. None of that ends the bead: what is left is designed below.

## 2. What exists today

**The limits key.** A declared source says limits when its file has a `limits` key: a `command` (a list run without a shell, one argument at least holding `{provider}`, `ProviderMark` in `internal/source/declaration.go`) and `kinds`, mapping "a harness kind (a group's or a crew member's kind) to the provider's own name for it". `Limits.Argv(kind)` substitutes the mapped name; a kind not in the table has no limits known through that source. The key is the operator's alone to add: "no pack brings it", and a pack declaration with one is refused. Adding a file is refused for a kind another source already answers for: one source answers for a kind. All this is the contract docs/integrations.md prints with a whole aiquokka file.

**Asking.** `limits.Ask(ctx, st, home, kind)` (`internal/limits/limits.go`) takes the sources that say limits, by name (`Answerers`), and asks the first whose kinds table lists the kind: one run of its command, stdin closed, in the yard's home, bounded by `Timeout` (30 seconds, never cut short for a command that answers). No source listing the kind is `*NoSource`, not a provider failure. The answer is one JSON object with `provider`, `plan` and `windows`; a window is used up at 100 percent or `used` at `limit`, and of those the one resetting last is what an agent waits for (`Report.UsedUp`). Nothing asks by itself and nothing is remembered: "every call of Ask is one run of the command".

**`yardr limits [kind]`.** With a kind it asks for that one; without, for every kind `kindsInUse` names that a source answers for: the yard's `default_kind`, then every kind a herdr group or crew member names (`harnessUses` in `internal/cli/needs.go`; a config naming no kind "runs on nothing yardr can name, and is left out"). A kind in use that no source lists is reported under `unmapped`, not asked. Each answer prints the report's windows, how far each is used and when it resets, and the window an agent waits for; `--json` prints per kind the report under `limits`, the waited-for window under `window` and `resets_at`, or the reason under `limits_unknown`. Any unknown exits 1. Nothing in this repository besides the command, the daemon and the `/limits` route reads that shape.

**The daemon's `rate_limited` path.** When a harness stops on a usage limit, `harnessError` for a session and `crewHarnessError` for a crew member (`internal/dispatch/harness.go`) call `harnessLimits(ctx, kind, data)` with the kind of the session's group, respectively the crew member (`agents.Kind`: config `kind`, else the built-in default `claude`). The event carries the report under `limits`, the waited-for window under `window` with `resets_at`, or the reason under `limits_unknown`; the hint begins with it in words ("kimi's 5h window is used up and resets at 00:02 (in 42m)"). What a provider said, or that it failed, is kept 60 seconds in the daemon's memory, keyed by source and the provider's name in the file, so agents stopping together are one run. At the wake of a window that resets within six hours, `windowOpen` (`internal/dispatch/harness_reset.go`) asks once more before prompting. Docs/groups.md draws both halves ("A usage limit says its window and when it resets", "A window that resets within six hours is waited for"), including that "Another group on the same subscription is not held".

**Doctor.** `limitsPart` says which source answers for which kinds ("aiquokka for claude, codex, kimi"), and notes each kind in use no source answers for: "%s is in use (%s) and no source says its limits (limits.kinds)". It asks nothing unless `--try`, which asks once per kind in use.

**Group config.** `ConfigKeys` (`internal/store/configkeys.go`) is what yardr reads from a group's or a crew member's config; `kind` and `model` are shared (`Of` unset) herdr keys. `PutGroup`, `SetGroup` and `PutCrew` refuse a key nothing reads, so `provider=zai` is refused today with the keys the runner takes. `yardr group set builders provider=zai` would print, as every such change does: `group builders saved` and `provider: (not set) -> zai` (`changeLines` in `internal/cli/crew.go`). `yardr group list --json` prints the groups whole (`a.out(gs, ...)` in `internal/cli/ops.go`), and `GET /groups` answers the same rows: docs/web.md's rule is "whatever a list command prints with `--json`, the view answers at a route of the same name, with the same fields", the rows "the command's own, of the same Go types". So a new config key appears in both with no further change. Today no list resolves: `/groups` rows are `store.Group` as stored (`internal/web/lists.go`), and `/crew`'s `kind` is config `kind` as stored, absent when unset (`internal/web/crew.go`). But `/crew` already adds page fields beside the command's (`running`, `agent`, `kind` and the rest in `CrewRow`, docs/web.md), the pattern a resolved field follows.

**The web's `/limits`.** `GET /limits` (`internal/web/limits.go`) answers what the command answers with no kind named, field for field, with `unmapped` beside it: at most one run of the operator's command per kind a minute, shared between readers, a failing provider nulling its entry without failing the route.

**Signalbox today.** `providers(yard)` (`src/layout.ts`) is "the kind of every group that starts agents, then of every crew member, each once" (manual and exec groups excluded). `src/project.ts` builds each group as name, runner, limit, members with `kind` picked from the group's web config, and each crew member likewise. The quota is still asked by signalbox's own server, which runs `aiquokka --json` at most once a minute (`quota()` in `scripts/yard.mjs`, `QUOTA_EVERY` in `scripts/serve.mjs`) — not from yardr's `/limits`. A tower matches its quota by key (`refuel` in `src/scene.ts` finds the quota entry whose `key` equals the tower's `provider`, a group's kind today; the silo's name is the quota's `name`, the key until it answers), which is why a pi kind draws a pi silo whatever subscription it burns. (`livery` in `src/palette.ts` colours by that key, "a group's kind".)

**This yard, verified.** The groups run kinds claude, codex, kimi, grok and muse (`yardr group list`); the crew are yardmaster on claude and brakeman on kimi; `pi` is a known herdr kind (`HerdrKinds` in `internal/agents/models.go`). No source of this yard has a limits key, so `yardr limits` prints the no-source lines and asks nothing.

## 3. The proposal

The existing mechanism carries it: a runner config key, the kinds table as the default, the first source by name answering, one ask per subscription. What is new is one key, one resolution, and asking by the resolved provider.

**The setting.** `ConfigKeys` gains `provider`: a string, read from a herdr group's config (`Of` group; open question 1 is the crew). A person types `yardr group set builders provider=zai` (or `group add --set provider=zai` when the group is written whole); `--unset provider` removes it. The value is the name the limits command takes, exactly as a kinds table's values are, and is otherwise unchecked at set time, as `model` is: a name no source answers for gets no answer, and doctor says so (below). Unset, everything resolves as today: nothing changes. The key flows to `group list --json` and `GET /groups` inside `config` with no further change on either side; the resolved provider the web carries beside it is "The web" below.

**Resolution.** The provider a group burns is its `provider` setting when set, else the kinds table's mapping of its kind, as the bead asks (a crew member's, as open question 1 was answered). The answering source follows the same split: with the setting, the first source by name whose kinds table *names* that provider among its values; without it, the first whose table *lists* the kind, as today. So a group with `provider=zai` is answered by a source whose kinds have no `pi` but name `zai` somewhere, and `yardr limits` runs its command with `zai`. A kinds table may name a provider no group uses, as the bead allows. Where two sources name one provider, the first by name answers, deterministically as `Ask` picks today; no new cross-source refusal is proposed (the one-source-per-kind refusal stays exactly as it is). Where no source answers for the provider, the ask fails as `NoSource` does today, naming the provider, and the reason reads like today's ("no source of this yard answers for provider zai (a source with a limits key whose kinds name it)").

**Asking.** `limits.Ask(ctx, st, home, kind)` stays for the callers that ask for a bare kind: `yardr limits <kind>` and `yardr source check`, which checks the declaration's mapping, not any group. Beside it, `Answerer` gains what the resolution needs: `Provides(name)` (the name is among the kinds values), `AskName(ctx, name)` (one run with the name substituted directly, through a `Limits.ArgvName`), and a top-level `AskFor(ctx, st, home, kind, provider)` that resolves and asks once; a `Resolve` helper both use lets the web's rows resolve without asking. The daemon's 60-second memory is already keyed by source and provider name, so it stands unchanged.

**`yardr limits` with no kind** lists by provider: the kinds in use are resolved to their providers, each distinct provider asked once, and each row names the provider, the groups and kinds burning it, and the report (or the reason under `limits_unknown`, which is where a provider no source answers for shows). Kinds in use that resolve to nothing stay under `unmapped`, as today. A person would see, for two pi groups on different subscriptions:

```text
zai  aiquokka says (provider Z.ai): burned by groups builders, nightshift (kind pi)
  5h      100% used (100 of 100)  resets 00:02 (in 42m)             used up
  an agent of these groups waits for the 5h window, which resets 00:02 (in 42m)
openai  aiquokka says (provider OpenAI): burned by group dayshift (kind pi)
  no window is used up
```

`--json` prints one entry per provider with the burning groups and kinds beside the report, `window`, `resets_at` or `limits_unknown` as today; the per-kind shape goes (open question 3 is the alternative). The bare `yardr limits <kind>` form is unchanged.

**The daemon.** `harnessError` passes the session's group's provider beside its kind, and `harnessLimits` and `windowOpen` resolve and ask for it; the crew path is unchanged (open question 1). The event's fields are unchanged, and the hint keeps the kind in its words ("pi's 5h window is used up …"), since the report under `limits` already names the provider that answered; no prose churn. The hold beside a waiting session is unchanged: it is per group and per model already.

**Doctor.** `limitsPart` keeps its kinds notes and gains the provider's: for each herdr group whose `provider` no source's kinds values name (a crew member's, as open question 1 was answered), "%s names provider %s and no source answers for it (limits.kinds)". With `--try` it asks once per distinct resolved provider rather than once per kind, and says which it tried.

**The web.** `GET /limits` keeps its contract — what the command answers with no kind named — so it answers the by-provider shape with the same cache, keyed by provider instead of kind, and docs/web.md's row for it is rewritten. `/groups` and `/crew` gain the resolved provider beside what they answer today, so a client needs no kinds table of its own, as the bead asks: signalbox reads `/groups` (`scripts/yard.mjs`) and projects only `kind` from each config (`src/project.ts`), so the setting alone inside `config` would leave every unset group to its kind. Each herdr group's row carries `provider`: its `provider` setting when set (even where no source answers for it, so doctor's note and the empty tower agree), else the kinds table's mapping of its kind through the first source by name that lists it, as `Ask` picks; absent for a herdr group with neither, and for groups of every other runner, which burn no quota. Each herdr crew member's row carries the same, from its own setting where open question 1 allows one, else from its kind; absent likewise. The rows stay the command's plus one field: `/groups` gains a row type embedding `store.Group` with `provider,omitempty` (the one exception to the "same fields" rule for a JSON-only list, following `/crew`'s page fields), and `CrewRow` gains the field beside `kind`. Resolving reads the sources' tables (`Answerers`, as `/limits` already does per request) and runs no command. The socket API is untouched: signalbox does not read it, and the yardr side needs nothing there. `group list --json` and `crew list --json` stay as stored, the setting visible inside `config`; docs/web.md records what the two routes add.

## 4. Left out

Several providers in one group: the bead puts it outside, and one setting holds one subscription. Aiquokka itself, whether a provider reads another login: outside, as the bead says. Per-model providers: no provider answers by model (docs/integrations.md). Choosing an account: the answer stays the operator's login on the machine; a group whose `env_file` gives its harness another account is still not described by it, as the docs say today. A refusal for two sources naming one provider: first by name wins, no new rule. Any migration of the kinds table: unset groups resolve as today, so there is nothing to migrate (mem-j0y0). `yardr source check` stays per listed kind: it checks the declaration. The bare `yardr limits <kind>` stays kind-based: with no group there is nothing to resolve from. A resolved `provider` on `group list --json` itself: the web carries it, the command stays stored, and `yardr limits` says what each provider carries and who burns it. The hint's words keep the kind: the report says who answered. Signalbox reading its quota from `/limits` instead of running aiquokka itself: not proposed; the follow-up keeps `quotaOf` as it is, and that move, if wanted, is its own bead later.

## 5. Open questions

1. **May a crew member set `provider` too, or only a group?** (a) Group-only, as the bead asks (`Of` group): the crew's `rate_limited` path stays kind-mapped, and a crew member on pi with a Z.ai login keeps drawing a pi silo until a later bead. (b) The key shared, like `kind` and `model` (`Of` unset): `yardr crew set` takes it, the crew path resolves it, and signalbox's crew towers follow; it costs the same single `ConfigKeys` row either way. I would take (b): one rule over a setting per case, and crew members burn quota — signalbox counts their kinds today.
2. **Does the resolved provider appear on the list commands too, or only on the web?** (a) Only on the web, as proposed: `/groups` and `/crew` carry it, the commands stay stored, and docs/web.md records the one exception for `/groups` (following `/crew`'s page fields). (b) On `group list --json` and `crew list --json` as well, keeping the "same fields" rule exact: new row types in the commands too, and lists reading the limits sources wherever they print. I would take (a): the bead's client is signalbox, which reads the web, and the commands' stored rows plus `yardr limits` already answer an operator.
3. **Does `yardr limits --json` break its per-kind shape?** (a) Rows per provider with the burning groups and kinds, as proposed: the clean break mem-j0y0 allows, and no reader in this repository parses the shape. (b) Keep one row per kind, each annotated with its resolved provider, the shared report repeated: compatible, but repeats answers and keeps the kind as the unit the bead moves away from. I would take (a).

## 6. The beads it would become

In the order they land. Each runs the depot's test command (`sh .yardr/test` in the worktree) on its last commit; none adds a test that reads a file by path, so none touches that script's table.

**1. A herdr group may say `provider`, and limits can ask for it.** Goal: the setting exists, resolves, and is asked. Where to look: `ConfigKeys` in `internal/store/configkeys.go` (the row; group, or shared, as open question 1 was answered); `internal/source/declaration.go` (`ArgvName` beside `Argv`); `internal/limits/limits.go` (`Provides`, `AskName`, `AskFor` beside `Ask`). Done when: `yardr group set <herdr group> provider=zai` saves and prints the change, `--unset` removes it, and any other runner refuses the key with the keys it takes; `AskFor` with `provider=zai` runs the first source naming `zai` among its kinds values even where no table lists the kind, and fails naming the provider where none does; a group without the setting resolves through the kinds table exactly as `Ask` does; unit tests in `store` (the key, the refusal) and `limits` (resolution, first-by-name, the failure). Depends on nothing.

**2. `yardr limits` lists by provider, and doctor notes an unanswered provider.** Goal: the command and doctor as section 3 says, with docs. Where to look: `internal/cli/limits.go` (`limitsCmd`, `kindsInUse`, the new row, `limitsPart`); docs/integrations.md ("Say what a subscription still carries"), docs/groups.md ("Changing a group" for the setting). Done when: with two groups on one provider the command asks once and names both groups; a group with `provider=zai` and kinds tables without its kind is asked as `zai`; a provider no source names shows under `limits_unknown`; kinds resolving to nothing stay under `unmapped`; bare `yardr limits <kind>` is unchanged; doctor notes a group whose provider no source answers for (a crew member's, as open question 1 was answered), and `--try` asks once per provider; tests in `cli` hold the grouping, the single ask and the notes. Depends on 1.

**3. The daemon asks for the group's provider at a usage limit.** Goal: the `rate_limited` path resolves the setting. Where to look: `harnessError` in `internal/dispatch/harness.go`, `harnessLimits` and `askLimits` in `internal/dispatch/harness_limits.go`, `windowOpen` in `internal/dispatch/harness_reset.go`; docs/groups.md ("A usage limit says its window and when it resets"). Done when: a session of a group with `provider=zai` whose harness stops on a usage limit carries the report asked as `zai` under `limits` with `window` and `resets_at`, or the reason under `limits_unknown` naming the provider; the wake asks the same way; the hint keeps the kind in its words; the 60-second memory coalesces two such sessions into one run; tests in `dispatch` hold the resolution, the wake and the memory. Depends on 1.

**4. `GET /limits` answers by provider.** Goal: the route keeps its contract with the command. Where to look: `internal/web/limits.go` (entries, the per-provider cache), docs/web.md (the `/limits` row and paragraph). Done when: the route answers the command's by-provider shape with `unmapped` beside it, asks at most once a minute per provider however often it is read, and nulls a failing provider's entry without failing the route; tests in `web` hold the shape and the cache. Depends on 1 for the resolution and on 2 for the shape.

**5. `/groups` and `/crew` carry each row's resolved provider.** Goal: the web answers what signalbox needs, as section 3 says. Where to look: `Groups` and `handleGroups` in `internal/web/lists.go` (the row type embedding `store.Group`), `CrewRow` in `internal/web/crew.go`, docs/web.md ("The lists" and the `/crew` paragraph). Done when: a herdr group's row carries its `provider` setting where set, else its kind's mapping through the first source by name that lists it, and carries none where neither answers or for a group of another runner; a herdr crew member's likewise (from its setting as open question 1 was answered, else its kind); `group list --json` is unchanged; resolving runs no command; tests in `web` hold the override, the mapping, first-by-name, and the absent cases. Depends on 1 for the resolution.

After these, the signalbox follow-up from the bead (a bead of the signalbox depot, not yardr's): `providers()` in `src/layout.ts` takes each group's and crew member's `provider`, falling back to the `kind` only where the row carries none (a yard with no limits source keeps today's towers); one silo per distinct provider; the tower already takes its label from the quota's `name`, the key until it answers (`refuel` in `src/scene.ts`), and `livery`'s "a group's kind" in `src/palette.ts` becomes the provider. It depends on yardr bead 5 (the resolved field on `/groups` and `/crew`); its `project.ts` allow-list gains the field on its side.
