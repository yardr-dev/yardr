# The yard installs a landed yardr itself, checks its health, and rolls back a build that fails

Design yardr-6ja6, proposed 2026-10-14. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. The store is `yard.db` in the yard's home, owned by the yardr server, which every other yardr process reaches over a unix socket. The daemon is the process that dispatches beads and starts agents. A depot is a git repository or a plain directory beads are worked in; a bead is one durable piece of work. The assembly is the group that tests an approved bead and lands it on the base. The operator is the person who runs the yard; the yardmaster is the crew member that coordinates. A build is one compiled yardr binary, named by the 12-character revision it was built from. See docs/glossary.md for all of yardr's words.

## 1. The question

mckean, 14 Oct 2026: the yardmaster installs yardr by hand after every landing on depot yardr (cd the checkout, git pull --ff-only, go install .), about ten times on 14 Oct alone. mckean: "a health check could make sure the new binary works as expected, that way rollback could be automated; also health could be on the web interface as well for other services. Not sure if doctor is the same thing." The question is whether the yard can do that hand step itself after a landing: install the landed build, check that the new binary works, put the previous one back when it does not, and show its health on the web view for other services.

## 2. What exists today

### 2.1. The server and the daemon replace themselves, and never downgrade

The server is the one process that owns the store file (`internal/server/server.go`, `Run`). It watches the binary it was started from: when a new build is installed over that path it drains (up to 5 seconds for connections to go idle, up to 10 more for calls still running), closes the store and execs the new build in its place, keeping its pid (`runner.run`, `serve`, `version.Binary.Replace`). A client of another build that calls, or a 10-second backstop, triggers the handover; the new build logs a `server_replaced` event with the `from` and `to` revisions once it owns the store. When the exec fails the old build keeps serving. The daemon does the same between dispatch passes, checking at least every 10 seconds, and the new build logs `daemon_replaced` (`internal/dispatch/dispatch.go`, `replace`, `noteReplaced`). This is documented under "How a newer build takes over" in docs/configuration.md.

Three facts about that mechanism shape everything below. First, a replacement is one way only: `version.Binary.Replacement` refuses an installed build that is older than the running one or of the same revision (`Newer`), logging a `replace_skipped` event with the reason instead, "so a downgrade never meets the store's one-way migrations". Putting the previous binary back over a running new one therefore does not hand anything back; the processes must be restarted to run older bytes. Second, an `exec` keeps the pid, so a daemon that runs as a login service upgrades with no part from the service manager, and the service's file names the binary by the path `go install` writes to, so the next login starts the new build too. Third, on macOS a new build is a new program to the privacy rules (`go install` signs ad hoc), so a grant of Full Disk Access given to the old build may not cover the new one; restoring the old bytes restores the old grant with them.

Calls in flight during a replace are covered: a client retries for 30 seconds (`rpc.ReplaceRetry` in internal/rpc/client.go), longer than the 15-second drain and the new build's start, and a client that finds a live pid but no answer waits as long rather than starting a second server (`server.Connect`). Sessions live in the store, so the new daemon carries on with them, and the web view is a client like any other command: it does not replace itself and keeps running the build it was started from until it is restarted.

### 2.2. Health exists in pieces: Ping, status, doctor

Every rpc reply carries the server's revision and pid in headers (`X-Yardr-Revision`, `rpc.PIDHeader`), which `rpc.Client.Owner` reads; `server.Describe` (internal/server/server.go) reports pid, revision and start time of the server that answers, starting none. `yardr status` (internal/cli/status.go) lists what runs now and where each part is reached: the server with its build, the daemon as running or not from its lock file (`daemon.lock`, `readDaemon` in internal/cli/service.go), every web view from the records views keep in `<home>/webviews` with the build each runs (internal/cli/webviews.go), and one line for the backups. It is read-only, starts nothing, holds facts only ("what is wrong or missing is yardr doctor's"), and exits 0 on any yard. `yardr doctor` (internal/cli/doctor.go, docs/doctor.md) is the other half of the split: it says what is wrong or missing and exits 1 on a fault. It is read-only too — it installs nothing, changes nothing in the store, starts no server — and it is already the documented check to run "after an upgrade". But its verdict covers the whole yard: a program missing from the machine fails it, a stopped server is a note rather than a fault, and it knows nothing of builds and revisions. Neither command takes an expected revision, and neither can say "this yard runs build R".

The daemon's build is recorded nowhere. Its liveness is the lock alone; `daemon_replaced` names the new build only when the daemon got there by replacing, while a daemon started fresh (`yardr daemon start`) logs nothing of its build.

### 2.3. Migrations are one-way, and the store refuses an older reader

`store.Open` (internal/store/store.go) runs every migration inside one update transaction and stamps the schema version (19 today), before the caller listens or serves. A server that answers on a build has therefore opened and migrated the store on that build; a migration that fails never listens. `checkSchema` (internal/store/migrate.go) refuses a store stamped newer than the build knows (`ErrNewerSchema`: "run the yardr that wrote it (or newer)"), so an old binary answers for itself whether it can read the current store: it starts, or it refuses with that error. The migrations' own comments say, version by version, what an older build would misread, which is why the replace path refuses downgrades.

Copies of the store are an existing mechanism. `Store.Backup` (internal/store/backup.go) streams a consistent copy while the yard keeps serving, through a temporary file renamed into place, and `yardr store backup <path>` calls it. The daemon keeps dated copies (`yard-<UTC>.db` in `<home>/backups`) once `backup_every` is set; a file with any other name there is never removed. A copy that cannot be made is one `backup_failed` event, of the class `attention`, with the daemon retrying on a backoff and saying nothing more until a copy succeeds and a later one fails. Docs/configuration.md ("Copies of the store") gives the restore recipe: `yardr down`, put the copy in the store's place, `yardr up`.

### 2.4. The assembly lands through a script the operator installed

The assembly is not built in; it is a composition (docs/line.md, section 4): a stage routed to an `exec` group whose script lands the bead, with `--limit 1` making a serial merge queue. Depot yardr merges directly to `main` with `contrib/assembly/merge-local`, installed from `main` to `~/.yardr/scripts/` — installed from `main` rather than run from a checkout, so a bead branch never changes how it is landed. The starter pack carries the same script (`packs/starter/scripts/merge-local`; the two copies are identical today) for yards set up by `yardr depot init`. The script runs on the yard's own machine as the daemon's child, with the daemon's environment (`internal/runner/exec.go`, `inherited`), the depot's path, base and test command in `YARDR_DEPOT_PATH`, `YARDR_BASE` and `YARDR_TEST`, and this yardr in `YARDR_BIN`. It rebases, runs the depot's test command with `YARDR_LANDING=1`, fast-forwards the base, pushes, and advances the bead to merged with a note; every outcome ends in an advance, a close or a hold. A push that fails does not un-merge: the bead stays merged locally, the note says the push failed, and the yardmaster is mailed (`YARDR_NOTIFY`). Its exec session logs under `<home>/logs/sessions`, with a line saying how many seconds each step took.

### 2.5. The web view serves reads, and has no health route

The web view (internal/web) is a client of the store that changes nothing: every route registers GET, so the mux refuses other methods itself (`Server.routes` in internal/web/server.go). It has no authentication yet, so it listens on loopback only unless started with `--unsafe`, and refuses Host names that are not this machine's (`Listen`, `knownHost`). A page is one template plus one handler ending in `respond`, which serves the same data as JSON or HTML (docs/web.md, "Adding a page"); a route that needs no page can answer directly instead, as `/favicon.ico` does. Each running view records its listen address, pid, start time and revision in `<home>/webviews` while it runs, holding a lock on its record. There is no route a monitor, a proxy or footplate — the tool that sets yards up — can ask whether the yard is up.

### 2.6. Telling runs on events, attention, mail and notes

The yard's memory is the event log. The daemon and its runners report through `LogDispatch`, which accepts only the kinds in `DispatchKinds` (internal/store/events.go), so a socket client cannot pass off another kind as the yard's own; the server, which owns the store, logs any kind with `LogEvent`. `attention` is the class of kinds that need someone (`AttentionKinds` in internal/store/crew.go; docs/subscriptions.md): a kind added there reaches every crew member and subscription that names the class, whenever they were made — a new crew member's `--on` holds the class by default, so the yardmaster hears it. `backup_failed` is the closest precedent: a dispatch kind, of the class attention, saying a keeping-the-yard-whole step failed.

Mail (`yardr mail <name>`, internal/cli/crew.go) lands in a crew member's or a user's inbox; nothing nudges a person, they read with `yardr inbox`, and a user that set where they are told outside the yard (`yardr user set`) is told there (internal/store/usernotify.go). Notes on beads (`yardr bead note`, `yardr bead advance --note`) are how scripts report per-bead outcomes. No command today logs a dispatch event: every `LogDispatch` caller is the daemon itself.

## 3. The proposal

What follows is the smallest version under the draft's picks in section 5; if mckean takes another option on any question, that part is rebuilt. In one sentence: one new command, `yardr upgrade`, builds the depot's checkout, installs it, checks the yard runs it, and otherwise puts the previous build back; the assembly calls it after the merge when a setting names the depot; the web view answers the same facts on GET /health.

### 3.1. One command carries the install: `yardr upgrade`

`yardr upgrade` does mckean's hand step whole: from the checkout of the depot the yard setting `upgrade_from` names (a depot name; unset, the command refuses and nothing happens), it runs `go install .`, exactly as by hand. Before that it takes a consistent pre-install copy of the store (`Store.Backup`, the way `yardr store backup` does) to `<home>/backups/yard.db.before-install` — that directory, not `backup_dir`, so a rollback never depends on a volume that may be unmounted, and a name the daemon's pruning never touches — and copies the running executable aside to `yardr.prev` beside it, one generation, on the same filesystem so restoring it is a rename. It refuses when `go` is not on its PATH (doctor's machine checks are what say so by hand), when the depot has no checkout on this machine, and when `go install` would not write the binary this yard runs from (the GOBIN it resolves against its own executable path): installing bytes the server does not watch would verify nothing. Where a depot sits in a folder macOS protects, it warns that the new build may need its access granted again (the `protectedDepots` check behind doctor's note already knows), without failing.

The command is the same by hand and in the assembly: the operator runs `yardr upgrade` after pulling instead of `go install .`, and merge-local runs `$YARDR_BIN upgrade` after the merge (section 3.4). One implementation, tested once, serves both.

### 3.2. The gate is `yardr upgrade --check`: the yard runs this build, or it says so

`--check` is the health check as a pure predicate, read-only like doctor: it asserts that every yard process that runs, runs this build — the build of the `yardr` that was asked, which after an install is the new one, so no revision argument is needed. It exits 0 with one line per check, 1 with one line per failure, and `--json` prints the same verdict as data. A part the yard does not run is skipped and reported, not failed, as doctor skips the checks a stopped server cannot answer: a yard with no daemon running skips the daemon check, a yard with no web view skips the views. The four predicates are the bead's four, measured:

1. The server answers on this build: `server.Describe` revision equals the command's own. This implies the store opened and migrated — the server opens the store before it listens, and a migration that fails never listens — so no separate migration probe is needed.
2. The daemon holds its lock and runs this build: the lock is probed the way `readDaemon` probes it, on every sample of the run rather than only the last, so a daemon that flaps (a crash loop under its service manager) fails; the build is the `to` of the latest `daemon_replaced` or `daemon_started` event. `daemon_started` is new: the daemon logs it on every fresh start beside `noteReplaced`'s `daemon_replaced`, joining `DispatchKinds` but not the class attention — a start is routine. Whether a running daemon completes passes is left out (section 4): death is what an install causes, and death is what this catches.
3. Every recorded web view answers: one GET of `/health` (section 3.5) on each address in `<home>/webviews`. Views do not replace themselves, so this checks that they answer, not that they run anything new.
4. The store opened and migrated: implied by the first, as said there.

`upgrade` without `--check` polls `--check`'s verdict every 5 seconds up to `--timeout` (default 5 minutes: the 15-second drain, the new build's start and migration, the daemon's replace between passes, and the views). It starts a stopped server first, so there is always a server to verify, and leaves running what it started. It starts nothing else.

This is not doctor and not status, deliberately: doctor's verdict covers the whole yard, so a program missing from the machine would fail every install, and doctor is read-only while telling writes events; status holds facts only with exit 0 on any yard, and the gate is a verdict with an exit status. The codebase's own split — doctor checks, status lists — leaves the install gate wanting its own predicate, and keeping it inside `upgrade` keeps the novelty in one command instead of spreading flags over two.

### 3.3. Rollback restores the bytes and restarts the processes; the old build is the oracle on the store

When the bound expires with the yard not on the new build, `upgrade` rolls back: it copies `yardr.prev` over the installed path first, then stops the server and the daemon (`yardr server stop`, `yardr daemon stop`) and starts again only what ran before the upgrade. The order matters twice over. First, the self-replace path refuses downgrades (section 2.1), so restoring the bytes alone would only log `replace_skipped`; only a restart runs older bytes again. Second, restoring before stopping means anything restarted by a service manager in between picks up the old bytes — a crash-looping new daemon heals into the old one by itself. Restoring the old bytes also restores the old build's macOS access grants, which the new build may have lost.

Whether the store must go back too is answered by the old build itself: it is started on the current store, and if it refuses with `ErrNewerSchema` the pre-install copy is put in the store's place (the documented restore, minus `down`, which the rollback already did) and it is started again. No stamp is compared and no new reader is needed; the refusal exists for exactly this. A rollback that needed no restore loses nothing. One that restored loses what the window held — bounded by the timeout, minutes — so everything is told after the restore, never only before it: anything told earlier is rewound with the store. The two failure events (section 3.6) are therefore logged from the restored yard, by the restored binary.

If the old build will not start even on the pre-install copy, the yard stays down and the reason is in the assembly session's log (or on the operator's terminal, by hand). That bottom exists today for every bad install; the rollback strictly improves it by restoring first. Reaching outside the yard from a dead one — mail needs the server — is left out.

Builders and reviewers in flight run the installed binary, and an install mid-session must not break them. Replacing the file does not touch running processes; a new CLI invocation during the window runs old or new whole bytes, and a binary still being written does not parse, so it is not offered as a replacement. On the socket the drain and `ReplaceRetry` cover the handover, the daemon execs between passes with its sessions in the store, and streams end at the drain for their readers to resume. Two residuals stay, both bounded and named: a replace whose migration outlasts the 30-second retry fails the calls in flight, which their callers run again against the new build; and work in a macOS-protected folder can fail with "operation not permitted" until the new build is granted again, which the upgrade warns about up front and doctor says how to fix.

### 3.4. The assembly calls it after the merge, when the setting names the depot

`contrib/assembly/merge-local` — both identical copies, the other in `packs/starter/scripts/` — gains one step after the push and before the advance: when `upgrade_from` names this bead's depot, run the install and fold its one-line summary into the landing note and its seconds into the group's log line. The shape follows the push failure exactly: the code has landed, so a failed install never sends the bead back; the bead advances to merged with a note that says the install failed and what was put back, and the telling is the command's (section 3.6). The script has `set -u` without `set -e`, so the step handles the exit status explicitly, as the push does. A yard without the setting set, and every other depot, runs the script exactly as today. Two activations are the operator's, outside any bead: reinstalling the script from `main` after the step lands (the assembly runs the installed copy, so landing the script changes nothing by itself) and setting `upgrade_from` to `yardr`.

### 3.5. The web view answers GET /health

GET /health serves the same facts the gate checks, minus the verdict: the server's build and start time, whether the daemon holds its lock and on which build, the store's head sequence, and the view's own build, as JSON. It answers 200 whenever the view serves it, with a `status` of `ok` or `degraded`; only a yard it cannot read at all fails, through the existing error path. The code therefore says whether the view answers — a proxy keeps routing to a view that answers, even over a yard whose daemon is down — and the JSON says whether the yard is whole, for a monitor or footplate to read. Nothing it says is a secret: builds, a sequence number and booleans, all already on `yardr status`, served to the same audience as the rest of the view (loopback, or behind the operator's proxy). It is a machine route: no template, no menu entry, answered directly as JSON the way `/favicon.ico` is answered directly, reading nothing but what it reports — no line, no beads, no stream. The daemon lock probe (`daemonRunning`, `daemonPID`) moves from internal/cli to internal/config, beside the `DaemonLock` path it probes, so the route can use it; docs/web.md gains the row its "Adding a page" asks for.

### 3.6. Telling: two events, two mails, one note line

A failed install or a rollback is never silent. Two new event kinds say it: `install_failed` (the revision, the stage — build, install or health — and the reason) and `rolled_back` (from and to revisions, whether the store was restored, and the reason). Both join `DispatchKinds`, so the upgrade command can log them as the socket client it is, and the class attention, so the yardmaster hears them on its default `--on`, as it hears `backup_failed`. A success logs nothing new: `server_replaced` and `daemon_replaced` already record it. The command also mails the yardmaster and the operator (the settings of those names), which follows the yard's rules by itself: crew read their inboxes, and a user that set outside telling is told outside. And the landed bead's note carries the one-line summary, success or failure. Where an older binary does not know the new kinds yet — the release the feature lands in, rolling back with the binary from before it — logging refuses with "not a dispatch event", and the command carries on with the mails and the note; from the next release on, every binary knows them.

## 4. Left out

A yard installed from a release archive, not from a checkout, is out: there is no depot to build from and perhaps no Go toolchain, so the setting stays unset there and nothing changes. The next step after this lands is a bead for installing from a signed release instead of a checkout; the gate, the rollback and the telling are the same, only the build step differs.

The gate does not check that a running daemon completes passes — only that it runs this build and holds its lock throughout. A heartbeat would be a new periodic write for a failure installs do not cause; death and flapping, which they do, are caught.

The install does not quiesce the yard first: no bead is held, no agent is stopped. Builders in flight keep working through the handover (section 3.3); a store restore rewinds the window's records, which is why the window is minutes and restores happen only when the old build refuses the store.

Telling from a yard that cannot be restarted — the old build refuses even the pre-install copy — is the session log alone. Mail, events and notes all need the server, and an outside channel for a dead yard is its own design.

Two yards on one machine share the installed binary: each yard's assembly installs the same bytes, and the second install is a same-revision `replace_skipped`, harmless. No coordination is proposed for that.

## 5. Open questions

1. Where does the install step live: the assembly script (the draft's pick), the daemon pulling a landed build, or a separate flow stage? The script is where the merged commit is already known, already serialized one landing at a time, and already reporting per-bead outcomes; it costs a step in a script and nothing long-lived. The daemon pulling — noticing a landing on the depot and building it — would install even where the assembly ran elsewhere (a peer group), but costs a new watcher plus a minutes-long build inside the dispatch loop, stalling passes or needing background jobs. A flow stage after the landing would route every bead through one more group for an operation that is not per-bead work. The draft picks the script.
2. What carries the health check: `upgrade --check` (the draft's pick), a doctor flag, or status with an exit code? Doctor already owns post-upgrade checks by documentation, but its verdict covers the whole yard — a program missing from the machine would fail every install — and it is read-only while telling writes. Status with an exit code would break its facts-only, exit-0 contract. `--check` keeps the novelty in the one new command and stays hand-runnable. The draft picks `--check`.
3. When the new build migrated the store and then failed, restore the pre-install copy (the draft's pick), or stop and call for a person? Restoring is automatic and usually right: the window is minutes, and only a migration forces it. Its cost is the window's records, rewound, and the re-logging that must follow. Stopping instead — the old binary refuses the store, the yard stays down, the operator restores by the documented recipe — loses nothing silently but leaves the yard down until a person acts, over a failure the automation caused. Forward-compatible migrations as the standing rule (every migration readable by the previous release) would avoid the choice, at the cost of constraining every migration to come; the store's history is renames, which that rule forbids. The draft picks restore-with-oracle.
4. Off until turned on (the draft's pick), or on wherever it can? Off changes nothing for any yard that does not set `upgrade_from` — release installs, second yards, cautious operators — at the cost of one setting to set. On-by-default with detection (a checkout on this machine, Go on the daemon's PATH, a `go install` binary) would help new yards and surprise existing ones the first time it wrote their binary. The draft picks off.
5. What does GET /health promise: facts with 200 whenever it serves (the draft's pick), or the gate's verdict as 200/503? Facts-with-200 keeps the proxy's question ("does this view answer") separate from the monitor's ("is the yard whole", read from the JSON), and never drains a view that serves reads over a daemon that is down. 200/503 lets a bare uptime check alert without parsing JSON, at the cost of conflating the two questions. The draft picks facts with 200.

## 6. The beads it would become

In landing order; each is built, with its tests, in an isolated yard where it starts servers (`contrib/isolated-yard/isolated-yard`, per the depot's rules), and each carries its docs.

1. The daemon's start is an event, and the install's two failure kinds exist. Goal: a fresh daemon start logs `daemon_started` with the build it runs, and `install_failed` and `rolled_back` exist as dispatch kinds of the class attention, logged by nothing yet. Where to look: `noteReplaced` in internal/dispatch/dispatch.go (the `REPLACED_FROM`-empty branch), `DispatchKinds` in internal/store/events.go, `AttentionKinds` in internal/store/crew.go, docs/subscriptions.md (the class list). Done when: a fresh start logs `daemon_started` with `to` the running build, a replace still logs `daemon_replaced` and nothing else, the two failure kinds are accepted by `LogDispatch` and matched by `kind=attention`, the docs list them, and the kinds land before anything logs them so the next release's binaries already know them. Depends on nothing.
2. The web view answers GET /health. Goal: a machine route serving the yard's liveness facts as JSON — server build and start time, daemon lock and build, store head, the view's build — 200 with `status` ok or degraded whenever the view serves, the existing error path when the yard cannot be read. Where to look: `routes` and `data` in internal/web/server.go, the webviews records in internal/cli/webviews.go, the daemon lock probe (`daemonRunning`, `daemonPID`, moved to internal/config beside `DaemonLock`), the latest `daemon_replaced`/`daemon_started` and `server_replaced` events for the builds, docs/web.md ("Adding a page", step 6). Done when: the route answers the shape in section 3.7 with no template and no menu entry, reads nothing it does not report, is covered in `web_test.go` over httptest, and `daemon_started` from bead 1 names the build of a fresh-started daemon instead of "unknown". Depends on bead 1.
3. `yardr upgrade --check`: the yard runs this build, or it says so. Goal: the read-only gate — the four predicates of section 3.2 with skip semantics, one line per check, exit 1 on a failure, `--json` for the same verdict. Where to look: `server.Describe`, the moved lock probe, the replaced/started events, the webviews records with a GET of `/health`. Done when: run by hand it prints the shape in section 3.7; a server, daemon or view on another build fails with a line naming it; a missing daemon or view skips instead of failing; a flapping daemon lock fails; and it changes nothing (no server started, nothing stored). Depends on bead 2.
4. `yardr upgrade`: install the depot's build, verified, or roll back. Goal: the command of sections 3.1–3.3 and 3.6 — the `upgrade_from` setting (a depot name, unset is off) in the `KnownSettings` table, pre-install backup and previous binary, `go install` with the target check, the poll of bead 3's verdict, restore-and-restart rollback with the old build as the store's oracle, and the telling: the two events (carrying on with mail and note where an older binary refuses the kinds), mail to the yardmaster and the operator settings, the macOS protected-folder warning, docs/configuration.md. Done when: by hand it installs the checkout's build and prints the shape in section 3.7; a build that fails the gate is replaced by the previous one with the yard answering on it; a migration followed by a failure restores the pre-install copy and re-logs; only what ran before is restarted; and a yard without the setting is untouched. Depends on beads 1 and 3.
5. The assembly installs yardr after landing on the yardr depot. Goal: the merge-local step of section 3.4 in both identical copies (`contrib/assembly/merge-local` and `packs/starter/scripts/merge-local`): when `upgrade_from` names the bead's depot, run the install after the push, fold the summary into the landing note and the seconds into the log line, and always advance — a failed install keeps the bead merged, as a failed push does. Done when: a landing on the named depot installs and notes the outcome; a landing elsewhere runs exactly as today; and the note names that the step activates only once the operator reinstalls the script from `main` and sets `upgrade_from`. Depends on bead 4.
