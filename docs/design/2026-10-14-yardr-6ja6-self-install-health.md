# The yard installs a landed yardr itself, checks its health, and rolls back a build that fails

Design yardr-6ja6, proposed 2026-10-14. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. The store is `yard.db` in the yard's home, owned by the yardr server, which every other yardr process reaches over a unix socket. The daemon is the process that dispatches beads and starts agents. A depot is a git repository or a plain directory beads are worked in; a bead is one durable piece of work. The assembly is the group that tests an approved bead and lands it on the base. The operator is the person who runs the yard; the yardmaster is the crew member that coordinates. A build is one compiled yardr binary, named by the 12-character revision it was built from. See docs/glossary.md for all of yardr's words.

## 1. The question

mckean, 14 Oct 2026: the yardmaster installs yardr by hand after every landing on depot yardr (cd the checkout, git pull --ff-only, go install .), about ten times on 14 Oct alone. mckean: "a health check could make sure the new binary works as expected, that way rollback could be automated; also health could be on the web interface as well for other services. Not sure if doctor is the same thing." The question is whether the yard can do that hand step itself after a landing: install the landed build, check that the new binary works, put the previous one back when it does not, and show its health on the web view for other services.

## 2. What exists today

### 2.1. The server and the daemon replace themselves, and never downgrade

The server is the one process that owns the store file (`internal/server/server.go`, `Run`). It watches the binary it was started from: when a new build is installed over that path it drains (up to 5 seconds for connections to go idle, up to 10 more for calls still running), closes the store and execs the new build in its place, keeping its pid (`runner.run`, `serve`, `version.Binary.Replace`). A client of another build that calls, or a 10-second backstop, triggers the handover; the new build logs a `server_replaced` event with the `from` and `to` revisions once it owns the store. When the exec fails the old build keeps serving. The daemon does the same between dispatch passes, checking at least every 10 seconds (`CheckBinary`, default 10 seconds in `internal/dispatch/dispatch.go`), and the new build logs `daemon_replaced` (`replace`, `noteReplaced`). This is documented under "How a newer build takes over" in docs/configuration.md.

Three facts about that mechanism shape everything below. First, a replacement is one way only: `version.Binary.Replacement` refuses an installed build that is older than the running one or of the same revision (`Newer`), logging a `replace_skipped` event with the reason instead, "so a downgrade never meets the store's one-way migrations". Putting the previous binary back over a running new one therefore does not hand anything back; the processes must be restarted to run older bytes. Second, an `exec` keeps the pid, so a daemon that runs as a login service upgrades with no part from the service manager, and the service's file names the binary by the path `go install` writes to, so the next login starts the new build too. Third, on macOS a new build is a new program to the privacy rules (`go install` signs ad hoc), so a grant of Full Disk Access given to the old build may not cover the new one; restoring the old bytes restores the old grant with them.

Each process watches its own executable path (`version.Self`, from `os.Executable`), and every yard on the machine installed the same way runs from the same path. One yard installing a new build over that path therefore replaces every yard's server and daemon that watch it, whether those yards asked for it or not; a yard whose own install step is off still wakes up on the new bytes. There is no per-yard binary. There is a registry of yards, of a kind: every yard whose daemon starts at login has a service file in the user's service directory (`serviceDir`, `unitFile` in internal/cli/service.go) naming its home in `WorkingDirectory` and the binary it runs first in `ProgramArguments` (the launchd `plist`) or `ExecStart` (the systemd `unitFile`). `otherLoginYards` (internal/cli/login.go) lists those homes by globbing the daemon service files. A yard with no login service is registered nowhere.

Calls in flight during a replace are covered up to a point: a client retries for 30 seconds (`rpc.ReplaceRetry` in internal/rpc/client.go), longer than the 15-second drain and the new build's start, and a client that finds a live pid but no answer waits as long rather than starting a second server (`server.Connect`). Past the 30 seconds the client returns the error; it does not retry after its deadline (`Client.call`). Sessions live in the store, so the new daemon carries on with them, and the web view is a client like any other command: it does not replace itself and keeps running the build it was started from until it is restarted.

### 2.2. Health exists in pieces: Ping, status, doctor

Every rpc reply carries the server's revision and pid in headers (`X-Yardr-Revision`, `rpc.PIDHeader`), which `rpc.Client.Owner` reads; `server.Describe` (internal/server/server.go) reports pid, revision and start time of the server that answers, starting none. `yardr status` (internal/cli/status.go) lists what runs now and where each part is reached: the server with its build, the daemon as running or not from its lock file (`daemon.lock`, `readDaemon` in internal/cli/service.go), every web view from the records views keep in `<home>/webviews` with the build each runs (internal/cli/webviews.go), and one line for the backups. It is read-only, starts nothing, holds facts only ("what is wrong or missing is yardr doctor's"), and exits 0 on any yard. `yardr doctor` (internal/cli/doctor.go, docs/doctor.md) is the other half of the split: it says what is wrong or missing and exits 1 on a fault. It is read-only too — it installs nothing, changes nothing in the store, starts no server — and it is already the documented check to run "after an upgrade". But its verdict covers the whole yard: a program missing from the machine fails it, a stopped server is a note rather than a fault, and it knows nothing of builds and revisions. Neither command takes an expected revision, and neither can say "this yard runs build R".

The daemon's build is recorded nowhere. Its liveness is the lock alone; `daemon_replaced` names the new build only when the daemon got there by replacing, while a daemon started fresh (`yardr daemon start`) logs nothing of its build. Nor does any completed dispatch pass leave a trace: `Run` calls `Reconcile` in a loop (internal/dispatch/dispatch.go), every 30 seconds by default with more on wake-ups, writing no event and no stamp per pass. A daemon wedged mid-pass holds its lock exactly like a live one.

Doctor reads the home's files without the server: on a yard whose server is stopped it reports what the machine and the home say (docs/doctor.md, "A server that is not running"). A file the home holds is therefore readable, and reportable as a fault, even when nothing of the yard answers.

### 2.3. Migrations are one-way, and the store refuses an older reader

`store.Open` (internal/store/store.go) runs every migration inside one update transaction and stamps the schema version (19 today), before the caller listens or serves. A server that answers on a build has therefore opened and migrated the store on that build; a migration that fails never listens. `checkSchema` (internal/store/migrate.go) refuses a store stamped newer than the build knows (`ErrNewerSchema`: "run the yardr that wrote it (or newer)"), so an old binary answers for itself whether it can read the current store: it starts, or it refuses with that error. The migrations' own comments say, version by version, what an older build would misread, which is why the replace path refuses downgrades.

Copies of the store are an existing mechanism. `Store.Backup` (internal/store/backup.go) streams a consistent copy while the yard keeps serving, through a temporary file renamed into place, and `yardr store backup <path>` calls it. The daemon keeps dated copies (`yard-<UTC>.db` in `<home>/backups`) once `backup_every` is set; a file with any other name there is never removed. A copy that cannot be made is one `backup_failed` event, of the class `attention`, with the daemon retrying on a backoff and saying nothing more until a copy succeeds and a later one fails. Docs/configuration.md ("Copies of the store") gives the restore recipe: `yardr down`, put the copy in the store's place, `yardr up`.

### 2.4. The assembly lands through a script the operator installed

The assembly is not built in; it is a composition (docs/line.md, section 4): a stage routed to an `exec` group whose script lands the bead, with `--limit 1` making a serial merge queue. Depot yardr merges directly to `main` with `contrib/assembly/merge-local`, installed from `main` to `~/.yardr/scripts/` — installed from `main` rather than run from a checkout, so a bead branch never changes how it is landed. The starter pack carries the same script (`packs/starter/scripts/merge-local`; the two copies are identical today) for yards set up by `yardr depot init`. The script runs on the yard's own machine as the daemon's child, with the daemon's environment (`internal/runner/exec.go`, `inherited`), the depot's path, base and test command in `YARDR_DEPOT_PATH`, `YARDR_BASE` and `YARDR_TEST`, and this yardr in `YARDR_BIN` — the installed binary that started the daemon (`Exec.env`, `Exec.Bin`). It rebases, runs the depot's test command with `YARDR_LANDING=1`, fast-forwards the base, pushes, and advances the bead to merged with a note; every outcome ends in an advance, a close or a hold. A push that fails does not un-merge: the bead stays merged locally, the note says the push failed, and the yardmaster is mailed (`YARDR_NOTIFY`). Its exec session logs under `<home>/logs/sessions`, with a line saying how many seconds each step took.

A script whose yardr calls fail ends without an advance, which counts as a failed session; three failed sessions for one bead and stage hold the bead for a person (`MaxAttempts`, default 3, in internal/dispatch/dispatch.go, "holding bead after repeated failures" with a `gave_up` event). The session log stays on disk either way.

### 2.5. The web view serves reads, and has no health route

The web view (internal/web) is a client of the store that changes nothing: every route registers GET, so the mux refuses other methods itself (`Server.routes` in internal/web/server.go). It has no authentication yet, so it listens on loopback only unless started with `--unsafe`, and refuses Host names that are not this machine's (`Listen`, `knownHost`). A page is one template plus one handler ending in `respond`, which serves the same data as JSON or HTML (docs/web.md, "Adding a page"); a route that needs no page can answer directly instead, as `/favicon.ico` does. Each running view records its listen address, pid, start time and revision in `<home>/webviews` while it runs, holding a lock on its record. A view from before a route answers 404 for it — the catch-all at the end of `routes` — while serving everything else. There is no route a monitor, a proxy or footplate — the tool that sets yards up — can ask whether the yard is up.

### 2.6. Telling runs on events, attention, mail and notes

The yard's memory is the event log. The daemon and its runners report through `LogDispatch`, which accepts only the kinds in `DispatchKinds` (internal/store/events.go), so a socket client cannot pass off another kind as the yard's own; the server, which owns the store, logs any kind with `LogEvent`. `attention` is the class of kinds that need someone (`AttentionKinds` in internal/store/crew.go; docs/subscriptions.md): a kind added there reaches every crew member and subscription that names the class, whenever they were made — a new crew member's `--on` holds the class by default, so the yardmaster hears it. `backup_failed` is the closest precedent: a dispatch kind, of the class attention, saying a keeping-the-yard-whole step failed.

Mail (`yardr mail <name>`, `Store.Mail` in internal/store/crew.go) is a write to the store, so it needs the server; nothing nudges a person, they read with `yardr inbox`, and telling a user outside the yard is the daemon's work on its passes (`Reconcile`, "tell users outside the yard of what landed in their inboxes", in internal/dispatch/dispatch.go; the user's `notify` source in internal/store/usernotify.go). Notes on beads (`yardr bead note`, `yardr bead advance --note`) are how scripts report per-bead outcomes, and need the server the same way. No command today logs a dispatch event: every `LogDispatch` caller is the daemon itself.

Users are told of yard events by subscription: a user's yardr-source subscriptions are matched as a bead event is logged (`wtx.deliver` in internal/store/yardrsource.go), each match becoming a notification in their inbox with a push queued in the same write (`wtx.notify` through `queuePush` in internal/store/notifications.go), and the daemon sends each user's due pushes as one message (`tell` in internal/dispatch/pushes.go) through the source their record names, via `notify.Send` (internal/notify/notify.go), which reads the source's declaration and the user's env file for one send and writes nothing. Only events on a bead are matched (`wtx.event` in internal/store/store.go matches nothing bead-less; the proposal extends kind matching to the bead-less failure events: section 3.6); a `kind` filter names a kind or the class attention (`kindWords` in internal/store/crew.go, matched by `match` in internal/store/subscriptions.go). A crew member's `--on` is different: it is checked when the inbox is read, and covers events not about a bead (`forCrew` in internal/store/crew.go, read through `inboxKeys`), so the yardmaster's inbox holds a bead-less event of a kind it hears with no delivery recorded at log time. The operator's user is ensured by the store itself (`ensureOperator` in internal/store/users.go, on every open through `migrateOperator` and whenever the operator setting is set): the place a default for the operator lives. A user is told outside the yard through the source their record names (`notify` in internal/store/usernotify.go); `notify.Send` answers `NotSetUp` where they name none (internal/notify/notify.go).

## 3. The proposal

What follows is the smallest version under the decisions in section 5. In one sentence: one new command, `yardr upgrade`, builds the depot's checkout, installs it, checks every covered yard runs it, and otherwise puts the previous build back; the assembly calls it after the merge when a setting names the depot; the web view answers the same facts on GET /health.

### 3.1. One command carries the install: `yardr upgrade`

`yardr upgrade` does mckean's hand step whole: from the checkout of the depot the yard setting `upgrade_from` names (a depot name; unset, the command refuses and nothing happens), it runs `go install .`, exactly as by hand. Before that it takes a consistent pre-install copy of every covered yard's store (`Store.Backup`, the way `yardr store backup` does), each to its own `<home>/backups/yard.db.before-install` — that directory, not `backup_dir`, so a rollback never depends on a volume that may be unmounted, and a name the daemon's pruning never touches — and copies the running executable aside to `yardr.prev` beside it, one generation, on the same filesystem so restoring it is a rename. The covered yards are its own home, always, plus every yard registered on this machine whose service runs the shared binary: the homes the login services name in `WorkingDirectory` whose program is the install target (the listing `otherLoginYards` does in internal/cli/login.go, filtered on the binary). A registered yard on another binary is left out — the install cannot move it — and a yard with no login service is covered only when it is the upgrading yard. The backup is unconditional: the `upgrade_restore` setting governs restoring, never copying, so the copy is there to read even where nothing will be restored. It refuses when `go` is not on its PATH (doctor's machine checks are what say so by hand), when the depot has no checkout on this machine, and when `go install` would not write the binary this yard runs from (the GOBIN it resolves against its own executable path): installing bytes the server does not watch would verify nothing. Where a depot sits in a folder macOS protects, it warns that the new build may need its access granted again (the `protectedDepots` check behind doctor's note already knows), without failing.

Concurrent upgrades are serialized by a lock beside the install path: `upgrade` holds an exclusive flock on `yardr.upgrade.lock`, next to the installed binary and `yardr.prev`, for the whole run, and a second upgrade – by hand while merge-local runs one, or from another yard on the machine – refuses at once with a line naming the holder's pid, as a second daemon does (`lockDaemon` in internal/cli/lock.go). The lock lives beside the binary rather than in any yard's home because what it guards, the installed file and the one-generation `yardr.prev`, is shared by every yard on the machine. Nothing serializes installs today; two `go install`s race the file. A run refused on the lock reports it as an install failure with that line (section 3.6); the next landing tries again.

The command is the same by hand and in the assembly: the operator runs `yardr upgrade` after pulling instead of `go install .`, and merge-local runs `$YARDR_BIN upgrade` after the merge (section 3.4). One implementation, tested once, serves both — the same argument `contrib/release/build` makes for releases ("a release made by the workflow and one made by hand cannot drift apart"). Against the yardmaster's note for a shared installer script: a script can hold the `go install` and the file copies, but the gate, the rollback and the telling all need the new binary's own code — `server.Describe`, the lock probe, the new event kinds, mail over the socket — so a script that works on the old binary would reimplement them in shell and drift from the Go it checks. The three lines a script would own live inside `upgrade` instead, and both callers run the one command.

### 3.2. The gate is `yardr upgrade --check`: the yard runs this build, or it says so

`--check` is the health check as a pure predicate, read-only like doctor: it asserts that every yard process that runs, runs this build — the build of the `yardr` that was asked, which by hand after an install is the new one, so no revision argument is needed. It exits 0 with one line per check, 1 with one line per failure, and `--json` prints the same verdict as data. A part the yard does not run is skipped and reported, not failed, as doctor skips the checks a stopped server cannot answer: a yard with no daemon running skips the daemon check, a yard with no web view skips the views. The four predicates are the bead's four, measured:

1. The server answers on this build: `server.Describe` revision equals the command's own. This implies the store opened and migrated — the server opens the store before it listens, and a migration that fails never listens — so no separate migration probe is needed.
2. The daemon holds its lock and runs this build: the lock is probed the way `readDaemon` probes it, on every sample of the run rather than only the last, so a daemon that flaps (a crash loop under its service manager) fails; the build is the `to` of the latest `daemon_replaced` or `daemon_started` event. `daemon_started` is new: the daemon logs it on every fresh start beside `noteReplaced`'s `daemon_replaced`, joining `DispatchKinds` but not the class attention — a start is routine. A daemon whose build is in neither — started fresh before `daemon_started` existed and never replaced since — fails with a line saying to restart it, not with a guess. And it completed a pass on this build: the daemon stamps `<home>/daemon.pass` (a `DaemonPass` path in internal/config, beside `DaemonLock`) with its build and the time at the end of every `Reconcile` (internal/dispatch/dispatch.go), through a temporary file renamed into place, and the check requires a stamp on this build at or after `--since` (default: ten minutes ago). A daemon that holds its lock but never stamped on this build — wedged mid-pass — fails. Ten minutes bounds a stuck daemon without false-failing a slow pass: passes run every 30 seconds, but a large store's backup pass takes a while. The gate passes the install's start as `--since`, so the evidence is one full pass under the new build, not an old stamp.
3. Every recorded web view answers: one GET of `/health` (section 3.5) on each address in `<home>/webviews`. A view that 404s `/health` but answers `/` is on a build from before the route: it is skipped with an `old:` line naming the restart (`yardr web stop`, then `yardr web start`), not failed — the install did not break it, and a view is a read-only client. A view that answers nothing at all fails. Views do not replace themselves, so this checks that they answer, not that they run anything new, and the upgrade restarts none: no view is interrupted and none needs restoring on rollback.
4. The store opened and migrated: implied by the first, as said there.

`upgrade` without `--check` polls the verdict every 5 seconds up to `--timeout` (default 5 minutes: the 15-second drain, the new build's start and migration, the daemon's replace between passes), for every covered yard in turn. `--check` checks the yard of its home (`--home`, as every command takes it), so each sample runs the installed binary once per yard. It starts a stopped server first, per yard, so there is always a server to verify, and leaves running what it started. It starts nothing else. A yard the gate cannot check — its home unreadable, its server unstartable — fails the gate with that yard named; the marker and the message name it too (sections 3.3 and 3.6).

The poll cannot run the predicate in-process: the process that runs `go install` still executes the old, already-loaded code, so its own build is the old revision and an in-process check could never pass once the server has replaced. Each sample therefore runs the installed binary's `upgrade --check` as a subprocess — the binary at the install target the GOBIN check resolved — so the predicate always runs in the build it asserts, and each sample also proves the new binary starts as a CLI. For the same reason the rollback's stop, start and verify steps run as subprocesses of the installed path: after the previous bytes are restored, they run the bytes that are in place.

This is not doctor and not status, deliberately: doctor's verdict covers the whole yard, so a program missing from the machine would fail every install, and doctor is read-only while telling writes events; status holds facts only with exit 0 on any yard, and the gate is a verdict with an exit status. The codebase's own split — doctor checks, status lists — leaves the install gate wanting its own predicate, and keeping it inside `upgrade` keeps the novelty in one command instead of spreading flags over two.

### 3.3. Rollback restores the bytes and restarts the processes; the old build is the oracle on the store

When the bound expires with any covered yard not on the new build, `upgrade` rolls back: it copies `yardr.prev` over the installed path once, then, in every covered yard, stops the server and the daemon (`yardr server stop`, `yardr daemon stop` with that yard's home) and starts again only what ran before the upgrade. The order matters twice over. First, the self-replace path refuses downgrades (section 2.1), so restoring the bytes alone would only log `replace_skipped`; only a restart runs older bytes again. Second, restoring before stopping means anything restarted by a service manager in between picks up the old bytes — a crash-looping new daemon heals into the old one by itself. Restoring the old bytes also restores the old build's macOS access grants, which the new build may have lost.

Whether a store must go back too is answered by the old build itself, per yard: it is started on the current store, and if it refuses with `ErrNewerSchema` that yard's pre-install copy is put in the store's place (the documented restore, minus `down`, which the rollback already did) and it is started again. No stamp is compared and no new reader is needed; the refusal exists for exactly this. A yard that needed no restore loses nothing. One that restored loses what the window held — bounded by the timeout, minutes — so everything is told after the restore, never only before it: anything told earlier is rewound with the store. The two failure events (section 3.6) are therefore logged from the restored upgrading yard, by the restored binary.

Whether the copies are restored at all is the upgrading yard's to say: `upgrade_restore`, a boolean setting in the `KnownSettings` table (internal/store/settings.go) defaulting to true, with `YARDR_UPGRADE_RESTORE` (`Setting.Env`, read through `config.Getenv` as `hook_addr` and the other addressed settings are) and a `--no-restore` flag on `yardr upgrade` overriding it for one run: the setting is the source, the variable and the flag only override. The one setting governs the whole run, every covered yard with it. With restoring off, a failed check after a migration stops and tells instead: each yard whose store the old build refuses stays down, the marker and the telling of section 3.6 are the record, and the operator restores each by the documented recipe. On is the default because a failed check surfaces within minutes, while a yard down overnight costs more than minutes of records.

If the old build will not start even on the pre-install copy, that yard stays down. The failure is durable on disk, not only on a terminal: `upgrade` writes `<home>/upgrade.failed` in the upgrading yard with the revision, the stage, the reason, every covered yard and its outcome — including any yard the gate could not check — and who was already told outside the yard with what each send answered, which `yardr doctor` reports as a FAULT until the next successful upgrade logs the failure event marked as told and clears it (section 3.6) — doctor reads the home without the server, so the fault is loud while the yard is dead. That bottom exists today for every bad install; the rollback strictly improves it by restoring first.

Rollback restarts every covered yard's processes, each on the restored bytes, since their replace paths refuse the downgrade too. A yard the run did not cover is untouched by it: one on another binary never saw the new bytes, and one with no login service that is not the upgrading yard replaced to the new bytes on its own and needs a restart by hand once the old bytes are back. The machine-wide effect is decision 4 as extended by decision 11 (section 5).

Builders and reviewers in flight run the installed binary, and an install mid-session must not break them. Replacing the file does not touch running processes; a new CLI invocation during the window runs old or new whole bytes, and a binary still being written does not parse, so it is not offered as a replacement. On the socket the drain and `ReplaceRetry` cover the handover, the daemon execs between passes with its sessions in the store, and streams end at the drain for their readers to resume. Two residuals stay, both bounded and named: a replace whose migration outlasts the 30-second retry fails the calls in flight — the rpc client returns the error then — and recovery is the caller's: the daemon's passes are idempotent (`Reconcile`, "one idempotent pass", in internal/dispatch/dispatch.go), so the next pass repeats the work, while a CLI invocation's invoker runs it again, a person by hand or a script by its own handling; and work in a macOS-protected folder can fail with "operation not permitted" until the new build is granted again, which the upgrade warns about up front and doctor says how to fix. In the other covered yards the same holds: their servers replace on the install and restart on a rollback, so their in-flight calls see the same bounded residuals.

### 3.4. The assembly calls it after the merge, when the setting names the depot

`contrib/assembly/merge-local` — both identical copies, the other in `packs/starter/scripts/` — gains one step after the push and before the advance: when `upgrade_from` names this bead's depot, run the install and fold its one-line summary into the landing note and its seconds into the group's log line. The shape follows the push failure exactly while the yard answers: the code has landed, so a failed install where the server still answers never sends the bead back; the bead advances to merged with a note that says the install failed and what was put back, and the telling is the command's (section 3.6). When the failure leaves the yard dead — the old build refuses even the pre-install copy — no advance is possible, because notes and advances need the server (section 2.6): the script's yardr calls fail, the session fails, and the bead is held after its sessions fail, with the marker, the doctor fault and the session log as the record. The script has `set -u` without `set -e`, so the step handles the exit status explicitly, as the push does. A yard without the setting set, and every other depot, runs the script exactly as today. Merge-local's environment already names the bead (`YARDR_BEAD`, which every started process gets: `runner.Env` in internal/runner/runner.go), which the step uses for the landing note alone: the failure events are yard events, logged with no bead, so a hand run and a landing run are told alike (section 3.6).

Four activations are the operator's, outside any bead, in this order: first be told outside the yard — the operator names a notify source (`yardr pack apply pushover` or `yardr pack apply telegram` with `--notify`), since setting `upgrade_from` is refused while they name none (section 3.6); then install a build that has the command — one `go install .` by hand from `main` after beads 1–5 have landed, since `$YARDR_BIN` is the installed binary and an older one knows no `upgrade`; then reinstall the script from `main` (the assembly runs the installed copy, so landing the step changes nothing by itself); then set `upgrade_from` to `yardr`. No fifth step subscribes the operator: the subscription is a store default (section 3.6). If the setting is set before the bootstrap, the step fails as an install failure with a line saying to install the new yardr once by hand first, and the bead still merges.

### 3.5. The web view answers GET /health

GET /health serves the same facts the gate checks, minus the verdict: the server's build and start time, whether the daemon holds its lock, on which build, and when it last completed a pass, and the view's own build, as JSON. It answers 200 whenever the view serves it, with a `status` of `ok` or `degraded`; only a yard it cannot read at all fails, through the existing error path. The code therefore says whether the view answers — a proxy keeps routing to a view that answers, even over a yard whose daemon is down — and the JSON says whether the yard is whole, for a monitor or footplate to read. Nothing it says is a secret: builds, a pass time and booleans, served to the same audience as the rest of the view (loopback, or behind the operator's proxy). The store's head sequence is left out: it is not public health data, and it is not on `yardr status` either; if the gate ever needs it, it reads it over the socket (`Head` on the rpc client, internal/rpc/client.go), not from the route. It is a machine route: no template, no menu entry, answered directly as JSON the way `/favicon.ico` is answered directly, reading nothing but what it reports — no line, no beads, no stream. The daemon lock probe (`daemonRunning`, `daemonPID`) moves from internal/cli to internal/config, beside the `DaemonLock` path it probes, so the route can use it, and the pass stamp is read beside it; docs/web.md gains the row its "Adding a page" asks for.

### 3.6. Telling: two events, two mails, one note line — and an escape hatch when the yard is dead

A failed install or a rollback is never silent while the yard answers. Two new event kinds say it: `install_failed` (the revision, the stage — build, install or health — and the reason) and `rolled_back` (from and to revisions, whether the store was restored, and the reason). Both join `DispatchKinds`, so the upgrade command can log them as the socket client it is, and the class attention, so the yardmaster hears them on its default `--on`, as it hears `backup_failed`. A success logs nothing new: `server_replaced` and `daemon_replaced` already record it. The events are yard events, not the landed bead's: they are logged with no bead whether the run came from the assembly or by hand. The one change in the store's deliver path (bead 4) makes that enough: a bead-less yard event is matched against yardr-source subscriptions on kind alone (`kind=install_failed`, `kind=rolled_back`, or the class attention), recording `notified` and `deliveries` as a bead event does, so a hand run and a landing run are told alike; a subscription that filters on bead fields still needs a bead to match. The operator is subscribed to the two kinds by default: `ensureOperator` (internal/store/users.go) adds the subscription when it creates the operator's user, and a version-gated migration (internal/store/migrate.go, as `migrateYardmaster` is) adds it once for yards that already have one, so `yardr unsubscribe` afterwards is respected. The yardmaster needs no migration: its default `--on` holds the attention class, which already covers bead-less events when the inbox is read (section 2.6). The command also mails the yardmaster and the operator (the settings of those names), which follows the yard's rules by itself: crew read their inboxes, and a user that set outside telling is told outside — as one message with the notification, since the daemon sends each user's due pushes as one. And the landed bead's note carries the one-line summary, success or failure. Where an older binary does not know the new kinds yet — the release the feature lands in, rolling back with the binary from before it — logging refuses with "not a dispatch event", and the command carries on with the mails and the note; from the next release on, every binary knows them.

When the yard does not answer — the old build refuses even the pre-install copy, or restoring is off — events, mail and notes all need the server that is down. The telling is then twofold. First, the escape hatch: on a dead-yard failure `upgrade` opens the pre-install store copy read-only (it predates the install, so its subscriptions are the yard's as they were) and matches its yardr-source subscriptions with the store's own matcher (`match` in internal/store/subscriptions.go, shared so the hatch matches what `deliver` would), then sends the one message itself through each matched user's source (`notify.Send` in internal/notify/notify.go, served by the copy, reading the env files from disk as a send always does). Who is told and through which source stays a subscription as everywhere: the hatch is a second delivery, not a second configuration. During the outage only users are told: the yardmaster is not reachable while the store is down and is not sent to; it is told when the yard is back, by the stored event in its inbox as usual. Second, the file: `<home>/upgrade.failed` with the revision, the stage, the reason, every covered yard and its outcome, and who was already told with what each send answered, written by the command and reported by `yardr doctor` as a FAULT (`FAULT upgrade to <rev> failed at <stage>: <reason>; the yard is down — fix it and run yardr upgrade, or remove <home>/upgrade.failed`) until the next successful upgrade logs the failure event marked `told` and clears it, or it is removed by hand. The store writes the marked event's notification but queues no push for it (`wtx.notify` in internal/store/notifications.go skips `queuePush` on `told`), so the recovery is recorded without telling twice; in a mixed release an old binary tells again, which is the pushes' own rule — told twice, never not at all. The assembly session's log holds the same lines, and the bead the step ran for is held after its sessions fail without an advance (section 2.4), so the yardmaster finds the held bead, the log and the fault together. Turning on the automatic install needs an address to send to: `SetSetting` refuses `upgrade_from` while the operator names no notify source (a store-aware check beside the `herdr_session` one in internal/store/settings.go), and the refusal names how to set one (`yardr pack apply pushover` or `yardr pack apply telegram` with `--notify`). A hand run of `yardr upgrade` without one prints the failure on the terminal, where the person is: not silent either way.

## 4. Left out

A yard installed from a release archive, not from a checkout, is out: there is no depot to build from and perhaps no Go toolchain, so the setting stays unset there and nothing changes. The next step after this lands is a bead for installing from a signed release instead of a checkout; the gate, the rollback and the telling are the same, only the build step differs.

The install does not quiesce the yard first: no bead is held, no agent is stopped. Builders in flight keep working through the handover (section 3.3); a store restore rewinds the window's records, which is why the window is minutes and restores happen only when the old build refuses the store.

Telling from a yard that cannot be restarted reaches whoever subscribed with a notify source set up (section 3.6). The automatic install cannot be turned on without one — setting `upgrade_from` refuses — and a hand run prints the failure on the terminal, so the marker file, the doctor FAULT and the session log are never the only record. Where the operator recovers by hand without running `yardr upgrade`, the marked failure event is never logged; the session log is the record.

Isolation between yards on one machine is out. Every yard that runs from the installed path replaces when any one of them installs (section 2.1); the upgrade answers by covering every registered yard on that path — backing up, checking and on failure restoring each — rather than by containing the effect. Per-yard binaries — installing to each home and re-pointing its login services — would contain each yard's upgrade to itself at the cost of a second install layout and the PATH confusion of two yardrs; it is the named next step if the machine-wide effect proves unwelcome.

## 5. Decided

Decided 14 Oct 2026. The yardmaster decided 1, 2, 4, 5, 7 and 8 (yard mechanics, on mckean's standing word that install is his call); 3 and 6 were asked of mckean (asks 4136 and 4137) and answered the same day; 9–12 answer the fourth critique, decided by the yardmaster the same day, with the shapes below.

1. The install step lives in the assembly script (decided: yardmaster). The script is where the merged commit is already known, already serialized one landing at a time, and already reporting per-bead outcomes; it costs a step in a script and nothing long-lived. The daemon pulling — noticing a landing on the depot and building it — would install even where the assembly ran elsewhere (a peer group), but costs a new watcher plus a minutes-long build inside the dispatch loop, stalling passes or needing background jobs. A flow stage after the landing would route every bead through one more group for an operation that is not per-bead work.
2. The health check is `upgrade --check` (decided: yardmaster). Doctor already owns post-upgrade checks by documentation, but its verdict covers the whole yard — a program missing from the machine would fail every install — and it is read-only while telling writes. Status with an exit code would break its facts-only, exit-0 contract. `--check` keeps the novelty in the one new command and stays hand-runnable. The one-time `go install` bootstrap is accepted, and the command — not a script — is accepted as the one entry point the landing step and a person both run, which is what mckean's script idea asked for.
3. When the new build migrated the store and then failed, restore the pre-install copy (decided: mckean, ask 4136, Restore). Restoring is automatic and usually right: the window is minutes, and only a migration forces it. Its cost is the window's records, rewound, and the re-logging that must follow. Stopping instead — the old binary refuses the store, the yard stays down, the operator restores by the documented recipe — loses nothing silently but leaves the yard down until a person acts, over a failure the automation caused. Forward-compatible migrations as the standing rule would avoid the choice, at the cost of constraining every migration to come; the store's history is renames, which that rule forbids. With mckean's addition, "perhaps a flag to prevent auto rescue": `upgrade_restore` (default on) with `YARDR_UPGRADE_RESTORE` and `--no-restore` (section 3.3), the yard's way — the setting is the source, the variable and the flag only override. With it off, a failed check after a migration stops and tells, as the stopping option described.
4. The install step is per yard but its effect is machine-wide, and that is accepted and documented (decided: yardmaster). Accepting it changes nothing for a yard that does not set `upgrade_from` except what already happens by hand today — any install over the shared path replaces every yard that watches it — at the cost that one yard's upgrade moves the others, which decision 11 answers by covering every registered yard on the shared binary, at the cost of a slower upgrade and a restart of each yard on rollback. Per-yard binaries would contain each yard's upgrade to itself, at the cost of a second install layout, re-pointed login services and two yardrs on one PATH. This bead's scope is the one yardr depot on this Mac; isolation is the named next step.
5. GET /health serves facts with 200 whenever it serves (decided: yardmaster). Facts-with-200 keeps the proxy's question ("does this view answer") separate from the monitor's ("is the yard whole", read from the JSON), and never drains a view that serves reads over a daemon that is down. 200/503 lets a bare uptime check alert without parsing JSON, at the cost of conflating the two questions.
6. When the yard is dead after a failed install, the telling is a subscription plus a direct-send escape hatch (decided: mckean picked Notify directly on ask 4137, asking "it should be a subscription though right? or a separate escape hatch?"; yardmaster: both). Who is told and through which source is a subscription as everywhere — the failure kinds, which the operator subscribes to by default — and delivery normally goes through the daemon. Only when the yard is down does the upgrade command itself send that one message, reading the same subscriptions from the pre-install store copy and the user's notify source: an escape hatch for delivery, not a second configuration. When the yard is back, the event is recorded as usual, marked as already told, so it is not sent twice — and the yardmaster, sent nothing while down, reads it in its inbox (decision 9). The marker file and the doctor FAULT alone would leave nobody nudged; a bare second sending path with its own configuration would drift from the subscriptions. The hatch costs one direct send without the daemon's queue and retries, for the one case the daemon cannot send at all.
7. The gate requires evidence of one completed dispatch pass on the new build (decided: yardmaster, YES — a wedged daemon must fail it). The lock alone is cheap but blind: a daemon wedged mid-pass holds it like a live one. The pass stamp costs one small file write per pass — not an event per pass — and the daemon predicate one file read per sample.
8. Concurrent upgrades serialize on a lock beside the install path, taken by hand runs and merge-local alike (decided: yardmaster, YES). No lock races the shared binary and the one-generation `yardr.prev`; a lock in the yard's home would not serialize the actual sharers, the yards beside it. The beside-the-binary lock costs one flock file and a refused second run, which reports it as an install failure and tries again on the next landing.
9. The failed-upgrade event is a yard event, not a bead's (decided: yardmaster). Subscriptions by kind match it with or without a bead — the one change in the store's deliver path — so a hand run and a landing run are told alike. During the outage only users are told, by direct send through their notify source, selected by those same subscriptions read from the store copy; the yardmaster is not reachable while the store is down and is not sent to. It is told when the yard is back, by the stored event in its inbox as usual, subscribed by default like the operator. Logging on the landed bead instead would leave hand runs untold; a second route to the yardmaster during the outage would need a reachable store that is down by premise. It costs the deliver-path change and the read-only open of the copy.
10. Turning on the automatic install is refused while the operator has no notify source (decided: yardmaster). Setting `upgrade_from` refuses, and the refusal names how to set one (the pushover or telegram pack); a hand run without one prints the failure on the terminal, where the person is. Marker-only telling for the automatic path would break the never-silent requirement the bead states; the check costs one store-aware setting refusal, beside the `herdr_session` one.
11. The upgrade backs up, checks and, on failure, restores every yard registered on this machine that runs the shared binary, not only its own (decided: yardmaster). A yard it cannot check is named in the marker and the message. Covering only the upgrading yard would leave a second yard down with no backup and no marker from a migration or start it did not ask for; per-yard isolation stays the named next step. It costs a slower upgrade — a backup, a check and possibly a restart per yard — and the disk the copies take.
12. The store head sequence is not public (decided: yardmaster). GET /health leaves it out; if the gate needs it, it reads it over the socket, not from `status --json`. Serving it would publish store internals to whoever reaches the view, including through `--unsafe`. It costs nothing: the gate's predicates do not need it today.
