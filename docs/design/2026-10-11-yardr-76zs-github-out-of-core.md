# GitHub out of the core, as a pack of kind source

Design yardr-76zs, proposed 2026-10-11. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

## 1. The question

Linear left yardr's Go code on 11 Oct 2026 and became packs/linear, a pack of kind source. mckean asked: "is github still in yardr? can we use the same mechanics to get it out? or we need to cover additional logic?", then said "yes, let's go". This design answers what it takes to do the same for GitHub, in what order, and which parts need something a declared source cannot say today. mckean's test of the proposal: after it, adding Jira or Asana is writing a pack (a declaration, scripts, setup notes) and changing no Go.

## 2. What exists today

A source is an outside system a hook receives from (docs/glossary.md). A declared source is one yardr knows from a YAML file and no Go (docs/integrations.md#a-declared-source, internal/source/declaration.go). A pack of kind source is an integration as one pack, imported into the yard itself (docs/packs.md#an-integration-pack-kind-source). What follows names the files a reader can open.

### 2.1. The declared-source machinery, as Linear proved it

The declaration (internal/source/declaration.go) names the service's address (base), the credential (credential.env names the variable, never the value; header says where the value goes; update_env names a second variable for update calls), the calls agents may make (calls, check, notify), the operator's limits command, how the yard speaks in threads (thread.reply, posted, read, open, opened, state, place, states: one command per thing, one JSON object on stdin, one on stdout), the source's issues as a bead's link (link.host, issue, fixed, thread), and what the service sends in (hook.verify, bodies, normalize, keys). The key events is reserved and refused: "the key is kept for them" (internal/source/declaration.go, around line 717).

One adapter in Go serves every declared source (internal/hooks/declared.go, type Declared). Verify checks the delivery as hook.verify says (HMAC-SHA256 over the body, the signature's header and prefix, the delivery's header, an optional signed timestamp) without running anything: the signing secret reaches no command. Normalize runs hook.normalize with {headers, body} and no credential; the core sets the source itself. Each thread command gets the credential's value under credential.env plus YARDR_SOURCE_BASE, and nothing else of the yard (internal/source/command.go, CommandEnv). Bodies maps unique to per-source dedup and repeat to delivery ids alone (internal/hooks/hooks.go, DedupeKeys); the per-hook scope exists in Go (BodiesUniquePerHook) but no declaration can ask for it.

Every lookup finds the declared source first: AdapterFor, ReplierFor, OpenerFor, StaterFor, ForwarderFor (internal/hooks/declared.go, reply.go, open.go, state.go, forward.go). A name cannot be both builtin and declared: source.BuiltIn holds github, token and yardr, and a declaration may not take those names. CredentialWays for a declared source is the one way, its one variable (internal/hooks/reply.go).

What the yard does with an event is data on the hook: the says table (yardr hook add --says, or a pack's sources.\<name\>.says) and the makes table (--makes), matched by Hook.Said and Hook.Made (internal/store/hooks.go). What a stage means in the source is the flow pack's hears map (docs/packs.md). A pack of kind source brings the declaration and its command files, which the import copies under \<home\>/sources/\<name\>/; the plan names each file and its sha256. The limits command is the operator's alone: no pack brings it. store.MoveSourceRecords folds one source's records into another's (internal/store/movesource.go); the Linear move used it to fold linear-declared into linear.

packs/linear is the proof: pack.yaml, linear.yaml, two scripts (linear/normalize in sh and jq, linear/thread in bash with curl and jq), and SETUP.md. internal/hooks holds the pack to golden files: the envelopes for recorded bodies and the requests the stand-in received.

### 2.2. GitHub in Go

The adapter, internal/hooks/github.go (361 lines). Verify checks X-Hub-Signature-256 (hex HMAC-SHA256 of the body, prefix "sha256=") and returns X-GitHub-Delivery; GitHub signs no timestamp, so replays are caught by body, per hook (BodiesUniquePerHook: one event's body goes to every webhook on the repository). Normalize reads six event types (pull_request, issues, issue_comment, pull_request_review, workflow_run, check_suite) into the envelope: the thread owner/repo#number, the actor lowercased, mentions (@login outside code spans, teams left out, lowercased), and fields the where keys name (store.GitHubWhereKeys: event, number, state, merged, conclusion, workflow, head_branch, head_sha, head_repo, base, train, sender, association). The train comes from the head branch (yard/\<train\> via store.Branch); the sender's kind (a login ending in [bot] is a bot); the association is the comment's or review's writer where there is one, else the issue's author.

The App login, internal/hooks/githubapp.go (265 lines) with internal/hooks/reply.go and forward.go. A crew member speaks with GITHUB_TOKEN or as a GitHub App (GITHUB_APP_ID with GITHUB_APP_PRIVATE_KEY_FILE, an absolute path; one without the other is refused, never passed over). The App's credential is not a token but where one is minted: the core signs a short-lived JWT with the key, finds the installation on the repository, and takes an installation token narrowed to that repository, cached in the process's memory only (never the store, an event or a log), with a five-minute expiry margin and eviction on a 401. Every GitHub call for a crew member goes through githubCall. At a person's own shell only, GitHub.Credential falls back to what gh is logged in with; a crew member's session never does. CheckKey reports why the key file cannot sign.

Speaking in threads. Reply/Posted/Thread (reply.go) comment on the issue or pull request, carrying the key in a marker comment; Open/Opened (open.go) open an issue in a repository (place "repository"), Opened bounding its search with since; SetState (state.go) maps started to open and done to closed-as-completed, refuses review and refuses pull requests (a state would close one unmerged), and adds label:\<name\> (to a pull request too, never removing one); Forward (forward.go) never moves backwards and never reopens, reporting where the issue stood (Stood: started, done or other), which nothing in Go reads. IssueThread reads owner/repo#number from an issue or pull URL. CredentialFrom never tries gh. The API endpoint is YARDR_GITHUB_API or https://api.github.com.

Links and identity. Issue (issue.go) fixes https://github.com/\<owner\>/\<repo\>/issues|pull/\<n\>, lowercasing owner and repo; Puller adds PullOf (is this URL a pull request's) and PullURL (build one's URL from repo and number), found through PullerFor, which looks in Adapters only. KeyFolder lowercases identity keys (identity.go); Repoer maps a git remote to owner/repo through store.RemoteForm plus the issue host (repos.go), found through RepoerFor, likewise Adapters only.

### 2.3. The dispatcher's rules

internal/dispatch/github.go (664 lines) puts each hook event to its hook's tables. The shape is general already: the bead an event is about is the open bead tracking its thread, else the open train its train field names; a held bead is left alone; what the yard itself did (the actor is a crew member's identity in that source) says nothing; each judged event is recorded on the bead (hook_seq) and logged as a hook_rule event; the outcome goes through the bead's flow as a session's would. GitHub is in the details: githubThreadAlias (an issue and its pull request share a number; a bead linked with one form must be found by an event in the other), parsePRURL, tellsHead (pull_request and pull_request_review carry the pull request's head into pr_head), run (workflow_run and check_suite are CI runs, judged against the head), and onHead, which asks gh pr view for the head when no event has told it (PRQuery, by URL or number, never by branch). The train binding (pr_url, pr_number, pr_head_repo, stored by integrate-train) and its check (boundPR.other) are general logic over metadata plus the GitHub URL parse.

internal/dispatch/ci.go (448 lines) reads CI as state for trains in a stage the table has an event=ci line for. The machinery is general (ci, ciTrain, judgeCI, verdict, ciEnvelope, ciHook, the made-up event with conclusion success or failure); the reading is ghCI through the gh CLI (the pull request's head, base and state; the required checks from branch protection and rulesets; check runs and commit statuses on the reviewed commit), and CICheck.result maps GitHub's conclusion vocabulary. The seams are the d.CI and d.PRHead function fields. internal/dispatch/makes.go is general except githubThreadAlias and RepoerFor (gitDepotRepo reads the depot's origin remote). internal/dispatch/issues.go is fully general (ForwarderFor; the daemon reads the crew member's env per move and tries nothing ambient). dispatch.go's pullOf finds the tracked pull request through PullerFor for Job.Pull.

The runner's brief knows GitHub too. internal/runner/runner.go writePR writes a train's brief when the bead's metadata has pr_url (stored by the operator script integrate-train): the pull request's URL, permission to push to the train's branch, instructions to post the review with gh pr review (including GitHub's rule that the pull request's author may not approve or request changes on their own), and a CI snapshot from prChecks, which runs gh pr checks with a twenty-second timeout and prints "checks: unavailable" when there is no output. internal/runner/herdr.go pullHead needs no change: it reads the pull request's head through git alone (fetching refs/pull/N/head), never the gh CLI.

### 2.4. Around it

The contributors pack (packs/contributors/pack.yaml) is GitHub's main user and already speaks pure data: sources.github.makes (trust as a where: association=OWNER/MEMBER skips triage), says (labels, closes, merges, pushes as outcomes) and hears (issue: new=started, merged/done=done; pr: closed=done). It needs no change beyond what any github source provides.

The token source (internal/hooks/token.go) is yardr's own: Bearer [REDACTED] equality, bodies repeat. It stays in Go; this design does not touch it. internal/standin keeps serving the services' APIs for tests and isolated yards, as it kept Linear's. contrib/assembly's integrate-train, pr-train and pr-merge drive gh directly; they are operator scripts already outside Go and stay where they are. About seventy non-test Go files mention GitHub; outside internal/hooks and internal/dispatch they are help texts and examples (notably hook add, thread state, thread open, subscribe) plus small Doc mentions, of the kind yardr-ecan generalized for Linear.

The Linear removal set the order that works: prove each capability under a -declared name, make the declared source win every lookup (commit 760dbc6), let the pack take the name (1631b6a), fold the yard's records with MoveSourceRecords and a pack apply step (76500e9, f77ff58, 2a769fe, c587c7a), pin the pack with goldens (56549dd), delete the adapter (8736bfa), name the pack in missing-source errors (86deb31), rename what still says the old name with no compatibility reads (72b858f and its review follow-ups), and rewrite the docs (f91c916). Its accepted deltas are the model for honest ones: non-canonical-case Linear URLs refused, Stated.Instead dormant for packs, daemon thread_state events carrying the key with no title (notes on yardr-ecan).

Credentials touch YRD-27 (design bead yardr-0qs5): mckean's direction is that a credential belongs to a person, a bead carries the grant, and a secret is not handed to an agent. The grants-and-identity half of yardr-s48v (a module's declared actions as granted capabilities, with scopes) is still to design and stays out of this proposal; what it proposes must not block it.

## 3. The proposal

Ship packs/github, a pack of kind source shaped like packs/linear, and first teach the declaration seven general things GitHub needs that it cannot say today. Each is a capability any source may declare, named with no service in it; GitHub is their first user, never their name. Then delete GitHub from Go the way yardr-ecan deleted Linear. Nothing below keeps a GitHub case in the core, even briefly: the pack proves itself under the name github-declared while the Go adapter still serves github, exactly as linear-declared did.

### 3.1. What the declaration learns

Seven additions, each carried by an existing mechanism. The names are proposed; the beads may rename them, but not into service names.

1. Bodies scoped per hook. The declaration's bodies gains the value the core already implements: unique-per-hook (BodiesUniquePerHook in internal/hooks/hooks.go). GitHub needs it because one event's body is sent to every webhook on the repository. Any source with per-endpoint subscriptions of the same events says the same. The change is the reader, Declared.Bodies, and tests; DedupeKeys already handles the scope.

2. A minted credential. The declaration's credential gains mint: the names in the env file that together select it (for GitHub, GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY_FILE), and nothing else — names only, never a value and never a command, so a pack may bring it as it brings credential.env today, with no change to the pack key lists. The command that turns those inputs into a short-lived token is not in the declaration at all: it is a setting on the source's store record, mint_command, on the model of the source's env_file (internal/store/sources.go) and with the execution rule of a crew member's env_command (internal/config/crewenv.go). The operator sets it with `yardr source set <name> mint_command=<program> [args...]`, one line split on spaces without a shell, the program absolute or on PATH; like every source setting it is the operator's under maySource, refused from an agent's pane; PutSource keeps it across pack applies as it keeps env_file; a pack cannot bring it by construction, which is stronger than the limits refusal. The core runs it with stdin {inputs, scope}: the named values read from the same env the static credential would come from (the acting crew member's env_file or env_command for thread commands and look-back reads, the source's own env_file for source check and declared calls), plus the caller's scope (the thread, or the repository and number) so a token narrows where the service allows, as installation tokens narrow to one repository today; this is the recommended answer to open question 2, and scope-free would drop the scope field and key the cache per source. It parses {token, expires_at}, caches the token in the process's memory only (never the store, an event or a log; today's githubTokens, generalized), the cache keyed per scope, and hands the token to every thread command, declared call and look-back read under credential.env. One shared resolve (a new internal/source/mint.go, called from the hooks credential path and the declared-call path) keeps a single precedence: the mint's names when set together, one of them alone refused, else the static variable. CredentialWays gains the minted way (names only, for crew show and the pack plan). yardr source check reports the mint way (the input names, whether a mint_command is set, the token's expiry after a mint) and runs the mint and then the check call with the token; every failure names the setting that fixes it. The private key stays out of the pack's script: only the operator's mint command reads it. GitHub's JWT-and-installation exchange itself lives in the operator's mint script, shipped as a contrib script needing openssl and curl, like the assembly scripts: service knowledge, outside the binary. Custody holds at this: the value reaches only commands' environments, never a pane, mail, event, brief or bead, and agents are not shown it unasked. Whether that boundary is enough is open question 4: yardr-0qs5 explicitly leaves it open, since every agent runs as the same OS user and could go looking.

3. Labels as statuses. The thread key gains labels: true, meaning the source takes free-form tags. Places then accepts label:\<name\> (today Declared.Places refuses every label with "the yard sets no label in a declared source"), and the state script adds the label and never removes one, to any thread. GitHub uses it for its labels; Jira would use it for its own. The change is Places, the reader, and the thread.state contract.

4. Case folding. Identity keys gain fold: lower on a small identity key (KeyFolderFor reads the declaration, not Adapters), and the link key gains fold: lower, lowercasing every group before the fixed and thread templates expand. GitHub logins and owner/repo spellings are case-insensitive; without folding, one thread linked under two cases is two threads, and the tracking bead is missed. Linear could adopt link folding later and drop its accepted delta.

5. Pull requests as declared. The link key gains the source's second thread shape: pull with its own issue pattern plus fixed and thread templates over the same groups in the same order (the reader refuses a pull pattern with a different group count). From it the core derives what PullerFor gives today: PullOf (the URL matches the pull shape), PullURL (the pull fixed template expanded with the parts), and the issue/pull alias (the other shape's fixed form over the same groups), replacing githubThreadAlias and parsePRURL. The link key also gains repos, a pattern for the repository path: RemoteRepo becomes the path of the git remote (store.RemoteForm already normalizes any remote to host and path) when it matches, replacing the "exactly one slash" rule GitHub hard-codes and leaving room for services whose repositories nest. PullerFor and RepoerFor read the yard's declarations; Job.Pull, the run's thread URL and the makes depot match follow with no service in them.

6. The events key, and look-back reads. The reserved events key is given its format: runs (the event types that are CI runs, judged against the pull request's head), head_from (the types whose head_sha becomes the pull request's head), and two commands, pr and ci. The pr command reads the pull request live (in {repo, number, url}, out {head, base, state}) for the onHead fallback that gh pr view serves today; the ci command reads CI state (in {repo, number, sha}, out {head, base, state, required, checks}) for ghCI. The checks keep today's CICheck shape and vocabulary (status completed or not; conclusions success, neutral, skipped, failure, timed_out, startup_failure), and the pack's script translates its service into them, as a state script translates statuses into started, review and done: the verdict stays the core's, over a documented tongue. The events key joins SourceDeclarationKeys (internal/pack/pack.go), so a pack of kind source may bring it and a pack for a depot may not, as with hook, thread and link. The rule for whose credential a look-back read runs with is that a daemon read uses the credential its caller already holds: the dispatcher's reads run with the hook's as crew member's credential (the credential issues.go already reads for Forward; nothing ambient is tried, so the operator's gh login leaves the daemon path), and a hook with an event=ci line but no as, or whose source declares no ci command, is refused with the setup named. This is the recommended answer to open question 3; the alternative runs the dispatcher's reads with the source's own env file instead, and the refusal names that setup. The runner's brief snapshot is the same ci command: prChecks finds the pull request's source from its URL through the link shapes of item 5 above and runs that source's ci command with the source's own env file, since the runner has no hook and no as member; "checks: unavailable" stays the fallback. The brief's review howto (the gh pr review instructions, including GitHub's author rule) leaves runner Go for the flow pack's stage file: the contributors pack already owns pr behaviour, so its review stage says how a review is posted, and writePR keeps only the general shape (the pull request's URL, the push permission, the CI snapshot). The dispatcher otherwise stands: tellsHead and run read the declaration instead of type names, and boundPR.other compares through the link's shapes.

7. Two small envelope points. The core derives train from head_branch after Normalize (the yard/\<train\> branch is yardr's convention, not the service's; a pack script must not restate it), filling it only when the script left it empty. And thread.opened's input gains since, which Declared.Opened drops today and GitHub's search needs to bound itself; scripts that do not need it ignore the field.

### 3.2. What needs no change

Verify is data already: GitHub's header, prefix, delivery id and absent timestamp are exactly what hook.verify says. Normalize, the thread commands, the link templates, hook.keys, the says and makes tables, the hears maps, the base override (YARDR_SOURCE_BASE takes YARDR_GITHUB_API's place) and MoveSourceRecords all carry GitHub as they carried Linear. Stood needs no protocol: nothing reads it. Instead needs none: GitHub never sets it. The contributors pack's sources.github lines work unchanged against a declared github, field for field.

### 3.3. Honest deltas

Three behaviours change, in the open, ecan-style. The gh auth token fallback goes: outside a crew member's session a person sets their own credential, as with every declared source. A minted token is not evicted on a 401 (the core cannot see a script's curl answer); the expiry margin is the guard. And the daemon's CI and pull-request reads need setup where the operator's gh login served ambiently: the dispatcher's reads need the hook's as and a crew member's credential, the runner's brief snapshot needs the source's own env file. Both are one setup step each in the pack's SETUP.md.

### 3.4. What a person types and sees

Setting the yard up, after the pack lands:

```sh
yardr pack apply github
# applied pack github to the yard: 1 created, 0 changed, 0 unchanged
# source github is declared (yardr source show github)
yardr source set github env_file=~/.yardr/sources/github.env
# source github: GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY_FILE are set in ~/.yardr/sources/github.env
yardr source set github mint_command=/Users/me/bin/github-mint
# source github: mint command /Users/me/bin/github-mint
yardr source check github
# github credential: minted from GITHUB_APP_ID and GITHUB_APP_PRIVATE_KEY_FILE, good until 14:02
# check installation_repositories: ok (3 repositories)
```

The hook, the identity and the grants are as docs/integrations.md says for GitHub today, with the source now declared: yardr hook add gh --source github --secret-file ~/.yardr/github.secret, yardr crew identity yardmaster --source github --key octocat (folded to lowercase), yardr crew set yardmaster open_threads=github set_state=github. A yard that never applied the pack gets errors naming yardr pack apply github, as Linear's removal did (commit 86deb31). A yard still on github-declared folds it once, as linear-declared folded.

### 3.5. A third tracker

Jira, walked against the proposal, file by file. The author writes pack.yaml (kind source, setup SETUP.md, sources.jira.declaration), jira.yaml, two or three scripts, and SETUP.md. The declaration uses: credential.env for the API token (Jira's Basic pair travels as one base64 variable in the header "Authorization: Basic {credential}", which the header shape already allows); no mint (static tokens do not expire); hook.verify as Jira signs (if Jira signs HMAC-SHA256 over the body, today's verify covers it; said plainly: if it signs another way, or not at all, the proposal does not cover it, and the bearer-equality Token proves in Go how small such a scheme is to add — that would be the next declaration bead, not a rethink); hook.normalize for Jira's issue and comment events; hook.keys for project, issuetype and whatever wheres the pack's says lines name; thread.reply, posted, read, open, opened and state (the state script maps started, review and done onto the project's status names, which differ per project — a script's job, as with Linear's per-team statuses); thread.labels: true for Jira's labels, the key GitHub paid for; link.host jira's host with the /browse/PROJ-123 shape and fold: lower only if Jira's keys prove case-insensitive; no pull shape, no repos pattern, no events key (no pull requests, no runs — the dispatcher never asks). Identity needs no fold (account ids are opaque). What the proposal does not give Jira today: a verify scheme other than HMAC-SHA256 if Jira needs one, and per-project status maps (a map is per source; gap 14 in docs/integrations.md, unchanged by this design). Nothing in the walk needs a new trick in the core beyond those two named items.

### 3.6. The template for a new source pack

packs/linear is a worked example, not a template: copying it copies Linear's API shapes (GraphQL queries, Linear's field names, its webhook's body) and teaches nothing about which keys are required. The template is a skeleton with no service in it: a declaration naming every key with comments saying when to keep or drop it, normalize and thread stubs in sh and jq showing the stdin and stdout shapes from the core's contracts, a SETUP.md checklist shaped like Linear's (webhook, hook, credential, identity, grants, test), and a test that the skeleton still reads and applies in a scratch yard so it cannot drift from the reader. Whether that skeleton is a directory to copy or a command that writes one is open question 1 below; the bead builds whichever is decided.

## 4. Left out

A notify call for the github pack: no compiled adapter tells a user, and GitHub gives an App no direct message to send; the pack declares what the adapter had. The token source stays in Go: it is yardr's own, not a service. The assembly scripts keep driving gh: they are the operator's scripts, already outside the binary. A second verify scheme (Token's bearer equality as data) waits for the tracker that needs it; GitHub does not. The Stated.Instead protocol stays dormant for packs; GitHub never set it. Grants and identity per action (yardr-s48v's points 3 and 4) still want their one-paragraph design; the mint is built not to block it (the credential belongs to the crew member whose env names it, and every use is through the existing grants). The secret-asking flow of yardr-0qs5 is not this design: this design only holds the custody it can (mint inputs named in the declaration, values never in the store, events, logs or briefs) and names the variables a future asker asks for, leaving whether that boundary is enough to open question 4.

## 5. Open questions

1. The template's form: a directory to copy, or a command that writes one (yardr source new)? The directory costs almost nothing (a skeleton plus a test that it reads) and drifts unless the test holds it; the command costs new CLI surface, its tests and its maintenance, and holds the author's hand (names, key choices). I would take the directory: the declaration's contracts are the documentation, and the test holds it.

2. The mint's scope: pass the caller's scope (thread, or repository and number) so tokens narrow per repository, as installation tokens do today, or mint scope-free? Scope keeps a real security property at the cost of a cache key with two parts and a stdin field every mint command takes; scope-free is simpler and mints installation-wide tokens that live up to an hour in command environments. I would keep the scope: the property is cheap and dropping it widens every minted token.

3. Whose credential reads a pull request and CI for the dispatcher's daemon half: the hook's as crew member, or the source's own env file? The as member reuses issues.go's rule and the existing grants directly, at the cost of needing a crew member with the credential on every hook that judges runs or CI; the source's own file (today read only by source check and declared calls) would make daemon reads the yard's own, at the cost of broadening that file's role. I would take the hook's as member: it is the credential the yard already reads for everything the daemon does in a source. The runner's brief snapshot is not part of this question: the runner has no hook, so it always uses the source's own env file.

4. The custody line for minted credentials: is "not shown unasked" enough, or must the design go further? yardr-0qs5 explicitly leaves this open: every agent runs as the same OS user and can read a 0600 file, or the environment of a command it can see, if it goes looking. Holding at "not shown unasked" (values only in command environments, never in panes, mail, events, briefs or beads) costs nothing beyond this design and matches what the yard does for every credential today; going further (the macOS Keychain, a file owned by another user, a mint the daemon performs and agents never see even in environments) is a yard-wide change with its own design and platform costs, and belongs to yardr-0qs5, not to these beads. I would hold at "not shown unasked" here and let yardr-0qs5 move the line for all credentials at once if the operator wants it moved.

No part of GitHub was found that cannot be made general without bending the core: the mapping above is total, and the nearest bends (the fixed check vocabulary, the pull pattern's group-count rule) are declared contracts with validation, not service cases. The fourth question is the custody line, not a generality failure.

## 6. The beads it would become

In the order they land. B1 to B4 land in numeric order, each depending on the previous: all four extend the declaration reader in internal/source/declaration.go, B1 and B3 both touch the fold and link lookups in internal/hooks/issue.go and identity.go, and B3 and B4 both touch internal/dispatch/github.go, so parallel branches would conflict textually. There is no other technical order between them; the sequence exists so builders never race on shared files. B5 through B9 then chain in order, each depending on the previous: B9's technical need is only B1 to B4, but it also touches docs/integrations.md, so it waits for B8. Sizes follow the Linear beads: each is one concern with its tests, finishable without asking.

B1. Declared sources: per-hook bodies, labels, folding, opened-since, train from head_branch. Goal: the five small generalizations of sections 3.1.1, 3.1.3, 3.1.4 and 3.1.7, each inert until a declaration uses it. Where to look: internal/source/declaration.go (the reader), internal/hooks/declared.go (Bodies), internal/hooks/forward.go (Places), internal/hooks/identity.go and issue.go (fold lookups), internal/hooks/open.go (since into thread.opened), the receiver that stores envelopes (train from head_branch when absent). Done when: fixture declarations exercise each key; sh .yardr/test passes; no behaviour changes for existing yards.
