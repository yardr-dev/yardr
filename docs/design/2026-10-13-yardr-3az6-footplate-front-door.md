# footplate is the front door: it opens with no yard, sets one up, and switches it on and off

Design yardr-3az6, proposed 2026-10-13. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory that beads are worked in; a bead is one durable piece of work. The crew are the yard's always-on agents, and the yardmaster is the one that coordinates: it shapes beads, keeps the line moving and answers people. A harness is the agent program herdr starts (claude, codex); herdr is the terminal multiplexer whose server runs every agent's pane. A pack is a way of working as one directory: flows, groups, roles, crew members; importing one into a depot makes its line. The operator is the person who runs the yard. footplate is the native window over a yard, for macOS and Linux, in its own repository and depot. docs/glossary.md of yardr has all of these words. In this document "the person" is someone who does not use a terminal, and "first-run" is everything between opening footplate with no yard and talking with the yardmaster.

## 1. The question

mckean, 13 Oct 2026 (mail 24578): two friends installed yardr and footplate, one replacing Replit with it, a teacher running essays. "Sometimes concepts are a bit hard and I basically tell him to just talk to you about the needs. One other thing ... a bit tricky for both of my friends today, installation. Herdr is something they do not know, the terminal is something they are not familiar with. Turning yardr on and off is something they do not know how to do. Onboarding in the cli seems a bit foreign." So: what is the smallest footplate, and the smallest change in yardr under it, with which such a person gets from a downloaded program to talking with the yardmaster, and can switch the yard off and on, without typing a command?

## 2. What exists today

### 2.1. Getting yardr onto the machine

docs/install.md: yardr is one static binary, by release archive or `go install`. The archive's way needs `gh`, logged in, while the repository is private (a plain download gets a 404), then a checksum over `checksums.txt`, which "shows that the download is whole, not who made it", then a move onto PATH. A browser download marks the archive quarantined, and Gatekeeper refuses an unsigned binary until the mark is cleared; a signed one needs the network once for Apple's ticket, which cannot be stapled to a bare binary. `go install` needs the Go toolchain. Either way yardr then needs git, herdr and a harness beside it, and `yardr doctor` says which are missing.

footplate's README: Rust with gpui, "no installer. The binary is the application: copy it where you like and run it." `scripts/bundle-mac.sh` wraps it as `Footplate.app`, signed ad hoc, "not notarized, so it is for the Mac that built it". Every change "is reviewed twice before it lands: against its bead, then for security alone."

### 2.2. The setup is already data

The onboarding (bare `yardr` in a terminal; `firstRun` and `onboard` in internal/cli/init.go, the skip list `noOnboarding`) asks: default harness, yardmaster name, shell directory, model, operator name, operator style (default "Show me"), an about line, then "Create this yard?" and "Start the yard now?". Before the first page it names git or herdr when one is not on PATH. `yardr init` with flags does the same without the form (`--harness` required to create), is safe to run again, and reports `found` and `added` as JSON; `init --start --json` reports the start under `start` (docs/configuration.md, "Creating a yard", "Starting the yard").

The rest of the setup is one list of steps read from the store by one function, which `yardr doctor` prints, `yardr setup` walks as forms, and the yardmaster's first run reads through `yardr doctor` (docs/setup.md, "One list of steps"). Each setup page asks what its command needs and runs that command: `yardr depot add`, `yardr depot init`, `yardr bead create` plus `advance`, `yardr subscribe`; with `operator_style` `guide` the pages print no command lines. Without a terminal, with `--json`, or in an agent's session, `yardr setup` asks nothing and prints the steps with the next command; `setup --json` prints `home`, `steps` and `next` (docs/setup.md, "Where no form runs", "As a script"). `yardr doctor --json` prints `home`, `yard`, `machine` (every program with its install hint and, for herdr, whether its server answers), `steps`, `next` and `optional`; on a home with no yard it checks the machine, creates nothing (no store, no server), and exits 0 or 1 (docs/doctor.md, "JSON"). `yardr status --json` reports what runs (server, daemon, crew, web views, work) but on a home with no yard exits 2 and starts no onboarding (docs/doctor.md, "yardr status").

The import already answers a form driver: without a terminal, `depot init --yes` reports what is still missing as JSON (`{"error": ..., "missing": [...]}` with the flags to add, one to a line: `planImport` in internal/cli/pack.go), so a caller can ask for exactly those and run it again. `yardr harness show <kind> --json` prints what a kind's file says (`harnesses/<kind>.yaml`: version and one-shot flags, error lines, install hint).

### 2.3. Starting, stopping, and staying started

A yard is four things that run: the server, the daemon, the web view, and herdr's server. `yardr daemon` / `start` / `stop` / `status` / `install`, and the same verbs for `web`, `bdp` and `otel`, are one shared shape (docs/configuration.md, "Long-running commands", "Login services"): user-level services, launchd agents on macOS and systemd user units on Linux, holding the installing shell's PATH and `YARDR_HOME`. The onboarding offers "Start the daemon at login?" and the web view, each starting at no.

Bead yardr-0pk6 (blocked by this design) is `yardr up` / `yardr down`: up brings up what is not running and says in plain lines what it started and could not; down stops what up would start; both safe to repeat. It is not to be built until mckean says whether yardr may start herdr's server and install its login service. That is open question 1 here too.

### 2.4. What herdr and a harness still ask of the person

herdr on PATH is a program; what starts agents is its server. Without one every start fails with `server_not_running` and doctor reports `FAULT`. It is started by running `herdr` in a terminal or, headless, `herdr server` under a service the person writes by hand from the example files (docs/install.md, "herdr's server", "Keep it running after a reboot"). yardr installs nothing for herdr and does not know whether its server starts at login: doctor's `herdrLoginPart` (internal/cli/doctor.go) and the setup's `Optional` section (docs/setup.md, "Herdr's server at login") say exactly that, always. One server serves every yard on the machine. yardr knows where to get herdr only as `https://herdr.dev` (`needs.go`).

A harness needs installing (the kind file's `install:`: an npm command for claude and codex, a page for opencode, its own documentation for the rest) and logging in. The login is the harness's own screen in a pane; yardr types nothing into it, except answering Claude Code's trust-folder question at session start, and a login screen is "told of at once, never typed into" (design yardr-8wxe, section 2.3; the crew's `not logged in` line in docs/doctor.md). `yardr doctor --try` proves a login with one real call per harness, which costs a model call, so the onboarding asks "Check that \<harness> answers?" first. A harness run for the first time may also show a welcome screen of its own; the wait for the yardmaster then shows the pane's last lines and how to reach it (`herdr agent attach`), and goes on waiting for the person to answer it in the pane (docs/setup.md, docs/configuration.md "Starting the yard").

### 2.5. footplate today

footplate (github.com/yardr-dev/footplate) "is an interface over yardr's socket API and starts nothing of yardr's". `src/api.rs` is the whole client: HTTP/1.1 over `$YARDR_HOME/yard.sock`, else `~/.yardr/yard.sock`, or a paired yard at an address with a device token. Who the window is for "is not typed": `$YARDR_ACTOR`, else the login name, else the operator. With no yard "the window says so, names the socket, and tries again every 3 seconds"; it does not start the server. The only program it starts anywhere is `notify-send`, on Linux, to show a desktop notification (`src/notify.rs`). Settings live in `settings.json` (`~/Library/Application Support/footplate/` on macOS, `$XDG_CONFIG_HOME/footplate/` elsewhere; `src/settings.rs`); tokens live beside it in 0600 files, never in the settings. A menu-bar item on macOS, a tray item on Linux, lists the yards with what waits and offers "Show window" and "Quit footplate" (`src/tray.rs`). The first slice is conversations with the crew, as `yardr chat` shows them; a secret ask's value "is typed in that field and held nowhere else in the window".

### 2.6. The web view cannot carry the setup today

`yardr web serve` is a client of the socket in its own process: every route is registered GET, "so the mux refuses every other method itself: the view changes nothing" (`routes` in internal/web/server.go), loopback unless `--unsafe`, no login (docs/web.md). It is not in `noOnboarding`, so on a home with no yard it runs the terminal onboarding first, or with no terminal exits 2: it cannot serve a yard that does not exist yet. Acting from the browser is decided (design yardr-8wxe, `--as <user>`; beads yardr-y6ty for mail and the conversation, yardr-bvt3 for asks and moves) but both wait in backlog behind the trial yardr-aj24. So a setup in the web view needs, in order: the trial, the two acting beads, serving before a yard exists, and writes for init and the import. That is open question 3.

## 3. The proposal

The existing mechanism that carries the whole first run is yardr's JSON plus its idempotent commands: `doctor --json` for what is missing, `init` flags for creating, the import's `missing` JSON for the depot's setup, `up`/`down` for the switch. footplate becomes a guided runner of those commands. What is new is: the first-run screens in footplate (bead F1), the switch in footplate (bead F2), a signed footplate release carrying yardr (bead F3, open question 2), one login recipe per harness as data in yardr (bead Y1), the JSON gaps that keep a driver from running the first run with stdin closed (bead Y2), and `yardr up`/`down` itself (bead yardr-0pk6, which exists and waits on open question 1).

### 3.1. From download to the yardmaster

The person downloads footplate, opens it, and never types a command. Each screen runs the bundled yardr (absolute path inside the app; open question 2) as the user, with argv and no shell:

1. **What this needs.** footplate runs `yardr doctor --json`, which works with no yard and creates nothing. One row per prerequisite — yardr itself (the bundle: always ok), git, herdr and its server, one harness — in plain words. A missing row has two buttons: the vendor's page (herdr.dev, the harness's install page from its kind file) opened in the browser, and "Check again", which re-runs doctor. footplate installs nothing itself (section 3.4). Nothing proceeds until git and herdr are present, herdr's server answers, and one harness is installed.
2. **Your yard.** One form: your name (default: the login name), the harness (the installed ones, the first preselected, as the onboarding preselects), the yardmaster's name (default `yardmaster`), an optional model, "How should agents work with you?" (the four styles with their meanings, preselected to Guide me, which prints no command lines anywhere), and the optional about line. "Create and start" runs `yardr init` with those flags, then starts the yard exactly as the switch does (section 3.2): one Start path, not two.
3. **Logging the harness in.** Only when the yardmaster does not come up logged in (doctor's `not logged in` note, or a failed start whose reason the kind file marks). The card is made from the kind's login recipe (bead Y1): what to open (a button for the URL), what to paste back (a field), and "Check", which makes the one real call `yardr doctor --try` makes for that kind only, after saying it costs a model call, as the onboarding does. The pasted code is fed to the command's stdin and never stored, like a secret ask's value. A kind with no recipe is marked "needs a terminal to log in" back on screen 2; the smallest version brings the recipe for claude only.
4. **The depot and the first bead.** A folder picker for the repository or directory, the depot name (the directory's, lowercased), the base branch (prefilled from a read-only `git` call footplate makes itself; a directory that is no checkout becomes a dir depot, as the setup page does). "Set up" runs `yardr depot add`, then `yardr depot init --yes`, reading its `missing` JSON and asking only for those: agent binds default to the yard's default kind, people default to empty and the operator. Then the first bead's title and goal (`bead create`, `advance --to new`), and "Be told when beads land?" (a checkbox; `yardr subscribe`), as the setup asks. Pairing with another yard is not asked: a yard is complete without it.
5. **Talking.** footplate opens the yardmaster's conversation, its existing chat, where the yardmaster's greeting mail (its `greet` config) is the first word. This is the onboarding's "Talk to the yardmaster" with no terminal. The yardmaster then does its setup conversation by mail, as it does today.

Where a step fails, footplate shows yardr's words and the one thing to do, as `yardr up` will (bead yardr-0pk6): it never shows a command line unless the style is not Guide me, and it never asks the person to run one.

### 3.2. The switch

The yard's row in the window's head shows its state — Running, Starting, Stopped, or what it lacks — read from `yardr status --json`, and a Start/Stop button. Start runs `yardr up`; Stop runs `yardr down`; both are safe to repeat, so a double click is harmless. The "No yard" state becomes the Start screen: with a yard that is stopped, "Start"; with no yard at all, the first run of section 3.1. Beside the switch, "Start at login" runs `yardr daemon install` (and removes it again when unchecked); herdr's server at login is open question 1. footplate never starts or installs the web view: footplate is the view.

Whether Start covers herdr's server depends on open question 1. If yardr may start it, Start just works and the promise holds through a reboot; if not, Start ends where herdr is down with the one step the person must take in herdr, and the no-terminal promise breaks at the first reboot. That is why the question is asked first.

### 3.3. How yardr gets onto the machine (open question 2)

Recommended: footplate carries yardr. The release pipeline downloads the yardr release for the named version, verifies `checksums.txt`, and places the binary in the app bundle (macOS) or beside footplate in the archive (Linux). The person then never meets `gh`, a checksum, or PATH; the private repository stays a build-time fact, since the pipeline is what logs in. The bundle's signature carries authorship, which `checksums.txt` alone never does, and an app can staple Apple's ticket, which a bare binary cannot (docs/install.md, "macOS"). The release notes name the yardr release inside; the bundled yardr always wins over a PATH one, so what the window drives is what was tested, and a terminal user's own copy is untouched. The alternatives — footplate fetching a release at first run, or a one-line installer or Homebrew tap bringing both — are open question 2.

### 3.4. What footplate runs, as whom, and what it never does

footplate runs as the user, with no elevation and no shell: every command is argv, never `sh -c`. The trust changes from "shows a yard" to "runs yardr as you"; the table below is the whole of it, and each footplate bead is reviewed against it in the security review its README requires.

| footplate runs | for |
|---|---|
| the bundled `yardr`: `doctor --json [--try]`, `status --json`, `setup --json`, `init`, `up`, `down`, `depot add`, `depot init --yes ...`, `bead create`, `bead advance`, `subscribe`, `daemon install/uninstall/status`, `harness show --json` | every screen and the switch |
| the login recipe's command for one harness, with the pasted code on stdin | screen 3, kinds with a recipe only |
| `git` read-only (`rev-parse`, `branch --show-current`) in the picked directory | prefilling the depot form |
| the OS opener with an `https://` URL, or revealing a file | vendor pages, the login page, showing what was written |

What it never does: run anything as root or another user; run an installer of any kind (no npm, brew, pip, no `curl | sh`, no package the vendor's page offered — the person runs those); change PATH or any shell profile; type into a herdr pane or start herdr's server itself (that is yardr's to do, open question 1, or the person's in herdr); store a harness credential or the pasted login code anywhere; write outside its settings and token files except through yardr commands into the yard home; make a network call of its own beyond the yard socket and paired addresses it already speaks (downloading and logging in happen in the browser); write the store except through yardr (no second setup logic against the database); phone home.

### 3.5. Why not the web view (open question 3)

The web view carrying the setup's pages would share them between footplate and a browser, but it is the longer road to the same place: the view is GET-only, cannot serve a home with no yard (section 2.6), and its acting beads wait behind a trial. footplate would still need its own native prerequisite screen, since installing git, herdr and a harness needs the OS (a browser, a vendor installer, re-checks), not a page. So the shared mechanism is the JSON and the idempotent commands, not the markup: the terminal forms, footplate's screens, and a later web setup all drive the same steps (the one list of docs/setup.md) and the same commands. A web setup built later reuses beads Y1 and Y2 unchanged.

## 4. Left out

- **footplate installing anything.** No npm, no brew, no script from a page. Running installers as the user who clicked is the largest trust in this design, and the vendors' installers already lead. footplate opens the page and checks again.
- **A web setup.** Section 3.5 and open question 3: later, on the same JSON, reusing Y1 and Y2.
- **Typing into panes.** Beyond feeding the pasted login code to the recipe's stdin, footplate types nothing anywhere: no harness welcome screen answered, no `herdr agent attach`. Where the yardmaster waits at something the recipe does not cover, footplate shows the pane's last lines and where it is, as the terminal wait does today, and waits. Full pane access without a terminal is a herdr question, not this design's.
- **Pairing, cloning, and second yards.** No peer pairing in the first run (a yard is complete without one), no clone-from-URL (a local folder only; `depot add --clone` stays a terminal command), no `--home` choice (the default home's yard; footplate's other-yards settings stay as they are for later).
- **The tray switch.** Start/Stop lives in the window only. The tray keeps its menu of yards; a background process starting daemons from a menu is more surface for no new capability.
- **footplate starting itself at login.** The yard comes back through its services; footplate opens when the person opens it.
- **More than claude's login.** One recipe proves the shape; each further kind is a small bead of its own once its login is read.
- **Windows, phones, auto-update.** footplate is macOS and Linux; a phone's footplate is design yardr-xpf8's question; updates are a fresh download until someone designs them.

## 5. Open questions

**1. May yardr (or footplate through it) start herdr's server and install its login service?** This is also what bead yardr-0pk6 waits on; the answer lands there, and this design only depends on it. Option A, both: `yardr up` starts the server when it is down and `daemon install` (or `up` asked once) installs its login service from yardr's own unit, replacing the hand-saved files of docs/install.md; the no-terminal promise holds through a reboot, at the cost of overturning the docs' stated rule, owning another program's lifecycle (upgrades, a server other yards and the person's own panes share — `down` must not strand them), and review on both sides. Option B, start only: Start works until the next reboot, then the person opens herdr once; less owned, and the promise breaks weekly. Option C, neither: Start ends at herdr with instructions, as the terminal does today; nothing owned, and the person keeps a terminal step. I would take A: without it the switch this design exists for stops at the first reboot, and a launchd agent and a systemd unit are a mechanism yardr already owns for its own services.

**2. How does yardr get onto the machine when footplate is first?** Option A, footplate carries yardr in its release (section 3.3): no `gh`, no checksum, no PATH for the person; it costs tracking yardr releases in footplate's pipeline, a larger download, and two copies on disk for people who also use the terminal. Option B, footplate fetches a yardr release at first run and verifies it: a smaller download that is always fresh; it costs network at first run, trust on first sight, and, while the repository is private, a credential baked into the app or a login the person cannot do without a terminal. Option C, a one-line installer or Homebrew tap brings both: familiar, and nothing bundled; it costs a terminal, which is what this design removes — it stays the road for terminal users. I would take A.

**3. Do the setup's pages live in footplate, or in the web view shared with a browser?** Option A, footplate-native on yardr's JSON (sections 3.1 and 3.5): the shortest road, since the prerequisite screen is native either way; it costs a third face on the setup (terminal forms, footplate screens, later web pages) over the one list of steps, which stays one. Option B, the web view carries them: one face for footplate (which would embed or open it) and a browser; it costs waiting for the trial and both acting beads, teaching the view to serve before a yard exists and to take setup writes, and a security review of writes-before-a-yard — while footplate still needs its native prerequisite screen. I would take A, with the JSON kept clean enough that B reuses Y1 and Y2 later.

## 6. The beads it would become

In the order they would land. Beads that exist and are not made here: yardr-0pk6 (`yardr up`/`down`, depot yardr, waits on open question 1) is the switch's mechanism and F2's dependency; yardr-y6ty and yardr-bvt3 (the web view acts, depot yardr, behind the trial yardr-aj24) are the road open question 3 does not take. Each bead below passes its depot's gate (`sh .yardr/test` for yardr; `cargo fmt`, clippy, test and build for footplate, each change reviewed twice, the second for security alone). Anything that starts servers or drives commands as subprocesses is tried in an isolated yard (yardr) or against a stand-in yardr (footplate), never the operator's own.

**Y1 (yardr). A harness's login as data, and a one-kind check.** Goal: footplate can lead a login for a kind with a recipe and prove it with one call. Where to look: `harnesses/claude.yaml` and `InstallHint`/`OneShotArgs` in internal/agents/harness.go for the shape of kind data; `yardr harness show --json` (internal/cli/harness.go) for the surface; `yardr doctor --try` (docs/doctor.md, "--try") for the one real call. Done when: the kind file carries a `login:` recipe (the command argv, which output lines hold the URL or prompt, what stdin takes) for claude; `harness show claude --json` prints it and doctor's `--json` machine items say which kinds have one; `doctor --try` takes one kind and tries only it, saying it costs a model call; docs/doctor.md documents the recipe and the flag. Depends on nothing.

**Y2 (yardr). The whole first run drivable with stdin closed.** Goal: every command footplate's screens run takes JSON in or out (or `--yes` with `missing` JSON, as `planImport` already prints) and is refused cleanly with no terminal, so a driver never parses prose. Where to look: `initYard` and its `found`/`added` JSON, `setup --json`, `depot add` errors, and `planImport`'s `missing` JSON in internal/cli as the model. Done when: a test script runs create-yard, add-depot, init-depot, create-and-advance-bead and subscribe with stdin closed, asserting each step from JSON alone, and names in docs/setup.md which commands a driver runs; any gap the script finds is closed in this bead. Depends on nothing; F1 needs it.

**F1 (footplate). The first-run window: no yard to talking.** Goal: section 3.1 — prerequisites, create, login, depot and first bead, ending in the yardmaster's conversation. Where to look: the "No yard" state and retry in src/window.rs and src/yard.rs; the client in src/api.rs and the fake yard in src/fake.rs; the settings and token files in src/settings.rs; footplate's README ("What it talks to", "No yard"). Done when: with no yard, the window shows the prerequisite rows from the bundled yardr's `doctor --json` (a stand-in script in tests), each missing row opening the vendor's page and re-checking; the create form runs `init` and Start; the login card follows the claude recipe, feeding the pasted code to stdin and storing nothing; the depot form picks a folder and loops `depot init --yes` on its `missing` JSON; the run ends with the yardmaster's conversation open; every subprocess is argv, never a shell, and the run-table of section 3.4 holds, checked by the security review. Depends on Y1 and Y2.

**F2 (footplate). The switch.** Goal: section 3.2 — the yard's state with Start/Stop in the window's head, backed by `yardr up`/`down`, plus "Start at login". Where to look: the head and yard switcher in src/window.rs; the "No yard" state, which becomes the Start screen; `yardr status --json` for the state. Done when: the head shows Running/Starting/Stopped (or what it lacks, in yardr's words) and Start/Stop run `up`/`down`, safe to repeat; with no yard the window offers the first run; the login checkbox installs and removes the daemon's service (and herdr's, as open question 1 was answered); the security review holds the run-table. Depends on yardr-0pk6 and F1.

**F3 (footplate). A signed release carrying yardr.** Goal: section 3.3 — the downloaded program of section 3.1. Where to look: `scripts/bundle-mac.sh`; yardr's `contrib/release/build` and docs/install.md ("From a release archive", "macOS", "Signed darwin binaries") for archives, checksums and notarization. Done when: the pipeline builds a macOS disk image with a signed, notarized Footplate.app holding the named yardr release (checksums verified at build time) and a Linux archive with both binaries; installing either needs no terminal; the release notes name the yardr release inside; the bundled yardr wins over PATH and About shows both versions. Technically independent; listed here because it ships F1 and F2.

**T (footplate). The trial: one friend, one week.** mckean's and the yardmaster's, not a builder's. One person who does not use a terminal installs F3's release, reaches the yardmaster, and runs a real small thing (an essay's drafts, a toy app) for a week. Depends on F1, F2 and F3. Done when a note on the bead says: time from download to the first talk with the yardmaster; each place the person was stuck and what unblocked them; each time anything asked for a terminal and for what (this orders the follow-ups: further login recipes, the tray switch, a web setup); whether the switch was used and understood; whether the yard came back after a reboot unaided.
