# footplate is the front door: it opens with no yard, sets one up, and switches it on and off

Design yardr-3az6, proposed 2026-10-13. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A depot is a git repository or a plain directory that beads are worked in; a bead is one durable piece of work. The crew are the yard's always-on agents, and the yardmaster is the one that coordinates: it shapes beads, keeps the line moving and answers people. A harness is the agent program herdr starts (claude, codex); herdr is the terminal multiplexer whose server runs every agent's pane. A pack is a way of working as one directory: flows, groups, roles, crew members; importing one into a depot makes its line. The operator is the person who runs the yard. footplate is the native window over a yard, for macOS and Linux, in its own repository and depot. docs/glossary.md of yardr has all of these words. In this document "the person" is someone who does not use a terminal, and "first-run" is everything between opening footplate with no yard and talking with the yardmaster.

## 1. The question

mckean, 13 Oct 2026 (mail 24578): two friends installed yardr and footplate, one replacing Replit with it, a teacher running essays. "Sometimes concepts are a bit hard and I basically tell him to just talk to you about the needs. One other thing ... a bit tricky for both of my friends today, installation. Herdr is something they do not know, the terminal is something they are not familiar with. Turning yardr on and off is something they do not know how to do. Onboarding in the cli seems a bit foreign." So: what is the smallest footplate, and the smallest change in yardr under it, with which such a person gets from a downloaded program to talking with the yardmaster, and can switch the yard off and on, without typing a command?

## 2. What exists today

### 2.1. Getting yardr onto the machine

docs/install.md: yardr is one static binary, by release archive or `go install`. The archive's way needs `gh`, logged in, while the repository is private (a plain download gets a 404), then a checksum over `checksums.txt`, which "shows that the download is whole, not who made it", then a move onto PATH. A browser download marks the archive quarantined, and Gatekeeper refuses an unsigned binary until the mark is cleared; a signed one needs the network once for Apple's ticket, which cannot be stapled to a bare binary. `go install` needs the Go toolchain. Either way yardr then needs git, herdr and a harness beside it, and `yardr doctor` says which are missing.

footplate's README: Rust with gpui, "no installer. The binary is the application: copy it where you like and run it." `scripts/bundle-mac.sh` wraps it as `Footplate.app`, signed ad hoc, "not notarized, so it is for the Mac that built it". Every change "is reviewed twice before it lands: against its bead, then for security alone."

### 2.2. The setup is already data

The onboarding (bare `yardr` in a terminal; `firstRun` and `onboard` in internal/cli/init.go, the skip list `noOnboarding`) asks: default harness, yardmaster name, shell directory, model, operator name, operator style (default "Show me"), an about line, then "Create this yard?" and "Start the yard now?". Before the first page it names git or herdr when one is not on PATH. `yardr init` with flags does the same without the form (`--harness` required to create), is safe to run again, and reports `found` and `added` as JSON; `init --start --json` reports the start under `start` (docs/configuration.md, "Creating a yard", "Starting the yard"). Creating needs no herdr server: only starting does, since starting begins the yardmaster's agent in herdr.

The rest of the setup is one list of steps read from the store by one function, which `yardr doctor` prints, `yardr setup` walks as forms, and the yardmaster's first run reads through `yardr doctor` (docs/setup.md, "One list of steps"). Each setup page asks what its command needs and runs that command: `yardr depot add`, `yardr depot init`, `yardr bead create` plus `advance`, `yardr subscribe`; with `operator_style` `guide` the pages print no command lines. Without a terminal, with `--json`, or in an agent's session, `yardr setup` asks nothing and prints the steps with the next command; `setup --json` prints `home`, `steps` and `next` (docs/setup.md, "Where no form runs", "As a script"). `yardr doctor --json` prints `home`, `yard`, `machine` (every program with its install hint and, for herdr, whether its server answers), `steps` and `next`; for a program missing from the PATH doctor was run with, doctor itself runs the user's login shell once (`$SHELL -l -c 'command -v …'`, stdin closed) and reports where that finds it as `login_shell_path` (`loginShellFinds` in internal/cli/needs.go); on a home with no yard there is no `state` and no `optional` (the comment on `doctorReport` in internal/cli/doctor.go), it checks the machine, creates nothing (no store, no server), and exits 0 or 1 (docs/doctor.md, "JSON"). Doctor changes nothing to answer: it installs nothing, starts no daemon, no yardr server and no herdr server (docs/doctor.md, "Read-only"). `yardr status --json` reports what runs (server, daemon, crew, web views, work) but on a home with no yard exits 2 and starts no onboarding (docs/doctor.md, "yardr status").

The import already answers a form driver: without a terminal, `depot init --yes` reports what is still missing as JSON (`{"error": ..., "missing": [...]}` with the flags to add, one to a line: `planImport` in internal/cli/pack.go), so a caller can ask for exactly those and run it again. `yardr harness show <kind> --json` prints what a kind's file says (`harnesses/<kind>.yaml`: version and one-shot flags, error lines, install hint).

### 2.3. Starting, stopping, and staying started

A yard is four things that run: the server, the daemon, the web view, and herdr's server. `yardr daemon` / `start` / `stop` / `status` / `install`, and the same verbs for `web`, `bdp` and `otel`, are one shared shape (docs/configuration.md, "Long-running commands", "Login services"): user-level services, launchd agents on macOS and systemd user units on Linux, holding the installing shell's PATH and `YARDR_HOME`. The onboarding offers "Start the daemon at login?" and the web view, each starting at no.

The yard's server runs on demand: `yardr server stop` ends it and any later yardr command starts it again (docs/configuration.md, "yardr's own state"). The web view, the BDP server and the telemetry export are optional parts beside the daemon, each with its own `start`, `stop`, `status` and login service (docs/configuration.md, "Long-running commands"); doctor lists the web view and the login services under Optional.

Bead yardr-0pk6 (blocked by this design) is `yardr up` / `yardr down`: up brings up what is not running and says in plain lines what it started and could not; down stops what up would start; both safe to repeat. It is not to be built until mckean says whether yardr may start herdr's server and install its login service. That is open question 1 here too. Decided already, on yardr-0pk6's note: stopping or tearing a yard down also stops all its running agents in herdr; only whether down stops herdr's shared server itself is left for that bead's shaping.

### 2.4. What herdr and a harness still ask of the person

herdr on PATH is a program; what starts agents is its server. Without one every start fails with `server_not_running` and doctor reports `FAULT`. It is started by running `herdr` in a terminal or, headless, `herdr server` under a service the person writes by hand from the example files (docs/install.md, "herdr's server", "Keep it running after a reboot"). yardr installs nothing for herdr and does not know whether its server starts at login: doctor's `herdrLoginPart` (internal/cli/doctor.go) and the setup's `Optional` section (docs/setup.md, "Herdr's server at login") say exactly that, always. One server serves every yard on the machine. yardr knows where to get herdr only as `https://herdr.dev` (`needs.go`); herdr arrives by `brew install herdr`, by `curl -fsSL https://herdr.dev/install.sh | sh`, or as a binary from its GitHub releases, every one a terminal road, and keeps itself current afterwards with `herdr update`. git's hint in `needs.go` is `https://git-scm.com/downloads`, adding on macOS `xcode-select --install`, which pops Apple's own installer dialog. A harness needs installing (the kind file's `install:`: an npm command for claude and codex, a page for opencode, its own documentation for the rest; claude also ships a native binary, likewise fetched over the terminal) and logging in.

The login is the harness's own screen in a terminal. Claude Code with no login draws a menu of login methods, then a browser sign-in with a code to paste (`login:` in harnesses/claude.yaml, read live from Claude Code 2.1.288); its only login-shaped command is `setup-token`, which needs a subscription, and there is no headless login that prints a URL. yardr types nothing into a login screen, except answering Claude Code's trust-folder question at session start, and a login screen is "told of at once, never typed into" (design yardr-8wxe, section 2.3; the crew's `not logged in` line in docs/doctor.md). But the machinery for driving such a screen exists: the runner reads a pane's screen, matches a dialog by pattern, and sends keys, answering the trust dialog and cancelling the auto-mode offer with Esc (`trustAnswer` and the `dialogs:` handling in internal/runner/trust.go; `dialogs:` in harnesses/claude.yaml). `yardr doctor --try` proves a login with one real call per harness, which costs a model call, so the onboarding asks "Check that \<harness> answers?" first. A harness run for the first time may also show a welcome screen of its own; the wait for the yardmaster then shows the pane's last lines and how to reach it (`herdr agent attach`), and goes on waiting for the person to answer it in the pane (docs/setup.md, docs/configuration.md "Starting the yard").

### 2.5. footplate today

footplate (github.com/yardr-dev/footplate) "is an interface over yardr's socket API and starts nothing of yardr's". `src/api.rs` is the whole client: HTTP/1.1 over `$YARDR_HOME/yard.sock`, else `~/.yardr/yard.sock`, or a paired yard at an address with a device token. Who the window is for "is not typed": `$YARDR_ACTOR`, else the login name, else the operator. With no yard "the window says so, names the socket, and tries again every 3 seconds"; it does not start the server. The only program it starts anywhere is `notify-send`, on Linux, to show a desktop notification (`src/notify.rs`). Settings live in `settings.json` (`~/Library/Application Support/footplate/` on macOS, `$XDG_CONFIG_HOME/footplate/` elsewhere; `src/settings.rs`); tokens live beside it in 0600 files, never in the settings. A menu-bar item on macOS, a tray item on Linux, lists the yards with what waits and offers "Show window" and "Quit footplate" (`src/tray.rs`). The first slice is conversations with the crew, as `yardr chat` shows them; a secret ask's value "is typed in that field and held nowhere else in the window".

footplate already opens more than the default yard. Its settings keep a list of yards: "add a yard of this machine" takes a name and a socket path, for another home's yard (`<its home>/.yardr/yard.sock`), and needs no pairing; "add a yard at an address" takes a name, the address and a code, and pairs once (`POST <address>/user/pair`), keeping the device's token in a 0600 file (footplate's README, "A yard at an address"). That pairing makes footplate a *device* of one user of that yard (docs/users.md, "Devices"; docs/api.md, "Over the network"): picks and approvals there count as that user's. It is not yardr's *peer* pairing, which links two yards to each other by public key so crew members can mail across and one yard can work beads for the other (docs/peers.md): over a peer link an approval never crosses, while a paired device approves as its user. The two pairings share the code shape (eight characters, good once, five wrong ones end it) and nothing else.

### 2.6. The web view cannot carry the setup today

`yardr web serve` is a client of the socket in its own process: every route is registered GET, "so the mux refuses every other method itself: the view changes nothing" (`routes` in internal/web/server.go), loopback unless `--unsafe`, no login (docs/web.md). It is not in `noOnboarding`, so on a home with no yard it runs the terminal onboarding first, or with no terminal exits 2: it cannot serve a yard that does not exist yet. Acting from the browser is decided (design yardr-8wxe, `--as <user>`; beads yardr-y6ty for mail and the conversation, yardr-bvt3 for asks and moves) but both wait in backlog behind the trial yardr-aj24. So a setup in the web view needs, in order: the trial, the two acting beads, serving before a yard exists, and writes for init and the import. That is why section 3.5 takes footplate-native screens as sequencing, not as a question.

## 3. The proposal

The existing mechanism that carries the whole first run is yardr's JSON plus its idempotent commands: `doctor --json` for what is missing, `init` flags for creating, the import's `missing` JSON for the depot's setup, `up`/`down` for the switch, and footplate's own settings entries for a second local yard and a yard at an address. footplate becomes a guided runner of those commands. What is new is: the first screen and first-run flow in footplate (bead F1), the switch in footplate (bead F2), a signed footplate release carrying yardr (bead F3, open question 2), prerequisite installation as data in yardr if footplate may install (open question 3), one login recipe per harness as data in yardr plus a driver that plays it (bead Y1), the JSON gaps that keep a driver from running the first run with stdin closed (bead Y2), and `yardr up`/`down` itself (bead yardr-0pk6, which exists and waits on open question 1).

### 3.1. The first screen, and from download to the yardmaster

The person downloads footplate, opens it, and never types a command. The first screen offers three ways, and the window remembers none until one is taken:

1. **Set up yardr on this machine.** The first run below, ending talking with the yardmaster. This is the only new road; the other two exist in footplate's settings today and are surfaced here.
2. **Open a yard on this machine.** A name and a socket path, prefilled with this run's socket, as "add a yard of this machine" has it: a yard at another home is `<its home>/.yardr/yard.sock`, and needs no pairing. Choosing it opens that yard straight into its conversations.
3. **Pair with a yard at an address.** A name, the address and the code, as "add a yard at an address" has it; the other yard's operator opens the device pairing and reads both over. This pairs footplate as a device of that yard's user, not the two yards with each other: peer pairing between yards (docs/peers.md) stays a terminal road, and is not offered here.

Each screen of the first run runs the bundled yardr (absolute path inside the app; open question 2) as the user, with argv and no shell. A window opened from the desktop inherits a PATH without `~/.local/bin` or Homebrew, and `daemon install` writes the installing process's PATH into the unit, so footplate builds each child's PATH from data, not from a shell: its own inherited PATH plus the directories of doctor's `login_shell_path` answers. footplate itself never runs the login shell; the one login-shell run in the whole flow is yardr doctor's own (section 2.2), so no profile script runs in a process footplate starts:

1. **What this needs.** footplate runs `yardr doctor --json`, which works with no yard and creates nothing. One row per prerequisite — yardr itself (the bundle: always ok), git, herdr and its server, one harness — in plain words. A missing program's row offers what open question 3 decides (recommended: footplate installs it, showing the vendor's own progress; otherwise the vendor's page opened in the browser and "Check again"). On macOS a missing git is always one button, `xcode-select --install`, which is Apple's own dialog, not a terminal road. A herdr server that is installed but stopped is a row that waits: it blocks neither creating nor the other rows, because the Start path starts it (open question 1). Nothing proceeds to step 2 until git, herdr and one harness are installed; the server may still be down.
2. **Your yard.** One form: your name (default: the login name), the harness (the installed ones, the first preselected, as the onboarding preselects; a kind with no login recipe is marked "needs a terminal once to log in", bead Y1), the yardmaster's name (default `yardmaster`), an optional model, "How should agents work with you?" (the four styles with their meanings, preselected to Guide me, which prints no command lines anywhere), and the optional about line. "Create" runs `yardr init` with those flags, which needs no herdr server, then moves to step 3; starting is the switch's one Start path (section 3.2), not a second one.
3. **Logging the harness in.** footplate runs `yardr harness login <kind> --json` (bead Y1), which plays the kind's login recipe under a terminal of yardr's own and prints what it needs as JSON: `choose` for the method menu (footplate shows the methods as buttons), `open_url` for the browser sign-in (a button), `input` for the code to paste back (a field). Answers go back on stdin as JSON lines; the pasted code is never stored, like a secret ask's value. The run ends with `done`, proved by the one real call `yardr doctor --try` makes for that kind only, after saying it costs a model call, as the onboarding does. A kind with no recipe is marked back on step 2; the smallest version brings the recipe for claude only.
4. **Start the yard.** The switch of section 3.2, offered here first: Start runs `yardr up`, which starts herdr's server first when open question 1 allows, so a server that was down on step 1 is no longer in the way. Where up cannot start something it says the one thing to do, in yardr's words; footplate never shows a command line unless the style is not Guide me, and never asks the person to run one.
5. **The depot and the first bead.** A folder picker for the repository or directory, the depot name (the directory's, lowercased), the base branch (prefilled from a read-only `git` call footplate makes itself; a directory that is no checkout becomes a dir depot, as the setup page does). "Set up" runs `yardr depot add`, then `yardr depot init --yes`, reading its `missing` JSON and asking only for those: agent binds default to the yard's default kind, people default to empty and the operator. Then the first bead's title and goal (`bead create`, `advance --to new`), and "Be told when beads land?" (a checkbox; `yardr subscribe`), as the setup asks. Linking with another yard is not asked: a yard is complete without it.
6. **Talking.** footplate opens the yardmaster's conversation, its existing chat, where the yardmaster's greeting mail (its `greet` config) is the first word. This is the onboarding's "Talk to the yardmaster" with no terminal. The yardmaster then does its setup conversation by mail, as it does today.

Where a step fails, footplate shows yardr's words and the one thing to do, as `yardr up` will (bead yardr-0pk6): it never shows a command line unless the style is not Guide me, and it never asks the person to run one.

### 3.2. The switch

The yard's row in the window's head shows its state — Running, Starting, Stopped, or what it lacks — read from `yardr status --json`, and a Start/Stop button. Both buttons are `yardr up` and `yardr down` (bead yardr-0pk6), safe to repeat, so a double click is harmless; a paired yard at an address has no switch, since its processes are elsewhere. The "No yard" state becomes the Start screen: with a yard that is stopped, "Start"; with no yard at all, the first screen of section 3.1. Beside the switch, "Start at login" runs `yardr daemon install` (and removes it again when unchecked); herdr's server at login is open question 1.

Start (`yardr up`) brings up, in this order: herdr's server, but only when open question 1 is answered yes (a server already answering is left alone); the yard's server; the daemon. It never starts the web view, the BDP server or the telemetry export: those are optional parts with their own `start` and login service, and footplate is the view. If yardr may not start herdr's server, Start ends where herdr is down with the one step the person must take in herdr, and the no-terminal promise breaks at the first reboot. That is why the question is asked first.

Stop (`yardr down`) ends the yard: the daemon, the yard's server, and all the yard's running agents in herdr (decided on yardr-0pk6; footplate inherits it). It stops neither the web view nor the others up never starts. It never stops herdr's server itself: one server serves every yard on the machine and the person's own panes, and ending it would strand them; whether down stops it when nothing else uses it is the one shared-server rule left for yardr-0pk6's shaping, and this design assumes it does not. Before stopping with agents running, footplate shows how many and that their work is in worktrees while their live panes end, in yardr's words.

### 3.3. How yardr gets onto the machine (open question 2)

Recommended: footplate carries yardr. The release pipeline downloads the yardr release for the named version, verifies `checksums.txt`, and places the binary in the app bundle (macOS) or beside footplate in the archive (Linux). The person then never meets `gh`, a checksum, or PATH; the private repository stays a build-time fact, since the pipeline is what logs in. The bundle's signature carries authorship, which `checksums.txt` alone never does, and an app can staple Apple's ticket, which a bare binary cannot (docs/install.md, "macOS"). The release notes name the yardr release inside; the bundled yardr always wins over a PATH one, so what the window drives is what was tested, and a terminal user's own copy is untouched. The alternatives — footplate fetching a release at first run, or a one-line installer or Homebrew tap bringing both — are open question 2.

### 3.4. What footplate runs, as whom, and what it never does

footplate runs as the user, with no elevation and no shell: every command is argv, never `sh -c`, and footplate never runs `$SHELL -l` either — child PATHs come from doctor's `login_shell_path` data (section 3.1). The trust changes from "shows a yard" to "runs yardr as you"; the table below is the whole of what footplate runs, and each footplate bead is reviewed against it in the security review its README requires. The one login shell in the whole flow is the one `yardr doctor` itself runs for missing programs (`loginShellFinds` in internal/cli/needs.go), which runs the user's profile scripts once with stdin closed; that is yardr's documented behavior (docs/doctor.md, "Read-only"), reviewed with yardr, not a process footplate starts.

| footplate runs | for |
|---|---|
| the bundled `yardr`: `doctor --json [--try]`, `status --json`, `setup --json`, `init`, `up`, `down`, `depot add`, `depot init --yes ...`, `bead create`, `bead advance`, `subscribe`, `daemon install/uninstall/status`, `harness show --json`, `harness login --json` | every screen and the switch |
| the prerequisite installers yardr names as data, as the user, one row of step 1 each (open question 3) | step 1, only if answered yes |
| `xcode-select --install` on macOS (Apple's own dialog) | git on step 1 |
| `git` read-only (`rev-parse`, `branch --show-current`) in the picked directory | prefilling the depot form |
| the OS opener with an `https://` URL, or revealing a file | vendor pages, the login page, showing what was written |

What it never does: run anything as root or another user; run a shell of its own (`sh -c`, `$SHELL -l`); run an installer yardr does not name as data (no `curl | sh` typed or pasted, no package the vendor's page offered beyond the named one); change PATH or any shell profile; type into a herdr pane or start herdr's server itself (that is yardr's to do, open question 1, or the person's in herdr); drive a harness login itself — the terminal the recipe plays under is yardr's (`harness login`), footplate only shows its JSON needs; store a harness credential or the pasted login code anywhere; write outside its settings and token files except through yardr commands into the yard home; make a network call of its own beyond the yard socket and paired addresses it already speaks (downloading happens in the vendor's installer, logging in in the browser); write the store except through yardr (no second setup logic against the database); phone home.

### 3.5. Why not the web view

The web view carrying the setup's pages would share them between footplate and a browser, but it is the longer road to the same place, and not a live choice today: the view is GET-only, cannot serve a home with no yard (section 2.6), and its acting beads wait behind a trial, while footplate needs its own native prerequisite screen either way, since reaching git, herdr and a harness needs the OS (installers, a browser, re-checks), not a page. So this design takes footplate-native screens as sequencing, not as a question: the shared mechanism is the JSON and the idempotent commands, not the markup — the terminal forms, footplate's screens, and a later web setup all drive the same steps (the one list of docs/setup.md) and the same commands. A web setup built later reuses beads Y1 and Y2 unchanged.

## 4. Left out

- **A web setup.** Section 3.5: later, on the same JSON, reusing Y1 and Y2.
- **Typing into panes.** footplate types nothing anywhere: the login recipe is played by yardr under its own terminal (bead Y1), and beyond that no harness welcome screen is answered, no `herdr agent attach`. Where the yardmaster waits at something the recipe does not cover, footplate shows the pane's last lines and where it is, as the terminal wait does today, and waits. Full pane access without a terminal is a herdr question, not this design's.
- **Peer pairing and cloning.** No yard-to-yard link in the first run (a yard is complete without one; device pairing with a yard at an address is on the first screen, section 3.1), and no clone-from-URL (a local folder only; `depot add --clone` stays a terminal command).
- **The tray switch.** Start/Stop lives in the window only. The tray keeps its menu of yards; a background process starting daemons from a menu is more surface for no new capability.
- **footplate starting itself at login.** The yard comes back through its services; footplate opens when the person opens it.
- **More than claude's login.** One recipe proves the shape; each further kind is a small bead of its own once its login is read.
- **Windows, phones, auto-update.** footplate is macOS and Linux; a phone's footplate is design yardr-xpf8's question; updates are a fresh download until someone designs them.

## 5. Open questions

**1. May yardr (or footplate through it) start herdr's server and install its login service?** This is also what bead yardr-0pk6 waits on; the answer lands there, and this design only depends on it. Option A, both: `yardr up` starts the server when it is down and `daemon install` (or `up` asked once) installs its login service from yardr's own unit, replacing the hand-saved files of docs/install.md; the no-terminal promise holds through a reboot, at the cost of overturning the docs' stated rule, owning another program's lifecycle (upgrades, a server other yards and the person's own panes share — `down` must not strand them), and review on both sides. Option B, start only: Start works until the next reboot, then the person opens herdr once; less owned, and the promise breaks weekly. Option C, neither: Start ends at herdr with instructions, as the terminal does today; nothing owned, and the person keeps a terminal step. I would take A: without it the switch this design exists for stops at the first reboot, and a launchd agent and a systemd unit are a mechanism yardr already owns for its own services.

**2. How does yardr get onto the machine when footplate is first?** Option A, footplate carries yardr in its release (section 3.3): no `gh`, no checksum, no PATH for the person; it costs tracking yardr releases in footplate's pipeline, a larger download, and two copies on disk for people who also use the terminal. Option B, footplate fetches a yardr release at first run and verifies it: a smaller download that is always fresh; it costs network at first run, trust on first sight, and, while the repository is private, a credential baked into the app or a login the person cannot do without a terminal. Option C, a one-line installer or Homebrew tap brings both: familiar, and nothing bundled; it costs a terminal, which is what this design removes — it stays the road for terminal users. I would take A.

**3. How do git, herdr and a harness get onto the machine — may footplate install them?** Every road the vendors offer today needs a terminal (`brew install herdr`, `curl … | sh`, `npm install -g`, a binary moved onto PATH); only macOS git has a dialog (`xcode-select --install`). Without an answer here the first run ends at step 1 with a page and "Check again", and the design fails its question. Option A, footplate installs them: each prerequisite row runs the installer yardr names for it as data (argv, as the user, the vendor's own progress shown), reviewed per vendor in footplate's security review; it costs the largest trust in this design — a window that shows a yard becomes one that runs installers — plus install data in yardr to keep beside the vendors (new bead Y0, before F1), and breakage whenever a vendor changes its road. Option B, the person installs them following vendor pages footplate opens, then "Check again": it costs a terminal step for everything but macOS git, which the person may not have; the no-terminal promise then starts only once a terminal-owning friend has set the machine up. Option C, that narrower scope stated plainly: footplate requires git, herdr and one harness up front and says so on the download page, and step 1 only checks. I would take A: without it this design does not deliver its stated path, and data-reviewed installers are a smaller trust than a standing permission to run what a page says. (The earlier third question, footplate-native pages versus the web view, is taken as sequencing in section 3.5 instead: the web road is not a live choice until the trial and both acting beads land.)

## 6. The beads it would become

In the order they would land. Beads that exist and are not made here: yardr-0pk6 (`yardr up`/`down`, depot yardr, waits on open question 1) is the switch's mechanism and F2's dependency; yardr-y6ty and yardr-bvt3 (the web view acts, depot yardr, behind the trial yardr-aj24) are the later web road of section 3.5. Y0 exists only under answer A to open question 3.
