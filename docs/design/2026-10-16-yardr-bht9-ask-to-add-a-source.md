# Adding a source by a run ask, approved on a card that shows what would be added

Design yardr-bht9, proposed 2026-10-16. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A source is a service outside the yard, declared by one file; a pack is a way of working as one directory, and a pack of kind `source` declares a source yardr has no Go for. An ask is one question as data on a bead; a run ask (`yardr bead ask --run "<command>"`, design yardr-x3g8) proposes one yardr command of a fixed list, and the operator's approval (`ApproveAsk` in internal/store/runask.go) has the yard run exactly that command, as the operator, in the write that records the approval. The operator is the person who runs the yard. In this document **the card** is what a run ask shows the person asked, **a loose file** is a declaration file that stands on the yard's machine and is in no pack, and **carrying out** is the step after an approval that this design adds for the rows whose change is not one write of the store.

## 1. The question

mckean, 16 Oct 2026 (mails 41030-41051): "can you not apply the yardr pack?", and "we need find an elegant way to do this, via ask?" Today `yardr pack apply <pack>` adds the pack's sources only when the operator types it, because adding a source is operator-alone and never a run ask (yardr-fz1j), and for a good reason: a source decides where a credential of the yard is sent, and its file may name commands the yard runs. The card of a run ask shows the command, not the file, so approving `yardr source add <file>` from a phone would approve a file nobody saw. The yardmaster offered (mails 40087, 41046) to make it askable when the card shows the whole declaration. So: may a crew member propose adding a source as a run ask, what does the card show so that the approval is of what would actually be added, what makes that approval stale, and how does the yard run what was approved?

## 2. What exists today

### 2.1. Run asks, and the shape every row has

A run ask stores one command in the yard's own form (`AskRun` in internal/store/runask.go: `Argv`, the yard's sentences in `Does`, the command that takes the change back in `Back`, and `Seen`, a fingerprint of each thing the command names). The list (`runList`, and `runask_list.go` and `runask_more.go` beside it) holds commands that are each one function and one write of the store: a link's mail limit and kinds, a source's calls an hour (`sourceSeen` fingerprints a source by its declaration text, `env_file` and `mint_command`), a grant of a source's calls, a user's subscriptions and what their phone is told of, a user added or removed, a crew member's grants, a setting, a link renamed, a bead's originator, a timer removed. `ApproveAsk` approves in one write: it refuses anyone but the operator and every call from an agent's pane (`mayApprove`), writes the card again from the yard's records as they are now, refuses when the sentences or the fingerprints differ from the ones stored on the ask, runs the command through the store function the command itself calls, and records an answer holding the command and what it printed. It is served on the yard's socket and, to a device of the operator and nobody else, on the listener (`OperatorCalls` in internal/rpc/api.go, `operatorCall` in internal/rpc/user.go). No copy of a run ask crosses a link. Every ask write and every approval in production runs in the yard's server process: the command line connects over the yard's socket (`connect` in internal/cli/root.go, `Connect` in internal/server/server.go, which starts the server where none answers), the server owns the store (`store.Open` in internal/server/server.go is the one production owner), and the listener's approvals run on that same store — so a check the server registers on its store stands on every production path, from a terminal and from a device alike.

Whether a run ask may propose a command at all is the command's own check: `AskClass` in internal/store/users.go is `Alone` until a site marks it `Askable`, so nothing becomes proposable by omission. `yardr source add`, `yardr source key` and `yardr source rm` are refused as run asks in internal/store/runask_alone.go through `maySource` with the `Alone` mark, and `yardr pack apply` is refused there in words of its own: "applying a pack changes many things at once, from files of this machine: it is the operator's alone, typed in a terminal and never proposed as a run ask". Those two refusals are what this design moves, and only in the cases section 3 names.

### 2.2. Adding a source in a terminal

`yardr source add <file>` (internal/cli/sourcecmd.go) reads the file, parses it (`source.Parse` in internal/source/declaration.go: the source's name, its base address, the names of its credential's variables, and each call with its kind and its request's method and path), stores the whole text with `PutSource` in internal/store/sources.go under `maySource` with the `Alone` mark, and then copies each command file the declaration names beside the declaration into `<home>/sources/<name>/`, mode 0700 (`CopyCommandFiles` in internal/source/command.go). The copy reads every file first, then removes the destination and writes the files one by one (`writeCommandFiles`), so a stop inside it leaves anything from no files to all of them; a pack's apply stores the source first and copies after (`write` in internal/pack/apply.go), so a stop between them leaves the new text with the old files or none. A declaration's commands (`Declaration.Commands`) are the limits command, the thread commands, a hook's normalize command and the events commands; a relative program is a file the yard runs from that copy, and an absolute one is the operator's own and is not copied. A declaration is at most 256 KiB (`MaxDeclaration`). A source that is replaced keeps its `env_file`, `mint_command` and limits. Nothing is sent anywhere by adding a source: it has no credential until the operator sets `env_file` or gives a key through a secret ask, and no call is made until a grant.

### 2.3. Applying a pack

`yardr pack apply <pack>` (internal/cli/pack.go) is not a store function and not one write. The command reads the pack — a directory, a URL, a pack this yard imported before, read again from where the import recorded, or a name yardr embeds in the binary (`resolvePack`: a bare word is never tried as a directory, and an embedded pack is named "embedded in yardr <sha>", the build's version) — builds a plan (`pack.Build` in internal/pack/plan.go), answers what the plan asks through flags or in a terminal (which group of the yard takes one of the pack's, the agent and model of one it lacks, the members of a people group, and more), prints the plan, asks for confirmation, and applies it (`pack.Apply` in internal/pack/apply.go). Applying writes files under `<home>/packs/<pack>/` and `<home>/flows/`, makes many store calls in the plan's order, copies a declared source's command files, records the import (`RecordPack` in internal/store/packs.go, the event `pack_applied`), and folds a replaced source's old `-declared` links and records into it. There is no transaction across it: apply checks what it can before the first write, a write that fails stops it where it is, and because every object is matched by name, applying again finishes the import rather than repeating it.

A pack of kind `source` (internal/pack/pack.go: it carries sources alone, and is imported into the yard itself, into no depot) is the narrow case this bead is about. The packs yardr embeds of that kind are `linear`, `github`, `pushover` and `telegram`; of depot kinds, `starter`, `dir`, `contributors` and `design` (package packs; `template` is a directory to copy, and is not embedded). A kind-source pack's plan asks nothing: no group, crew member, flow or members, so no flag and no terminal answer shapes them. What holds a declaration's text is the pack as read, not the plan's summary of it: `pack.Pack.Declared` (internal/pack/pack.go) holds each declaration's file, its whole text and its parse; `pack.Plan.Declared` (`DeclaredPlan` in internal/pack/plan.go) holds only the source's name, file and base address, its calls as `name (kind)`, its command plans, its action, what it still needs and what a replacement would reach — no text, and no call's method, path, parameters or body. The plan's objects hold the text a second way, for applying: each source object (`SourceOp` in internal/pack/plan.go) carries the declaration text the plan was made from, so `pack.Apply` adds what was planned. The planner (`declared` in internal/pack/plan_sources.go) makes the summary from the parse: each call by name and kind alone, every command with its program and the sha256 of the pack's file (`sourceCommands`, `CommandPlan`), what a declaration the yard has under that name would change to (`declarationDiff`, which compares the base address, the credential, the check call, the idempotency header, the notify key and each call whole, and nothing else of the file), and what the yard must still be told (the file its credential is read from; for a source that can tell a user, which user names it). Of the four, `pushover` names no command; `linear`, `github` and `telegram` name command files the import copies and the yard runs. Applying any of them still grants nothing, makes no hook, and sets no `env_file`: after it, a secret ask gives the key and `yardr user set <user> notify=<source>` tells a user, each by its own road.

`yardr pack check <pack>` prints that plan and writes nothing. It is the nearest terminal showing to what a card must say, and it is not enough for one: read today, `yardr pack check pushover` prints one declared source, its one update call at `https://api.pushover.net/1` as `message (update)`, and what is still owed; `yardr pack check telegram` prints the same shape with four command lines, each with its file's full sha256. Neither prints a call's method or path, where the credential goes, what a call sends, or what the file's hook, hear, thread, link or identity keys do. A card made from that output would approve what nobody saw, so section 3.2 carries the declaration itself and the store writes the card from its own parse of it; `pack check` stays the desk showing, named in refusals.

A depot pack's plan is `Plan` in internal/pack/plan.go: its objects (`Object`: file, group, flow, pointer, route, crew, member, subscription, map or source, each with an action — create, change, unchanged, not_in_pack, dropped or takes — and, for a change, its diffs), its questions (`Questions`, with `Missing` for the ones no answer covers), what it would ask the operator beside answers (`OpenThreads`, `Calls` and `Expose`, each with its `Asks`), what forbids applying it (`Refused`), and the installed files it would overwrite though they were edited by hand (`EditedFiles`). A re-apply with no flags takes its shape from the standing record: the flow, the crew and group binds and the roles choice default to the last import's (`b.rec` in internal/pack/plan.go and plan_groups.go), as do the recorded answers to what it asked. `printPlan` in internal/cli/pack.go prints each object with its action and diffs, each unanswered question, and what an import would ask. Files install by temporary file and rename (`install` in internal/pack/apply.go), so one file is never read half written.

### 2.4. What was already decided about this

Design yardr-x3g8 built the run ask and left two things here. Its rule 3 for the list — every word of a command is a name the yard holds, a number or a flag; no path, no file's text — is what keeps `source add <file>` off the list, and its open question 7 proposed, as its option B, exactly a commands-free `source add` whose ask carries the declaration's text, as a bead (its Y5) to be built after a trial of the first rows. That trial has run: the list now holds thirteen rows, approvals come from a device of the operator, and docs/chat.md ("Questions for you") and docs/integrations.md ("A crew member may propose two of these commands") describe them. This design takes up Y5 and the pack question together, because a pack of kind source and a loose file are two roads to the same change — a declaration entering the store — and one card should serve both. It does not reopen yardr-x3g8's other answers: who may approve, from where, and that nothing approves over a link all stand.

## 3. The proposal

### 3.1. In one paragraph

Two commands join the run-ask list, and no other. `yardr pack apply <name>`, only for a pack yardr embeds and with no flag — of kind `source`, or of a depot kind where the plan asks nothing (3.7); and `yardr source add <file>`, only for a new source, its declaration alone or with the texts of the command files it names. Both are carried by the mechanism every row uses — the ask stores the command, the yard's sentences and fingerprints, and the operator's approval is `ApproveAsk` — with one addition the pack row and the loose row with commands force: an approval of either is recorded first and carried out straight after by the yard's server, because applying a pack writes files and makes many store calls and cannot be one write of the store, and neither can writing a loose file's command files. What the card shows is the declaration itself in the yard's words: for each source, its base address, the names of its credential's variables, every call with its kind, method and path, every command with its program and its file's sha256, and what the import changes beside the source and what it still leaves owed — and for a depot pack, the plan's objects, each with its action and what it changes (3.7). An approval is held to that showing: to the build the pack is embedded in, to the declaration texts and command files as they were carded, and to the yard's sources as they stood. A loose file's absolute programs, a pack that is not embedded, a depot pack's first install and any plan that asks, and every flag of `pack apply` stay the operator's to type in a terminal. mckean chose both widenings past the starting point — depot kinds where the plan asks nothing, and loose files that name commands — on 16 Oct (notes 6314–6319): his goal is an operator with no shell access keeping a running yard with working packs, approving each addition. The proposal follows his picks; section 5 records them.

### 3.2. The two rows

```text
$ yardr bead ask yardr-k3vd "Add the telegram source so I can tell you on your phone?" \
    --context "yardr has no source that tells a user outside the yard." \
    --run "pack apply telegram"
ask 2715 on yardr-k3vd for mckean: to approve, yardr pack apply telegram

$ yardr bead ask yardr-k3vd "Add the crm source?" \
    --context "Its declaration is crm.yaml beside this bead's worktree." \
    --run "source add crm.yaml"
ask 2716 on yardr-k3vd for mckean: to approve, yardr source add crm.yaml
```

The rows, beside the thirteen that stand:

| the command | what the ask carries beside `argv` | how the approval runs it |
|---|---|---|
| `pack apply <name>` | the pack's name and the server's build ("embedded in yardr <label>"), and for each source it declares the declaration's whole text with each command file's bytes and sha256 — and for a depot kind, the plan's objects (3.7) — read by the server from its own binary, never sent by the asker | recorded by `ApproveAsk`, carried out by the server (3.5) |
| `source add <file>` | the declaration's whole text with each command file's bytes, read from the files by the asker's command when the ask is written | commands-free in the approval's own write, through `PutSource`; naming commands recorded and carried out (3.5) |

One mechanism carries both, and it is the new thing in this design: **a run ask that adds a source carries the declaration it would add, as bytes on the ask.** Who reads those bytes differs by road. For the pack road it is the yard's server, from the binary it runs: the asker sends `pack apply <name>` as argv alone. The store cannot read the pack itself — an embedded pack is read through internal/pack and package packs, which the store may not call (internal/pack reads the store) — so the server registers a reading on its store when it takes it up (`serve` in internal/server/server.go, beside `SetYard` in internal/store/peersend.go, by which the server already tells its store what only the process knows): for the pack of a name, its kind (`KindSource` in internal/pack/pack.go, or another), each declared source's whole text (`Pack.Declared`), and each command file's program and the sha256 of the pack's own bytes for the relative programs the parse names, taken as `sourceCommands` takes it for a plan (internal/pack/plan_sources.go), with the server's own build label (`version.Describe`). The reading is `fs.Sub` over package packs and `pack.Load` (as `resolvePack` in internal/cli/pack.go reads an embedded pack), never a directory, a URL or an earlier import's record. For a pack of a depot kind the reading goes one step further and builds the plan, against the yard as the write holds it: `pack.Build` takes a narrow yard reader — the some twenty reads the planner makes (groups, crew, flows, routes, sources, hooks, settings and the rest), which `store.API` satisfies as today and which the store also implements over its write — so the plan is built inside the write that stores the ask, from the server's pack and the yard's records both. `askedRun`, in the write that stores the ask, calls it for the pack row and throws away whatever carried bytes the writer sent, as it throws away any `Does`, `Seen` or description the writer sent: there is no payload to forge, because no writer's payload is kept. It refuses the ask, storing nothing, when the reading has no embedded pack of the name, when no reading is registered — a store no server owns, which in production never happens, since every ask write runs in the server process (2.1), but which a test's direct store is — or, for a pack of a depot kind, when 3.7 refuses it. For the loose road the asker's own command reads: the file stands on the asker's machine under a path only the asker resolves, so `yardr bead ask` reads the one file the command names, resolved as `yardr source add` resolves it, and sends its text — and where the declaration names commands, each relative program's bytes as well, read from beside the file as `CopyCommandFiles` reads them. `AskRun` gains one field for the bytes of either road, a list of what each source's adding takes: the source's name, the declaration's whole text, and each command file's program with its bytes and sha256. The asker sends nothing else of a pack: no plan, and none of the yard's sentences.

For both roads the store parses every carried text itself (`source.Parse`, as `PutSource` does) and refuses the ask, storing nothing, when a text does not parse, when its name is not the name the field claims, when the command list names a program the parse does not (`Declaration.Commands`) or leaves one out, or — for a loose file — when a carried file's bytes are not what its sha256 claims, or a program is absolute. For the loose road those bytes are the writer's, and that is sound because the bytes are the whole of what is approved: the card renders them, the approval stores exactly the declaration, and the carrying out writes exactly the carried bytes as its command files (3.5). For the pack road they are the server's own, read inside the write that stores the ask, so the card is proven to describe the installed pack before it is stored: bytes no installed pack holds are never carded. The texts, the names and the hashes are kept on the ask, as `Does` and `Seen` are kept because every view renders an ask from its note alone. The file a loose `source add` names is named on the card for the record and read once, when the ask is written: what is approved is the text the ask holds, whatever the file holds by then. That is firmer than holding an approval to a hash of a file that is read again later, and it is yardr-x3g8 Y5's rule; the bead's starting point (2) is taken in this form.

Each row is refused, storing nothing, in these cases, in words that say which road remains:

- **`pack apply`**: the name is no pack yardr embeds (a directory, a URL, or a name an earlier import recorded from one of those — what a bare word resolves to is not what an approval may apply, so the row reads the embedded pack of that name or refuses); any flag is given (`--depot`, `--prune`, `--yes`, `--source-env`, `--notify`, `--calls` and the rest shape an import, and a card answers none of them); the plan the pack makes against this yard asks anything, is refused, or would overwrite a file a person edited by hand (`plan.EditedFiles`, which a terminal answers with `--yes` and a card cannot); for a pack of a depot kind, no single depot to re-apply to (3.7); or the card would be too long (3.3, 3.7). The refusal is the alone refusal of today with its reason changed for the cases that are now askable, not a new kind of refusal.
- **`source add`**: the file cannot be read or does not parse; a source of the declaration's name is in the yard already (a replacement keeps a credential's file and may widen a grant of `read` to calls the new file adds, and is a change to a standing source, not an adding: decided add-only, section 5); a command file cannot be read, or a program is absolute (the operator's own to have installed, checked in a terminal: only a relative program names bytes the ask can carry); or a text is too long for a card (3.3).

Who may write these asks, who they are put to, and who may approve are the list's, unchanged: a crew member or a user and not a bead's agent, to the operator alone, approved by the operator and never from an agent's pane and never over a link. `maySource` keeps its check and its words; the two sites that mark it for these rows — `PutSource`, and the pack row's own check — mark it `Askable` for exactly the cases above, and `Alone` for a replacement, an absolute program, and everything else `maySource` guards (`env_file`, `mint_command`, `source key`, `source rm`). Nothing becomes proposable by omission: a pack apply the row refuses falls to the alone list, whose pack entry stays for every other form of the command.

### 3.3. The card, and how long it may be

In `yardr chat`, `yardr prime --bead` and `yardr review`, and on a device in footplate, the card is the run-ask card of today with the source's showing under the yard's part. The showing is complete, and that word is held to a list: the yard's sentences render every part of the declaration that changes what the yard sends, runs, keeps or grants — every field of `source.Declaration` (internal/source/declaration.go, with its credential, its calls, and the notify, hear, limits, thread, link, identity, hook and events keys in internal/source/notify.go, hook.go, thread.go and limits.go) — so that approving without opening the text approves nothing the card has not named. A part that is not there is said once ("it names no command", "it can tell no user"), and no part waits behind the tap: the tap is for checking the yard's reading against the file, never the only place a behaviour stands. The telegram card, of the declaration in packs/telegram/telegram.yaml as the current binary embeds it, is:

```text
ask 2715 · open · to mckean · asked by yardmaster · 1m ago
  Add the telegram source so I can tell you on your phone?
  yardmaster says: yardr has no source that tells a user outside the yard.
  when you approve, the yard runs this as mckean, and nothing else:
      yardr pack apply telegram
  what the command does: Import a pack into the yard: set the yard to what the pack says
  the yard says: pack telegram (embedded in yardr fbf20cc4794f), of kind source, into the yard: it adds one source and copies 2 command files (4 commands), and changes nothing else. It grants no call, makes no hook, and sets no credential's file.
  the yard says: source telegram: its calls go to https://api.telegram.org. Its credential is the variable TELEGRAM_BOT_TOKEN (the name, never the value), sent in the request path (credential.in_path: true): a call's path holds it, so it stands in the logs of every server on the way. It has no second credential for updates, no mint, and no header of its own.
  the yard says: call message (update): POST /bot{credential}/sendMessage. It takes chat (string, required, pattern ^-?[0-9]+$), title (string, required, at most 250) and text (string, required, at most 3800), and sends no query.
  the yard says: call message sends the body {chat_id: "{chat}", text: "{title}\n{text}"}: the chat and the title and text, no credential but the one in the path. Its answer is returned as it comes. The source names no check call and no idempotency header.
  the yard says: it can tell a user: the call message, whose chat takes the person's address, read as TELEGRAM_CHAT_ID from the person's own env file; the title fills title and the text fills text, and it takes no link.
  the yard says: it hears deliveries: only one whose chat is the address of a user told through it, read as TELEGRAM_CHAT_ID, and only the operator's: another told user's chat, and a stranger's, is dropped.
  the yard says: what it sends in: deliveries are verified by the header X-Telegram-Bot-Api-Secret-Token holding the hook's secret itself (scheme secret); a delivery is named by update_id in its body; bodies are unique; the command [telegram/normalize] turns a verified body into the envelope, handed no credential; its events may carry the field chat.
  the yard says: command file telegram/thread: [telegram/thread reply] (thread.reply), [telegram/thread posted] (thread.posted) and [telegram/thread read] (thread.read), each handed the credential as every thread command is: sha256 70e39176f93f2756b16176ea3e46a26b9b523fd0d2febb03a82bcf1d721a457e
  the yard says: command file telegram/normalize: [telegram/normalize] (hook.normalize), handed no credential: sha256 dc249d6fcdbf396dc3237d7e922d1ef71a256a47549b3db670651dcf1957d70a
  the yard says: still owed after it: the credential, by a secret ask for telegram; and which user it tells, by yardr user set <user> notify=telegram.
  the operator can take it back: yardr source rm telegram
  approve with: yardr bead answer yardr-k3vd 2715 --approve
```

Two wordings in it are held to the road the command takes. "What the command does" is the command's help line as the card prints it for every row (`AskRun.Description`); `yardr pack apply`'s help (`internal/cli/pack.go`) says "import a pack into a depot", and a pack of kind source is imported into the yard (`checkDepot`, `inDepot`), so this row's card says the yard for one, as the pack line under it does — the row writes that line from the pack's kind, and a depot pack's card names the depot (3.7). And the call line shows the path as the file has it, `{credential}` and all: the earlier draft of this design showed `POST /messages.json` here, which is pushover's path, not telegram's, and hid that the token travels in the address. A card that hides where the credential goes approves the one thing this design exists to show.

For each source, the sentences say, in the declaration's own order, and a builder renders exactly these and no summary beside them:

- **The source and its credential.** Its name; its base address, or that it has none and calls nothing; and, where it names a credential, the variables it is read under — the credential's own, its updates' where that is another, and a mint's inputs, each by name and never a value, as a secret ask's line names them — where it goes (the header, as the file's `"Name: text {credential}"` with the mark shown; in the path, where `in_path` is set, with the warning the sample carries; or as a leaf of a call's body, named on that call), and that a mint runs only where the yard's own `mint_command` — which no row here sets — is the operator's already.
- **Every call**, one sentence-group to a call: its name and kind; its request's method and path whole (`Request.Line`), with `{credential}` standing where the file puts it; each parameter with its type, whether it is required or optional, and its pattern, its most, its values or that its value is kept in the record of each call (`log`), as the file bounds it; its query, each key with its value as the file has it, a `{name}` where a parameter stands; its body rendered whole as the JSON the yard would send — keys, literal values, and `{name}` and `{credential}` where they stand, on one line however the file breaks it; what of the answer is kept (`select`) and its most; and the source's check call and the header an update's key goes in (`idempotency`), where the file names them, or that it names neither.
- **What the source does beside calls**, one sentence to a key the file has: telling a user (`notify`: the call, the parameter and variable its address is read under, and which parameters the title, the text and the link fill, or that it takes no link); hearing (`hear`: the envelope field, the variable addresses are read under, and whose are kept — every told user's, or the operator's alone); the limits command (`limits`: its whole command and the harness kinds it answers for); speaking in threads (`thread`: each thing it does — reply, posted, read, open, opened, state — with its whole command, and what a place to open one is called, the words state takes, whether it takes labels, and which part of a person's identity an assignee is); its issues as a bead's link (`link`: the host, the expression that reads an issue, the one fixed form and the thread id as templates over its groups, how they fold, the pull-request shape beside it, and what a repository's path matches); how its identity keys fold (`identity`); what it sends in (`hook`: how a delivery is verified — the scheme, what is signed, the header and how the signature arrives, where the delivery is named and where its time arrives with its unit and window, or that it sends none — how far a body names a delivery (`bodies`), the normalize command whole, and the fields its events may carry); and what it sends of pull requests and CI (`events`: the envelope types that are runs and that tell a head, and the two read-back commands whole).
- **Every command**, grouped by the file the yard would run, as the sample groups them: the keys it serves, its whole command — program and arguments, since `[telegram/thread, reply]` and `[telegram/thread, read]` are one file asked to do two things — and its sha256 where the pack or the declaration brings the file, with the file's text behind the tap (a loose file's bytes are the ask's own; a pack's are the binary's, carried for checking) — or that the program is the operator's own where it is absolute, which a pack may name and a loose file may not. A command the yard runs is never named by its key alone.
- **The import around the sources.** What the command changes beside them (for a pack of kind source: the command files it copies and the record of the import, and nothing else, said so that a depot pack's flows, groups and roles are known by their absence — a depot pack's card is 3.7's); that it grants no call, makes no hook and sets no credential's file, where that is so; what it leaves owed, with the commands that are owed; and, where the yard has a source of the name, that it would replace it, what stands there now in the same rendering, and one line to a top-level key that differs, old against new — every key, not only the base, credential, check, idempotency, notify and calls that `declarationDiff` compares today — with who already gets a widened call through a standing grant of `read`, where the plan's `Reaches` says someone does.

The asker's question and context stand above, marked as the asker's, as on every run-ask card. A pack's setup notes are its author's words, unchecked, and are no part of the card: `yardr pack show <name>` prints them in a terminal, and the card's "still owed" lines are the yard's own. The declaration's own `about` is its author's too: the card does not carry it, since it changes nothing the yard does, and the text behind the tap holds it for whoever wants the author's words.

Two lengths are held, at asking, because a card that cannot be read whole on a phone approves nothing knowingly:

- **The yard's part is at most 40 lines**, counted as the sentences render: the pack line, one line to a source's credential, one to a capability key, one to a command file, and for each call its method-and-path line plus one line each for its parameters, its query and its body where the file has them. A pack or a file whose showing would run longer is refused as a run ask: "its card would run to <n> lines: a card is read whole, so this is the operator's to type in a terminal (`yardr pack check <name>` shows it there)". Counted so, telegram runs to ten yard lines and github — one call, its hook, its events, six thread commands in one file, its link and its folded identity — to twelve; the bound refuses a declaration with dozens of calls or commands, which is a file to read at a desk. The completeness above is what the bound buys: a shorter card is had by refusing more files, never by leaving a field off one that is shown.
- **A loose declaration's text is at most 8192 bytes.** The store already keeps the whole text of every declaration it holds, and the ask keeps it too; past that size the text is a document, not a card, and `source add` in a terminal is its road. A pack's declarations are not held to this bound one by one but to the line bound above, and to a second one: the ask holds their texts whole (an approval must add what was carded, not what a file holds by then), so a pack whose declarations together run past 256 KiB — `MaxDeclaration`, the most one declaration may be — is refused the same way.
- **Command and file texts behind the tap are bounded.** A loose command file's bytes are at most 8192, like the declaration, and the declaration with all its files at most 32 KiB; a pack's command files, and a depot pack's created and changed files (3.7), are at most 64 KiB together. Past that the files are read at a desk, in a terminal, and the ask is refused with it named.

Where a view cannot show the yard's part whole it shows nothing of the ask and says where it can be read, as today. The texts an ask holds are shown whole in a terminal (`yardr bead show` and the card's own command print them under the yard's sentences); on a phone the yard's sentences are the card, and the texts are one tap behind them in footplate's card, as a long plan is behind `pack check`. Approving without opening them approves the sentences, and that is sound only because the sentences are the whole rendering above: no sentence on the card is the asker's, and no behaviour is the tap's alone to tell.

What takes the change back is on the card, as on every row. For a source row it is `yardr source rm <name>`, which removes the source, its grants and the copies of its command files, and which is the operator's alone — so `BackBy` says "the operator", and the line is a command for a terminal, not a promise that nothing happened in between: a credential given and calls granted in between are theirs to take back too, by the rows that govern them. A depot pack's take-back is 3.7's.

### 3.4. What makes an approval stale

`ApproveAsk` writes the card again and compares, as it does for every row. For these rows the comparison is:

- **The build.** `Seen["pack telegram"]` holds "embedded in yardr <label>" with a sha256 over the pack's declaration texts and command files' sha256s as they were carded. `approveAsk` reads the pack again through the server's reading, in the same write that holds the yard's side, and refuses the approval, recording nothing, when the reading's build label or bytes are not the card's. A yardr build installed since the ask was written — the one event that changes an embedded pack, since its content shipped in the binary — makes the approval stale in the words of section 3.8 of yardr-x3g8: "ask 2715 was written from pack telegram as yardr <label> embeds it: this yard runs <label>, whose pack differs. Nothing ran. Decline it; it is asked again if it is still wanted." Where the label moved but the bytes are the same file for file, the words say that instead — the pack is unchanged, but the card named the build it was carded from — and still nothing runs. The same refusal covers a pack file changed in a checkout: there is none, since a directory pack is never on this row.
- **The yard's sources.** For each source the command would add or replace, `Seen["source <name>"]` is `sourceSeen` of the source as it stands, or its absence where the card said "would be added". A source added, replaced or removed under that name since, or its `env_file` or `mint_command` set since, makes the approval stale: the card described an adding (or a replacing of a named text), and the yard no longer holds what it described. For `source add` this is the whole check beside the ask's own text: the name was free when the card was written and must be free still — the carried bytes cannot drift, since they are on the ask. For a depot pack the yard's side is the whole plan rebuilt (3.7).
- **The sentences.** `Does` is compared whole, as for every row, so a change in what is owed — a credential's file set meanwhile, a user now told through the source — refuses the approval too, with what changed named. The yard does not judge which change matters.
- **At carrying out (pack row).** The server makes the plan again from the embedded pack before it writes anything, and holds it in two parts, because a first carrying out that stopped part way has already changed what a rebuilt plan says. The pack's side is held whole: the rebuilt plan's declared sources, their texts and each command file's sha256 — and for a depot pack its objects and files (3.7) — must be the ones `Seen["pack <name>"]` and the carried texts record, or nothing is applied and the approval is recorded as failed in the stale words (3.5) — the embedded pack cannot change under a running build, so this catches only a build installed between approval and carrying out. The yard's side is held a source at a time, never by the plan's actions or counts: for each source the pack declares, the source as the yard now holds it must be either the one the approval was held to (its `sourceSeen` as the card recorded it, absence included) or the pack's declaration text already stored, with its command files in whatever state the stop left — absent, the replaced one's, a subset of the pack's, or complete — or the carrying out is refused for that source in the stale words and applies nothing further. A depot pack holds its yard side an object at a time (3.7). A source of the second kind is not accepted as done: the carrying out writes it again, `PutSource` of the pack's text and the whole copy of its command files (which removes the copies and writes every file, so a partial copy is repaired, not resumed into), and then verifies it — the stored text parsed, each copied file's sha256 held to the carried one — before it counts the source finished. A rebuilt plan whose action for such a source — create, change or unchanged — and whose counts differ from the card's for that reason alone is progress to finish, not a difference to refuse. This second holding is needed because carrying out is not in the approval's write (3.5).

Nothing else makes a source approval stale: another source's declaration, a grant on a source the command does not name, a group's or crew member's definition. The command names sources and a pack, and it is held to those. For a depot pack the plan is the whole holding (3.7): anything that moves it stales the approval.

### 3.5. How the yard carries out an approval

A commands-free `source add` approval needs no new machinery: `PutSource` is one write of the store, the ask holds the text, and the row's `run` calls it in the approval's write with the operator as actor, as every row runs its command's own function. The answer records what `yardr source add` prints: "source crm saved: 3 calls under https://crm.example.com", with the changes of its calls where it replaced none (it never replaces).

A pack apply cannot run so, and neither can a loose add that names commands, and this design does not pretend they can: `pack.Apply` writes files, makes many store calls, and lives in internal/pack, which the store cannot call (internal/pack reads the store, so the store reading it back would be a circle) — and a loose file's command files are files too, which no store write writes. The approval of either therefore runs in two steps, both the yard's:

1. **The approval is recorded, as an approval.** `ApproveAsk` does what it does for every row — `mayApprove`, the stale comparison of 3.4, one write — and records the answer with `Ran` holding the command and the words "approved, to be carried out". For a loose add that names commands the same write stores the declaration, through `PutSource` as the operator; the files wait for the second step. The ask is answered from that moment: a second approval is refused, a pick and words are refused, and every view reads `approved, being carried out: ` with the command. Nothing of a pack is written in this step.
2. **The yard's server carries it out, once, as the operator.** The yard's server process (internal/server, which composes the store today and may compose internal/pack without a circle) gains a small watcher — one goroutine, so one carrying out at a time in a process — that takes each approved-and-not-carried-out pack ask and each loose ask that names commands, and finishes it. For a pack it makes the plan again from the pack yardr embeds (never from a directory, a URL or an earlier import's record: the embedded pack of the name, read from the binary the server runs — for a depot pack against the record's depot, 3.7), holds it as 3.4 says (3.7 for a depot pack), and applies it with the answers a card can give: no answers, no prune, no overwrite, and the operator's own grants filled as an import run by the operator fills them (`OpenThreads`, `Calls` and `Expose` empty, `SourceRefused` empty, `Actor` the operator). For a loose ask the declaration is already stored, so it holds the stored text to the approved one, writes the carried bytes under `<home>/sources/<name>/` — the destination removed first and every file written, as `writeCommandFiles` writes them — and verifies each file's sha256 against the carried one. It then records the carrying out on the bead with a store method of its own, which the server's call alone may make: the answer is completed with what the import printed (its counts, the sources it declared, what it left owed), or what `yardr source add` prints for a loose add, or, where the holding fails or the carrying out failed part way, with the failure in words. A completed ask reads `approved, ran: yardr pack apply telegram` with that output, as every approved row reads. The asker's inbox line says which of the two it was.

Taking an ask, finishing it and surviving a stop between them are one mechanism, and it is written here whole because "taken once" alone does not survive the stop it promises to. The store keeps, beside the ask, a carrying record the approval's write makes and only the server's methods move: approved and not yet taken, then **claimed**, with the claiming server's boot — a value the server mints at each start — and the time; then done, with the import's output, or failed, with its words. Three rules move it. **Claiming is one write**: a watcher claims an approved ask only where the record is untaken, or is claimed under another boot; the write is the store's, so two claims cannot both win, and a second watcher in the same process is kept out by the one goroutine before the store is asked. **A claim of this boot is never reclaimed while this boot runs**: a carrying out that runs long is still this server's, however long `pack.Apply` takes, and no timer frees it under its hands. **A claim of an earlier boot is dead with that boot**: the yard's socket is held by one server at a time, so a server that is starting knows every earlier boot has stopped, and at start — before it serves — it takes up each ask claimed under another boot and not done or failed, exactly as it takes up one approved and never claimed. A stop after the claim and before the first write, a stop during apply, a stop after apply before the record is completed, and a stop between a loose declaration's storing and its files' writing are therefore the same case at the next start: claimed, not finished, taken up again.

What the taken-up carrying out does is held by 3.4's per-source rule, which is what makes finishing safe where a whole-plan holding would refuse its own progress. It rebuilds the plan, holds the pack's side whole to the approval, and for each source goes on only where the yard holds what the approval was held to or the pack's text already stored; anywhere else — a source replaced by a third text while the server was down, a credential's file set on the half-added source — it records the ask failed in the stale words, applies nothing further, and leaves what stands for the operator, named in the failure. `PutSource` is one write of the store, so the stored text is the old one or the pack's, never a mix; the command files, written one by one after the destination is removed (`writeCommandFiles` in internal/source/command.go), may stand in any state from absent to complete, which is why the rule accepts the pack's text with files in any state and always writes the source again and verifies it (3.4) rather than trusting what stands. A taken-up loose ask is finished the same way: the stored text held to the approved one — anything else fails the ask with what stands named — and the carried bytes written whole and verified, whatever the files' state. A taken-up depot ask follows 3.7's per-object rule instead. Where it goes on, `pack.Apply` is the terminal apply's own road: it checks the pack's files are still the planned ones before it writes (`check` in internal/pack/apply.go), matches every object by name so what stands is left or finished rather than repeated, and only then records the import and folds a replaced source's `-declared` records in — a stop before the record leaves no record, and the taken-up apply writes it (`RecordPack` in internal/store/packs.go writes where no record stands, even when nothing further changed); a stop after it finds the import recorded and finishes the fold, and a fold run twice moves nothing the second time, since the `-declared` name stands empty after the first. Completing the record is itself held to the claim: the write that marks done or failed names the boot that claimed the ask, and is refused under another, so a server that lost its claim — which, by the rules above, means it stopped — cannot complete an ask its successor has taken. Done and failed are ends: neither is taken up again, and a failed ask is asked again if it is still wanted, as a stale approval is.

What this costs, said plainly: between approval and carrying out the yard may stop, and an ask can stand at "being carried out" while the server is down; it is taken up at the next start, and "being carried out" on a card therefore means claimed or waiting, never lost. A failure part way (a file that cannot be copied, a store call refused) leaves what a failed terminal apply leaves — the objects written so far, no import record — and the recorded failure names it and names the terminal command that finishes or undoes it; the ask is answered as failed and is never carried out twice, since a claim is one write, a running boot never yields its own, and a dead boot's claim is finished by one successor at a time under the holding of 3.4 (3.7 for a depot pack). Approving from a device works as for every row: the approval travels as `ApproveAsk` over the listener to the operator's yard, and the carrying out is that yard's server's, on that yard's machine — the phone approves, and nothing runs on the phone.

### 3.6. A declaration that names commands, and one that does not

They are treated differently, and the difference is where the command's file comes from — mckean decided it (note 6316; section 5):

- **A commands-free declaration** (no limits, thread, hook or events command: `Declaration.Commands` is empty) adds one record to the store and copies nothing. Its whole effect is in the text the ask holds, so a loose file of that kind is askable (3.2), and so is a pack whose sources are all of that kind (`pushover` today).
- **A declaration that names commands from an embedded pack** asks the yard to run programs that shipped in the binary the operator installed: their files' sha256s are on the card, and the applied copies are the binary's own — the trust is the trust in the yardr build, which the operator already runs. Such a pack is askable on the same row.
- **A declaration that names commands from a loose file** is askable with the files' texts carried: the ask holds each relative program's bytes, the card shows each file's sha256 whole with the text behind one tap (whole in a terminal), and the carrying out writes exactly those bytes. mckean's words: "basically the operator still needs to approve" — the approval is of bytes shown, hash on the card and text a tap away, and what is installed is those bytes and no others. An absolute program is refused: it names no bytes the ask could carry, only the operator's own machine, and its being there is checked in a terminal.

`mint_command` and `env_file` are untouched by both rows: no ask carries a path or a program for the yard to run for a credential, `source key` stays a secret ask, and `source rm` stays the operator's, named on the card only as what takes the change back.

### 3.7. A depot pack on the same row

The row takes an embedded pack of a depot kind — `starter`, `dir`, `contributors` or `design` — when the yard holds exactly one standing import of it and the plan built from the embedded pack against that depot asks nothing. The depot is the record's; the content is the embedded pack's, which an upgrade may have moved past the record's source — the card shows the diff, and the record afterwards names the embedded build. No standing record is a first install, which asks, and stays in a terminal; several depots holding the pack need one named, in a terminal too. Either refusal names `yardr pack check <name> --depot <depot>` as where the plan is read.

"Asks nothing", whole: no missing answers (`Missing` over empty answers is empty), nothing left to ask beside answers (every `OpenThreads`, `Calls` and `Expose` has no `Asks`), nothing forbidding it (`Refused` is empty), and no installed file edited by hand in its way (`EditedFiles` is empty). Objects the pack dropped are carded as left where they stand — there is no prune on a card — and are never refused for.

What the ask holds is the plan the reading built inside the write (3.2): every object (kind, name, action, and for a create or change its changes and, for a file, the sha256s old and new), the governs that change, the counts, the texts of created and changed files for the tap, the declared sources' texts, and the build label. Writer-sent plan data is thrown away like everything else the writer sends.

The card is the run-ask card with the plan's objects under the yard's part: the pack line (pack, embedded label, kind, depot, the counts to create, to change, unchanged, and dropped-but-left); one line to a created or changed object (`<kind> <name>: <action>`, a file with its sha256 old to new whole, a record with each change as `field: old -> new`, as `printPlan` prints them); one line to a dropped object (left alone) and to a keep or shadow where the plan has one; the governs where the flow changes; each declared source in the 3.3 rendering; and what the plan still needs, with the commands. Unchanged objects are counted, never listed. Past 40 yard lines, counted as the sentences render, the ask is refused for a terminal, as a source card is. The pack's setup notes are no part of it, as in 3.3.

An approval is held to the whole plan rebuilt in the approval's write: objects, changes, hashes, governs and label must equal the stored ones, or the approval is refused stale with what differs named. The one comparison covers a build installed since and a yard moved since, since either moves the plan.

The carrying out holds the pack's side whole (the label, the file hashes, the object identities) and the yard's side an object at a time: each carded create or change must rebuild identical or `unchanged` — the planner reading `unchanged` is what "already as the pack says" means, so no new fingerprint per kind is needed — each carded `unchanged` must rebuild `unchanged`, and each dropped must still read dropped, or the carrying out fails in the stale words and applies nothing further. Then it applies (no answers, no prune, no overwrite, as the operator), and verifies: the plan made once more must read every carded object `unchanged`, and every written file must hash to the planned one. The pack's declared sources go through the per-source write and verify of 3.4 — they are kind-source objects of the same apply.

What takes a depot import back is no one command: `Back` says so and names `yardr pack check <name> --depot <depot>` in a terminal as where the standing state is read, and `BackBy` says "the operator".

## 4. Left out

- **A pack that is not embedded.** A directory or URL pack is files of this machine that an agent may have written, and its content can change between the asking and the approval with nothing but a file's mtime to say so. It stays in a terminal.
- **A first install of a depot pack.** It asks for binds, members, an agent and a model, and a card answers none of them; closing that gap, by defaults or a question per plan question, is its own design. What this design answers is mckean's goal the other way round: a yard whose packs were installed at a desk stays running and working with no shell, re-applying on a card after each upgrade; a yard never set up still needs one setup.
- **`--prune`, and every other flag of `pack apply`, on a card.** A prune removes what an earlier import brought; the flags name files (`--source-env`, `--notify`), people and grants. Each is its own command or its own row, proposed apart where the list holds it (a grant of the pack's source's calls is the grant row, once the source stands).
- **Replacing a source by `source add`, and replacing one by approving a pack whose source's credential a standing grant already reaches.** The pack row cards a replacement with its diffs, since a yardr upgrade changing an embedded pack is the ordinary way these packs change; a loose replacement stays in a terminal (section 5). Where a replacement would widen a standing grant of `read` to a call the new file adds, the plan already names who gets it (`DeclaredPlan.Reaches`), the card carries that line, and it is part of what is approved — said here because nobody is asked twice.
- **Secrets, hooks, and telling a user.** The import sets none of them; a secret ask, `yardr hook add` and `yardr user set notify=` keep their own roads and their own checks.
- **An atomic copy of a source's command files** (to a temporary directory, renamed into place, as `install` in internal/pack/apply.go writes one file). It narrows the window in which a stop leaves a partial copy but does not close it — removing the destination and renaming still has a stop between them that leaves the files absent — and the resume rule of 3.4 already finishes every state of that window, absent included. It would also change the terminal apply of every pack for the sake of one row, so the row finishes forward instead.
- **Absolute programs in a loose declaration.** They name no bytes the ask could carry, only the operator's own machine; a file worth running from an absolute path is installed at a desk, in a terminal.
- **A second step at approval for a pack that names commands** (typing the source's name, a passphrase). Decided against (section 5: a device approves).
- **Approving in the web view, and a copy of either ask over a link**, as for every run ask.

## 5. Open questions

mckean answered all four during the draft (notes 6314–6319); each keeps its options, costs and recommendation below, with his pick recorded. The proposal follows his picks.

**1. Should an embedded pack of a depot kind ever be askable, when its plan asks nothing?** Option A, no: the row is for adding a source, and a depot pack changes flows, groups, roles and scripts — a change of who works and how, which is a design of its own. Option B, yes, where a re-apply against a depot whose import already stands asks nothing and changes little: the card would show the plan's objects, and the carrying out is the one this design builds. It costs a card of objects a phone reader must judge (roles and stage files by name, scripts by sha256) and widens what a stolen device of the operator can have carried out from a source to a depot's whole line. I would take A: the question that was asked was about adding a source, and a depot pack that needs applying again after an upgrade is run once, at a desk, by the person who upgraded. Decided 16 Oct 2026: option B — mckean (note 6314): "the goal is that the operater can have a running yard with working packs even if they do not have shell access." The proposal follows it (3.7).

**2. Should a loose declaration that names commands ever be askable, with the command files' texts carried on the ask as the declaration's is?** Option A, no, as proposed: the operator types `yardr source add <file>` in a terminal, where the files stand beside it and can be opened. Option B, yes: the ask holds each command file's text with its sha256 on the card, the approval writes exactly those bytes under `<home>/sources/<name>/`, and the bound of 3.3 grows to cover them. It costs an approval installing a program an agent wrote, approved from a card that shows its hash and, behind a tap, its text — which no reader judges as code on a phone — and it is the one case where what runs was not shipped by anyone the operator chose. I would take A. A service worth a command file is worth a pack, and a pack of kind source in the binary, or in a directory the operator applies once, is its road in. Decided 16 Oct 2026: option B — mckean (note 6316): "basically the operator still needs to approve." The proposal follows it (3.2–3.6).

**3. May a pack whose sources name commands be approved from a device of the operator, or only on the yard's socket?** Option A, from a device too, as proposed: the commands are the installed build's own files, and approving its own pack adds no program the operator has not already been running since they installed that build. Option B, socket only for a pack that names a command, a device for a commands-free one: it splits question 3 of yardr-x3g8 by row, and costs a second rule on the card ("approve this one at the yard's terminal"). It holds against a stolen device having new command files installed and run, though the same device can already approve a grant of those commands' source's calls once the source stands. I would take A, and B if the row in the stolen-device table of docs/users.md reads as too much when it is written. Decided 16 Oct 2026: option A, as proposed — mckean (note 6317, no words).

**4. Should the first step replace a source, or only add one?** Option A, as proposed: the pack row cards a replacement with its diffs (a yardr upgrade is the ordinary change to an embedded pack, and refusing it would leave the row answering only the first install), and the loose row adds only, a replacement staying in a terminal where its widened grants can be read. Option B, both rows add only at first: a replacement of either kind is the operator's until the rows have been used, which costs the operator typing `yardr pack apply linear` after every upgrade that changes its declaration or a command file — the case that recurs — for a first step that approves only what was not there. I would take A: the card shows the diff and the changed files' sha256s, and `Seen` holds the approval to the text it replaces. Decided 16 Oct 2026: option A, as proposed — mckean (note 6319, no words).

In the order they would land. Each yardr bead passes `sh .yardr/test` and updates the pages named. No bead's own tests start an agent: they use a store in a temporary home, and a test that needs a pane gives the call a caller with `WithCaller`, as the run-ask tests do.

**B1. A run ask that adds a source: `source add` with the declaration on the ask.** Goal: section 3.2's second row and 3.3's card for it — a commands-free add run in the approval's write, an add that names commands recorded for B3's file step.
