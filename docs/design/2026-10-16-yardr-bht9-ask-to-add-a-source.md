# Adding a source by a run ask, approved on a card that shows what would be added

Design yardr-bht9, proposed 2026-10-16. A proposal as it was decided on, not a description of what the code does today; the decision is on the bead.

A yard is one installation of yardr: its store, its crew and its depots. A source is a service outside the yard, declared by one file; a pack is a way of working as one directory, and a pack of kind `source` declares a source yardr has no Go for. An ask is one question as data on a bead; a run ask (`yardr bead ask --run "<command>"`, design yardr-x3g8) proposes one yardr command of a fixed list, and the operator's approval (`ApproveAsk` in internal/store/runask.go) has the yard run exactly that command, as the operator, in the write that records the approval. The operator is the person who runs the yard. In this document **the card** is what a run ask shows the person asked, **a loose file** is a declaration file that stands on the yard's machine and is in no pack, and **carrying out** is the step after an approval that this design adds for the one row whose change is not one write of the store.

## 1. The question

mckean, 16 Oct 2026 (mails 41030-41051): "can you not apply the yardr pack?", and "we need find an elegant way to do this, via ask?" Today `yardr pack apply <pack>` adds the pack's sources only when the operator types it, because adding a source is operator-alone and never a run ask (yardr-fz1j), and for a good reason: a source decides where a credential of the yard is sent, and its file may name commands the yard runs. The card of a run ask shows the command, not the file, so approving `yardr source add <file>` from a phone would approve a file nobody saw. The yardmaster offered (mails 40087, 41046) to make it askable when the card shows the whole declaration. So: may a crew member propose adding a source as a run ask, what does the card show so that the approval is of what would actually be added, what makes that approval stale, and how does the yard run what was approved?

## 2. What exists today

### 2.1. Run asks, and the shape every row has

A run ask stores one command in the yard's own form (`AskRun` in internal/store/runask.go: `Argv`, the yard's sentences in `Does`, the command that takes the change back in `Back`, and `Seen`, a fingerprint of each thing the command names). The list (`runList`, and `runask_list.go` and `runask_more.go` beside it) holds commands that are each one function and one write of the store: a link's mail limit and kinds, a source's calls an hour (`sourceSeen` fingerprints a source by its declaration text, `env_file` and `mint_command`), a grant of a source's calls, a user's subscriptions and what their phone is told of, a user added or removed, a crew member's grants, a setting, a link renamed, a bead's originator, a timer removed. `ApproveAsk` approves in one write: it refuses anyone but the operator and every call from an agent's pane (`mayApprove`), writes the card again from the yard's records as they are now, refuses when the sentences or the fingerprints differ from the ones stored on the ask, runs the command through the store function the command itself calls, and records an answer holding the command and what it printed. It is served on the yard's socket and, to a device of the operator and nobody else, on the listener (`OperatorCalls` in internal/rpc/api.go, `operatorCall` in internal/rpc/user.go). No copy of a run ask crosses a link.

Whether a run ask may propose a command at all is the command's own check: `AskClass` in internal/store/users.go is `Alone` until a site marks it `Askable`, so nothing becomes proposable by omission. `yardr source add`, `yardr source key` and `yardr source rm` are refused as run asks in internal/store/runask_alone.go through `maySource` with the `Alone` mark, and `yardr pack apply` is refused there in words of its own: "applying a pack changes many things at once, from files of this machine: it is the operator's alone, typed in a terminal and never proposed as a run ask". Those two refusals are what this design moves, and only in the cases section 3 names.

### 2.2. Adding a source in a terminal

`yardr source add <file>` (internal/cli/sourcecmd.go) reads the file, parses it (`source.Parse` in internal/source/declaration.go: the source's name, its base address, the names of its credential's variables, and each call with its kind and its request's method and path), stores the whole text with `PutSource` in internal/store/sources.go under `maySource` with the `Alone` mark, and then copies each command file the declaration names beside the declaration into `<home>/sources/<name>/`, mode 0700 (`CopyCommandFiles` in internal/source/command.go). A declaration's commands (`Declaration.Commands`) are the limits command, the thread commands, a hook's normalize command and the events commands; a relative program is a file the yard runs from that copy, and an absolute one is the operator's own and is not copied. A declaration is at most 256 KiB (`MaxDeclaration`). A source that is replaced keeps its `env_file`, `mint_command` and limits. Nothing is sent anywhere by adding a source: it has no credential until the operator sets `env_file` or gives a key through a secret ask, and no call is made until a grant.

### 2.3. Applying a pack

`yardr pack apply <pack>` (internal/cli/pack.go) is not a store function and not one write. The command reads the pack — a directory, a URL, a pack this yard imported before, read again from where the import recorded, or a name yardr embeds in the binary (`resolvePack`: a bare word is never tried as a directory, and an embedded pack is named "embedded in yardr <sha>", the build's version) — builds a plan (`pack.Build` in internal/pack/plan.go), answers what the plan asks through flags or in a terminal (which group of the yard takes one of the pack's, the agent and model of one it lacks, the members of a people group, and more), prints the plan, asks for confirmation, and applies it (`pack.Apply` in internal/pack/apply.go). Applying writes files under `<home>/packs/<pack>/` and `<home>/flows/`, makes many store calls in the plan's order, copies a declared source's command files, records the import (`RecordPack` in internal/store/packs.go, the event `pack_applied`), and folds a replaced source's old `-declared` links and records into it. There is no transaction across it: apply checks what it can before the first write, a write that fails stops it where it is, and because every object is matched by name, applying again finishes the import rather than repeating it.

A pack of kind `source` (internal/pack/pack.go: it carries sources alone, and is imported into the yard itself, into no depot) is the narrow case this bead is about. The packs yardr embeds of that kind are `linear`, `github`, `pushover` and `telegram` (package packs; `template` is a directory to copy, and is not embedded). Their plans ask nothing: no group, crew member, flow or members, so no flag and no terminal answer shapes them. The plan for a declared source (`declared` in internal/pack/plan_sources.go) names the source, where its calls go, each call by name and kind, every command with its program and the sha256 of the pack's file (`sourceCommands`, `CommandPlan`), what a declaration the yard has under that name would change to, and what the yard must still be told (the file its credential is read from; for a source that can tell a user, which user names it). Of the four, `pushover` names no command; `linear`, `github` and `telegram` name command files the import copies and the yard runs. Applying any of them still grants nothing, makes no hook, and sets no `env_file`: after it, a secret ask gives the key and `yardr user set <user> notify=<source>` tells a user, each by its own road.

`yardr pack check <pack>` prints that plan and writes nothing, which is why the bead calls the plan what the card shows. Read today, `yardr pack check pushover` prints one declared source, its one update call at `https://api.pushover.net/1`, and what is still owed; `yardr pack check telegram` prints the same shape with four command lines, each with its file's full sha256.

### 2.4. What was already decided about this

Design yardr-x3g8 built the run ask and left two things here. Its rule 3 for the list — every word of a command is a name the yard holds, a number or a flag; no path, no file's text — is what keeps `source add <file>` off the list, and its open question 7 proposed, as its option B, exactly a commands-free `source add` whose ask carries the declaration's text, as a bead (its Y5) to be built after a trial of the first rows. That trial has run: the list now holds thirteen rows, approvals come from a device of the operator, and docs/chat.md ("Questions for you") and docs/integrations.md ("A crew member may propose two of these commands") describe them. This design takes up Y5 and the pack question together, because a pack of kind source and a loose file are two roads to the same change — a declaration entering the store — and one card should serve both. It does not reopen yardr-x3g8's other answers: who may approve, from where, and that nothing approves over a link all stand.

## 3. The proposal

### 3.1. In one paragraph

Two commands join the run-ask list, and no other. `yardr pack apply <name>`, only for a pack yardr embeds, only of kind `source`, and with no flag; and `yardr source add <file>`, only for a new source whose declaration names no command. Both are carried by the mechanism every row uses — the ask stores the command, the yard's sentences and fingerprints, and the operator's approval is `ApproveAsk` — with one addition the pack row forces: an approval of a pack apply is recorded first and carried out straight after by the yard's server, because applying a pack writes files and makes many store calls and cannot be one write of the store. What the card shows is the declaration itself in the yard's words: for each source, its base address, the names of its credential's variables, every call with its kind, method and path, every command with its program and its file's sha256, and what the import changes beside the source and what it still leaves owed. An approval is held to that showing: to the build the pack is embedded in, to the declaration texts and command files as they were carded, and to the yard's sources as they stood. A loose file that names a command, a pack that is not embedded, a pack of any other kind, and every flag of `pack apply` stay the operator's to type in a terminal.

### 3.2. The two rows

```text
$ yardr bead ask yardr-k3vd "Add the telegram source so I can tell you on your phone?" \
    --context "yardr has no source that tells a user outside the yard." \
    --run "pack apply telegram"
ask 2715 on yardr-k3vd for mckean: to approve, yardr pack apply telegram

$ yardr bead ask yardr-k3vd "Add the crm source?" \
    --context "Its declaration is crm.yaml beside this bead's worktree." \
    --run "source add crm.yaml"
ask 2716 on yardr-k3vd for mckean: to approve, yardr source add crm.yaml
```

The rows, beside the thirteen that stand:

| the command | what the ask carries beside `argv` | how the approval runs it |
|---|---|---|
| `pack apply <name>` | the pack's name and build ("embedded in yardr <sha>"), and for each source it declares: the declaration's whole text, and each command file's sha256 | recorded by `ApproveAsk`, carried out by the server (3.5) |
| `source add <file>` | the declaration's whole text, read from the file when the ask is written | in the approval's own write, through `PutSource` |

One mechanism carries both, and it is the new thing in this design: **a run ask that adds a source carries the declaration it would add.** For a loose file the asker's command reads the file; for an embedded pack the asker's command reads the pack yardr embeds (`resolvePack` already reads it from the binary, and the plan's `Declared` part already holds each declaration's text). Either way the store parses every text itself (`source.Parse`, as `PutSource` does) and writes the card's sentences from the parse, never from the asker's words; the texts are kept on the ask, as `Does` and `Seen` are kept because every view renders an ask from its note alone. The file a loose `source add` names is named on the card for the record and read once, when the ask is written: what is approved is the text the ask holds, whatever the file holds by then. That is firmer than holding an approval to a hash of a file that is read again later, and it is yardr-x3g8 Y5's rule; the bead's starting point (2) is taken in this form.

Each row is refused, storing nothing, in these cases, in words that say which road remains:

- **`pack apply`**: the name is no pack yardr embeds (a directory, a URL, or a name an earlier import recorded from one of those — what a bare word resolves to is not what an approval may apply, so the row reads the embedded pack of that name or refuses); the pack is not of kind `source` (open question 1); any flag is given (`--depot`, `--prune`, `--yes`, `--source-env`, `--notify`, `--calls` and the rest shape an import, and a card answers none of them); the plan the pack makes against this yard asks anything, is refused, or would overwrite a file a person edited by hand (`plan.EditedFiles`, which a terminal answers with `--yes` and a card cannot); or the card would be too long (3.3). The refusal is the alone refusal of today with its reason changed for the cases that are now askable, not a new kind of refusal.
- **`source add`**: the file cannot be read or does not parse; a source of the declaration's name is in the yard already (a replacement keeps a credential's file and may widen a grant of `read` to calls the new file adds, and is a change to a standing source, not an adding: open question 4); the declaration names any command (`Declaration.Commands` is not empty: 3.6); or the text is too long for a card (3.3).

Who may write these asks, who they are put to, and who may approve are the list's, unchanged: a crew member or a user and not a bead's agent, to the operator alone, approved by the operator and never from an agent's pane and never over a link. `maySource` keeps its check and its words; the two sites that mark it for these rows — `PutSource`, and the pack row's own check — mark it `Askable` for exactly the cases above, and `Alone` for a replacement, a command the declaration names, and everything else `maySource` guards (`env_file`, `mint_command`, `source key`, `source rm`). Nothing becomes proposable by omission: a pack apply the row refuses falls to the alone list, whose pack entry stays for every other form of the command.

### 3.3. The card, and how long it may be

In `yardr chat`, `yardr prime --bead` and `yardr review`, and on a device in footplate, the card is the run-ask card of today with the source's showing under the yard's part:

```text
ask 2715 · open · to mckean · asked by yardmaster · 1m ago
  Add the telegram source so I can tell you on your phone?
  yardmaster says: yardr has no source that tells a user outside the yard.
  when you approve, the yard runs this as mckean, and nothing else:
      yardr pack apply telegram
  what the command does: Import a pack into a depot: set the yard to what the pack says
  the yard says: pack telegram (embedded in yardr 5e252f2c…), of kind source, into the yard: it adds one source and copies 2 command files, and changes nothing else. It grants no call, makes no hook, and sets no credential's file.
  the yard says: source telegram: its calls go to https://api.telegram.org, with the credential TELEGRAM_BOT_TOKEN (the name, never the value): message (update, POST /messages.json). It can tell a user: their address is read from TELEGRAM_CHAT_ID.
  the yard says: command file telegram/thread (thread.reply, thread.posted, thread.read): sha256 70e39176f93f2756b16176ea3e46a26b9b523fd0d2febb03a82bcf1d721a457e
  the yard says: command file telegram/normalize (hook.normalize): sha256 dc249d6fcdbf396dc3237d7e922d1ef71a256a47549b3db670651dcf1957d70a
  the yard says: still owed after it: the credential, by a secret ask for telegram; and which user it tells, by yardr user set <user> notify=telegram.
  the operator can take it back: yardr source rm telegram
  approve with: yardr bead answer yardr-k3vd 2715 --approve
```

The yard's sentences are made from the parse and the plan, and they say, for each source: its name; its base address, or that it has none and calls nothing; the names of its credential's variables (the credential's, its updates' where that is another, and a mint's inputs by name), never a value, as a secret ask's line names them; every call with its name, its kind, and its request's method and path (`Request.Line`), since a call's name alone says nothing of what it does; what the source can do beside calls that the file says (tell a user, hear deliveries, say a harness kind's limits), each in one clause; every command file, grouped by the file the yard would run, with the keys it serves, its program and arguments, and its sha256 where the pack or the declaration brings the file, or that the program is the operator's own where it is absolute; what the import changes beside the sources (for a pack of kind source: the command files it copies and the record of the import, and nothing else, said so that a depot pack's flows, groups and roles are known by their absence); what it leaves owed, with the commands that are owed; and, where the yard has a source of the name, what stands there now and what would change, as the plan's diffs say it. The asker's question and context stand above, marked as the asker's, as on every run-ask card. A pack's setup notes are its author's words, unchecked, and are no part of the card: `yardr pack show <name>` prints them in a terminal, and the card's "still owed" lines are the yard's own.

Two lengths are held, at asking, because a card that cannot be read whole on a phone approves nothing knowingly:

- **The yard's part is at most 40 lines** (the sentences above, one call or one command file to a line). A pack or a file whose showing would run longer is refused as a run ask: "its card would run to <n> lines: a card is read whole, so this is the operator's to type in a terminal (`yardr pack check <name>` shows it there)". The four embedded source packs run to between four and sixteen lines; the bound refuses a declaration with dozens of calls or commands, which is a file to read at a desk.
- **A loose declaration's text is at most 8192 bytes.** The store already keeps the whole text of every declaration it holds, and the ask keeps it too; past that size the text is a document, not a card, and `source add` in a terminal is its road. A pack's declarations are not held to this bound one by one but to the line bound above, and to a second one: the ask holds their texts whole (an approval must add what was carded, not what a file holds by then), so a pack whose declarations together run past 256 KiB — `MaxDeclaration`, the most one declaration may be — is refused the same way.

Where a view cannot show the yard's part whole it shows nothing of the ask and says where it can be read, as today. The declaration text a `source add` ask holds is shown whole in a terminal (`yardr bead show` and the card's own command print it under the yard's sentences); on a phone the yard's sentences are the card, and the text is one tap behind them in footplate's card, as a long plan is behind `pack check` — what is behind the tap is the text as data, and approving without opening it approves the sentences, which name every call and command in it. Open question 4 in yardr-x3g8's sense does not arise here: no sentence is the asker's.

What takes the change back is on the card, as on every row: `yardr source rm <name>`, which removes the source, its grants and the copies of its command files, and which is the operator's alone — so `BackBy` says "the operator", and the line is a command for a terminal, not a promise that nothing happened in between: a credential given and calls granted in between are theirs to take back too, by the rows that govern them.

### 3.4. What makes an approval stale

`ApproveAsk` writes the card again and compares, as it does for every row. For these rows the comparison is:

- **The build.** `Seen["pack telegram"]` holds "embedded in yardr <sha>" with a sha256 over the pack's declaration texts and command files' sha256s as they were carded. A yardr build installed since the ask was written — which is the one event that changes an embedded pack, since its content shipped in the binary — makes the approval stale in the words of section 3.8 of yardr-x3g8: "ask 2715 was written from pack telegram as yardr <sha> embeds it: this yard runs <sha>, whose pack differs. Nothing ran. Decline it; it is asked again if it is still wanted." The same refusal covers a pack file changed in a checkout: there is none, since a directory pack is never on this row.
- **The yard's sources.** For each source the command would add or replace, `Seen["source <name>"]` is `sourceSeen` of the source as it stands, or its absence where the card said "would be added". A source added, replaced or removed under that name since, or its `env_file` or `mint_command` set since, makes the approval stale: the card described an adding (or a replacing of a named text), and the yard no longer holds what it described. For `source add` this is the whole check beside the ask's own text: the name was free when the card was written and must be free still.
- **The sentences.** `Does` is compared whole, as for every row, so a change in what is owed — a credential's file set meanwhile, a user now told through the source — refuses the approval too, with what changed named. The yard does not judge which change matters.
- **At carrying out (pack row).** The server makes the plan again from the embedded pack before it writes anything, and holds it to a sha256 over the plan's declared sources, their texts, their command files and its counts, kept in `Seen`. A plan that differs is not applied; the approval is recorded as failed in the stale words (3.5). This second holding is needed because carrying out is not in the approval's write (3.5), and it is cheap: the embedded pack cannot change under a running build, so what it catches is the yard's sources changing in the moments between.

Nothing else makes these approvals stale: another source's declaration, a grant on a source the command does not name, a group's or crew member's definition. The command names sources and a pack, and it is held to those.

### 3.5. How the yard runs an approved pack apply

A `source add` approval needs no new machinery: `PutSource` is one write of the store, the ask holds the text, and the row's `run` calls it in the approval's write with the operator as actor, as every row runs its command's own function. The answer records what `yardr source add` prints: "source crm saved: 3 calls under https://crm.example.com", with the changes of its calls where it replaced none (it never replaces).

A pack apply cannot run so, and this design does not pretend it can: `pack.Apply` writes files, makes many store calls, and lives in internal/pack, which the store cannot call (internal/pack reads the store, so the store reading it back would be a circle). The approval therefore runs in two steps, both the yard's:

1. **The approval is recorded, as an approval.** `ApproveAsk` does what it does for every row — `mayApprove`, the stale comparison of 3.4, one write — and records the answer with `Ran` holding the command and the words "approved, to be carried out". The ask is answered from that moment: a second approval is refused, a pick and words are refused, and every view reads `approved, being carried out: yardr pack apply telegram`. Nothing of the pack is written in this step.
2. **The yard's server carries it out, once, as the operator.** The yard's server process (internal/server, which composes the store today and may compose internal/pack without a circle) gains a small watcher takes each approved-and-not-carried-out pack ask, makes the plan again from the pack yardr embeds (never from a directory, a URL or an earlier import's record: the embedded pack of the name, read from the binary the server runs), holds it to `Seen` (3.4), and applies it with the answers a card can give: no answers, no prune, no overwrite, and the operator's own grants filled as an import run by the operator fills them (`OpenThreads`, `Calls` and `Expose` empty, `SourceRefused` empty, `Actor` the operator). It then records the carrying out on the bead with a store method of its own, which the daemon's or the operator's call alone may make: the answer is completed with what the import printed (its counts, the sources it declared, what it left owed), or, where the plan no longer matches or apply failed part way, with the failure in words. A completed ask reads `approved, ran: yardr pack apply telegram` with that output, as every approved row reads. The asker's inbox line says which of the two it was.

What this costs, said plainly: between the two steps the yard may stop, and an ask can stand at "being carried out" while the server is down. It is taken up again when the server starts, and applying is safe to take up: every object is matched by name, an import that stopped part way is finished by applying again rather than repeated, and the plan is held to the card before anything writes, so what a resumed carrying-out applies is still what was approved. A failure part way (a file that cannot be copied, a store call refused) leaves what a failed terminal apply leaves — the objects written so far, no import record — and the recorded failure names it and names the terminal command that finishes or undoes it; the ask is answered as failed and is asked again if it is still wanted, and is never carried out twice by two watchers, since the taking is one write of the store that marks the ask taken before apply runs, and a second taker finds it taken. Approving from a device works as for every row: the approval travels as `ApproveAsk` over the listener to the operator's yard, and the carrying out is that yard's server's, on that yard's machine — the phone approves, and nothing runs on the phone.

### 3.6. A declaration that names commands, and one that does not

They are treated differently, and the difference is where the command's file comes from:

- **A commands-free declaration** (no limits, thread, hook or events command: `Declaration.Commands` is empty) adds one record to the store and copies nothing. Its whole effect is in the text the ask holds, so a loose file of that kind is askable (3.2), and so is a pack whose sources are all of that kind (`pushover` today).
- **A declaration that names commands** asks the yard to run programs. From an embedded pack those programs shipped in the binary the operator installed, their files' sha256s are on the card, and the applied copies are the binary's own — the trust is the trust in the yardr build, which the operator already runs. Such a pack is askable on the same row. From a loose file the programs are files beside it on this machine, written by whoever wrote the file: their checksums on a card would name bytes the person approving has never seen and cannot open from a phone, and carrying their texts on the ask would make an approval install an agent-written program from a card that shows its hash. That is the file nobody saw, one step removed, so a loose `source add` that names a command stays the operator's in a terminal (open question 2). An absolute program in a loose declaration is refused the same way: it is the operator's own to have installed, and its being there is checked in a terminal.

`mint_command` and `env_file` are untouched by both rows: no ask carries a path or a program for the yard to run for a credential, `source key` stays a secret ask, and `source rm` stays the operator's, named on the card only as what takes the change back.

## 4. Left out

- **A pack that is not embedded, and a pack of any kind but `source`.** A directory or URL pack is files of this machine that an agent may have written, and its content can change between the asking and the approval with nothing but a file's mtime to say so; a depot pack's plan asks for binds, members and a flow, installs roles, flows and scripts, and changes who works a depot — none of which is "adding a source", and none of which a card answers. Both stay in a terminal. Open question 1 asks whether an embedded depot pack with a plan that asks nothing should ever join.
- **`--prune`, and every other flag of `pack apply`, on a card.** A prune removes what an earlier import brought; the flags name files (`--source-env`, `--notify`), people and grants. Each is its own command or its own row, proposed apart where the list holds it (a grant of the pack's source's calls is the grant row, once the source stands).
- **Replacing a source by `source add`, and replacing one by approving a pack whose source's credential a standing grant already reaches.** The pack row cards a replacement with its diffs, since a yardr upgrade changing an embedded pack is the ordinary way these packs change; a loose replacement is open question 4. Where a replacement would widen a standing grant of `read` to a call the new file adds, the plan already names who gets it (`DeclaredPlan.Reaches`), the card carries that line, and it is part of what is approved — said here because nobody is asked twice.
- **Secrets, hooks, and telling a user.** The import sets none of them; a secret ask, `yardr hook add` and `yardr user set notify=` keep their own roads and their own checks.
- **A second step at approval for a pack that names commands** (typing the source's name, a passphrase). Open question 3.
- **Approving in the web view, and a copy of either ask over a link**, as for every run ask.

## 5. Open questions

**1. Should an embedded pack of a depot kind ever be askable, when its plan asks nothing?** Option A, no: the row is for adding a source, and a depot pack changes flows, groups, roles and scripts — a change of who works and how, which is a design of its own. Option B, yes, where a re-apply against a depot whose import already stands asks nothing and changes little: the card would show the plan's objects, and the carrying out is the one this design builds. It costs a card of objects a phone reader must judge (roles and stage files by name, scripts by sha256) and widens what a stolen device of the operator can have carried out from a source to a depot's whole line. I would take A: the question that was asked was about adding a source, and a depot pack that needs applying again after an upgrade is run once, at a desk, by the person who upgraded.

**2. Should a loose declaration that names commands ever be askable, with the command files' texts carried on the ask as the declaration's is?** Option A, no, as proposed: the operator types `yardr source add <file>` in a terminal, where the files stand beside it and can be opened. Option B, yes: the ask holds each command file's text with its sha256 on the card, the approval writes exactly those bytes under `<home>/sources/<name>/`, and the bound of 3.3 grows to cover them. It costs an approval installing a program an agent wrote, approved from a card that shows its hash and, behind a tap, its text — which no reader judges as code on a phone — and it is the one case where what runs was not shipped by anyone the operator chose. I would take A. A service worth a command file is worth a pack, and a pack of kind source in the binary, or in a directory the operator applies once, is its road in.

**3. May a pack whose sources name commands be approved from a device of the operator, or only on the yard's socket?** Option A, from a device too, as proposed: the commands are the installed build's own files, and approving its own pack adds no program the operator has not already been running since they installed that build. Option B, socket only for a pack that names a command, a device for a commands-free one: it splits question 3 of yardr-x3g8 by row, and costs a second rule on the card ("approve this one at the yard's terminal"). It holds against a stolen device having new command files installed and run, though the same device can already approve a grant of those commands' source's calls once the source stands. I would take A, and B if the row in the stolen-device table of docs/users.md reads as too much when it is written.

**4. Should the first step replace a source, or only add one?** Option A, as proposed: the pack row cards a replacement with its diffs (a yardr upgrade is the ordinary change to an embedded pack, and refusing it would leave the row answering only the first install), and the loose row adds only, a replacement staying in a terminal where its widened grants can be read. Option B, both rows add only at first: a replacement of either kind is the operator's until the rows have been used, which costs the operator typing `yardr pack apply linear` after every upgrade that changes its declaration or a command file — the case that recurs — for a first step that approves only what was not there. I would take A: the card shows the diff and the changed files' sha256s, and `Seen` holds the approval to the text it replaces.

This is yardr-x3g8's bead Y5, taken up.
